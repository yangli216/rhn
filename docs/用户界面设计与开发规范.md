# 用户界面统一设计与开发规范

> 状态：Draft 0.1（后续业务功能默认基线）  
> 适用范围：RHN Web 门户、业务工作台及其共享组件  
> 最近更新：2026-08-25  
> 维护责任：产品设计与前端共同维护

## 1. 目的与约束级别

本规范用于统一 RHN 后续业务模块的视觉语言、交互行为和前端实现方式，降低跨模块学习成本与误操作风险，并使医疗业务界面在高信息密度下仍然清晰、可信、可追溯。

规范使用以下约束词：

- **必须（MUST）**：不满足则不得合并或发布。
- **应该（SHOULD）**：默认遵循；偏离时必须在评审中说明业务原因。
- **可以（MAY）**：按场景选用，不形成强制约束。

本规范不是视觉稿的替代品。新能力没有单独设计稿时，应优先复用本文定义的页面模板与共享组件，不得在业务模块内自行发明另一套交互语言。

## 2. 设计原则

### 2.1 患者与任务优先

- 页面首屏必须回答三个问题：当前在处理谁、当前处于什么业务阶段、下一步可以做什么。
- 居民/患者上下文进入后，关键身份信息必须在业务操作区之前出现；切换对象必须是显式操作。
- 一个页面只设置一个视觉上的主操作。多个动作并存时，按“主操作、次操作、文字操作、危险操作”分级。

### 2.2 安全胜过速度

- 临床记录、处方、费用、身份合并等高风险动作必须展示目标对象、动作结果和不可逆影响。
- 不得仅依赖颜色表示状态、风险或校验结果，必须同时提供文字、图标或结构差异。
- 不可逆操作必须二次确认；可逆但影响较大的操作应提供撤销或明确的恢复路径。
- 临床提交不得使用无法确认最终状态的乐观更新。

### 2.3 一致胜过新奇

- 相同概念必须使用相同名称、颜色、图标和交互位置。
- 优先复用 `frontend/src/shared/ui` 中的组件；功能页不得复制通用组件后局部改造。
- 业务组件只能使用语义化设计令牌，不直接使用任意颜色、阴影、字号或层级值。

### 2.4 高密度但不拥挤

- 核心业务信息优先，说明信息按需展开。
- 使用分组、对齐和留白表达层级，避免依靠大量边框分割页面。
- 数据列表允许紧凑，但交互目标、正文和表单不得因追求密度而缩小到不可读。

### 2.5 状态始终可见

- 每个异步区域必须具备初始、加载、成功、空、无结果、失败和无权限状态。
- 用户提交后必须得到明确反馈：正在处理、已成功、失败原因及下一步。
- 页面刷新或返回后，已提交业务状态必须能从服务端重新确认。

### 2.6 PC 桌面端优先与宽屏高效利用

- 本项目前端**默认仅适配 PC 端桌面浏览器**（基准视口 `1280px` ~ `1920px+`），非特殊业务说明**无需考虑移动端兼容性**。
- **坚决杜绝“长条型”反模式**：严禁将大屏页面限制在窄幅单列中从上至下垂直堆叠（在宽屏中央仅占狭窄一列、两侧大面积留白、用户必须频繁纵向滚屏）。
- **宽屏高密度协同**：优先采用分栏协同（Split Panes，如主次分栏、三栏工作台）、多列栅格（Form Grid 2~4列）及横向自适应卡片流，充分利用桌面宽屏空间，提升高密度医疗业务的协同与录入效率。

## 3. 品牌与视觉基调

RHN 的视觉关键词为：**可信、克制、清晰、连续照护**。

- 深青色代表平台品牌与主要行动，不代表某一种临床状态。
- 大面积使用浅灰绿画布与白色信息面板，保持长时间操作的稳定感。
- 蓝、琥珀、红等颜色只承担明确的语义，不作为随意装饰。
- 圆角适度，阴影克制；医疗业务界面不得使用强烈霓虹、玻璃拟态或持续动态背景。
- 当前不建设深色模式。未完成完整的临床颜色、图表与对比度验证前，不得局部引入深色主题。

## 4. 设计令牌

### 4.1 颜色

所有新代码必须使用语义名称。下表为基线值；若未来调整，仅修改令牌，不逐页覆盖。

| 令牌 | 值 | 用途 |
|---|---:|---|
| `--color-brand-primary` | `#0B6B62` | 主按钮、当前步骤、关键链接 |
| `--color-brand-strong` | `#064F49` | 主按钮悬停、深色品牌区域 |
| `--color-brand-soft` | `#E4F2EF` | 选中背景、弱品牌提示 |
| `--color-text-primary` | `#172B29` | 标题、正文、关键数值 |
| `--color-text-secondary` | `#526663` | 次级说明、字段补充信息 |
| `--color-text-disabled` | `#7E8D8A` | 禁用文字；不得承载必要信息 |
| `--color-canvas` | `#F3F6F5` | 页面画布 |
| `--color-surface` | `#FFFFFF` | 面板、弹窗、输入区域 |
| `--color-surface-subtle` | `#F7FAF9` | 悬停、分组、只读区域 |
| `--color-border` | `#DFE7E5` | 常规边框和分隔线 |
| `--color-border-strong` | `#B8C8C5` | 强分隔、控件边界 |
| `--color-success` | `#17735F` | 已完成、成功 |
| `--color-success-soft` | `#E2F3EE` | 成功背景 |
| `--color-info` | `#286A9F` | 信息、进行中 |
| `--color-info-soft` | `#E7F0F7` | 信息背景 |
| `--color-warning` | `#8A611C` | 待处理、需关注 |
| `--color-warning-soft` | `#F7EFDE` | 警告背景 |
| `--color-danger` | `#B42318` | 错误、高风险、删除 |
| `--color-danger-soft` | `#FDF0EE` | 错误背景 |
| `--color-overlay` | `rgba(4, 25, 23, .48)` | 模态遮罩 |

颜色使用规则：

- 正文与背景对比度必须至少为 `4.5:1`；大号文字至少为 `3:1`。
- 控件边界、焦点和图形化状态与相邻颜色的对比度必须至少为 `3:1`。
- 品牌色不得替代成功色；红色不得用于普通强调。
- 业务状态必须通过集中映射输出，不得在功能组件中根据状态临时拼颜色。
- 图表应优先使用形状、标签、线型和排序辅助识别；同图颜色类别原则上不超过 6 个。

### 4.2 字体与排版

字体栈：

```css
-apple-system, BlinkMacSystemFont, "Segoe UI", "PingFang SC",
"Microsoft YaHei", system-ui, sans-serif
```

| 层级 | 字号 / 行高 | 字重 | 用途 |
|---|---|---:|---|
| Display | `32 / 42px` | 700 | 登录页或少量品牌表达 |
| H1 | `28 / 38px` | 700 | 页面标题，每页一个 |
| H2 | `22 / 32px` | 700 | 弹窗标题、主要区块 |
| H3 | `16 / 24px` | 600 | 面板标题 |
| Body | `14 / 22px` | 400 | 默认正文、表格、表单值 |
| Body strong | `14 / 22px` | 600 | 关键正文、行标题 |
| Small | `12 / 18px` | 400 | 辅助信息、时间、元数据 |
| Label | `12 / 18px` | 600 | 字段标签、状态标签 |

- 中文业务界面的常规可读文字不得小于 `12px`；正文和表单值默认 `14px`。
- 关键数值应使用等宽数字特性 `font-variant-numeric: tabular-nums`。
- 不使用全大写英文承载正文；缩写首次出现应给出中文或完整名称。
- 标题最多两级连续嵌套，禁止仅通过加粗模拟标题层级。
- 中文与数字/英文之间由排版或文案保持清晰间隔；单位紧随数值，如 `148 mmHg`。

### 4.3 间距

采用 `4px` 基础网格：

| 令牌 | 值 | 常见场景 |
|---|---:|---|
| `--space-1` | `4px` | 图标与微型标签 |
| `--space-2` | `8px` | 紧凑控件内部间距 |
| `--space-3` | `12px` | 字段和小组件间距 |
| `--space-4` | `16px` | 卡片内部、列表行间距 |
| `--space-5` | `20px` | 面板内部 |
| `--space-6` | `24px` | 区块间距 |
| `--space-8` | `32px` | 页面级间距 |
| `--space-10` | `40px` | 大区块分隔 |
| `--space-12` | `48px` | 品牌展示区 |

- 功能页外边距：桌面端标准为 `24px` ~ `32px`（紧凑高密度工作台可设为 `16px`），充分保障宽屏可用宽度。
- 同组间距必须小于异组间距；不得用连续空行或不可解释的任意值修正布局。
- 表单采用字段间距 `16px`、分组间距 `24px`、分组标题与内容间距 `12px`。

### 4.4 圆角、边框和阴影

| 令牌 | 值 | 用途 |
|---|---:|---|
| `--radius-sm` | `6px` | 标签、小状态块 |
| `--radius-md` | `8px` | 输入框、按钮 |
| `--radius-lg` | `12px` | 卡片、下拉面板 |
| `--radius-xl` | `16px` | 弹窗、大面板 |
| `--shadow-panel` | `0 8px 24px rgba(23,43,41,.06)` | 浮于画布的面板 |
| `--shadow-modal` | `0 24px 70px rgba(0,0,0,.22)` | 模态层 |

- 常规卡片优先使用 `1px` 边框；只有需要表达层级浮起时才使用阴影。
- 同一容器层级不得叠加多个强阴影。
- 输入框、按钮和相邻卡片的圆角应来自同一令牌族，不使用胶囊形按钮作为默认样式。

### 4.5 动效与层级

- 快速反馈 `120ms`，常规状态变化 `180ms`，抽屉/弹窗 `240ms`。
- 默认缓动：`cubic-bezier(.2, 0, 0, 1)`。
- 只允许用动效解释状态变化，不使用持续闪烁、弹跳或大幅位移动效。
- 必须支持 `prefers-reduced-motion: reduce`，在该模式下取消非必要动画。
- 建议层级：普通内容 `0`、吸顶内容 `10`、侧栏 `20`、下拉/浮层 `40`、弹窗 `50`、全局通知 `60`。业务代码不得写更高的任意层级。

## 5. 页面框架与 PC 桌面端适配

### 5.1 标准应用框架

本项目为专业医疗与医共体业务工作台，采用 PC 桌面端工作框架：

- 左侧主导航宽 `248px`，固定显示（可按需折叠为迷你导航）。
- 顶部上下文栏高 `82px`（或高密度工作台紧凑型 `56~64px`），展示当前机构、科室、登录身份和全局入口。
- 内容区宽度随桌面视口自适应伸展（`width: 100%`，基准保障宽度 `1280px`，推荐视口 `1440px ~ 1920px+`）。
- 页面由“页面标题区 → 对象上下文 → 页面级反馈 → 主工作区 → 辅助信息”组成。

顶部栏与侧栏只承载全局信息，不放置当前表单的保存、提交等页面级动作。

### 5.2 页面标题区

每个一级页面必须使用统一 `PageHeader`，包含：

1. 所属领域或模块眉题；
2. 唯一的 H1 页面标题；
3. 一句说明当前页面目标的描述；
4. 右侧最多一个主操作，必要时附一个次操作。

页面标题不得使用“管理”“列表”等空泛名称；优先使用用户任务，如“居民中心”“门诊接诊”“处方审核”。

### 5.3 PC 桌面端适配基线与反“长条型”布局约束

> **核心硬性约束**：本项目前端**默认仅适配 PC 端桌面浏览器**（基准宽度 `1280px` ~ `1920px+`），非特殊业务说明**不需要考虑移动端（手机/窄屏平板等）兼容性**。严禁将桌面业务页面做成狭窄单列的“长条型”。

#### 5.3.1 杜绝长条型反模式（Anti-Patterns）

- **禁止单列窄幅居中**：严禁在 PC 宽屏下设置过小的固定最大宽度（如 `max-width: 600px~800px`）导致页面呈单列居中长条，两侧留下大面积无用空白画布。
- **禁止无意义垂直单列拉伸**：严禁将所有表单字段、卡片、数据列表单列垂直由上到下无限堆放，迫使医生/护士在 1080P/2K 大屏幕上不断滚屏。
- **禁止编写移动端冗余逻辑**：不需要添加 `@media (max-width: 760px)` 或针对 320px/480px 的手机抽屉菜单、单列折叠、底部操作条等移动端特化代码，降低维护复杂度。

#### 5.3.2 推荐的 PC 宽屏高效布局范式

| 布局模式 | 适用场景 | 布局要点 |
|---|---|---|
| **多栏分流工作台 (Split Panes)** | 门诊接诊、住院工作站、病历录入 | 左右双栏或三栏协同（如左栏队列/目录 `280~360px`，中栏核心操作 `1fr`，右栏辅助时间轴/参考报告 `320~420px`） |
| **多列网格栅格 (Multi-Column Grid)** | 登记建档、排班维护、体检录入、表单页 | 表单字段采用 2 列、3 列或 4 列栅格排布，按业务逻辑分组，同组信息横向充盈 |
| **自适应卡片阵列 (Responsive Grid Cards)** | 候诊全景大厅、病区床位一览、库房盘点 | 使用 `grid-template-columns: repeat(auto-fill, minmax(280px, 1fr))` 自动横向铺满屏幕 |
| **高密度宽表与主从详情 (Master-Detail)** | 药品目录、处方明细、医保结算审核 | 充分利用宽屏横向展示多指标列，支持行展开或侧边抽屉式详情，避免小表格被挤压 |

#### 5.3.3 PC 桌面端视口验证基线

| 视口规格 | 代表场景 | 适配预期 |
|---|---|---|
| `≥ 1920px` | 常见医用显示器、医院台式机 | 完整三栏/宽屏高密度展开，卡片多列自适应铺满，视觉饱满无空旷感 |
| `1440px – 1919px` | 笔记本外接显示器、主流一体机 | 标准工作台形态，双栏/多列栅格自然呈现，为推荐基准视口 |
| `1280px – 1439px` | 常见笔记本屏幕、紧凑桌面环境 | 最小基准宽度，侧栏与核心区域紧凑显示，无横向滚动条，辅助栏可按需收拢 |
| `< 1280px` | 非标或窗口缩放状态 | 仅作为桌面窗口缩放的下限容错（允许出现主横向滚动），不单独设计手机视图 |

- 页面验证重点覆盖 `1280px`、`1440px`、`1920px` 三个典型桌面视口。

### 5.4 滚动层级

- 普通业务页只保留一个主垂直滚动容器，统一由工作区内容层承担；页面卡片、表单分组和普通列表随主容器滚动。
- 列表内容超出可视区时优先使用分页、虚拟化或服务端加载，不得为面板内普通目录另设第二条垂直滚条。
- 只有主导航、树形目录、下拉浮层、长数据表格和必须保持上下文的独立浏览区可使用局部滚动；局部滚动区必须有清晰边界和稳定高度。
- 弹窗在当前视口内应尽量完整展示；确需滚动时只允许弹窗内容区滚动，标题和底部操作区保持可见，同时锁定背景页面。
- 任一可见业务区不得同时出现两条用于阅读业务内容的垂直滚条；嵌套滚动必须在走查中单独说明其必要性。

## 6. 核心组件规范

### 6.1 按钮

按钮分为：

- **Primary**：每个操作区最多一个，用于完成当前主要任务。
- **Secondary**：不改变核心状态或作为次要提交。
- **Text/Ghost**：返回、取消、查看详情等弱操作。
- **Danger**：删除、撤销合并、作废等高风险操作，只在确认场景使用。

统一规则：

- 默认高度 `40px`，紧凑型 `32px` 仅用于表格行内，重要操作可用 `48px`。
- 纯图标按钮的可点击区域不得小于 `40 × 40px`，并必须有可访问名称。
- 文案使用“动词 + 对象”，如“保存病历”“建立居民主索引”，避免“确定”“提交”。
- 加载时保留按钮原宽，显示进度并禁用重复提交；不得只把文字替换成长度明显不同的“处理中”。
- 禁用按钮必须保留可读标签；若禁用原因不明显，应提供邻近说明。
- 高风险主操作不得与普通 Primary 共享品牌色，必须使用 Danger 样式。

### 6.2 输入与表单

- 输入框默认高度 `40px`，多行输入最小高度 `96px`。
- 标签永久显示在控件上方；占位符只能提供示例，不能替代标签。
- 必填字段使用文字或统一符号标记，并在表单开头解释；不得仅靠红色星号。
- 单位应固定显示在标签或输入尾部，不要求用户手工输入。
- 校验优先在离开字段或提交时触发；用户修正后及时清除错误。
- 错误信息必须说明问题与修正方式，如“收缩压应为 40–300 mmHg”。
- 服务端错误显示在相关字段或表单操作区；不得把所有错误统一丢到页面顶部。
- 表单提交失败后必须保留用户输入，并将焦点移至错误摘要或第一个错误字段。
- 临床和费用表单在离开未保存页面前必须提示；自动保存时必须展示最后保存时间和失败状态。
- 只读数据使用只读样式或描述列表，不用禁用输入框伪装。

下拉选择统一使用共享 `Select` 组件；业务字典项统一使用 `DictionarySelect`：

- `Select` 同时覆盖单选和多选，并统一支持名称、编码和拼音首字母检索；业务模块不得自行拼接另一套下拉菜单。
- `DictionarySelect` 优先配置稳定的 `dictionaryCode`，仅在明确绑定具体记录时使用数据库 `dictionaryId`。
- 表单保存字典项编码，展示名称由字典服务解析，不在页面内复制字典文案。
- 字典下拉仅提供当前租户可见的启用项，并统一处理缓存、加载、空结果、失败与重新加载。
- 字典选项采用左侧名称、右侧浅色编码的固定布局；保存编码，不保存显示名称。
- 下拉层必须脱离弹窗和面板的裁剪容器，根据视口空间自动上下翻转并限制宽度，不得造成页面或弹窗横向滚动。
- 单选值使用 `string`，多选值使用 `string[]`；与 React Hook Form 集成时通过 `Controller` 传递 `value` 和 `onChange`。
- 诊断、药品、诊疗项目等大规模业务主数据使用 `ClinicalResourceSearch`，不得在页面初始化时加载完整目录；至少包含输入防抖、旧请求竞态保护、加载/失败/空结果状态和结果数量上限。
- 远程检索结果仍遵循左侧名称、右侧浅色编码；辅助摘要放在名称下方，每次过滤后默认高亮第一条可用记录并允许回车快速选择。

### 6.3 面板与卡片

- `Panel` 用于一个完整任务或信息集合，默认带标题区。
- 面板标题左侧为名称，右侧只放简短元数据或轻量操作；主操作放页面标题区或面板底部。
- 嵌套面板最多两层。第三层应改用分组标题、分隔线或标签页。
- 指标卡只展示一个主指标、一个名称和一个解释；不得把指标卡当作普通导航入口。

### 6.4 数据列表与表格

- 有稳定列结构、需要比较的数据使用表格；以对象摘要和下一步任务为主的数据使用列表。
- 表格列按业务语义对齐，表头与该列全部内容必须使用相同对齐方式，不得只调整 `th` 或 `td`：
  - 文本列默认左对齐，包括名称、说明、日期时间以及编号、手机号、证件号、条码等文本标识符。
  - 数值列右对齐并使用等宽数字，包括金额、数量、单价、比例、统计值和可计算的度量；单位随数值一起右对齐。
  - 状态列居中对齐并保持适合最长状态文案的稳定宽度，包括 `StatusBadge`、开关和短状态文案。
  - 选择框、展开按钮、拖拽手柄、行序号等结构控制列居中对齐；行序号不是业务数值。
  - 操作列默认右对齐；只有单个纯图标操作时可以居中，但同一张表内必须一致。
- 复合单元格按主信息的业务语义决定对齐方式，不能因为辅助信息中含数字就改为右对齐。空值 `—` 跟随所在列对齐。
- 列语义必须显式声明，不根据运行时内容自动推断。共享 `DataTable` 使用 `tableCellClass` 为对应的表头和单元格同时标记 `text`、`numeric`、`status`、`control` 或 `actions`。
- 时间默认格式为 `YYYY-MM-DD HH:mm`；同年可在紧凑视图省略年份，但详情中必须完整展示。
- 空值统一显示 `—`，不得混用空白、`null`、`N/A` 和“无”。业务确有语义时使用“未登记”“尚无诊断”等明确文案。
- 行点击可进入详情时，整行应有悬停和焦点样式，同时保留明确的可访问名称。
- 批量操作只在选择行后出现，并明确已选数量。高风险批量操作必须再次确认目标范围。
- 大数据列表必须提供分页、虚拟化或服务端加载策略；不得一次渲染不受控数据。

### 6.5 状态标签

- 标签必须同时包含文字；颜色只是辅助。
- 统一语义：绿色=已成功/已完成，蓝色=进行中/信息，琥珀=待处理/需关注，红色=失败/高风险，灰色=未开始/已关闭/不适用。
- 标签文案使用业务语言，如“待审核”“接诊中”“已作废”，不直接显示后端枚举。
- 同一状态在列表、详情、筛选器和时间轴中必须使用同一映射。

### 6.6 反馈、加载与空状态

- **局部加载**：在触发区域内显示骨架或进度，不遮挡整个页面。
- **首次加载**：保留页面结构，避免内容突然跳动。
- **空状态**：说明当前为何为空，并在有合理下一步时提供操作。
- **无搜索结果**：保留搜索条件，提供修改条件或新建对象的路径。
- **错误状态**：使用人能理解的原因和恢复动作；关联 ID 可放在展开详情中供排查。
- **成功反馈**：小范围保存使用邻近状态或短暂通知；创建、签署等重要动作进入结果页或显示持久结果摘要。
- 全局通知不得展示证件号、诊断详情等敏感内容。

### 6.7 弹窗与抽屉

- 弹窗用于需要立即决策、且不超过一个主要任务的内容；复杂流程进入独立页面。
- 默认宽度 `480–640px`；包含大表格或多步骤表单时不得继续扩大弹窗，应改用页面或抽屉。
- 打开后焦点进入弹窗，Tab 焦点不得离开；Escape 可关闭非强制弹窗；关闭后焦点返回触发元素。
- 标题、说明、正文和底部操作必须结构清晰。底部从左到右放“取消 / 次操作 / 主操作”。
- 点击遮罩关闭只适用于无未保存内容、无高风险确认的弹窗。
- 删除、作废等确认弹窗必须重复对象名称与影响；禁止只问“是否确认”。

### 6.8 图标

- 必须使用同一套矢量图标，并保持统一线宽和视觉尺寸；文本符号、Emoji 仅作为当前原型的过渡实现。
- 常规图标尺寸 `16px`，导航和空状态可使用 `20px`、`24px`。
- 图标不得单独表达陌生业务含义；首次出现或低频操作必须带文字标签或提示。
- 装饰图标对辅助技术隐藏，功能图标提供可访问名称。

## 7. 医疗业务专用模式

### 7.1 居民/患者上下文条

进入居民业务上下文后必须展示：

- 姓名；
- 性别、年龄或出生日期；
- 脱敏身份标识；
- 健康档案号或当前业务必需的主标识；
- 当前就诊/住院/服务状态；
- 切换或返回对象列表的明确入口。

高风险提交前应在操作区域再次显示姓名和关键标识，避免用户滚动后失去对象感知。不得仅以头像颜色表达性别。

### 7.2 临床数值

- 数值与单位必须成组出现，单位不可由用户自由输入。
- 异常值必须同时提供数值、范围或文字说明，不能只变红。
- 超出生理合理范围时阻止提交并说明范围；高但可能真实的临床异常应要求确认，而不是简单阻止。
- 小数精度、日期时区、空值含义由领域规则统一，不在各页面自行格式化。

### 7.3 业务步骤与状态变更

- 多步骤临床流程展示当前位置、已完成步骤和可返回范围。
- 已完成且不可修改的记录应明确显示“已签署 / 已完成 / 已归档”和时间、操作者。
- 修订不得覆盖历史内容；界面必须区分“编辑草稿”“创建修订”“查看历史版本”。
- 操作成功后优先展示服务端返回的新状态，必要时刷新关联时间轴与记录列表。

### 7.4 隐私与脱敏

- 列表默认展示脱敏证件号、手机号等个人信息；完整信息仅在权限允许且任务必需时展示。
- 敏感信息的复制、导出、打印和外链必须是显式受控操作。
- URL、页面标题、通知、埋点和前端日志不得包含姓名、证件号、诊断内容等敏感信息。
- 自动退出或会话失效时应保留安全的恢复提示，不在登录页回显业务数据。

## 8. 文案规范

- 使用用户熟悉的业务术语，术语来源应与 `docs/foundation/核心领域词汇表.md` 一致。
- 操作文案用主动语态，结果文案说明已发生的事实。
- 错误提示结构为“发生了什么 + 如何处理”，避免“系统错误”“非法参数”。
- 不使用带责备意味的表述，如“你输入错了”；使用“证件号格式不正确，请核对后重试”。
- 一个概念只使用一个名称。例如选定“居民”后，不在同一业务层级混用“患者”“人员”。进入具体医疗服务语境时可使用“患者”，但必须有明确边界。
- 标点使用全角中文标点；按钮和状态标签末尾不加句号。

## 9. 无障碍基线

RHN Web 界面以 [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/) 为最低目标，并额外采用 `40 × 40px` 的项目级常用交互目标尺寸（高于 WCAG 2.2 的 `24 × 24 CSS px` 最低目标要求）。

所有功能必须满足：

- 仅用键盘可完成完整任务，焦点顺序与视觉顺序一致。
- 所有交互元素具有清晰的 `:focus-visible` 样式，焦点不被吸顶栏、弹窗或滚动容器遮挡。
- 使用语义 HTML：按钮用 `button`，导航用 `nav`，表格使用正确表头，字段与 `label` 关联。
- 图标按钮、输入错误、加载状态、弹窗标题和动态通知具有正确的可访问名称或状态声明。
- 页面缩放到 `200%` 时不丢失功能或关键信息。
- 不以自动播放、闪烁或仅依赖拖拽完成任务；拖拽功能必须提供等价的点击/键盘方式。
- 登录和身份验证不得要求纯认知测试；密码管理器和粘贴能力不得被无故禁用。

## 10. 前端实现约束

### 10.1 组件边界

- 跨两个及以上业务模块使用的组件必须进入 `frontend/src/shared/ui`。
- 共享组件只接受语义属性，如 `variant="danger"`、`status="warning"`，不得暴露任意颜色参数。
- 业务状态到展示状态的映射集中维护；功能组件只传入业务状态。
- 通用行为必须内建：焦点、键盘、加载、禁用、错误关联和可访问名称不得留给每个调用方重复实现。

### 10.2 样式约束

- 设计令牌统一定义在全局 `:root`；业务样式仅引用令牌。
- 新增样式不得使用小于 `12px` 的业务文字，不得新增未经说明的十六进制颜色。
- 禁止使用 `!important` 覆盖组件状态；确有需要时应修正组件 API 或选择器结构。
- 不以 DOM 顺序技巧修复视觉布局，视觉顺序与阅读顺序必须一致。
- 组件样式应覆盖默认、悬停、按下、焦点、禁用、加载、错误和只读状态。

### 10.3 数据与异步状态

- 读取操作采用稳定的查询键，并在对象变更后刷新所有相关视图。
- 写操作必须防重复提交；业务接口具备幂等能力时，前端仍需提供明确加载状态。
- 错误展示使用稳定错误码映射为用户文案，未知错误保留关联 ID 供支持人员定位。
- 权限不足和资源不存在是独立状态，不得统一显示成空列表。
- 日期、数值、枚举和脱敏格式通过共享格式化函数输出。

### 10.4 推荐目录演进

设计基础已经按以下职责拆分；`frontend/src/styles.css` 只作为统一入口，不在其中继续堆叠规则：

```text
frontend/src/
├── styles/
│   ├── tokens.css       # 颜色、字号、间距、圆角、阴影、层级
│   ├── base.css         # reset、排版、焦点、reduce-motion
│   ├── components.css   # 共享 UI 组件视觉规则
│   ├── layout.css       # 应用框架与响应式规则
│   └── features.css     # 当前业务专用布局，规模增长后按领域拆分
├── shared/ui/           # 通用交互组件
├── shared/presentation.ts # 业务状态到统一展示语义的映射
└── features/<domain>/   # 业务编排与领域专用组件
```

前端提交统一运行 `npm run check`。其中 `ui:check` 会阻止裸颜色、废弃令牌、低于 `12px` 的字号和旧组件类名重新进入业务代码。

## 11. 标准页面模板

### 11.1 查询列表页

```text
页面标题 + 新建主操作
筛选 / 搜索面板
页面级错误或筛选摘要
结果面板
  ├─ 加载
  ├─ 初始 / 空 / 无结果
  └─ 表格或对象列表 + 分页
```

### 11.2 对象详情 / 工作台

```text
返回入口
对象上下文条 + 当前状态 + 主操作
风险 / 错误 / 权限提示
主工作区
  ├─ 当前任务或表单
  └─ 历史、时间轴或关联信息
```

### 11.3 新建 / 编辑页

```text
页面标题 + 保存状态
对象或流程说明
分组表单
  ├─ 基本信息
  ├─ 业务信息
  └─ 风险 / 影响摘要
底部操作区：取消 + 保存草稿 + 主提交
```

新页面应从最接近的模板开始，只有业务任务明显不适配时才引入新模板。

## 12. 设计与开发完成定义

每个新增或修改的 UI 功能合并前必须完成以下检查：

### 设计一致性

- [ ] 使用标准页面结构、设计令牌和共享组件。
- [ ] 页面只有一个主操作，相同状态和术语与现有模块一致。
- [ ] 已覆盖默认、加载、空、无结果、错误、无权限和成功状态。
- [ ] 医疗对象、关键状态、单位、时间和风险信息清晰可见。

### 交互安全

- [ ] 写操作防重复提交，失败保留输入并提供恢复路径。
- [ ] 高风险动作明确目标与影响，并完成二次确认。
- [ ] 未保存内容、会话失效和并发状态变化有处理策略。
- [ ] 敏感信息已按最小必要原则展示和脱敏。

### 可访问性

- [ ] 键盘可完成完整流程，焦点可见且顺序正确。
- [ ] 表单标签、错误、图标按钮、弹窗和动态状态可被辅助技术识别。
- [ ] 文字/控件对比度达标，状态不只依赖颜色。
- [ ] 在 `200%` 缩放及减少动效设置下可正常使用。

### PC 浏览器适配与布局质量

- [ ] 默认仅适配 PC 桌面端浏览器（在 `1280px`、`1440px`、`1920px` 宽度验证，非特殊说明不考虑移动端）。
- [ ] 杜绝单列“长条型”布局，页面充分利用宽屏横向空间进行分栏、多列栅格或卡片流排布。
- [ ] 桌面视口下无遮挡、非预期横向滚动、布局跳动或不可点击区域。
- [ ] 长姓名、长机构名、空值、大数值和极端列表长度已验证。
- [ ] 前端构建通过；关键交互具备自动化测试或明确的人工验收记录。

## 13. 现有界面迁移优先级

本文发布后，新功能立即遵循完整规范；现有页面按以下顺序收敛：

### P0：安全与可访问性

1. 将 `8–11px` 的业务文字提升到规范字号。
2. 为所有交互元素补齐 `focus-visible`，完善弹窗焦点约束和关闭后焦点恢复。
3. 消除窄幅单列“长条型”布局，改造为利用宽屏的多栏/多列桌面工作台布局。
4. 将错误、成功、警告、信息从单一 `Alert` 扩展为语义化反馈组件。
5. 修正整行按钮、图标按钮和弹窗关闭按钮的可访问名称与状态声明。

### P1：令牌与组件收敛

1. 将现有 `--teal`、`--ink`、`--muted` 等变量迁移到语义令牌。
2. 补齐 Danger Button、Status Badge、Toast、Skeleton、Table、Tabs 等共享组件。
3. 用统一矢量图标替换文本符号和 Emoji。
4. 集中维护业务状态、日期、数值和空值格式。

### P2：效率与规模化

1. 为复杂业务引入标准筛选器、批量操作和分页模式。
2. 建立共享组件示例页与视觉回归基线。
3. 将本规范检查项纳入 Pull Request 模板和功能验收清单。

## 14. 治理方式

- 本文件作为 UI 基线的唯一规范来源；视觉稿、代码和口头约定发生冲突时，先更新规范或记录例外。
- 新增设计令牌、共享组件变体或页面模板必须经过设计与前端共同评审。
- 临时例外必须记录：业务原因、影响范围、负责人和回收条件。
- 每个版本迭代至少复盘一次新增模式，重复出现两次以上的模式应评估进入共享组件。
- 规范变更遵循语义版本：视觉微调为补丁版本，新增兼容模式为次版本，破坏既有用法为主版本。
