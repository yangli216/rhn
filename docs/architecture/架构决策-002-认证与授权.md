# 架构决策-002：认证框架保持可替换，Sa-Token 作为受控候选

- 状态：已采纳
- 日期：2026-08-25

## 背景

RHN 需要同时处理登录会话、县域多租户、机构/科室数据范围、时效角色、医疗数据访问审计，以及后续统一身份源、MFA、SSO 和紧急访问。认证框架只能解决其中一部分，不能成为业务授权模型本身。

当前 HTTP Basic 只服务本地纵向切片，不可用于真实医疗数据。生产环境仍以 OIDC/OAuth2 对接统一身份平台为优先方向。

## 对 Sa-Token 的评估

Sa-Token 1.45.0 已提供 Spring Boot 4 Starter，和当前 Spring Boot 4.1 技术栈具备开展集成验证的基础。它在登录会话、Token、踢人下线、并发登录控制、基础角色/权限判断和 SSO 等方面较完整，适合国内自建账号体系和管理端应用。

但以下能力仍必须由 RHN 自己建模并执行：

- 租户内账号与租户边界；
- 带有效期的角色、权限和授权撤销；
- 机构、科室、辖区、医患关系等数据范围；
- 访问目的、敏感数据、导出/打印和紧急访问策略；
- 认证、授权、数据访问和策略判定的完整审计；
- 与统一人员、执业身份、OIDC/MFA 和账号生命周期的映射。

因此，Sa-Token“适合作为认证/会话技术组件候选”，但“不适合作为医疗授权底座的替代品”。

## 决策

本轮不直接把 Spring Security 替换为 Sa-Token，也不让业务模块依赖任何框架静态 API。

1. 账号、角色、权限、管理模块、时效授权和数据范围归 `platform.identityaccess` 所有。
2. 业务模块只依赖 `ExecutionContextProvider` 和后续的授权策略端口。
3. 当前 Spring Security 是认证适配器；正式身份源接入前，HTTP Basic 只允许本地/测试使用。
4. Sa-Token 保留为认证和会话适配器候选。是否引入，以独立技术验证结果决定，不改动领域授权模型。

## Sa-Token 准入门槛

验证必须覆盖：

- Spring Boot 4.1、Jakarta Servlet、Jackson 3 的真实集成测试；
- Redis 会话存储、网络分区、过期、续签、主动注销和强制下线；
- 单点登录、并发登录、跨端策略、Token 泄漏后的撤销时效；
- OIDC/统一身份平台衔接、MFA 状态与人员执业身份映射；
- CSRF、CORS、Cookie/Authorization Header 策略和前后端分离部署；
- 认证成功/失败、授权拒绝、紧急访问和数据导出的审计挂点；
- 依赖漏洞、SBOM、升级节奏、性能与故障降级。

只有上述验证通过，且相对 Spring Security/OIDC 方案存在明确运维或交付收益时，才新增 Sa-Token 依赖。即使引入，也只替换安全适配层。

## 后果

该决策稍微增加一个适配层，但避免后续业务代码被认证框架锁定，也避免把简单的角色字符串判断误当成医疗数据授权。Spring Security 与 Sa-Token 可以用同一套 IAM 表和执行上下文进行对比验证。
