# 架构决策-006：物理模块化单体与调用方 Port

- 状态：已采纳并完成首批工程落地
- 日期：2026-09-15
- 延续：[ADR-001](架构决策-001-模块化单体.md)

## 问题

RHN 的医疗、公卫和协同业务持续扩展，单 Maven 工程不能在编译时约束粗粒度依赖。原有包级规则漏掉部分顶级模块，且平台打印直接依赖处置实现，退费与医技/处置 API 之间存在循环，收费日结直接访问平台用户仓库。

## 决策

采用 Maven 父工程和 11 个子工程，由 rhn-app 生成唯一可执行包；保留一个主要业务部署单元及当前数据库事务模型。既有业务源码迁入能力组，原逻辑包继续作为数据与 API 边界。Public Health、Quality 在本轮建立独立骨架，按后续业务切片实现。

Module Catalog 是模块登记和依赖白名单的唯一来源。ArchUnit 自动覆盖全部生产顶级包，未知模块、未声明依赖、跨模块内部实现/Entity/Repository 以及循环均失败；不能通过包名以 `api` 开头绕过公开接口判定。

同步调用采用公开 API。需要平台/横向能力回调业务，或可能形成循环时，在消费方定义 Port/不可变快照，提供方实现 Adapter。副作用传播复用事务 Outbox/Inbox；复杂质控、AI 和上报未来按运行需求独立，不在此阶段引入服务发现或分布式事务。

## 保留与代价

Java 包名、数据库表、Flyway 文件、HTTP 路由和业务规则不因工程迁移改变。集中迁移资源和回归测试暂由 rhn-app 引用原路径；本地开发的 spring-boot:run 需指定 rhn-app，并先安装当前反应堆依赖。Oracle 启动脚本及 CI 已改为读取新的制品路径。

Maven 依赖本身不会限制对依赖 Jar 内部 public 类型的访问，因此必须保留 ArchUnit；当前门禁也不解析任意 SQL 字符串。现有 Kernel 框架依赖、观察事实归属、通用文档存储和外部集成抽取另行渐进治理。

模块图、修复清单和后续业务边界见 [RHN 2.0 模块架构](RHN2.0模块架构.md)。
