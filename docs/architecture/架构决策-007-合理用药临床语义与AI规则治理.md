# 架构决策-007：合理用药临床语义与 AI 规则治理

- 状态：提议采纳，作为合理用药实施基线
- 日期：2026-09-15
- 延续：[ADR-006](架构决策-006-物理模块化与依赖倒置.md)
- 详细方案：[RHN 合理用药平台总体方案](rational-medication/README.md)
- 实施路线：[合理用药实施路线图](rational-medication/实施路线图.md)

## 问题

RHN 将开始建设合理用药、病历质控和档案质控等质量能力。合理用药对药品、成分、规格、剂量单位、给药途径、给药频次和患者临床事实的标准化程度要求很高，但现有系统保留大量动态维护入口；同时项目当前没有完整的专业药学知识团队，也没有可直接使用的开箱规则库，希望利用 AI 提升药学知识和规则建设效率。

如果继续把临床语义当普通字典直接 CRUD，已发布频次、单位、规格等语义变化会使历史处方无法解释，并可能导致剂量、相互作用和禁忌规则失真。如果直接让 AI 生成或运行生产阻断规则，则存在不可重复、不可审计、来源不明、模型漂移和医学含义误读等风险。

因此需要同时解决两个问题：

1. 如何保留基层医疗系统所需的机构动态配置能力，同时保证参与临床决策的数据语义稳定；
2. 如何充分利用 AI 进行药学知识工程，又不把 LLM 变成生产环境的最终安全决策者。

## 决策

### 1. 临床语义与本地配置分离

凡参与临床规则计算的数据，必须具有稳定 ID、Canonical Semantic、版本、有效期、来源、状态和运行时快照能力。

机构可以动态维护：

- 本院码；
- 别名/显示名称；
- 排序；
- 本院药品启停；
- 发药药房；
- 价格、库存等业务配置；
- 本地值到 Canonical Concept 的映射。

机构不得通过普通 CRUD 自由改变已发布的临床语义，例如：

- `BID` 从每日 2 次变成每日 3 次；
- 已发布剂量单位的换算含义；
- 已发布给药途径的临床分类；
- 药品成分、规格强度等参与安全判断的核心语义。

### 2. 已发布临床语义不可原地修改

临床语义采用版本化发布生命周期：

```text
DRAFT → VALIDATED → APPROVED → PUBLISHED → RETIRED
```

`PUBLISHED` 版本只读。临床语义变化通过 Clone/New Version 发布；历史处方继续引用当时版本或快照。

显示变化、映射变化和临床语义变化必须分类。`CLINICAL_SEMANTIC_CHANGE` 需要更高等级审批、影响分析和受影响规则回归测试。

### 3. 默认值与安全知识分离

`defaultDose/defaultRoute/defaultFrequency` 等主数据默认值仅用于提升业务录入效率，不视为安全范围。

最大单次剂量、最大日剂量、年龄限制、肝肾调整、相互作用、禁忌等属于 Quality Medication Knowledge，必须独立版本化并绑定证据。

### 4. 临床剂量单位与包装单位分离

临床剂量单位用于安全计算，需要明确维度、Canonical Unit 和确定性换算；包装单位用于库存和发药。规则引擎禁止通过单位显示文本进行猜测性换算。

### 5. 规则运行使用确定性引擎

第一阶段规则使用强类型 Java 和版本化参数/知识执行。生产运行时不得把 LLM Prompt 作为 `PASS / WARN / REQUIRE_OVERRIDE / BLOCK` 的直接执行器。

后续即使引入规则 DSL，也必须编译/验证为确定性的可测试执行定义，保留 RuleVersion。

### 6. AI 只生成 Candidate，不直接发布生产规则

AI 可以承担：

- 说明书/指南/法规文档理解；
- 药品、成分、剂量和特殊人群知识抽取；
- 术语标准化和知识关系建议；
- Candidate Rule 生成；
- Evidence 定位；
- 冲突发现；
- AI Critic 复核；
- 规则测试用例生成；
- 规则解释和优化建议。

所有 AI 产物首先进入 Candidate 状态，必须经过 Schema Validation、证据绑定、冲突检查以及与 Decision 风险等级匹配的审核/发布流程，才能生成不可变的生产 RuleVersion。

### 7. AI 抽取置信度与医学证据等级分离

`extractionConfidence` 只表示模型对“是否正确理解/抽取文本”的估计，不等价于 `clinicalEvidenceLevel`。生产规则的动作等级不得由 AI confidence 单独决定。

### 8. 强动作要求强证据

规则发布按风险分级：

- L1：明确法规、说明书禁忌、明确剂量上限、机构强制制度等，在满足审核要求后可使用 `BLOCK / REQUIRE_OVERRIDE`；
- L2：相互作用、慎用、重复治疗、剂量偏高等药学建议，早期优先 `WARN`，高风险动作需提高审核等级；
- L3：AI 推断性临床提示只能 `INFO / SUGGESTION`，不得直接 `BLOCK`。

原则：系统动作越强，要求的证据、测试和审核越强。

### 9. Safety Evaluation 必须可审计和可重复

生产 Evaluation 至少记录：

- target ID/version；
- prescription revision；
- inputHash；
- RuleSetVersion；
- 实际执行的 RuleVersion；
- Evidence；
- 必要的输入/事实版本。

历史审计不能使用“当前最新主数据”重新解释历史处方。

### 10. 结果必须显式区分 UNAVAILABLE

合理用药接口统一区分：

```text
PASS
WARN
REQUIRE_OVERRIDE
BLOCK
UNAVAILABLE
```

`UNAVAILABLE` 不能作为 `PASS` 返回。缺失事实、规则执行失败和基础设施不可用的处理策略按具体规则和业务场景配置、测试和验收。

### 11. 医生机器检查与药师人工审方保持独立责任

Quality 拥有机器规则、Evaluation、Finding 和 Evidence；Pharmacy 继续拥有人工审方流程和 `PharmacyReview`。二者通过 Finding、医生 Override 和 Review 关联形成反馈闭环，不建设第二套平行药师审方流程。

### 12. 模块边界继续遵守 ADR-006

Quality 不直接访问其他模块的 Repository、Entity、application、infrastructure 或数据库表。Clinical/Public Health 定义业务消费 Port 或公开快照，Quality 提供实现；异步深度评价通过 Outbox/Inbox 处理。

## 影响

### 正向影响

- 保留机构动态配置能力，同时避免临床语义漂移；
- 历史处方、规则和评价可以长期解释；
- AI 能显著降低知识整理和规则工程的人力成本，但生产安全边界清晰；
- 合理用药积累的 Rule/Evaluation/Finding/Evidence 能复用到病历质控和公卫档案质控；
- 规则库成为带证据、版本、测试和反馈的长期资产，而不是散落在业务代码中的 if/else。

### 代价

- 基础主数据维护从简单 CRUD 升级为版本/发布治理，后台实现和操作流程更复杂；
- 需要补齐 Medication/Frequency/Route/Unit 等 Canonical Semantic 和历史兼容；
- AI 不能“生成完马上上线”，需要 Candidate、Review、Shadow 和回归过程；
- 高风险生产规则最终仍需要合适的医学/药学审核资源，AI 只能显著降低审核前的知识工程工作量，不能完全消除专业责任。

## 实施顺序

按以下顺序推进：

1. `QMED-0`：Medication Semantic Baseline；
2. `QMED-1`：Quality Safety Engine Foundation；
3. `QMED-2`：现有过敏/抗菌药/皮试规则 Shadow 迁移；
4. `QMED-3`：医生 safety-check / submit 安全工作流；
5. `QMED-4`：Medication Knowledge Base；
6. `QMED-5`：AI Knowledge Factory；
7. `QMED-6`：PharmacyReview 反馈闭环；
8. `QMED-7`：肝肾、实验室、妊娠等高级临床规则。

具体任务和 Definition of Done 见 [实施路线图](rational-medication/实施路线图.md)。
