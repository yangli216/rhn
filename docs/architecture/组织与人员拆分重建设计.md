# 组织与人员拆分重建设计（待确认，未开发）

日期：2026-10-19。替代 [组织资料维护收敛设计](组织资料维护收敛设计.md)。

## 1. 决定

| 事项 | 结论 |
| --- | --- |
| 菜单 | 原「组织与人员」(`/settings/organization`) 下线，拆成两个独立菜单：「机构与科室」`/settings/organizations`、「人员管理」`/settings/personnel`。旧路径重定向到机构与科室 |
| 前端 | 废弃 `OrganizationPersonnelManagement.tsx`、`OrganizationProfileEditor.tsx`、`PersonnelLifecycleDialog.tsx` 及其专属辅助文件，两个功能各自新建目录 `features/settings/organizations/`、`features/settings/personnel/`。数据校验类纯函数（回执校验、字典校验）若仍适用，迁入新目录复用，不复制 |
| 后端 | 组织/科室/人员/聘用/任职/岗位领域模型、停用影响检查、乐观锁、变更快照**复用**：它们被排班、挂号、接诊、开单、收费、药房、住院等 40 余处消费，不能重写。只新增执业资质、人员查询和任职自动聘用三块 |
| 聘用与任职 | 界面只出现「任职（机构·科室·岗位）」。聘用由系统维护：入职时创建；新任职落在尚无聘用的机构时自动创建；离职结束全部聘用 |
| 人员范围 | 档案 + 任职 + 执业资质（职称、执业类别与证号、医保医师编码、处方权）。登录账号、CA 证书不在本次范围，人员详情只读显示关联账号并跳转「角色与权限」 |

## 2. 机构与科室

**模板**：`MasterDetailPage`。左侧组织树（机构 → 院区/科室，可搜索、显示停用），右侧当前节点详情。

**详情（默认只读，单页无页签）**：

```
┌ 青禾镇中心卫生院  QH-TOWN-HC  [已启用]            [编辑] [新增下级科室] [更多 ▾: 停用 / 变更记录]
│ 基本信息    名称 · 类型 · 上级 · 时区 · 虚拟组织 · 说明
│ 运行属性    （科室）业务属性 · 具体科室类型 → 下方一句话说明它驱动哪些业务
│ 资质与联系  机构标识 · 地址 · 联系电话 · 负责人 · 服务能力   （科室只有 联系电话 · 负责人 · 服务能力）
│ 在岗人员    在岗 8 人 · 主任职 6 人      [在人员管理中查看 →]
└
```

- 读写分离：只读视图用描述列表，信息密度高、视觉统一；点「编辑」弹出编辑对话框（基本信息 + 运行属性），「资质与联系」各分区标题旁有「维护」入口，打开该分区的编辑对话框（行内表格）。不再有固定底部「保存全部资料」。
- 「运行规则」页签取消，规则说明并入「运行属性」字段旁的说明文字；「变更记录」移到「更多」菜单，用对话框查看。
- 人员列表不在本页展示，只显示统计并跳转到人员管理（带机构/科室筛选）。

**字段**（沿用上一版取舍，不再重复论证）：

| 分组 | 机构 | 科室 |
| --- | --- | --- |
| 基本信息（编辑弹窗首层） | 名称*、组织结构类型*、上级、时区、虚拟组织、说明 | 名称*、上级*、虚拟组织、说明 |
| 运行属性 | — | 业务属性*、具体科室类型* |
| 更多设置（折叠） | 简称、机构性质、同级排序、生效/结束日期 | 简称、同级排序、生效/结束日期 |
| 资质与联系 | 机构标识（类型+编码）、地址（省市区+详细地址）、联系电话、负责人、服务能力 | 联系电话、负责人、服务能力 |

- 协作关系不在界面出现，数据和接口保留。
- 资质与联系行内不显示每条记录的生效/结束日期和启用状态：新增以当天生效，移除即作废并保留历史。
- 停用沿用现有依赖检查对话框（启用下级、在岗/待生效任职、未结束聘用）。

## 3. 人员管理

**模板**：`ListPage`（人员是大量数据的查询与维护，主从树不适合）。

```
[搜索 姓名/工号/拼音] [机构·科室 ▾] [岗位类型 ▾] [职称 ▾] [处方权 ▾] [状态: 在职 ▾]  [查询] [重置]        [办理入职]
┌──────┬──────┬────┬──────────────────┬────────┬────────┬────────────────┬──────┬──────┐
│ 工号 │ 姓名 │性别│ 主任职（科室·岗位） │ 职称    │ 执业类别 │ 处方权            │ 状态 │ 操作  │
│ P001 │ 张三 │ 男 │ 内科门诊·主治医师   │ 主治医师 │ 临床    │ 普通 · 抗菌:限制级 │ 在职 │ 查看 ▾│
└──────┴──────┴────┴──────────────────┴────────┴────────┴────────────────┴──────┴──────┘
                                                                        分页
```

- 「查看」打开人员档案（右侧宽抽屉或独立详情页，二选一见第 7 节），分三块：
  1. **基本档案**：工号、姓名、性别、证件号（只写入、显示脱敏）、联系电话、状态。
  2. **任职**：表格列 机构 · 科室 · 岗位 · 主任职 · 起止日期；操作 新增任职 / 调岗 / 结束任职。底部「办理离职」。
  3. **执业资质**：职称、执业类别、执业证书编码、资格证书编码、医保医师编码、处方权（普通处方、麻醉与第一类精神药品、抗菌药物处方级别）。单独保存。
  4. 只读：关联登录账号（有则显示账号名，跳「角色与权限」）。
- **办理入职**对话框一次完成：姓名、性别、工号（按编码规则生成，可改）、证件号、联系电话、入职日期、机构·科室·岗位；执业资质可选，入职后也可补。
- 岗位目录维护放在页面右上「岗位设置」对话框（低频）。
- 行操作 ▾：调岗、结束任职、办理离职、停用档案。

## 4. 后端改动

### 4.1 复用（不改语义）

`OrganizationApplicationService`、`DepartmentApplicationService`、`OrganizationMaintenanceService`（基本信息与档案项事务提交）、`OrganizationProfileMaintenanceService`、`OrganizationImpactService`、`PersonnelLifecycleService`（调岗/结束任职/离职）、入职接口、岗位接口、变更记录接口。

资质与联系分区单独保存时，前端提交未改动的主体字段加该分区变更，`OrganizationMaintenanceService.save` 现已支持，无需后端改动。

### 4.2 新增

1. **执业资质**：新表 `RHN_SYS_PRACT_QUALIF`（每人一行，带 REVISION 和变更快照）。

   | 列 | 含义 | 来源 |
   | --- | --- | --- |
   | SD_PROF_TITLE | 职称 | 新字典 `PRACT_PROF_TITLE`（主任医师、副主任医师、主治医师、住院医师、医士；主任护师…护士；主任药师…药士；主任技师…技士） |
   | SD_PRACT_CATEGORY | 执业类别 | 新字典 `PRACT_CATEGORY`（临床、中医、口腔、公共卫生、护士、药师、技师、其他） |
   | CD_PRACT_CERT / CD_QUALIF_CERT | 执业证书编码 / 资格证书编码 | 文本 |
   | CD_INSUR_PRACT | 医保医师（护士）编码 | 文本 |
   | FG_RX | 普通处方权 | 布尔 |
   | FG_NARCOTIC_RX | 麻醉药品和第一类精神药品处方权 | 布尔 |
   | SD_ANTIMICROBIAL_RX_LEVEL | 抗菌药物处方级别 | 复用 `BD_ANTIMICROBIAL_LEVEL`，空为无权限 |

   接口：`GET/PUT /api/platform/practitioners/{id}/qualification`（expectedRevision）。平台公开读接口 `PractitionerQualificationDirectory`，供后续开单校验使用。
2. **人员查询**：`GET /api/platform/personnel?keyword&organizationId&departmentId&positionType&title&rx&status&page&size`，服务端分页，返回列表行（主任职、职称、处方权摘要）。替代前端拉全量人员再与任职拼接。
3. **任职自动聘用**：新增任职时如果该人员在目标机构没有有效聘用，同一事务内自动创建聘用（类型取入职默认值）。现有接口要求先建聘用。

### 4.3 本次不做（需单独决定）

- 开单时校验医生处方权（抗菌药级别、麻精处方权）。现在门诊开药只校验药品本身的门诊可用和天数，不校验医生。资质建好后再逐项接入；存量医生没有资质数据，直接开启会阻断开单，需要先补数据并给开关。
- 账号与人员绑定的维护、CA 证书。

## 5. 权限

暂沿用：查看 `ORGANIZATION.ACCESS`，写入 `IAM.MANAGE`，两个菜单相同。若要把人员维护交给人事岗位而不给其权限管理，需要新增 `PERSONNEL.MANAGE`，见第 7 节。

## 6. 迁移、兼容与验证

| 项目 | 影响 |
| --- | --- |
| 数据库 | 新增 1 张表、2 个字典定义及字典项；Oracle 与 H2 迁移各一份。不改已有表 |
| API | 新增 3 个接口，更新 OpenAPI 和 generated.ts；已有接口不变 |
| 存量数据 | 已有人员无执业资质（列表显示“未登记”）；已有协作关系保留不展示 |
| 菜单与路由 | AppShell 菜单、页签标题、旧路径重定向；其他页面中跳往 `/settings/organization` 的链接改到新路径 |
| 测试 | 旧页面测试随页面删除；两个新页面各自 DOM 测试；后端资质服务、人员查询、自动聘用单元/集成测试 |
| 验证 | `./scripts/verify-scope.sh organization`，加 `api-contract`；迁移执行 schema refresh/check；人工验收 1280/1440/1920 |

### 分阶段交付

1. 后端：资质表与接口、人员查询、自动聘用、迁移与契约。
2. 前端：机构与科室页。
3. 前端：人员管理页（列表、档案、入职、调岗/离职、资质）。
4. 菜单切换、旧页面删除、文档更新、整体验证。

每阶段结束可单独查看；第 4 步前旧页面保持可用。
