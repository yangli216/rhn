# 三方支付对账功能设计

状态：第一期交易对账已实现，待渠道联调及上线验收。设计日期：2026-10-18；实施记录：2026-10-19。适用范围：机构自有支付宝、微信直连商户及后续可扩展渠道。

本设计复用现有收费对账领域、支付编排及商户配置，补齐正式渠道账单接入和财务差异闭环。第一期采用增量迁移和版本化契约，不改写既有业务数据。对账核对过程不发起收退款。医保对账、财政票据核验属于各自领域，不纳入本期。

## 1. 目标与边界

第一期完成“交易账单自动获取 → 完整性校验 → 逐笔核对 → 差异核查 → 财务复核”，覆盖收款、部分退款、多次退款、跨日退款、撤销和在途支付。自动核对只读取外部交易和内部资金事实；需要补记时，必须查询原支付指令并复用现有支付结果入账事务。

| 核对层次 | 比较对象 | 本期安排 |
| --- | --- | --- |
| 交易对账 | 渠道收款／退款记录与本地支付指令、成功资金事实 | 第一阶段实施 |
| 资金对账 | 渠道账户的收支、手续费、优惠承担、划拨及余额变化 | 第二阶段；第一阶段保留来源字段及扩展位置 |
| 银行到账核验 | 渠道结算批次与银行到账流水 | 后续独立能力，不能用交易对平代替银行到账证明 |
| 收费员日结 | 收费员、终端与已固定的支付成员 | 沿用现有日结；展示关联对账结果，既有日结规则保持独立 |

第一阶段“对平”仅表示指定商户账单范围的交易已核对，不表示手续费、商户余额或银行到账已核验。

## 3. 对账范围与商户归属

### 3.1 两级批次

下载范围由渠道实际出账口径决定。微信 V2 明确以商户号出账，多 AppID 共用同一商户号也会出现在同一份账单内，不能按应用或机构各下载一份后分别把整账金额计入本机构。[微信官方协议](https://pay.weixin.qq.com/doc/v2/merchant/4011939627)

采用两级结构：

- **商户账单批次**：按租户、渠道适配器、支付环境、渠道声明的商户／账户覆盖范围、账单类型、账单日和币种唯一。负责完整下载、汇总校验、文件版本和全账归属。
- **机构核对批次**：在商户批次下，按支付指令的原始机构归属生成；同一账单行最多归属一个机构，不能按当前操作员机构、患者当前档案机构或配置列表第一项回退。

现有 `ReconciliationBatch` 继续承载机构核对结果；新增商户账单来源实体及其关联，不建立另一套独立支付对账引擎。既有批次作为历史结果保留，不擅自重新解释。

归属优先采用现有商户订单号 `P + 支付指令ID`、商户退款请求号 `R + 退款指令ID`，并交叉验证商户、环境、支付方式、原单关系及渠道流水。格式符合并不构成归属证明，必须找到同租户真实原指令。

范围模型允许机构保留历史商户，并支持多个机构共用同一商户账户。第一期沿用现有“每机构每支付方式一个当前商户”的配置约束；同时启用多个商户的收款路由不在本设计范围内，不能借对账绑定绕过商户身份锁定。账户覆盖范围使用稳定标识，应用 ID 只有在渠道确实按应用分账时才进入账单范围键。凭证版本变化不改变该稳定标识。

### 3.2 不能归属的流水

商户全账中的院外收款、其他系统交易和未知退款进入商户级“待归属”队列，不能随意挂到患者账单。机构账号只能查看本机构已确定归属的数据；全账和未归属数据要求额外的商户范围财务授权。

跨租户共用同一实际收款商户的存量情况必须先登记隔离规则。第一期不自动开启这种账户的全账下载及导入；不得让某租户通过账单看到另一租户的交易。不能用“筛掉未匹配流水”掩盖账单不完整。

## 4. 渠道能力与配置扩展

演进现有 `ReconciliationAdapter`，引入声明式路由与账单能力。以下为设计概念，实施中对应 `PaymentReconciliation` 及生成的 API 契约：

| 声明／输入 | 主要内容 |
| --- | --- |
| 唯一路由 | 对账类型、渠道适配器编码、支付方式、账单类型；与 `PaymentChannelRegistry` 的归属校验一致 |
| `ReconciliationCapabilities` | 支持自动下载／受控上传、交易／资金账单、账单覆盖范围、时区、最早可用时刻、历史可查窗口、格式版本、状态确认要求、校验方式 |
| `StatementFetchContext` | 显式租户、商户范围、环境、账单日、币种、凭证引用、任务 ID、尝试号及关联 ID；后台任务不依赖操作员当前上下文 |
| `StatementFetchResult` | `AVAILABLE / NOT_READY / NO_DATA_CONFIRMED / NOT_FOUND / AUTH_FAILED / RATE_LIMITED / UNSUPPORTED` 等结构化结果，以及文件引用、范围证明、汇总和校验信息 |
| 规范化账单行 | 行身份、收退类型、商户订单号、渠道交易号、退款请求号、渠道退款号、原交易号、金额口径、渠道状态、发生时间、记账日期及原文件定位 |

注册时拒绝重复路由、空能力或配置提供者归属冲突。未支持的账单类型不能靠 Bean 顺序选择；可靠外部交接仅在相应路由明确声明并启用时使用。旧 `supports/fetch` 迁移到统一注册表，兼容入口也走同一校验／匹配流程。

“系统设置 → 支付渠道”增加渠道声明的对账配置区：是否自动对账、账单时区、首次拉取时刻、补拉策略、通知对象、受控文件保留策略及账单权限检测。商户身份和凭证继续使用现有机构加密配置；调度策略作为有版本的普通配置保存。

“新收款停用”和“对账任务停用”分别控制。停用新收款后，原商户的对账、查询和退款仍可工作。后台使用精确的商户身份与凭证引用，不复制密钥；保存非秘密身份快照和凭证版本用于追溯。历史商户更换走单独迁移，凭证轮换不能改变历史交易所属商户。

前端按能力展示配置与操作，不写 `if 支付宝 / if 微信`。新增渠道原则上只增加适配器、能力／字段声明、字典、协议样本和契约测试；只有新增通用账单语义才调整核心模型。

## 5. 支付宝与微信接入策略

| 渠道 | 第一阶段 | 需要保留的协议差异 |
| --- | --- | --- |
| 支付宝 | 沿用当前官方 Java SDK，调用 `alipay.data.dataservice.bill.downloadurl.query`，交易账单选择 `trade`，获取地址后立即服务端下载 | 请求安全 HTTPS 链接；下载地址短期有效，不能作为持久文件引用。`signcustomer` 为后续资金账单。账单日及错误码由适配器解释 |
| 微信 | 沿用当前 WxJava 与 API V2 凭证，使用 `pay/downloadbill`；默认获取 `ALL` 并识别支付、退款和撤销行 | 账单单位为元，不能沿用支付 API 的整数分直接解析；按商户号出账。退款行可能表示受理成功而非最终退款成功，账单中的退款状态在出账后不会更新 |

不为了下载账单额外引入一套支付 SDK，也不把微信 API V3 的密钥／平台证书要求隐式加到当前 V2 商户上。若以后选择 V3 下载，作为明确的协议能力、凭证及迁移单独实施。

支付宝日账单按 T+1 获取，一般次日上午生成，下载链接目前要求获取后及时使用；微信建议次日 10 点后获取，V2 下载窗口为三个月。以上是当前官方协议条件，调度规则由适配器声明并在商户联调时再次确认。[支付宝账单接口](https://opendocs.alipay.com/open/02ekfm)、[微信下载交易账单](https://pay.weixin.qq.com/doc/v2/merchant/4011939627)

建议默认在账单时区的次日 11:00 首次拉取，时间可配置，并加入抖动和渠道级限流。该时间是产品默认建议，不是渠道保证的到账／出账时限。

## 6. 流程、任务及版本

```text
人工发起／到期调度
  → 确定商户账单范围与凭证引用
  → 持久化任务并领取租约
  → 事务外申请、下载、校验与解析
  → 保存不可变文件及规范化版本
  → 固定本地资金事实／指令快照
  → 执行匹配，产出机构结果和商户待归属队列
  → 查询原单核实差异，必要时走既有补记事务
  → 重跑并保留前版结果
  → 财务复核／有差异结案
```

任务阶段与财务结果分开存储：

- 任务：`QUEUED → FETCHING → VALIDATING → MATCHING → COMPLETED`；等待账单为 `WAITING_STATEMENT`，可重试故障为 `RETRY_WAIT`，永久错误为 `FAILED`。
- 结果：`MATCHED / DIFFERENCE / AWAITING_CONFIRMATION`；结案另记 `OPEN / REVIEW_PENDING / CLOSED_MATCHED / CLOSED_WITH_EXCEPTION`。

所有差异都填写“忽略原因”不能把结果改成 `MATCHED`。历史上的 `RESOLVED` 仍表示旧流程已处置，不迁移成财务对平。没有新版本可用时，失败的重跑保留上一份可用结果及其时间，不能覆盖成空账。

任务使用持久化尝试记录、租约和递增领取令牌；进程重启可恢复，过期工作者不能提交结果。下载不持有账务行锁；大账单分块写入暂存区，校验完成后原子发布文件版本和执行结果，失败不能留下半个“已完成”批次。

唯一业务范围用于防止并发建重复批次；幂等命令还绑定完整范围及输入指纹，重复命令携带不同机构、商户、类型、币种或日期时拒绝。重试沿用逻辑任务并增加尝试；重跑新增执行版本，禁止删除明细后原地重算。

每版记录文件 SHA-256、渠道提供的校验值／签名验证结果、文件生成时间、解析器版本、规则版本、本地快照截止点和摘要。相同文件及相同本地快照、规则重复提交返回原结果；文件字节变化或本地迟到入账产生新版本。新版本发布后旧审批结论不自动继承。

## 7. 文件、空账单和安全校验

下载后必须先校验，后匹配：

1. 限定服务端官方地址／渠道声明的允许主机；校验 TLS、跳转目标、端口及解析后的地址，阻止内网跳转。含鉴权参数的下载 URL 不返回浏览器、不写日志，过期后重新申请。
2. 核验商户身份、应用适用范围、环境、账单类型、日期、币种及完整文件集合；多文件压缩包不能只解析第一份。
3. 原始字节保存受控文件对象并计算本地 SHA-256。本地摘要只证明存储一致性，不冒充渠道真实性证明；渠道支持验签／下载摘要时按其协议校验。
4. 检测压缩前后大小、条数及解压比例上限，防止路径穿越、压缩炸弹、重复文件和截断。流式解析，禁止将数万行装进现有同步 JSON 上传接口。
5. 按渠道版本识别编码、列头、字段和汇总尾行，正确处理 CSV 引号及微信格式前缀；未知状态、缺失关键列或不支持版本应报错，不能静默跳行。
6. 校验渠道定义的各项笔数／金额汇总。业务上不同口径的汇总不能强行相加；解析无法解释退款及优惠口径时停止核对。

`NOT_READY` 与网络错误不能转为空账；`NOT_FOUND` 也不能默认推断“当天无交易”。只有协议明确确认无数据，或取得范围完整且汇总为零的有效账单，才可标记 `NO_DATA_CONFIRMED`。支付宝已声明的空账单结果／无业务数据错误须按确定的协议映射；微信没有可靠空账证据时进入待确认，不能以本地也是零笔自动变绿。人工确认无交易保留证据，结论与自动验证空账区分。

解析失败、凭证失效、权限不足、账单未生成分别展示；超出可下载窗口后停止无效重试并提示财务取账。受控手工上传复用同一解析器、范围及汇总校验，标记 `MANUAL_UPLOAD`。无法验证渠道来源的文件不能获得与自动取得账单相同的真实性结论，需要单独复核。

原始文件加密、按商户范围鉴权并审计读取，下载权限不随普通机构查看权限下放。摘要视图不展示 payer 原始标识；导出应防 CSV 公式注入。文件生命周期可配置，但审计、差异和已入账资金证据不能由日常业务初始化直接清除。

## 8. 逐笔匹配与金额口径

### 8.1 交易身份

| 记录类型 | 主匹配依据 | 交叉核验 |
| --- | --- | --- |
| 收款 | 商户范围 + `PAYMENT` + 商户订单号 | 本地支付指令、渠道交易号、金额、币种、渠道商户身份 |
| 退款 | 商户范围 + `REFUND` + 商户退款请求号 | 原支付指令／渠道交易号、渠道退款号、退款金额与状态 |
| 撤销 | 渠道的撤销身份及原单引用 | 按协议判定是否真实退回资金；原单号相同不能当重复收款或自动生成退款 |

原支付渠道交易号不能作为退款唯一键。微信退款单有独立退款号；支付宝退款可能继续携带原交易号，必须使用 `out_request_no` 区分多次部分退款。若特定账单版本不能给出退款请求号，适配器需通过可验证的退款身份映射／原单查询补充；无法唯一确定时保留歧义，不能按金额、患者或近似时间自动挑一条。

每个执行版本内对本地事实和渠道行实施一对一消费约束；同一事实不能匹配两条行。撤销、跨日退款和多次部分退款是不同业务事件，必须与真正重复交易区分。

### 8.2 日期与迟到入账

账单日采用渠道声明的时区和账期规则，国内直连默认 `Asia/Shanghai` 并保存快照，不能依赖服务器默认时区。原始渠道时间、本地成功记账时间和账单归属日分别保存。

以渠道订单／退款身份查询本地指令时不限制同日；D 日交易在 D+1 补记，或 D 日收款在 D+3 退款，都不能因此成为永久单边。初始候选采用索引化时间窗口，精确身份匹配可跨日追溯；窗口参数及覆盖状态进入执行证据，查询不完整时不能宣称全量对平。

相同交易与金额一致但记账日不同，标记为时间差并关联原事实；不能把它再次计入另一日的收款。历史账单在本地补记后重跑产生新版本，保留此前差异。

### 8.3 金额与状态

使用现有六位 `BigDecimal` 账务语义，渠道 CNY 原始金额按分精确校验后无损转换，不使用浮点数或四舍五入隐藏差异。按渠道列单位分别转换，微信下载账单的“元”和支付 API 的“分”不得混用。

至少区分订单总额、申请退款额、实际／应结金额、用户现金、优惠及其承担方、手续费；原值、归一化值和映射规则均可追溯。与本地资金事实比较的应是对应的收款／退款业务金额，不用扣除手续费后的净到账额替代。存在优惠且当前协议不能解释金额组成时，进入“金额口径待确认”。

分别汇总收款笔数／金额、退款受理笔数／金额、退款完成笔数／金额和确认完成的净额，不以净额相等掩盖两笔相反的差异。账单表头汇总按渠道规则独立验证。

微信账单中的 `REFUND` 表示该行与退款有关，不直接映射为本地退款完成；必须结合退款状态并在必要时查询原退款。出账时 `PROCESSING` 的记录可能日后成功，但旧文件不会自动更新，需附加最终状态核查证据。只有符合当前支付编排要求的最终成功结果才能形成退款资金事实。[微信状态说明](https://pay.weixin.qq.com/doc/v2/merchant/4011939627)

## 9. 差异及处理闭环

| 差异 | 默认动作 | 关闭依据 |
| --- | --- | --- |
| 渠道有、本地尚无成功资金事实，但存在原支付／退款指令 | 查询原指令，展示在途状态，进入恢复流程 | 已验证渠道结果通过现有幂等入账事务落地，再重跑 |
| 渠道有、无法找到可信原指令 | 商户级待归属，人工核查院外交易或丢失记录 | 有证据的归属或例外复核；禁止虚构患者账户补单 |
| 本地成功、渠道未见 | 检查账单完整性、范围、跨日和渠道查询 | 找到可信渠道证据或完成授权的差错处理；不能自动退款／删除本地事实 |
| 金额／币种／商户不一致 | 保留原记录，限制自动处置，通知财务 | 修正接入映射并重跑，或走独立审批的账务调整流程 |
| 渠道处理中／退款状态未定 | 查询并等待，设置下一次核查时间 | 取得明确最终状态；超时升级，不将未知当失败 |
| 时间差 | 跨账期关联，不再次入账 | 原交易身份、金额和最终状态确认，保留账期归属说明 |
| 重复／多义匹配 | 阻断一对多入账，定位实际重复或解析问题 | 原始证据及唯一身份确定，重跑后核实 |
| 外部手工退款／撤销 | 识别对原交易的影响，人工核查业务授权 | 使用已有退费／差错审批路径；第一期不提供对账页一键强制冲账 |

差异状态建议为 `OPEN → INVESTIGATING → PENDING_ACTION → RESOLVED_PENDING_REVIEW → CLOSED`，无法修复但经批准接受的异常标记 `ACCEPTED_EXCEPTION`，与已对平始终分开。每次动作保留命令 ID、版本、操作者、理由、证据和时间。

对账本身不直接更新 `Payment / PaymentOrder / LedgerEntry` 的成功状态或金额。恢复动作必须找到既有原指令，调用支付查询／恢复及 `PaymentResultTransactionService` 等既有原子入账入口，沿用原幂等键与资金预占规则。重复点击、补偿重放或多任务并发不能重复形成资金事实。未能获得可信最终结果时只能待核查。

需要资金调整的处置与纯说明性处置分开授权。财务复核人不得审批自己的有资金影响操作或例外接受；复核要求任务及账单版本未变化。对账页“重新查询”和“重新核对”不会重新发送付款码或重新发起退款。

## 10. 数据模型演进

复用现有三张对账表，概念上补充以下关系；表名、列名、字典及索引在实施时按数据库规范登记，不在设计阶段抢占迁移版本：

| 数据对象 | 粒度及关键约束 |
| --- | --- |
| 商户账单范围／绑定 | 稳定账户覆盖范围、租户、渠道、环境、机构授权绑定及既有凭证引用；不含秘密副本 |
| 账单来源与文件版本 | 范围／账单日／类型／币种、来源、完整文件集合、存储引用、摘要、汇总、解析版本与原始生成时间；不可覆盖 |
| 拉取任务／尝试 | 计划时间、领取令牌、租约、错误类别、下次重试、幂等指纹和尝试历史 |
| 对账执行版本 | 商户账单版本、机构批次、本地快照截止点、规则版本、结果与各口径汇总；每次重跑新增 |
| 规范化账单行 | 来源版本及行号、稳定交易身份、全部必要金额／状态／时间、机构归属结果；来源内行身份唯一 |
| 既有对账明细扩展 | 执行版本、差异分类、原支付／退款指令和资金事实、账单行证据引用；不再只保存一个外部交易号 |
| 既有处置事件扩展 | 处置／复核状态、输入版本、命令指纹、动作结果及关联恢复命令；事件追加，不覆写历史 |

批次列表、差异列表均分页，详情按需读取；不能把全部明细嵌在每个批次列表项中。为完整身份查找、商户／日期任务、机构／差异状态和下一次重试时间建立索引。

迁移采用新增及兼容回填策略；旧批次保留 `LEGACY` 来源和原结论。不能从当前商户配置反推历史批次商户身份；无法确定的留为历史待确认。公共与 Oracle 对等迁移、物理目录、维护保留策略和权限元数据一同评审。

## 11. 页面、接口与权限

业务入口建议设为 **收费管理 → 支付对账**；渠道启停和拉取策略仍在 **系统设置 → 支付渠道**。日终结账可跳转查看关联批次，但不得默认为同一核算口径。

页面沿用 `ListPage + DataTable`，以机构／商户授权范围、渠道、账单日、账单类型及结果为固定筛选；顶部并列显示收款、退款受理、退款完成、手续费信息覆盖状态和未结差异，明确“截至何时／哪个版本”。主操作是“拉取并核对”，处理区局部滚动，PC 宽屏展示双边明细。

批次详情采用 `MasterDetailPage`：左侧差异清单，右侧本地指令／资金事实与渠道证据并列；固定底部放查询原单、提交处置和复核动作。渠道未开通账单能力、未出账、真实零账单、凭证失效、处理失败和部分覆盖均有独立提示，不用一个“无数据”混合表达。

沿用 `/api/billing/reconciliation-batches` 资源演进异步创建、筛选分页、版本／文件元数据、任务重试及差异分页。新增恢复、提交处置、复核和受控导出命令；原同步标准化账单入口限制为具有专门导入权限的兼容集成，不能让普通收费账号任意上传“渠道成功”结果。

拟议权限：`PAYMENT_RECONCILIATION.READ / RUN / HANDLE / REVIEW / EXPORT`，商户全账和未归属流水另加明确的商户范围授权。配置凭证的 `PAYMENT_CONFIGURATION.MANAGE` 不自动包含对账处置权限；普通 `BILLING.ACCESS` 也不授予导入、例外接受或资金恢复权限。

每个接口及后台任务都校验租户、机构／商户数据范围和对象归属。当前用户选错机构不能读到另一机构的差异；账户、机构或权限变化时，前端清除旧页数据和迟到结果。共享 API Client、字典文本、金额格式和生成契约继续沿用现有规范。

## 12. 实施顺序与验收

| 阶段 | 交付内容 | 放行条件 |
| --- | --- | --- |
| P1-A 基础模型 | 唯一适配路由、商户账单范围、异步任务、文件证据、执行版本、退款身份、权限 | 不接真实交易即可完成隔离测试；旧对账和日结回归通过 |
| P1-B 直连核对 | 支付宝 trade、微信 V2 ALL 自动下载与解析、机构分配、匹配及差异分页页面、策略配置 | 两家各自真实商户脱敏样本通过范围／汇总／身份／状态契约测试 |
| P1-C 差异闭环 | 查询恢复、处置复核、例外结案、审计导出、失败通知与补拉 | 重放／并发不重复入账，财务演练覆盖单边及在途场景 |
| P2 资金对账 | 支付宝 signcustomer、微信资金账单、手续费及结算批次核验 | 独立口径和会计处理经财务确认，不复用交易对平标识 |

第一期验收必须覆盖：

- 一笔 100 元收款分两次退 20 元、30 元，三项独立匹配且不误判重复；跨日发生也能找到原单。
- 微信退款账单行显示受理／处理中时，本地不新增退款成功事实；后续原单查询成功只入账一次，旧文件与新状态证据同时保留。
- 本地超时但渠道成功，可关联原指令恢复；没有原指令的账单行只进入待归属，不凭账单直接造成功记录。
- 商户号共用于两个机构或多个 AppID 时，只下载相应商户范围一次，每行只归属一次；机构用户不能读取另一机构及全账原文。
- 渠道促销、手续费、付款金额及应结金额有区别时，不以净额冒充本地收费金额；无法解释时明确阻断自动对平。
- 服务器时区与国内账单时区不同、跨午夜、历史迟到入账和跨日退款均不产生重复资金事实。
- 未出账、缺文件、真实空账、被截断、重复行、未知列／状态、解压上限及原始汇总不符分别给出确定结果。
- 重复任务、租约过期、重启、重传相同文件、修订账单和处置期间重跑均保持版本及幂等；重复命令不同输入拒绝。
- 查单、解析或入账故障不改变已完成资金事实、已冻结收费员日结或原始账单；新收款停用后仍能对账。
- 未授权导入／处置／导出失败，跨租户／机构访问失败，有资金影响或例外接受不能自审自批。

实施时先用 `verify-scope.sh billing --list` 选择维护检查，再按新持久化、权限和财务恢复影响扩大验证；采用随机 H2 与渠道假客户端，不在人工 Oracle 执行测试清理。真实商户账单、签约权限和资金口径由商户联调验收。

## 13. 实施前需确认的业务参数

默认按国内直连 CNY、商户账单时区、次日自动交易对账推进。实施前需盘点实际商户是否共用、账单签约／下载权限、是否存在渠道后台人工退款／撤销及历史交易优惠口径；这些是接入参数，不应通过新增核心品牌分支解决。

由财务确定参与复核的人员、例外接受规则、告警时限、账单文件保存期限和资金对账推进范围。第一期在这些参数未确认时，不开放自动资金调整和自动例外结案。
