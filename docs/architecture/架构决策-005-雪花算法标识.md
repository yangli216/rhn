# 架构决策-005：Snowflake BIGINT 主键与字符串接口契约

- 状态：已采纳
- 日期：2026-08-25

## 背景

系统需要在租户、机构、居民、就诊、文档、事件、审计等大量表之间长期关联数据。数据库主外键需要紧凑、趋势递增、可在应用侧提前生成，并尽量避免依赖某一种数据库的自增语法。与此同时，浏览器和部分外围系统不能安全处理超过 53 位的 JSON 数字。

原底座使用 UUIDv7。它无需节点协调且时间有序，但主外键为 128 位，不符合本项目对紧凑内部主键的统一要求。

## 决策

所有新建平台实体、业务实体、领域事件和审计记录默认使用正数 63 位 Snowflake ID：

- 数据库逻辑类型为 `BIGINT`，不使用 `BIGSERIAL`、`AUTO_INCREMENT` 或数据库默认值发号；
- Java 内部类型为 `long`/`Long`，持久化前通过 `GlobalIds.next()` 生成；
- JSON、OpenAPI、URL、消息和外围接口统一表示为 1 至 19 位十进制字符串；
- 输入格式为 `^[1-9][0-9]{0,18}$`，禁止零、负数、小数和科学计数法；
- 参数版本号、金额、数量等普通数值不是 ID，不因本决策改变业务语义；
- 就诊号、处方号、发票号、医保业务号等业务编号继续独立建模，不能直接拿主键代替；
- 外部系统自己的标识按“来源系统 + 外部标识”保存并建立唯一约束，不覆盖内部主键。

`GlobalIds` 使用 Hutool `Snowflake` 作为当前实现，但业务模块只依赖项目自己的稳定入口。纪元固定为 `2026-01-01T00:00:00Z`，经典布局为 41 位毫秒时间、5 位数据中心、5 位工作节点和 12 位序列。纪元和位布局属于永久数据契约，生产后不得修改。

## 节点与时钟规则

- `data-center-id` 和 `worker-id` 均为 0 至 31；同一时间运行的生成器组合必须唯一。
- 本地和测试环境允许保留 `0/0`。默认生产配置拒绝 `0/0`，必须通过 `RHN_ID_DATA_CENTER_ID` 和 `RHN_ID_WORKER_ID` 显式配置节点。
- 容器平台应使用稳定实例序号或带租约的节点注册能力，不能仅根据随机 IP、MAC 或进程号推导节点。
- 主机使用受控时间同步；发生超出生成器容忍范围的时钟回拨时停止发号并告警，不能通过复用旧时间生成潜在重复 ID。
- Snowflake 保证单生成器递增和跨节点趋势有序，不承诺跨节点严格全局时间顺序。

## 接口与前端

服务端统一把 boxed `Long` ID 序列化为十进制字符串，Spring MVC 可从同格式字符串绑定内部 `Long`。OpenAPI 将 `Long` ID 声明为字符串，前端类型必须保持 `string`，禁止转为 JavaScript `number`。

传输 DTO 中 boxed `Long` 保留给可空 ID；普通长整型数值必须使用 primitive `long`、`Integer`、`BigDecimal` 或显式的序列化与 Schema，避免被误应用 ID 字符串规则。

`X-Tenant-Id` 同样遵循该规则。`X-Correlation-Id` 是调用链字符串，不承担数据库实体标识语义。

## 数据库基线

本决策在尚未承载正式数据的底座阶段采纳，V1 至 V7 数据库基线及本地种子同步改为 `BIGINT`。固定产品字典和本地样例使用纪元之后、正式运行之前的合法 Snowflake 时间段，且所有表之间保持全局唯一，避免与运行期发号相撞。已按旧 UUID 基线创建的开发数据库需要重建，不能只执行 Flyway `repair`。若任何环境已经存在必须保留的数据，应先建立 UUID 到 Snowflake ID 的映射表，使用影子列分批回填全部外键并完成核对，禁止直接强制转换或散列 UUID。

## 后果

关系索引和外键缩小为 8 字节，应用可在事务前获得主键，数据库实现保持简单。代价是部署必须治理节点号和系统时钟，所有外部契约必须坚持字符串表示，并且内部 ID 与业务编号、外部系统编号必须保持分离。
