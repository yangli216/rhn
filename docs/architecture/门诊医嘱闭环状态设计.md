# 门诊医嘱闭环状态设计

- 状态：设计稿，待评审
- 日期：2026-10-21
- 关联：[门诊医嘱草稿事实边界](门诊医嘱草稿事实边界.md)、[ADR-008 CA 可选签名](架构决策-008-CA可选签名与签署行为证据.md)、[ADR-004 分层参数配置](架构决策-004-分层参数配置.md)、[ADR-006 物理模块化](架构决策-006-物理模块化与依赖倒置.md)

## 1. 要解决的问题

1. 医生站把医嘱只分成“待确认 / 已开立”，看不到缴费、发药、执行、退费进度，也说不清“待确认”是什么。
2. 各模块已经各自有状态：处方 `DRAFT/ACTIVE/CANCELLED`、检验检查申请 `ACTIVE/CANCELLED`、计费 `POSTED` + 冲销、发药任务 11 种状态、检查与治疗执行任务各 7–8 种状态。但没有一个统一的口径把它们串成一条医嘱的闭环。
3. **检验检查申请没有草稿状态**。医生点“保存草稿”时，申请已经生效：会发出 `SERVICE_REQUEST_AUTHORED`，触发记账（`ClinicalOrderChargeProjector`），也会生成执行任务。草稿和生效的边界不清，这是当前最大的缺口。
4. 不同等级医院对“签署”“审方”“先缴费后执行”的要求不同，需要参数化，但各个开关组合起来后，状态必须仍然自洽。

## 2. 设计原则

1. **一个状态只归一个模块所有**。医嘱模块只管“医生意图”的生命周期；收费、药房、医技、治疗各管各的履约状态，不往医嘱表里回写别人的状态（ADR-006）。
2. **医生看到的是推导出来的流转状态**。它由各模块的状态按固定优先级计算得出，只读、不落库，所以不会和各模块的事实不一致。
3. **生效是唯一的对外分界线**。医嘱生效之前，其他模块看不到它，不记账、不下发；生效之后的撤销必须走冲销或退费，不允许物理删除。
4. **签署指业务签署**。签署行为证据在业务事务内必定生成，可以作为生效的前置条件；个人 CA 签名异步补签，任何流程都不以它为前提（ADR-008）。
5. **参数只决定会不会经过某个状态，不新增状态**。关闭某项要求时跳过对应状态；所有组合共用同一张状态图。

## 3. 状态分层

```
┌──────────── 医嘱主状态（ordering 所有）────────────┐
 草稿 ──开立──▶ 待签署* ──签署──▶ 已生效 ──履约完成──▶ 已完成
   │              │                 │
   └──删除        └──撤回为草稿      └──撤销──▶ 已撤销
└──────────────────────────────────────────────────┘
           │ 生效事件                      ▲ 履约/退费事实（只读）
┌──────────▼──────────┐ ┌────────────────┴─────────────────┐
│ 费用面（billing）    │ │ 履约面（pharmacy / diagnostics /  │
│ 免费/待缴费/已缴费/   │ │ treatment）待审方/待发药/待执行/   │
│ 待退费/已退费         │ │ 执行中/已完成/异常/退药            │
└─────────────────────┘ └──────────────────────────────────┘
                  ↓ 按优先级合成
          医生站显示：流转状态（单一标签）+ 明细时间线
```

`*` 表示由参数控制是否经过这个状态。

### 3.1 医嘱主状态（ordering 所有，落库）

处方、药品医嘱、检验检查申请统一使用同一组取值。

| 状态 | 编码 | 含义 | 对外可见 | 进入方式 | 可执行操作 |
|---|---|---|---|---|---|
| 草稿 | `DRAFT` | 医生正在编辑，未承诺 | 仅本医生 | 录入、保存草稿、采纳 AI 推荐 | 修改、删除、开立 |
| 待签署 | `PENDING_SIGNATURE` | 内容已锁定，等待医生签署 | 仅本医生 | 开立（签署模式为“分步”时） | 签署、撤回为草稿 |
| 已生效 | `ACTIVE` | 医嘱已对外承诺，已记账、已下发 | 收费、药房、医技 | 签署（“合并”模式下开立即签署） | 撤销（受履约约束）、打印 |
| 已完成 | `COMPLETED` | 全部履约完成且没有待退项 | 全部 | 履约事件驱动 | 仅可查看；如需退药或退费，走对应模块 |
| 已撤销 | `CANCELLED` | 医生撤回意图 | 全部 | 撤销 | 无 |

约束：

- 只有在 `DRAFT → ACTIVE`、`PENDING_SIGNATURE → ACTIVE` 这两次转换时，才发布 `*_ACTIVATED` 事件。记账、下发药房和医技都只订阅这个事件。
  - 现在检验检查申请创建时就发布 `SERVICE_REQUEST_AUTHORED`，需要改为在生效时发布（见第 7 节 G1）。
- 草稿删除直接物理删除，不留撤销记录，因为它从未对外可见。
- 撤销以单条医嘱为单位。单据（处方、申请单）的状态是成员状态的汇总：成员全部撤销，单据才算撤销。
- `COMPLETED` 只由履约事实推进，医生不能手动置为完成。

### 3.2 费用面（billing 所有，只读投影）

| 显示 | 依据 |
|---|---|
| 免费 | 计费决策为非收费（`ClinicalOrderBillingDisposition` ≠ `CHARGEABLE`） |
| 待缴费 | 有 `POSTED` 原收费记录，所属结算单为 `PRICED / PAYMENT_PENDING / PARTIAL` |
| 已缴费 | 结算单 `SETTLED` |
| 待退费 | 医嘱已撤销或已退药，冲销记录已生成，但已缴金额尚未退回 |
| 已退费 | 冲销金额已在收费处退回，或已冲正 |

### 3.3 履约面（各执行模块所有，只读投影）

| 医嘱类型 | 履约状态（来源） |
|---|---|
| 药品 | 待审方 `PENDING_REVIEW`、审方干预 `INTERVENTION`、审方驳回 `REJECTED`、待配药 `READY_TO_PICK / PICKING`、待发药 `READY_TO_DISPENSE`、部分发药、已发药 `COMPLETED`、部分退药、已退药（发药任务） |
| 检验检查 | 待缴费 `WAITING_SETTLEMENT`、待执行 `READY`、已采集 `COLLECTED`、检查中 `IN_PROGRESS`、已出报告 `COMPLETED`、执行异常 `EXCEPTION`（执行任务；报告来自诊断报告） |
| 治疗处置 | 待缴费、待取药 `WAITING_DISPENSE`、待皮试 `WAITING_SKIN_TEST`、待执行 `READY`、执行中、已完成、异常（执行任务） |

## 4. 医生站流转状态（推导，单一标签）

按下表从上到下取第一个命中的规则，作为医嘱行的主标签；悬停或展开时显示完整时间线（开立 → 签署 → 缴费 → 发药或执行 → 完成，以及撤销、退费分支）。

| 优先级 | 流转状态 | 条件 | 色调 | 医生可做 |
|---|---|---|---|---|
| 1 | 草稿 | 主状态 `DRAFT` | 中性 | 修改、删除、开立 |
| 2 | 待签署 | 主状态 `PENDING_SIGNATURE` | 提醒 | 签署、撤回 |
| 3 | 已撤销·待退费 | 主状态 `CANCELLED` 且费用面为待退费 | 警告 | 提示患者到收费处退费 |
| 4 | 已退费 | `CANCELLED` 且已退费 | 中性 | — |
| 5 | 已撤销 | `CANCELLED`，且从未缴费或为免费 | 中性 | — |
| 6 | 审方驳回 | 履约面审方驳回或干预 | 危险 | 查看药师意见，撤销后重开 |
| 7 | 执行异常 | 履约面异常 | 危险 | 查看原因 |
| 8 | 退药中 / 已退药 | 履约面部分退药或已退药 | 警告 | — |
| 9 | 待缴费 | 费用面为待缴费 | 提醒 | 撤销（直接冲销，无需退费） |
| 10 | 待审方 | 履约面待审方（事前审方开启时） | 提醒 | 撤销 |
| 11 | 待发药 / 待执行 / 待皮试 / 待取药 | 已缴费或免费，履约尚未开始 | 信息 | 撤销（已缴费的撤销后进入待退费） |
| 12 | 执行中 / 已采集 / 已配药 | 履约进行中 | 信息 | 撤销受履约约束（见第 5 节） |
| 13 | 已完成 / 已出报告 / 已发药 | 主状态 `COMPLETED` | 成功 | 退药需由药房办理 |

“待确认”和“已开立”这两个词不再使用：

- “待确认”分别改为“草稿”“待签署”。
- “已开立”换成第 9–13 级中实际所处的进度。
- 工具栏上的“N 项待确认”改为“N 项草稿”。

## 5. 撤销与退费规则（闭环关键）

医生撤销前，由各履约模块的 `OrderFulfillmentGuard` 判断能不能撤（现有机制）。撤销后，费用如何处理统一交给 billing：

| 撤销时所处阶段 | 能否撤销 | 撤销后 |
|---|---|---|
| 草稿、待签署 | 可以（直接删除或撤回） | 无费用 |
| 已生效·待缴费 | 可以 | 自动冲销，结算单中减掉该项，无需退费 |
| 已缴费·未开始履约 | 可以 | 生成冲销，显示“已撤销·待退费”；药房发药任务和医技执行任务同步取消 |
| 药品已发药 | 不可以 | 由药房办理退药（`MedicationReturnChargeService` 生成退药冲销），之后再撤销剩余部分 |
| 检验已采集或检查已执行 | 不可以 | 须由医技科室先确认未执行或作废，再撤销 |
| 已完成 | 不可以 | 只能走退药或红冲流程 |

收费处退费以医生撤销或药房退药生成的冲销记录为准，不能凭空退费。这样“医嘱 — 费用 — 履约”三方始终可以对平。

## 6. 参数化与医院等级预设

只组合已有参数和一个新增参数，不新增状态：

| 参数 | 键 | 取值 | 影响的状态 |
|---|---|---|---|
| 开立核查模式（已有） | `outpatient.doctor-workstation.order-review-mode` | `SIMPLE` / `STANDARD` | `SIMPLE` 保存即生效（见 6.1），草稿只作为开立被拦下时的暂存；`STANDARD` 保存为草稿，经核查窗开立。不新增状态 |
| 医嘱签署方式（新增） | `outpatient.doctor-workstation.order-sign-mode` | `COMBINED`：开立即签署 / `SEPARATE`：开立后需签署才生效 | 是否经过“待签署” |
| 处方审方模式（已有） | `pharmacy.prescription-review.mode` | `DISABLED` / `PRE_DISPENSE` / `POST_DISPENSE` | 是否经过“待审方”；事后审方只留痕，不阻塞 |
| 履约前缴费（已有，执行项上的 `settlementRequired`） | 按项目或机构 | 是 / 否（先诊疗后付费、免费项目） | 是否经过“待缴费” |
| CA 个人签名 | 通用 CA 设置 | 开 / 关 | **不影响状态**；在时间线上显示“CA 已签 / 待补签” |

推荐预设：

| 场景 | 核查 | 签署 | 审方 | 典型路径 |
|---|---|---|---|---|
| 基层（社区、乡镇） | 简易 | 合并 | 不启用 | 草稿 → 待缴费 → 待发药 → 已发药 |
| 二级医院 | 标准 | 合并 | 事后 | 草稿 → 待缴费 → 待发药 → 已发药（事后抽审） |
| 三级医院 | 标准 | 分步（可配 CA） | 事前 | 草稿 → 待签署 → 待缴费 → 待审方 → 待发药 → 已发药 |

关于“签署后才计费”：生效以签署为前提，而记账只订阅生效事件，所以 `SEPARATE` 模式天然就是先签署后计费，不需要单独的开关。CA 签名即使失败，也只在时间线上提示补签，不阻断收费和发药（ADR-008）。

### 6.1 简单模式：保存即生效（2026-10-21 落地）

基层门诊医生的工作单位是“这一次就诊”，不是单张处方。简单模式下医生只做“写病历、录诊断和医嘱、保存”，状态仍走同一张图，只是由系统连续走完：

| 医生动作 | 系统行为 |
|---|---|
| 保存（工具栏按钮或 Ctrl+S） | 同一次操作内：保存病历和诊断 → 医嘱整批保存为草稿 → 一次开立命令全部生效（记账、下发）。没有单独的“开立”按钮 |
| 合理用药为旁路提示 | 自动确认后生效，提示留在医嘱区供医生知晓 |
| 合理用药需正式确认 / 阻断，或校验失败 | 病历照常保存；医嘱留在草稿，医嘱区显示“N 项未生效”和原因。正式确认才弹出核查窗，阻断只在医嘱区提示 |
| 修改医嘱 | 已生效、未进结算单、执行未接收的医嘱可“修改”，在原医嘱上进行：保存时先退回未签署（记账作废、未开始的执行任务删除），原地改完立即重新生效。同一条医嘱、同一个编号，收费只有一条，不产生撤销记录和正负冲销。药品以处方为单位，同方其余药品随之重新生效。中药饮片和输液组只能删除后重开。已进结算单的不显示“修改” |
| 删除医嘱 | 未进结算单的撤销对医生显示为“删除”；已进结算单的仍为“撤销”，由收费处按冲销退费（第 5 节） |
| 诊毕 | 有未保存内容或未生效医嘱时自动执行一次“保存”，全部生效后进入诊毕核对；未能生效则停在当前页并提示原因 |

### 6.2 签署模式（标准模式）：签署、取消签署

| 医生动作 | 系统行为 |
|---|---|
| 保存 | 医嘱保存为未签署（`DRAFT`），对收费、药房、医技不可见 |
| 修改未签署医嘱 | 在原医嘱上修改（药品可改用法用量、数量、嘱托；诊疗项目可改数量、临床说明），不能更换药品或项目 |
| 签署 | 原“审核开立”。核查分单、诊断、合理用药后签署，医嘱生效、记账、下发 |
| 取消签署 | 已签署、未进结算单、执行未接收的医嘱可取消签署，退回未签署：未进结算单的记账作废删除，未开始的执行任务删除，库存冻结释放。药品以整张处方为单位。之后可直接修改，再次签署时重新记账 |

### 6.3 锁定边界与数据口径

- **锁定从收费处划价开始**：原收费一旦进入任何结算单（含仅划价，或已冲正的结算单），就不能修改或取消签署，只能撤销，由收费处按冲销退费。判断由 billing 的 `OrderPaymentDirectory.inSettlement` 提供。执行侧由 `OrderFulfillmentGuard.withdrawBlockedReason` 把关：药房已接单、检查已开始、治疗已开始都不能取消签署。医嘱响应中的 `editBlockedReason` 汇总这些原因；有原因时前端不显示“修改”“取消签署”。
- **作废不留痕于业务表**：取消签署时，从未进结算单的收费连同明细、账务流水删除；医技、治疗未开始的任务删除。重新签署按新内容重建。审计依据保留在医嘱事件流（`*_WITHDRAWN`、`*_DRAFT_REVISED`）中。
- 修改通过整批保存命令的 `revisedOrders` 提交，与新增草稿同一事务；取消签署是独立命令（`POST .../prescriptions/{id}/withdraw-signature`、`POST .../service-requests/{id}/withdraw-signature`）。

## 7. 与现状的差距和落地顺序

| 编号 | 差距 | 改动 | 优先级 |
|---|---|---|---|
| G1（已完成 2026-10-21） | 检验检查申请没有草稿状态，保存草稿就记账、下发 | `ServiceRequestStatus` 增加 `DRAFT`；整批保存写成草稿；一次开立命令与处方一起转为生效。沿用 `SERVICE_REQUEST_AUTHORED` 事件名，只把发布时机从创建改到生效，记账、医技、治疗订阅方不变；草稿撤销按计费结论 `DRAFT` 不冲销。单条创建接口仍是直接开立。存量数据都已生效，无需迁移 | 高 |
| G2 | 医生站只能显示“待确认 / 已开立” | 新增只读接口 `GET /api/encounters/{id}/order-lifecycle`：ordering 通过 billing、pharmacy、diagnostics、treatment 的 `api` 目录接口组装流转状态和时间线；前端按第 4 节显示 | 高 |
| G3 | 没有“已完成”主状态 | ordering 订阅发药完成、执行完成、报告出具等事件，推进为 `COMPLETED`；撤销守卫已存在，不需要改 | 中 |
| G4 | 已缴费医嘱撤销后，医生和患者看不到退费进度 | billing 对外提供按医嘱查询冲销及退款的结果，用于流转状态第 3–4 级 | 中 |
| G5 | 审方驳回没有回到医生 | 流转状态第 6 级加上工作站提醒；驳回后医生撤销并重开，原处方保持只读 | 中 |
| G6 | 分步签署 | 新增 `order-sign-mode` 参数和 `PENDING_SIGNATURE` 状态；签署时在同一事务内写签署行为证据（`CLINICAL_ACTION_ATTESTATION`），CA 补签走现有签名任务 | 低（三级医院需要时再做） |
| G7 | 诊毕门禁 | 存在草稿或待签署医嘱时，诊毕提示“删除或开立”，不能静默带入下一次就诊。简单模式已由“诊毕前自动保存并生效”覆盖（6.1）；标准模式和服务端门禁待做 | 中 |

建议按 G1 → G2 → G7 → G3/G4/G5 → G6 的顺序推进：

- G1 需要迁移表结构，并调整记账和医技执行的触发点，是其余各项的前提。
- G2 只读、不改表，做完后医生站的状态显示就能统一。

## 8. 不做的事

- 不把各模块的状态合并成一个大枚举写进医嘱表，避免跨模块回写和多方状态不一致。
- 不以 CA 签名作为任何流程的门禁。
