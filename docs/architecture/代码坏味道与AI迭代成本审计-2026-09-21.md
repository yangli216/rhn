# 前后端代码坏味道与 AI 迭代成本审计

日期：2026-09-21。对象：当前工作区，包含未提交和未跟踪的源文件。

## 结论与边界

存在值得治理的局部上帝组件／服务，前端比后端更明显。最应优先解决的是业务语义重复和高频修改热点的职责耦合。已有 Maven 模块、公开 API 契约、ArchUnit、OpenAPI 同步 CI 可以作为渐进重构的保护，不需要因代码规模增长立即拆微服务。

本次为全仓文件规模扫描、最近 80 次提交热点统计和重点实现抽查，并非逐行覆盖全部代码。没有修改业务代码、提交或推送；唯一新增仓库文件为本报告。没有运行浏览器验证，也没有运行全量业务回归。没有取得历史会话逐任务 token 数据，因此成本归因是有代码证据支持的推断，不能给出实测节省比例。

## 优先发现

### F1：用药频次解释重复且不一致——最高优先

证据：

- frontend/src/features/outpatient/UnifiedOrderListEditor.tsx:101，resolveFrequencyTimesPerDay；:120，calculatePackageQuantity。
- frontend/src/features/pharmacy/PharmacyWorkspace.tsx:2205，frequencyTimesPerDay；:2316，剂量展示调用。
- backend/rhn-platform/src/main/java/com/rhn/platform/masterdata/api/ClinicalFrequencySemantics.java:14，interpret。
- frontend/src/shared/api/masterDataApi.ts:848，ActiveOrderFrequency 仍提供原始规则字段，:1674 直接请求后端；OrderFrequencyService.java:277 原样返回 periodUnit。

门诊按 executionTimes 数量、frequencyCount / periodValue、小写 w 和硬编码频次表推算每天次数；药房根据代码／中文名称猜测；后端根据 ruleType 和 MIN/H/D/WK 解释，并将 PRN、ONCE 等判为无固定日频次。

从当前 TS AST 提取原函数，转译后在内存执行了以下最小复现，未修改源文件：

| 输入，executionTimes 为空或未提供 | 门诊结果 | 结构化语义 |
| --- | ---: | --- |
| FIXED_INTERVAL，count=1，period=8 H | 0.125 次/天 | 3 次/天 |
| TIMES_PER_PERIOD，count=1，period=1 WK | 1 次/天 | 1/7 次/天 |
| PRN | 1 次/天 | 不可换算固定日频次 |
| ONCE | 1 次/天 | 单次事件，无固定日频次 |

这是函数级可复现差异，尚未证明上述配置均在当前人工验证数据库中启用。该函数参与包装数量和医嘱组数量重算，因此不能仅作为显示格式问题处理。

建议：确立后端结构化语义为业务权威；API 暴露版本化的可计算能力、次数／周期分母和不可计算原因。前端只做基于明确语义的预览，不从 code/name 推测；需要保留本地预览时，用共同样例验证 TS 与 Java 的一致性。不可计算时让用户明确输入数量并给出原因。也应检查两处从规格文字解析强度、单位换算失败仍沿用数值的逻辑。不要只把重复代码搬进共享工具后继续保留错误兜底。

保留验收：切换患者前保存提示、AI 采纳与撤销、诊断排序、医嘱组联动、失败重试、签名完成就诊。不要把存在中间状态的流程拆成互不关联的 effect。

### F3：药房以 mode 驱动多工作流共享一个大组件——高优先

frontend/src/features/pharmacy/PharmacyWorkspace.tsx:233：文件 2,332 行，主函数 1,825 行，35 个 useState、15 个 useEffect、15 个 useQuery。包含审方、发药、退药、查询、住院配送入口、扫描队列、定时器和批量操作。

AppShell.tsx:914 起让多个路由复用该组件的不同 mode。修改扫码或退药时，需要确认其状态和副作用不会影响其他模式，扩大阅读和测试范围。

建议拆为独立模式入口，共享患者／处方选择上下文；将扫码缓冲、批处理和清理提为独立控制器／hook；提取查询与命令并统一 query key。先保留原 props 和路由，再逐模式替换。重点回归切换患者／模式时的扫码队列归属、任务状态变化和重复提交。

### F5：内存分页和全量装配形成“看似分页”的查询——中优先

EncounterService.java:789 起先读日期区间内全部就诊，装配全部挂号／诊断，按搜索条件查询居民，再在 :855 起对 List 截取分页。数据增长时，每页工作量仍取决于整个日期区间。

MedicationKnowledgeDraftService.java:34 起先 store.latest(tenant)，在内存筛标题和分页；detail 又遍历其他草稿并逐个验证以提示重叠。

建议将过滤、计数、分页下推本模块的查询层；跨域检索采用批量公开 API 或读模型，不能直接跨模块 join 持久化实现。重叠评估可按候选范围筛选并结合版本缓存。此处确认了执行形态，尚未做数据量压测，不能宣称已发生生产性能事故。

### F6：基础资料页面与 AppShell 成为高频改动汇聚点——中优先

OperationalMasterDataPanel.tsx 3,270 行，但最大函数 425 行；BasicDataManagement.tsx 3,208 行，但入口函数仅 293 行。因此二者更偏向许多子组件堆在一个文件，优先按业务目录整理，不必直接引入全局状态框架。

AppShell.tsx 1,856 行，主函数 584 行，集中认证恢复、工作上下文、主题、导航、页签、路由装配；:109 定义 ClinicalContext，30 个生产文件从 AppShell 导入。这些导入主要为类型，不能据此声称存在运行时循环依赖。

建议将上下文类型放到独立契约文件，拆出 session、workspace-tabs、work-context、navigation 和 route registry。已有 lazy/Suspense 路由加载应保留。AppShell.tsx:464 仍有 <=760px 的移动布局分支，与当前默认 PC-only 约束不一致，清理前确认是否有已约定例外。

### F7：契约生成已有门禁，但手写 DTO 与宽 API 依赖仍扩大变更范围——中优先

frontend/src/shared/api/index.ts:83 起装配各领域客户端；shared/rhnApi.ts 全量导出。大量组件接收整个 RhnApi。masterDataApi.ts 1,749 行，pharmacyApi.ts 1,201 行；当前只有 5 个生产文件直接导入 generated.ts，多个业务接口仍手写响应结构。

全局客户端作为装配根是合理的，不应仅因它汇总 API 就称其为上帝对象。问题是叶子组件也能依赖全部领域，mock 容易退化为强制类型断言，手写传输结构未完全受到生成类型的约束。CI 比较 OpenAPI 与 generated.ts，不能自动保证每一个独立手写 DTO 与后端一致。

建议逐领域提供小型 transport 类型别名和显式 ViewModel 转换，让叶子组件接收其实际需要的客户端切片／命令。保留生成文件和 CI；常规检索默认排除生成体，需要查 schema 时按名称定位。

DoctorWorkstation.tsx:1930 的 persistOrderDrafts 还通过检查 batchOrderPrescriptions 函数是否存在，保留逐条创建处方／药品的旧实现，其中重复了分方、输液组规则。先核实需要支持的接口版本；如果仅为旧 mock，更新 mock 后移除。如果确实需要兼容，放入明确且有测试的 adapter。

### F8：测试组织放大反馈成本——中优先

backend/rhn-app/pom.xml:109 把 backend/src/test/java 作为应用模块测试源。129 个测试类继承 RhnIntegrationTestSupport；其 :21 使用整个应用的 @SpringBootTest，:24 设置 @DirtiesContext(AFTER_CLASS)，使每个类结束后丢弃上下文。随机 H2 隔离是正确的安全基础，应保留。

建议纯领域规则、编译器和转换器优先下沉所属模块做单元测试；仓储使用聚焦的集成测试；关键跨域链路继续保留应用级测试。评估数据清理和隔离可靠后，才让兼容的测试复用 Spring 上下文；不能直接删除 DirtiesContext。

scripts/verify-outpatient-main-flow.sh 先跑 outpatient-main-flow tag，再单独跑 ArchitectureTest；ArchitectureTest 自身带同一 tag，因此脚本会重复执行架构测试。可以在测试映射整理时去重。

测试运行慢主要影响时间；输出被反复读入、失败后重试和无关上下文才进一步放大 token。不能把耗时直接等同于 token。

### F9：部分新增代码把多条语句／长 JSX 压在一行——中优先

MedicationKnowledgeDeploymentService.java 仅 85 行，但最长行 482 字符；MedicationKnowledgeDeploymentDialog.tsx 61 行，最长行 805 字符。它们说明单纯的文件行数门禁会漏报复杂度。

建议渐进格式化被修改文件，增加函数体积、参数数量、分支和依赖方向检查。格式调整单独成批，以免淹没业务差异。压缩成单行不会可靠节省代码语义所需 token，反而使检索片段、补丁和评审难以定位。

## 降低每次迭代 token 的落地方案

目标：让完成一个用例所需的上下文更小、更稳定，同时减少错误返工。仓库文件多并不意味着模型每轮自动读完整个仓库。

### 第一阶段：先建立小型任务入口和按需检索

1. 根 AGENTS.md 保留现有安全／服务／PC 布局约束，增加简短“从哪里开始”的路由。不要把历史、全部接口和所有领域规范塞进根文件。
2. 建立 docs/ai/module-map.md：业务词 → 前端入口 → 后端公开契约与服务 → 相关测试 → 领域说明。以现有 module-catalog.json 为后端归属来源，避免手工复制一套互相冲突的目录。
3. 每个活跃领域提供短 README／上下文卡：职责、外部依赖、稳定入口、事务与幂等约束、测试命令、参考文档链接。建议 50–100 行作为起点，按需读取；这是项目建议，不是产品硬限制。
4. 为约束差异明显的目录放局部 AGENTS.md；从模块目录启动时利用指令层级，根目录任务则明确按路由读取相关说明。不要假设任意深度的所有 AGENTS.md 都会自动加载。
5. 提供小型脚本（后续实施）输出符号目录、调用入口、相关测试路径，避免为了找一个函数读完整个 4,000 行文件。先 rg --files／rg -n，再读取命中上下文。
6. 常规源代码检索排除生成类型、OpenAPI、药品静态数据、构建产物和日志；契约、数据迁移任务显式纳入必要文件。使用明确的路径／glob，不虚构未核实的忽略配置功能。

示例，仅打印路径与命中行：

```sh
rg -n 'resolveFrequencyTimesPerDay|ClinicalFrequencySemantics' frontend/src backend/rhn-platform/src/main/java -g '!generated.ts'
```

官方说明也建议保持 AGENTS.md 简短，通过引用补充按任务使用的文档，而非持续扩充自动加载内容：[OpenAI Docs 最佳实践](https://learn.chatgpt.com/guides/best-practices)。指令发现与当前工作目录有关：[AGENTS.md 加载规则](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

### 第二阶段：建立最小但充分的验证映射

后续增加 scripts/verify-scope.sh 或同等入口，维护“变更路径 → 单元测试／契约测试／主流程”的映射，命令应从真实存在的测试生成或校验。

- 纯函数变更：对应单元测试和必要类型检查。
- 医嘱、签名、库存、资金等状态流程：关联集成测试＋架构规则，不可仅以函数测试放行。
- 公开契约、schema、迁移、公共框架变更：扩大到契约和跨模块回归。
- CI 仍保留完整验证；本地避免同一未改变快照重复全量运行。
- 日志落文件，模型首先读取退出状态、失败摘要和相邻堆栈，需要时再展开原始日志。

不把选测用作漏跑必要测试的理由。建立失败基线时必须区分已有故障与当前改动。

### 第三阶段：只重构高频热点，逐步加入自动门禁

先修 F1，再在下一次涉及医生工作站的业务变更前，分离草稿模型／保存协调／AI 采纳；之后拆药房模式和主数据服务。每次一个可验收职责边界，避免同时改目录、接口、事务与 UI。

建议对新增和修改部分设置“告警 + 存量基线”，例如：复杂 TSX 超过 500 行需说明职责；单函数超过 150–200 行、后端构造协作者超过 10 个触发评审。阈值只是起点，不能代替判断；生成代码、清晰的数据声明不计入。

前端补 React hooks lint 和依赖方向门禁；现有 ui:check 主要检查颜色令牌、组件与部分原生控件，未覆盖职责复杂度。后端继续使用 ArchUnit，按需增加领域内部边界。避免为了让警告清零引入大量 pass-through service 或万能 base class。

### 第四阶段：任务粒度与交接方式

一个连续任务处理一个可验收用例；仍在解决同一问题时保留任务上下文，跨业务领域时用短交接卡开启新任务。卡片只写当前目标、权威文件路径、已作决策、验证结果、未解决事项。不要把完整旧聊天复制进新任务。

用户请求可写成：

> 修改门诊医嘱的频次数量预览。先读模块索引和频次契约，再读取直接相关代码。验收：小时／周／按需／单次语义一致，手动数量覆盖保持有效。优先运行关联测试，涉及公开契约时扩大验证。完整日志落文件，只汇报失败摘要和最终结果。

可在任务允许时选择合适模型和推理强度，但先改善上下文边界；本次没有比较模型价格或测量不同配置。多 agent 是缩短独立工作的等待时间的手段，不能默认视为节省总 token；重复加载上下文也有成本。

## 如何验证是否有效

选取 5–10 个相近规模的功能／修复任务作基线，再比较治理后的同类任务：

- 可获得时记录输入、输出、缓存 token；区分 token 数与最终费用／套餐用量。
- 记录实际读入的代码字符数、工具输出字符数、完整文件读取次数。
- 记录修改文件数、无关模块触及数、失败重试次数、测试用时和返工数。
- 看同类任务的中位数和范围，不能把小型 UI 改动与大型临床流程改动直接比较。

首次整理索引、拆分代码会有投入。长期收益应来自“局部需求可只理解局部代码”，不保证具体百分比，也不以删测试、减少验证或压缩代码可读性换取数字下降。
