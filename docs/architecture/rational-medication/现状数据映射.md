# QMED-0 现状数据映射与实施边界

更新：2026-09-16。用户约定：先贯通业务，暂不建设数据核验和审批流程；QMED-1 已从远程提交 6bfbb04 接入。

## 已完成与尚缺内容

标准参考目录、本院业务接入，以及本轮 QMED-0 的成分维护、单位语义、不可变记录和门诊/住院运行快照均已实现，并与 QMED-1 v2 快照对齐。下表保留实施前盘点，最终行为和范围见 [接入验收](QMED-0与QMED-1接入验收.md)。

## 当前字段与目标概念

| 当前模型/字段 | Canonical Concept | 处理方式 |
| --- | --- | --- |
| Medication.id/code/name | Medication ID/code/display | 保留业务 ID；STD-* 建档码关联参考规格。显示名称不参与临床等价判断 |
| 标准目录 GEN-* / STD-* | 品种 / 物质限定+剂型规格 | 参考快照稳定标识；未知属性不推断 |
| MedicationProduct.medicationId/manufacturerId | MedicationProduct → Medication | 沿用厂家产品关系；产品价格不参与药物语义版本 |
| Catalog Item / organization adoption / package | 本院经营配置 / PackageUnit | 保留现有生效区间和价格版本；包装换算只用于库存和计价 |
| preparationSpec / strengthValue / strengthUnit | MedicationStrength | 当前单一含量无法完整表达复方和浓度，参考目录保留多成分及分子/分母结构 |
| preparationUnit / package.quantityFactor | Presentation / PackageUnit | 不作为 g↔mg 的临床单位换算依据 |
| defaultDose / defaultDoseUnit | 临床默认用量 | 是可维护默认值；处方实际 doseValue/doseUnit 独立冻结 |
| defaultRouteId / defaultRoute | AdministrationRoute | 已关联术语概念并规范化别名，运行快照尚缺概念修订/语义版本 |
| OrderFrequency / OrderFrequencyConfiguration | MedicationFrequency | 已有稳定 ID、结构化规则、生效期和乐观锁；原位修改尚未形成不可变语义版本 |
| defaultFrequencyId / defaultFrequency | 本地频次映射 | 当前 requireActive 解析机构/科室覆盖值；不能仅依赖显示名或 BID 文本计算 |
| MedicationTerminologyDirectory.classifications | 药物分类 | 已有 NEML/ATC 分类关系；分类不等同于成分 |
| MedicationTerminologyDirectory.allergenConceptIds | 过敏原概念映射 | 供过敏匹配使用，不能直接当作 ingredientIds |
| Medication.antimicrobial* / skinTest* | 管理与安全事实 | 沿用现有业务属性与门禁；规则评价应冻结所用值 |
| MedicationRequest.medicationSnapshot | 药品知识快照 | 已冻结药品、管理属性、默认用法；缺 medicationSemanticVersion、ingredientIds、结构化强度版本 |
| MedicationRequest.frequencyRuleSnapshot | 频次规则快照 | 已冻结配置结果及主记录 revision；还需稳定语义版本，覆盖科室配置变化 |
| routeId/code/name/executionType | 实际给药途径 | 已冻结行为字段，需补语义版本 |
| dose / duration / quantity / baseQuantity | 用药方案 / 发药数量 | 已独立保存；quantity/baseQuantity 不能替代患者剂量 |

## 生效入口盘点

- 门诊直接药品请求：`MedicationRequestService.create`，无处方头时直接 ACTIVE；不能只在处方提交按钮接入。
- 门诊草稿处方：同一药品请求服务写入 DRAFT，再由处方提交服务统一生效；评价必须基于完整处方集合。
- 批量分方/组合开立：批量医嘱协调代码复用药品开立路径；提交边界需纳入整方评价。
- 住院开立：`InpatientCareRequestStore` 单独生成药品请求和知识快照，不能只修改门诊构造器。
- AI 辅助计划：经既有医嘱落地入口保存，仍需核对是否存在绕开公共运行快照的写入路径。

## 当前实施约定

不引入 DRAFT→VALIDATED→APPROVED 的数据审核界面，也不以来源待核验阻断建档。需要保留的技术约束是历史可复现：新维护值产生新的语义版本，新医嘱引用新版本，既有医嘱快照不被重写。历史无法还原的成分或版本应明确为 LEGACY/UNKNOWN。

QMED-1 已沿用同事的引擎、规则、评价存储和独立事务实现；升级输入合同以读取已保存的 QMED-0 语义，同时兼容 LEGACY 历史条目。
