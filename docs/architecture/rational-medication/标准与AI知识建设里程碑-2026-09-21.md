# 标准化、规则知识库与 AI 建设里程碑

日期：2026-09-21。基线：`69e146e`。本文件是现有[实施路线图](实施路线图.md)的增量交付安排，不取代既有临床语义及发布治理约束。

## 当前推进约束：先完成核心业务闭环

用户于 2026-09-21 明确要求：“先注重核心业务的闭环，不要过度建设版本管理、审计、日志追溯等外围支撑”。本节优先于下文历史阶段中的推进顺序与“后续待建设”安排；待建设清单不自动构成首轮验收前置条件。

此前持续扩展底层治理，未及时交付用户已选定的“重复用药与相互作用”首个业务闭环，交付节奏需要纠正。已有代码及隔离测试覆盖知识生成、规则验证、审核、旁路、正式启用和反馈改进的多个环节，但不能据此宣称真实业务闭环已经验收，真实模型质量也尚未验证。

接下来仅围绕一条重复用药样例和一条相互作用样例收口：

1. 准备明确来源和标准药品范围的知识材料，展示 AI 理解、缺项澄清及结构化结果，由人工确认；临床结论不能由模型补造。
2. 将知识生成可运行规则，准备命中、不命中及事实不足的处方样例，给出实际结果、原因和建议处理方式。
3. 复用现有统一规则目录、审核与启用能力，明确页面操作路径；在隔离环境验证正式启用后处方提示或控制生效，停用后行为恢复。
4. 在开方/审方业务中完成最小处置反馈：能看到哪个药品组合触发、依据是什么，能修改处方并重新检查；允许继续的情形能记录理由，阻断规则保持其已批准策略。反馈能供药师核对并关联知识改进需求。
5. 提交两条样例的操作步骤、预期与实际结果、已知限制，供用户手工验收；真实模型效果与真实业务验收分别标记，不用模拟模型测试代替。

第一轮完成判据是用户能够走通“知识建立 → 规则验证与启用 → 处方触发 → 业务处置 → 反馈改进”，并理解 AI 实际帮助了什么。只修复阻碍这条链路的问题，不新增规则大类，不扩展通用治理平台。不得为展示样例自动向真实临床环境发布规则或写入模拟临床记录。

版本管理、审计、日志追溯、目录版次切换、批量迁移、复杂效果统计等外围建设停止扩展，现有能力继续复用；它们不作为首轮闭环完成的新增门槛。标准化优先补齐这两类业务实际需要的身份、范围、条件和事实，不以全目录治理完成作为启动业务验收的前提。

### 核心业务补齐进展：开方处理入口

核查发现开方确认页将所有结果固定展示为“影子运行”，且未提供后端正式策略要求的继续开立理由，导致规则已具备正式执行能力但医生不能按要求完成操作。本次修复：

- 按实际审查模式展示旁路提示或正式审查；正式阻断、技术不可评价或未保存有效评价时不能点击继续开立。缺少事实的处理继续遵从后端已批准策略。
- 按处方展示涉及药品、触发说明、处理建议和可展开的来源依据；需要继续开立理由时逐张填写，调用既有提交接口传入理由，不增加新的管理机制。
- 每次确认提交前重新检查；处方事实或提示变化时清除旧确认和理由。返回修改后重新进入审核，也重新检查。
- 医生站组件测试 43 项通过；隔离 `test`/随机 H2 的正式发布及处方提交集成测试 7 项通过，新增验证空白理由拒绝、有效理由提交成功；测试使用合成材料，不代表真实临床知识已获验收。

### 核心业务补齐进展：药师审方衔接

入口：药事管理 → 处方审方 → 选择待审药品。复用既有药师、任职、通过/干预/驳回及审方说明，不增加第二套处置流程。

- 新提交的处方保存提交时的规则结果、涉及药品名称、医生继续开立理由；药师审方显示整张处方的重复用药/相互作用提示、依据和医生理由。该信息是提交时结果，不表示打开药房页面时重新执行了规则。
- 药师对当前药品任务填写审方结论及干预说明，页面可显示已有处理结果。明确“整张处方配对提示”和“本条药品审方结论”的范围差异，切换药品时清空尚未提交的处理意见，防止串用。
- 旧处方没有提交时信息时明确提示缺失，不补造历史理由，不将缺失认定为检查通过。读取仍使用既有租户及药房机构访问限制。
- 只在既有处方业务表增加 `JSON_SAFETY_REVIEW` 保存这份临床交接信息（V1_74_0；H2 CLOB 兼容补丁），没有新增版本、审计或日志管理工作流。
- 隔离业务测试通过真实接口完成标准关联、重复用药处方提交、药房接方、药师干预及继续审方，验证药师读到原提示和医生理由。前端工作台测试覆盖查看提示、提交干预及显示保存结果；组件同时验证缺失历史信息和不完整评价不误报通过。
- 验证：前端 9 项测试通过，前后端打包通过；正式启用及处方提交 7 项、架构检查 26 项通过，药房接方/审方测试及物理模型检查中的失败已修复并重跑通过。全仓 UI 规范检查仍有既有违规，本次修改的药房组件/样式无命中。Oracle 本地服务已更新至 V1_74_0，8080 健康为 UP，5173 返回 200；运行接口文档已包含药房处方安全信息。没有在真实库创建示例处方或启用临床规则，也没有执行浏览器自动验收。

### 核心业务补齐进展：两条可操作验收样例

入口：合理用药规则工作台 → 规则知识草稿 → 重复用药与相互作用验收样例。完整范围与操作见[首轮核心业务验收](首轮核心业务验收-重复用药与相互作用.md)。

- 使用当前标准目录身份，准备 18 个预设场景，展示预期与实际结果。支持填入未保存知识草稿、下载材料，以及在现有人工验证入口载入场景；读取和载入均不会自动保存、启用规则或创建临床记录。
- 隔离集成测试完成两例知识保存 → 候选生成 → 人工样例保存 → 引擎执行，18 个场景符合预期；后端集成及架构检查共 28 项通过，前端相关组件 20 项通过，前后端打包通过。

### 核心业务补齐进展：药师反馈转知识改进

入口：药事管理 → 处方审方 → 已保存的药师处理结果 → 转为 AI 改进需求。

- 可选择本次审方相关的规则提示，也可不关联提示提出漏报或新增知识需求。服务端从真实保存的审方意见和处方提交时提示读取来源，不能由前端传入任意意见或知识身份。
- 关联知识规则时，根据原提示的规则版本找到知识来源，AI 分析后载入该知识的最新草稿；内置规则及无提示的反馈转为新知识草稿，不直接修改内置规则。
- 复用现有需求分析、澄清、知识编辑与后续验证流程；AI 只收到用户编辑确认的需求与澄清，审方原文、处方和患者资料不自动发送。药师意见保留为改进线索，不能成为新的药学证据。
- 复用现有药房与知识管理权限及机构/科室范围。已保存的历史意见可作为线索；每条意见单独关联，后续审方结论不会冒充早先意见。查看、分析与保存知识均不会改变生效规则。
- 仅为既有需求记录增加药师审方关联字段（V1_75_0），不新增审计或版本管理工作流。
- 验证：真实药房接口的干预意见 → AI 需求分析 → 知识草稿链路通过隔离测试，并验证模型输入不含审方原文与患者标识；知识关联、无提示需求、错误提示、权限、澄清来源和模型调用期间来源变化共 6 项测试通过。既有旁路改进 6 项、架构 26 项、物理模型 1 项通过；前端相关 19 项通过，前后端打包通过。模型在自动化测试中使用受控返回，真实模型效果仍未验收。全仓 UI 规范检查仍有既有违规，本次涉及的组件无命中。

### 核心业务补齐进展：真实 AI 验证

使用实际配置的 qwen3.8-27b 和现有调用适配器，在随机 H2 测试库验证公开摘录、业务需求与机构策略草案，没有向真实库写入测试临床数据或启用规则。发现并修复模型漏填明确配对关系与临床意义的问题；补充法规来源类型，区分医学原文与机构策略。最终五组真实输入的 25 项检查通过，模型及抽取回归共 16 项通过，前端相关 12 项通过，前后端打包通过。

尚未闭环的具体缺口：两条完整业务流程的用户手工验收。后续围绕验收发现的核心断点处理，不扩展外围治理。

## 建设目标

标准目录及语义 → 有来源的结构化知识 → 确定性规则 → 门诊开方与药师审方 → 处置反馈 → AI 提出知识或规则改进候选。

标准目录解决“它是什么”，知识库解决“在什么条件下应当怎么用”，规则解决“怎样核查并采取什么业务动作”。AI 帮助整理依据、理解需求、发现缺口、生成候选和测试，不直接产生临床生效结论。

## 首轮实际交付：M1A

入口：基础数据 → 药品目录 → 用药标准 → 药品标准建设情况。

新接口：`GET /api/platform/master-data/clinical-semantics/readiness`，使用当前授权租户；查询参数 `query`、`filter`、`page`、`size`。

统计口径：

- 分母为本租户 `ACTIVE` 药品全量，不是当前机构采用目录，也不是知识搜索的前 40 条。
- 关联状态互斥：关联一致、未关联、冲突、版本不可用、信息不一致；五类合计等于分母。
- 来源待核验和换算不支持仅统计关联一致药品，两者可以重叠，不能相加当作药品总缺口。
- 关联异常时换算状态为“关联后核查”，不能虚报为已具备或缺少医学知识。
- 换算检查仅判断“一制剂单位能否通过当前标准机制转换到临床单位”。质量、体积可做各自同维度换算；可换算不证明能够做成分剂量计算，更不证明已具备推荐剂量或安全上限。
- 来源核验读取既有目录标记；本轮不提供把来源直接标为已核验的按钮。
- 状态筛选和药名/编码/规格查询影响列表，不改变顶部全量统计。空结果及查询失败都不能显示为“全部完成”。

实现复用正式运行的标准身份校验；按租户批量读取关联，避免每行重复访问数据库。当前为按需全量核查并在服务端分页输出，成本随租户药品量增长；大规模目录后续应迁移为可追溯的核查任务或投影视图，不能通过截断分母优化性能。

本轮不改变临床处方的判定策略，不新增数据库表，不自动修改药品或标准关系。修复当前标准规格不存在时核查整体失败的问题，将该条明确归为版本不可用。

## 下一切片的模型口径

**标准身份与药学证据分层。** 标准参考目录可承担身份与规格规范；用于规则控制的推荐剂量、最大剂量、禁忌等，需要另有可追溯的知识依据。来源核验应保存核验人、时间、版本/哈希、结论和证据定位；不能由“解析成功”自动转换为“已核验”。

**知识的最小单元。** 知识类型 + 标准对象范围 + 适用条件 + 约束值/单位/时间基准 + 证据位置 + 来源版本 + 审核状态 + 有效期。机构制度和药学知识应有不同来源类型，避免把机构策略误称为药品安全上限。

**规则与版本、部署状态分层。** 统一规则目录管理草稿、待审核、驳回、旁路、正式生效、停用、历史版本，默认可筛选有效规则；“批准旁路”和“正式启用”是不同操作。发布操作需校验该版本的测试、审批、旁路结论和标准/知识依赖；新版本不原地覆盖既有生效版本。

**作用域与可评价范围分层。** 支持全部药品、标准分类/成分、指定标准药品/规格、产品限定。选择“全部”不等于当前所有药品都能评价：需展示总范围、具备事实及知识的可评价范围和不足项，缺数据输出不可评价及原因。

**缺少事实的业务策略。** 规则先输出不可评价及所缺事实；是否提醒、要求补充或阻止提交，由该规则类型与业务场景的审核策略确定。不得一律放行，也不预先一律阻断。

## 用截图需求验收 AI 改造方向

输入：“所有药品单次用量超过 3 倍制剂规格用量时警告。”

## 第二轮交付：M1B 来源核验

上一轮属于实际进展：新增建设情况 API、页面与已验证统计口径。本轮在此基础上补齐来源核验，并继续保持总体目标；M1B、M2—M5 均未据此认定完成。

入口：基础数据 → 药品目录 → 标准参考目录 → 来源核验与历史。

接口：`GET/POST /api/platform/master-data/medication-standard-catalog/source-review`。读取支持 `historyPage`，历史每页 20 条且包括旧目录版本。当前目录摘要、详情及标准建设视图同步读取本租户的核验结论。

状态与职责：

- 初始未核验 → 提交来源材料 → 待复核 → 来源已核验或材料退回。
- 来源已核验可撤销，退回或撤销后可重新提交；每次操作追加事件，不提供修改或删除既有事件的接口。
- 提交人和复核人必须不同；写操作要求 `MASTER_DATA.MANAGE`。这是来源真实性及版次核对，临床知识的审核权限与依据另行建设。
- 提交须提供来源名称、发布机构、版次/日期、证据位置、核验说明与操作理由。复核操作不能替换原提交材料；核对不通过时须退回重提。
- 目录 ID、目录版本、目录内容哈希及来源文件哈希共同标识一个核验对象。版本或文件变化会回到未核验，历史记录仍可分页追溯。
- 请求携带当前核验序号；服务校验序号并由数据库唯一约束阻止同一版本的并发覆盖。权限、版本、证据或状态不满足时均不追加记录。
- 界面显示服务端允许的操作；查看历史材料时禁用当前核验动作。若目录来源在编辑过程中变化，清空未提交材料并说明原因。

核验记录编号写入 `MedicationStandardReference.sourceVerificationId`，随药品语义快照持久化。一次快照使用同一份标准引用生成药品语义版本和处方输入，避免核验在两次读取之间变化而形成不一致快照。撤销只改变后续获取的来源状态，保留历史处方对应的核验事件。

`V1_61_0` 为 PostgreSQL/H2 与 Oracle 新增来源核验事件表，物理模型目录及中文注释一并维护。目录原始文件和原始标记不被覆写；服务摘要单独保留 `suppliedVerificationStatus`，避免把机构复核与来源文件自述混为一谈。

来源核验通过不代表每个规格已核对、不代表目录有医学权威背书、不代表已有推荐剂量或最大剂量知识。本轮没有替用户核验真实材料，没有将任何规则改为正式生效，也没有更改处方拦截策略。

## 第四轮交付：M2A 重复用药与相互作用知识草稿

入口：合理用药规则工作台 → **规则知识草稿**。桌面端采用草稿目录、知识编辑、结构校验与样例三栏。“在行生效规则库”的导航文字同步改为“在行规则目录”，与其管理多状态规则的职责保持一致。

本轮可使用的三个模型：

| 模型 | 标准范围与匹配语义 | 需人工核对的知识含义 |
| --- | --- | --- |
| 同一标准条目重复开立 | 全部具有一致标准身份的药品；同一标准条目下不同有效医嘱达到设定条数；无需强制选药 | 标准条目不等同于活性成分，同名或同类不自动合并 |
| 明确药品组重复治疗 | 人工从标准目录选择具体条目或规格，A 组内不同有效医嘱累计计数 | 组内重复治疗关系与适用条件必须由证据支持，不能从名称推断 |
| 两组药品相互作用 | A、B 组各有一条不同有效医嘱；各自匹配标准范围与给药途径；顺序不影响结果 | 原文须支持这两组之间的关系；A/B 范围重叠时要求澄清，不能把自身配对视为相互作用 |

知识草稿记录：来源类型、标题、发布机构、版本、原文定位、原文片段、文件 SHA-256、可选来源有效期；年龄范围及单位、A/B 组标准给药途径、补充条件；临床意义、建议风险等级与动作。页面可从本地文件计算指纹，**不会上传或保管原文件**，仍须记录可追溯的原文位置。

标准药品范围直接引用标准参考目录，独立于机构是否已采用对应药品；条目或规格须显式选择并锁定目录 ID、版本和内容指纹，后端解析权威身份与来源文件指纹。目录改变后提示重新核对。给药途径解析为标准编码并随保存记录版本；已存版本与当前途径定义不一致时提示重新核对，历史快照不改写。

年龄上下限分别为“含下限、不含上限”，岁/月龄/日龄不隐式互换。不限年龄或途径需要显式选择。补充自由文本条件可以保存，但会标为未结构化；疗程重叠和在用药清单可以记录建设需求，本轮不能预演这些范围。当前模型只支持同一处方，不能把同时开立视作实际给药时间重叠，也不能用该草稿验证给药间隔、肾功能或剂量依赖的相互作用。

预演结果为“匹配命中、不匹配、不适用、无法评价”。不匹配不代表用药安全；同一医嘱重复传入不能凑数，停用及取消医嘱不参与，身份缺失、标准版本混用、年龄单位不一致、受限途径缺失等均不伪装为通过。自动合成正例、反例、顺序、阈值、重复医嘱、停用、缺失和年龄边界样例，展示输入与结果；样例用于验证模型表达，不是临床证据或独立专家测试集。

草稿可保存不完整内容，要求标题和保存理由。每次保存追加新版本，保留保存时原文、标准身份、条件、结构校验、作者及时间；基于期望版本和数据库主键拒绝并发覆盖。支持租户隔离、权限检查、标题检索、分页及历史查阅。编辑后清除旧预演结论，切换前保护未保存内容，版本冲突保留当前输入。范围可能重叠的其他草稿仅提示人工比对，不自动宣称证据矛盾或自动合并。

新增接口：

- `/review` 的 `POST`：由提交人撤回，或另一位具备基础数据管理权限的人员退回、复核通过并应用。

工作流为“提交 → 独立复核 → 应用／退回”，提交人可撤回。退回或撤回后允许重新提交，每次均保留原记录。提交期间不修改标准关联；历史详情只读，动作始终针对当前待处理记录。

应用事务在新关联通过运行时校验后提交，关系替换、前后药品语义版本和应用审计一起成功或回滚。审计保存旧关系的标识、原创建人/时间、目录版本/条目/规格/内容指纹，以及目标原文、提交人、复核人、理由和处理后的实际关系。原药品、产品、包装、默认用法等业务字段不在此流程中修改；历史语义记录及处方快照保留。

## 第八轮交付：频次标准语义与预演一致性

继续推进 M1 标准底座，未越过 M2 知识表达及临床审核职责的业务验收关口。本轮核查频次、途径和单位的现有实现，优先修复频次中已确认的行为偏差：后端将周/月周期次数和日历频次按每日时点展开、固定间隔默默忽略不为 1 的次数，以及前端执行配置预演读取已保存数据而非正在编辑的数据。

新增统一的 `ClinicalFrequencySchedule` 能力判断与计划预演，版本 `rhn-frequency-schedule-v1`。频次管理、草稿预演和用药标准页共用后端结果，返回能力状态、缺口原因、解释、结构化平均频率和预演来源：

- 每日固定钟点：核对周期、次数、时点数量/格式/重复、标准时点锚点和首日策略。支持跳过开立前时点及显式完整首日计划；后者可展示过去时点，不代表补执行授权。
- 固定间隔：从明确的医嘱开始时刻按分钟、小时、天或周生成；每个间隔的执行次数必须为 1。单次执行只返回一个时点。
- 周/月内固定次数：有平均频率不代表已经明确周期内执行日期。缺少日期分布时返回缺口，不再伪造每日计划。月间隔还需月末等日历策略，日历频次需具体日期/星期规则。
- 按需、持续执行及关闭自动生成的频次不预生成固定时点；每日钟点的“从开立时间顺延”尚缺偏移定义，明确返回能力缺口，不再替代成剩余时点策略。越界日期不返回半份计划。

固定间隔的多次冲突在新增/修改时拒绝；已存在的冲突数据读取时平均频率与排程均不可用，不替用户改写。周期数值限制在现有数据库可无损表达的 9 位整数、3 位小数范围内，避免入库隐式舍入。频次解释标准版本提升为 `rhn-medication-standards-v2`；新处方语义快照的无效频次标为不可计算，历史快照保留。

- `POST /api/platform/master-data/order-frequencies/preview-definition`：预演当前未保存主档结构，使用与保存相同的定义校验。
- `POST /api/platform/master-data/order-frequencies/{id}/preview-configuration`：预演当前未保存的机构/科室配置，校验租户、权限、主档期望版本、机构科室关系、时点数量、首日策略、状态及预演日期有效性。

两个接口均不保存定义/配置、不创建执行任务或语义版本。已有预演入口也复用统一引擎。预演模拟的是本次固定定义，不推断未来配置切换，不替代临床执行排程。

本轮没有添加新的临床规则或 AI 推断，没有新增数据库迁移，也没有自动修订真实频次。复杂日历/周期分布的结构定义、频次/途径/单位完整变更影响分析、知识审核发布仍待后续建设；不能将本轮一致性修复视作完整标准治理已完成。

## 第十轮交付：重复用药与相互作用知识的历史审查快照回放

上一轮为实际进展。本轮继续推进知识与业务事实的衔接，未越过知识审核职责及首批临床执行的验收关口。对照代码发现旧工坊的处方回放读取当前处方，并由当前居民资料计算年龄；不能用它宣称复现某次历史审查。本轮新增独立的知识回放入口，读取原审查不可变输入。

入口：合理用药工作台 → 规则知识草稿 → 打开已保存草稿 → **历史处方快照回放**。有未保存修改时禁用入口并提示先保存。弹窗左侧为当前机构/科室的原审查记录和回放历史，右侧展示固定知识版本、冻结事实、命中医嘱、缺口和来源依据；不自动发起回放，需明确选择并执行。

核心口径：

- 原数据来自质量域 `RHN_AUD_MED_EVAL.JSON_INPUT`，先按租户、当前工作机构及科室查询，再核对保存的原输入指纹和处方、就诊、范围、版本身份。没有读取当前药品、产品或居民资料来补齐历史事实，没有调用 AI。来源损坏或身份冲突明确拒绝本次回放。
- 固定已保存知识版本，带期望版本校验；回放记录保存完整知识及其指纹、原评价标识/输入指纹、最小化适配事实、独立的适配输入指纹、适配引擎版本、结果、执行时的当前知识缺口、操作者和时间。查看旧回放直接读取原记录，不以当前知识重新计算。
- 使用知识保存时的标准范围、证据和途径版本执行历史逻辑；当前标准已变化时仍可检查旧逻辑，但单独显示当前知识依赖缺口，结果不能直接用于发布。
- 草稿和有效医嘱参与；取消/停止条目不参与；不支持的状态、遗留/损坏药品快照、缺少标准身份、混用目录版本不能当作未命中。每行保留原状态，草稿参与匹配的映射有迹可查。标准条目重复与指定药品组、A/B 两组配对沿用同一确定性草稿模型。
- 限定途径的知识额外核对医嘱中冻结的途径概念、编码、来源系统和版次，以及医嘱字段的一致性；相同编码不同版次不能作为已满足条件。不同途径可排除的前提是来源版次可比较，缺失或不一致为不可评价。
- 年龄仅使用原审查保存的周岁；不能转换成精确月龄/日龄。新增处方评价日期与时区的可选冻结元数据，年龄计算与该日期使用同一个捕获值。旧输入未保存此元数据时日期保持未知，不用今天、开立日期或未注明时区的时间戳推算；需要来源有效期判断的知识返回不可评价。
- 结果区分草稿条件命中、未命中此草稿、不适用、不可评价。补齐模型命中明细：列出所有达到重复条数条件的组内医嘱，以及所有参与 A/B 配对的医嘱，不只显示第一组或第一对。
- 回放不是新的临床用药审查，不改写处方、原评价、知识版本或规则发布状态；不写入正式规则旁路观察记录。未命中不能表述为用药安全，匹配命中也不证明来源已完成药学审核。

新增接口：

- `GET /api/quality/medication-knowledge-drafts/replay-sources`：当前工作范围原审查记录，分页每页 20 条，含原处方版本及评价时间。
- `POST /api/quality/medication-knowledge-drafts/{id}/replays`：固定知识版本，对指定原审查输入执行并保存回放。
- 同路径 `GET`：该知识在当前工作范围的全部版本回放历史。
- `GET /api/quality/medication-knowledge-drafts/{id}/replays/{runId}`：读取指定不可变回放记录。

全部入口要求药品主数据管理权限和已选择工作机构/科室，列表、历史、详情及创建均按范围校验。返回最小业务事实，不复制姓名、出生日期、性别、过敏详情到新回放记录；原输入仍由原审查审计保存。

## 第十二轮交付：人工验证样例、版本与执行留痕

上一轮已完成知识候选进入统一目录。本轮补齐与自动合成样例分开的人工验证能力，为后续评审提供可追溯的预期与实际差异；没有越过知识审核职责或临床发布验收关口。

入口：合理用药工作台 → 统一规则目录 → 选择“知识编译”来源的具体候选版本 → **人工验证样例**。弹窗三栏分别为样例版本/执行历史、样例编辑、结果对照。每个候选版本维护独立样例版本链；换候选版本不沿用前一候选的通过结论。

本轮实现：

- 人工创建 1 至 30 个样例，每例填写不同名称、预期依据/测试意图、合成年龄及单位、合成日期、最多 30 条医嘱和明确的预期结果。开始时为空白，不从引擎输出或 AI 自动填入预期结果。

- “命中”必须人工指定预期参与医嘱，其余结果不能填写命中医嘱。执行同时比对结果类型与完整医嘱集合，集合顺序不影响判定；少报或多报参与医嘱均失败。
- 保存样例和运行分为两个操作。保存不会执行、推导或修正预期；运行只能引用已保存的具体样例版本及其指纹。两种操作均要求原因，记录各自操作者与时间。
- 样例追加为不可变版本，采用候选根记录锁及期望版本校验防止并发覆盖。旧样例及失败记录保留，旧版本可显式重跑。执行记录冻结整组样例、输入、预期、实际结果、表达/知识/样例指纹和引擎版本；读取历史不重新计算。
- 对候选身份和程序/知识指纹进行核验。不支持的执行器版本是执行失败，不能借样例预期为“不可评价”而伪装通过。样例指纹或候选指纹不一致拒绝执行。
- 统一目录显示该候选**最新样例版本**的“尚未编写、待运行、通过但未审核、有失败项”。保存新样例后显示待运行；重跑旧版本不覆盖新版本的状态。关闭样例弹窗后刷新目录状态。
- 界面编辑时隐藏旧结果，未保存修改切换/关闭有保护；读取失败清除旧结果。目录读取失败不会当作“没有样例，从零新建”，提供显式刷新入口；保存冲突保留用户输入，由用户核对后处理。
- 执行结果提示尚未定义的主要结果类型（命中、未命中、不可评价；有年龄或日期限制时包含不适用）。该提示仅统计样例的人工预期类型，不表示完整业务覆盖率或临床准确率。

新增接口：基础路径 `/api/quality/medication-knowledge-rule-candidates/{id}/tests`。

- `/runs` GET 分页执行摘要，POST 执行固定版本；`/runs/{runId}` GET 不可变执行详情。

## 第十三轮交付：知识候选的职责分离审核与固定材料

上一轮完成了人工验证。本轮将知识候选的提交、撤回、退回、批准纳入统一规则目录，继续保留旁路部署及正式启用的独立边界。审核职责已向用户询问；本轮采用“起草/验证人员提交，由另一名有权限人员审核”的实现假设，人员专业资格仍由机构授权管理，首次临床上线仍需业务验收。

入口：合理用药工作台 → 统一规则目录 → 选择知识编译候选 → **审核与提交**。左侧为提交时冻结的知识、规则、证据、可能重叠知识及人工样例明细，右侧为当前依赖缺口、审核操作和历史。审核历史只读，不能从历史材料页直接操作当前流程；当前依赖与已提交材料分开展示。

规则如下：

- 提交前校验当前来源知识与候选锁定版本/指纹一致，标准/途径无当前结构缺口，编译表达及编译版本一致，自动结构样例通过，最新人工样例存在且最新执行全部通过、指纹匹配。人工样例至少定义命中、未命中、不可评价；有年龄或来源有效期条件时还需不适用。结果类型齐备仅是最低检查，不代表临床覆盖充分。
- 提交材料冻结完整候选、人工验证执行及其样例/结果、知识/表达指纹，并形成材料指纹；同时保留可能重叠的知识标识、版本、标题及提示。重叠提示不自动判定临床矛盾，需人工对照知识历史及适用条件。
- 提交后新增知识版本、标准变化、最新样例/执行变化或重叠清单变化会阻止直接批准旧提交。原材料和失败记录不被覆盖；提交人可撤回，修订后重新提交；另一名符合职责分离要求的人员可退回。修订了来源知识时应生成新的候选，而不是覆盖旧候选。
- 审核人不能是该材料的来源知识作者、候选生成人员、人工样例作者、验证执行者或提交人。当前沿用 `MASTER_DATA.MANAGE` 权限，并检查明确的操作者身份及人员分离；没有自动认证药学专业资质，也尚未细分专业审核角色。
- 批准要求明确确认标准身份/范围/版次、来源原文/适用条件/证据有效性/潜在冲突、人工验证结果，填写药学审核意见和操作原因，并分别选择**命中时**与**无法评价时**的处置策略。策略无默认勾选或隐式沿用；支持提醒、继续需理由、阻止提交。这些目前只是固定审核策略，尚未参与临床执行。
- 原文证据直接取自锁定知识，审核接口不接受另传的任意原文替换。机构制度保留 `INSTITUTION_POLICY` 用途，不冒充临床药学证据；界面明确展示来源类型。
- 所有提交/撤回/退回/批准记录追加写入，包含材料、指纹、关联提交、核验结果、策略、审核意见、操作者及时间。读取历史核对材料身份与指纹，损坏记录不能被当作有效依据。
- 操作以统一目录治理修订号做并发校验；知识版本修改、人工样例保存/运行与审核采用一致的记录锁顺序，串行化当前来源知识及该候选的样例/执行写入。其他知识及全局标准按读取时版本检查；后续发布仍须重新核验依赖，不假设审批期间全库冻结。并发审核只能有一个成功，另一方收到刷新提示；审核审计和治理状态在同一事务内保存。
- 原通用目录命令继续拒绝知识候选的旧提交/批准/发布调用，避免绕过专用审核所需的材料指纹和人员分离。统一目录的审核状态来自同一个治理记录；不是另一份独立状态表。
- 审核通过不安装临床执行器，不创建规则发布记录，也不写真实处方审查或旁路观察。源知识草稿的不可变 `DRAFT` 记录不原地改写；此批准针对特定候选及其冻结来源，不等同于独立知识库全局发布。

## 第十四轮交付：知识候选的科室旁路部署与观察

首批继续以用户选定的**重复用药与相互作用**为主。知识候选现可在统一规则目录中显式进入旁路，由正常处方评价自动运行；审核通过仍不会自动启用，正式启用尚未开放。

本轮实现：

- 新部署须使用审核通过的候选，重新校验当前来源知识、标准/途径、编译表达、最新人工验证及审核材料指纹。材料变化阻止新部署；前端不会沿用读取失败时的旧操作状态。

## 第十五轮交付：AI 需求分析、澄清与知识起草入口

上一轮的科室旁路流程仍待用户体验验收，本轮没有推进正式启用。继续完成与该验收独立的 M4 入口：让 AI 先分析用户想控制的规则类型、药品范围及未明确条件，再由用户进入有来源的知识起草工作流。

入口：合理用药工作台 → **AI 规则工坊与候选孵化 → 需求分析与澄清**。此页成为工坊默认入口；原候选生成、模拟、候选历史保留在“模板候选与历史”。从统一目录打开旧模板候选会直接进入原入口，避免丢失已有查看路径。

本轮实现：

- 用户可直接描述需求，无需先勾选本院药品。真实模型按服务端给定能力表建议分类、拆分多个独立意图，引用用户需求或澄清回答中的连续原文，列出范围、条件及需要回答的问题。
- 能力表覆盖重复用药、相互作用、单次剂量、日剂量、体重/体表面积剂量、途径、频次、疗程、过敏、特殊人群、肝肾功能、适应证和其他需求。这里描述的是**当前知识编译工作流**的覆盖范围，不是全系统所有内置/旧模板规则的覆盖声明。
- 只有重复用药与相互作用可从分析入口进入现有知识草稿工作流；仍限定既有同一处方、标准身份及条件能力。其他类型保留需求与能力缺口，不伪造可执行规则；已存在的内置或模板能力需单独核查。
- “全部药品”作为需求范围处理，不转换为一张本院药品勾选清单。服务端核验范围引用；缺少可定位或明确的全部药品表述时保持待明确。分类及引用位置检查不等于语义正确性证明，仍须人工核对否定、例外和适用条件。
- 对截图中的“所有药品单次用量超过 3 倍制剂规格用量时警告”，单次剂量能力清单明确要求先区分制剂规格与临床常规用量，补充比较基准、单位、人群、途径及来源。本入口不会据规格或“3 倍”生成剂量上限，也不会因未选药品而拒绝需求分析。
- 模型只能提供枚举内的意图、原文条件与问题，不返回或采纳可执行代码、标准编码、推荐剂量、风险等级和处置动作。能力状态与是否允许进入知识工作流由服务端维护，模型不能自称某能力已实现。
- 引用记录保存来源键和原文起止位置。无法定位、未支持字段或分类被丢弃并提示；格式错误、超限、模型调用失败分别记录失败状态，不冒充完成分析。原始返回有大小上限，错误记录可重试。
- 每次澄清必须关联父分析中实际存在的问题，原需求不能偷换。保存问题文本、回答及来源分析标识；回答只作为业务意图，不作为药学证据。重新分析追加新记录，父记录不改写。失败重试保留已累计的澄清，不退回空白需求。
- 分析按租户及管理权限隔离，必须有操作者身份；保存模型、提示版本、能力版本、输入/结果指纹、操作者及时间。历史分页，读取具体记录校验指纹；历史先只读，明确“基于此记录继续澄清”后才恢复操作。
- 输入改变使旧结果失效；历史或分析读取失败不会保留可直接采纳的旧结果。模型不可用时显示配置状态，能力说明和现有手工知识入口仍可使用。
- 用户明确选择某条分类后，只新建未保存知识草稿。药品组、人群、途径、检查范围、次数、来源及处置保持待明确，不把 AI 分类当成完整知识。草稿留待结构化标记，须对照完整关联需求与澄清，将可表达条件填入相应字段，不能表达的条件继续保留。
- 知识版本单独关联需求分析来源，可在当前草稿及版本历史中查看。使用独立数据库列保存关联，**没有给不可变 `Version` 的 JSON 添加字段**，避免让已生成候选、已审核或已部署版本的知识指纹因扩展而变化。该关联仅是需求出处，不改变药学证据字段。
- 同类型的 AI 原文抽取采纳仍保留需求关联，并重新提示对照需求条件；改变知识类型时不静默沿用不匹配关联。保存接口也会核对来源分析是否包含可进入该知识类型的意图。

接口：`/api/quality/medication-rule-intakes` 的 POST 分析、GET 分页历史、`/{id}` GET 固定记录、`/capabilities` GET 当前能力表。知识版本新增 `/{id}/versions/{version}/intake-origin` 读取需求来源。

`V1_69_0` 双数据库迁移新增 `RHN_AUD_KNOW_INTAKE`；知识草稿表增加可空的需求来源列和租户内外键。既有草稿没有关联时保持空，不猜补历史需求。

边界：本轮不提供真实医学知识检索，不自动给新类型增加运行支持，不把用户需求或模型问题当作药学证据，也不修改任何临床启用状态。自动测试使用受控模型返回验证协议、引用和治理边界；不能据此宣称真实模型对所有中文用药需求的分类准确率或条件召回率已验收。真实模型表现仍需结合机构需求语料人工检查。

建议手工体验：先输入截图中的剂量需求，查看“全部药品”与基准/证据缺口；再输入包含重复用药及相互作用的两条独立需求，核对分类和例外，补充回答，确认历史保留；明确采纳其中一条，核对草稿的未确定字段、待结构化标记和关联需求原文。

## 第十八轮交付：知识候选独立正式启用、暂停与回退

1. 选择当前候选的具体旁路发布。服务端重新核对当前候选、来源知识、标准身份/途径、人工验证与批准版本；已被替换的旁路不能直接晋级。
2. 形成一批固定观察材料，按所选旁路的观察编号上界收集全部记录，包含四类结果及每条观察最新的研判、依据和指纹。清单无 20/100 条截断，前端明细按 20 条分页展示。

4. 启用人填写旁路验收与上线风险评估、回退/应急方案、操作原因，分别确认本批观察、命中及不可评价双策略、暂停与回退安排。正式启用不根据统计或 AI 判断自动发生。
5. 提交时携带目录修订号、观察上界和材料指纹。锁定知识根、候选验证及本批观察行后重新核对，研判更正/撤回、批准变化或并发发布均不能沿用过期确认。新的、更大编号的观察不加入本批；页面明确显示核对边界和未纳入后续观察的含义。
6. 成功后保存不可变的独立启用材料并创建当前机构科室的 `ENFORCED` 发布，替换同规则同科室的旧正式记录，暂停所选来源旁路。知识草稿、候选、原旁路观察和审批材料均不改写。
7. 正式发布可单独暂停。暂停不要求标准或验证预检仍通过，也不会自动恢复任何旧正式版本或来源旁路。界面保留该记录的固定上线材料。
8. 回退须明确选择曾在当前机构科室正式发布的记录。重新验证其原批准、固定材料、旧版标准/表达兼容性、来源有效期、最新人工验证及原观察批次的最新研判；旧审核已失效/废止、表达或验证变化、研判出现疑点时均阻止回退。当前知识草稿可以已是新版，回退不把草稿恢复成旧版；恢复的旧规则会生成新的正式部署和独立回退材料。

运行与临床行为：

- 正式运行仍使用批准时固定的类型化表达，不调用 AI 或实时药品主数据推断规则。运行时按当前租户读取对应的不可变启用记录，核验该记录与候选、部署、机构科室及批准指纹的绑定；缺失、损坏或不匹配时不能运行成通过结果。

## 第十九轮交付：旁路反馈进入 AI 改进需求与知识新版本

上一轮完成独立正式启用链路；默认上线门槛和具体真实规则的验收节点继续保留。本轮推进 M5 的知识改进来源链，不改变临床运行策略。

入口：统一规则目录 → 知识候选 → 旁路部署与观察 → 查看与研判 → **转为 AI 改进需求**。

- 对最新有效的疑似误报、疑似漏检、数据问题、规则问题或尚不能判断意见开放改进入口。意见一致、撤回、缺失或损坏的观察材料不能直接进入；后两者应先核查运行审计。
- 进入后显示固定观察、机构科室、发布、知识版本、研判人及意见。用户编写并明确核对要发送给模型的需求与澄清；系统不自动附带处方事实、患者资料、研判原文或依据。模型只分析这份用户输入，使用既有能力表和原文定位约束；它不会据研判推断药学结论或改写规则。
- 每次分析与失败记录都绑定固定研判事件；支持在原观察下分页查看分析/澄清历史。普通需求历史也能查看当前科室的改进记录，但关联研判的继续澄清须从原观察入口核对，不可通过普通分析接口脱离来源。更正后的意见必须作为新的来源，不能承接旧研判的澄清链。
- 模型调用前校验来源；调用后对原观察加锁并再次核对最新意见与指纹。若期间意见更正、撤回或材料改变，不保存过期的改进分析。分析结果和来源快照同事务写入；模型失败本身会留存失败状态及来源供原样重试。
- 原始研判引用与分析输入/输出分开存储。来源 JSON 保存 SHA256，并核对机构科室及研判事件索引；普通需求没有新增空的快照字段。查看、历史和关联知识均遵守租户与原机构科室范围。
- 用户采纳受支持的分类后，读取**原知识根的当前最新版本**作为未保存编辑，保留已有来源证据、条件和标准范围，并增加“待核对与结构化”标记。不会用旧旁路的知识快照覆盖已发生的新修改；保存沿用当前版本并发检查，形成同一知识的新草稿版本。类型与当前知识不一致时提示单独建设，不能静默换类覆盖。
- 未结构化标记须逐项核对处理，未支持条件应继续保留；既有校验禁止带未结构化条件的知识直接编译。研判说明不会自动填入药学证据字段，保存、编译、独立测试、审核及部署仍需分别执行。
- 知识当前与历史版本的需求来源中可继续查看原始研判。后续更正/撤回不改写历史改进分析，也不自动宣布新草稿完成整改；依据质量和问题是否解决仍须独立核验。

接口：原 feedback 下新增 `GET/POST /improvement-intakes`；需求分析下新增 `GET /{id}/feedback-origin`。`V1_72_0` 双数据库迁移给需求分析表增加机构、科室、研判外键及独立来源快照/指纹，原分析 JSON 和知识版本指纹保持兼容。

边界：本轮 AI 提供需求分类与澄清，不自动证明误报/漏检、不自动产生医学修改方案，也不将数据问题误标为知识已修复。尚未提供独立改进任务的分派/结案、正式告警的医生处置或药师任务、改进前后临床效果对比、自动检索可信医学来源和自动建议边界样例。M5 和整体建设目标仍未完成。真实模型及浏览器流程待用户体验，本轮自动测试使用受控模型返回和合成业务材料。

建议手工验收：从已有的待核查意见进入改进需求，检查固定来源；编写不含患者身份的业务问题后分析并回答澄清；采纳重复用药或相互作用类型时，确认编辑器打开的是当前知识版本，来源原文保留，待处理条件明确，保存后可沿需求来源追溯到原研判。

## 第二十轮交付：标准目录版次登记、运行归档与字段差异

前轮完成研判到知识改进的来源链。本轮回到 M1B，解决参考目录只有随程序加载的单版 JSON、缺少新版登记和稳定对照基准的问题。当前运行目录选择机制尚未改变，版次切换和批量迁移继续作为后续节点建设，不能将本轮登记功能视为已完成升级发布。

入口：基础数据 → 药品目录 → 标准参考目录 → **目录版次与差异**。

- 管理人员上传 schemaVersion=1 的完整 JSON 目录包并填写登记原因，显式确认后保存不可变候选版次。限定同一目录编码体系；租户内同版号只能登记一次，不能覆盖当前运行版次或已登记内容。新条目或规格使用新的标识，同标识的内容修改会在差异中逐字段显示。
- 服务端检查结构、唯一标识、条目/规格/待核验项之间的引用、来源文件引用、语义版本、剂型/规格和可计算强度数值。重复 JSON 字段、无效引用、范围条目下的规格、非正强度等直接拒绝。未知扩展字段会保留并参与对照；结构检查不证明医学含义或字段之间的全部业务关系正确。
- 保留原登记文本及其 SHA256、原声明内容指纹、完整规范化目录与服务端重新计算的内容指纹。规范化内容指纹使用公共的排序键及数值规范化算法，排除 contentHash 字段本身；原提供者的指纹不会自动当作校验通过。原来源 DOCX/PDF 等文件未随 JSON 上传，来源文件指纹仍须人工核验。
- 第一次登记新版前，在同一事务内归档当前运行目录的完整内容；后续同版号引用该固定归档。若程序资源已经原地修改成与已登记同版号不同的内容，停止新登记并提示核查，不能静默覆盖归档。同租户登记对租户行加锁，并由版号唯一键阻止并发覆盖。
- 新版记录关联登记时的运行归档，页面默认使用这份归档进行对照。可明确将其他登记版设为基准，或改看当前运行版；以后程序资源变化也不会失去原对照材料。
- 条目与规格按标准标识对齐，新增/移除保留完整对象；已有对象递归比较全部字段，包括所属条目、剂型、规格、单位、强度、类别、来源与扩展字段。其他数组按位置比较，顺序变化也显示，尚不推断名称等价、成分等效或医学影响。字段路径区分新增、移除、修改；全量差异统计与固定对照指纹不受每页 20 项限制。
- 可按版次独立核验来源，复用提交/复核分离、退回、撤销和不可变事件历史。登记包即使自行声明 VERIFIED，系统状态也从未核验开始。核验对象是具体目录、内容和来源文件身份，不能将新版核验写入旧版；运行归档与当前运行目录身份完全相同时，共用同一份来源核验记录。
- 当前依赖入口盘点同一目录体系中各版次保存的药品、产品、知识、规则及部署，包含历史和动态作用域，展示覆盖边界及指纹。它是迁移前的依赖盘点，不是每一项均受本次字段变化影响的结论；读取也不会迁移关联或重写规则。
- 登记列表使用独立摘要与摘要指纹，不在每页列表读取时加载全部目录包。详情和导出核验完整包指纹；可分别导出规范化目录和原登记文本。读取失败时撤去旧差异与可操作材料，不显示“无差异”假象。

接口：`/api/platform/master-data/medication-standard-catalog/editions` 提供登记/分页列表、runtime、详情、content、original、comparison、dependencies 和 source-review。`V1_73_0` 双数据库迁移新增 `RHN_BD_STD_EDITION`；目录原文与规范化版本、摘要及各自指纹同事务保存。严格 JSON 文档解析通过公共 JsonCodec 提供，没有让业务服务自行依赖 ObjectMapper。
