# RHN 合理用药实施路线图

- 日期：2026-09-15
- 上位设计：[RHN 合理用药平台总体方案](README.md)
- 架构约束：[ADR-007 合理用药临床语义与 AI 规则治理](../架构决策-007-合理用药临床语义与AI规则治理.md)

## 1. 实施原则

本路线图以“小步纵向闭环、先标准化再批量规则、保留既有安全行为”为原则，不采用“大爆炸”方式一次性重写现有开药和审方逻辑。

每个阶段都必须满足：

1. 能独立回滚；
2. 不破坏当前处方、发药和药师审核主流程；
3. 有明确验收标准；
4. 新旧规则迁移有 Shadow/回归证据；
5. 不用未完成的新引擎替代现有安全校验。

建议开发顺序：

```text
QMED-0 Medication Semantic Baseline
        ↓
QMED-1 Safety Engine Foundation
        ↓
QMED-2 Existing Rule Migration
        ↓
QMED-3 Doctor Safety Workflow
        ↓
QMED-4 Medication Knowledge Base
        ↓
QMED-5 AI Knowledge Factory
        ↓
QMED-6 Pharmacist Feedback Loop
        ↓
QMED-7 Advanced Clinical Rules
```

# 2. QMED-0：Medication Semantic Baseline

## 目标

先把所有会参与合理用药计算的基础药品语义稳定下来。这个阶段不追求规则数量，追求“输入可信”。

## 2.1 盘点现有数据模型

先完成只读盘点，列出当前：

- Medication / Product / Catalog Item 的关系；
- 规格与强度字段；
- defaultDose/defaultDoseUnit；
- defaultRoute；
- defaultFrequency；
- 剂量单位与库存单位；
- 频次字典；
- 给药途径字典；
- 抗菌药属性；
- 皮试属性；
- MedicationTerminologyDirectory 现有匹配能力；
- MedicationRequest 中已经持久化的知识快照。

产出：

```text
docs/architecture/rational-medication/现状数据映射.md
```

至少记录“当前字段 → 未来 Canonical Concept → 是否需要迁移”。

## 2.2 建立标准语义模型

首批定义：

```text
Ingredient
Medication
MedicationProduct
MedicationStrength
ClinicalDoseUnit
PackageUnit
AdministrationRoute
MedicationFrequency
```

要求：

- 稳定 ID；
- code + display 分离；
- clinical semantic 不依赖显示名称；
- 有 version/status/effective period；
- 可记录标准编码和来源；
- 本地值通过 mapping 指向 Canonical Concept。

### Frequency 重点

至少支持：

```text
TIMES_PER_DAY
INTERVAL
AS_NEEDED
ONCE
SCHEDULED_TIME
OTHER/UNCOMPUTABLE
```

`BID/TID/Q8H/PRN` 等常用值必须可结构化解释。

### Unit 重点

临床剂量单位与包装单位分开。临床单位建立 dimension/canonicalUnit/conversionFactor，禁止在规则代码中依赖名称字符串换算。

## 2.3 动态维护治理

将涉及 S0 临床语义的数据维护从“直接更新”改为版本化发布：

```text
DRAFT → VALIDATED → APPROVED → PUBLISHED → RETIRED
```

对已 PUBLISHED 记录：

- display-only 变化可以按低风险流程处理，但仍要有审计；
- semantic 变化必须新建版本；
- 不允许原地改写历史语义。

建立 Change Classification：

```text
DISPLAY_CHANGE
MAPPING_CHANGE
BUSINESS_CONFIG_CHANGE
CLINICAL_SEMANTIC_CHANGE
```

## 2.4 影响分析最小版

第一阶段只需做到规则级和模板级影响分析，不必一次实现完整全图分析。

输入一个被修改的 Medication/Frequency/Route/Unit，返回：

- 依赖该概念的规则版本；
- 依赖该概念的医嘱模板/常用组套（若已有公共查询能力）；
- 是否存在 ACTIVE 使用；
- 是否要求重新跑规则测试。

## 2.5 Runtime Snapshot 补齐

检查 MedicationRequest/Prescription 当前快照，补齐合理用药运行必需字段：

```text
medicationId
medicationSemanticVersion
ingredientIds
strength + unit
dose + doseUnit
routeConceptId + version
frequencyConceptId + version
duration
```

注意：历史处方不要求立即全量回填无法可靠恢复的数据；迁移脚本不得伪造历史临床语义。无法恢复的字段明确标记 unknown/legacy。

## 2.6 验收标准

- 常见 Frequency 能稳定计算语义，不读取 display 文本；
- `g ↔ mg` 等首批受支持剂量单位可确定性转换；
- 包装单位不能参与临床剂量比较；
- PUBLISHED 临床语义不能直接修改；
- 本地别名/本院码修改不会改变 Canonical Concept；
- 新处方保存必要的临床语义版本/快照；
- 原有开药、计价、库存和发药回归通过。

# 3. QMED-1：Safety Engine Foundation

## 目标

在 `rhn-quality` 建立最小可运行的合理用药评价骨架，只放一条测试/真实规则也可以，但必须贯通“输入 → 规则 → Finding → Evaluation → 持久化”。

## 3.1 Clinical 定义消费 Port

建议在 Clinical 的公开 API 中定义：

```text
com.rhn.outpatient.api
├── MedicationSafetyPort
├── PrescriptionSafetyRequest
├── PrescriptionSafetySnapshot
├── MedicationSafetyDecision
└── MedicationSafetyFindingSnapshot
```

原则：

- DTO 不暴露 JPA Entity；
- 输入不可变；
- 明确 tenant、prescriptionId、encounterId、revision；
- 明确 medication item snapshot；
- 需要患者事实时只携带公共事实版本/快照，或由 Quality 通过公开 API 补充；
- 不把 Quality 内部 Rule/Entity 暴露给 Clinical。

## 3.2 Quality 实现 Adapter

建议建立：

```text
com.rhn.quality.medication
├── application
│   ├── MedicationSafetyAdapter
│   ├── MedicationSafetyEngine
│   ├── MedicationContextAssembler
│   └── DecisionAggregator
├── domain
│   ├── MedicationSafetyEvaluation
│   ├── MedicationSafetyFinding
│   ├── DecisionStatus
│   ├── FindingSeverity
│   └── rule
│       ├── MedicationSafetyRule
│       └── ...
└── infrastructure
```

## 3.3 决策模型

实现：

```text
PASS
WARN
REQUIRE_OVERRIDE
BLOCK
UNAVAILABLE
```

Severity 和 Decision 分离。

聚合规则建议：

- 任一 BLOCK → 整体 BLOCK；
- 无 BLOCK、任一 REQUIRE_OVERRIDE → REQUIRE_OVERRIDE；
- 无前两者、任一 WARN → WARN；
- 全部成功且无 Finding → PASS；
- 规则执行基础设施不可用/关键输入无法取得 → UNAVAILABLE（不能 PASS）。

具体按规则“缺失数据策略”决定某条规则是跳过、WARN、UNDETERMINED 或导致整体 UNAVAILABLE，不能全局一刀切。

## 3.4 Evaluation / Finding / Override

第一阶段至少建立：

```text
quality_rule_definition
quality_rule_version
quality_evaluation
quality_finding
quality_override
```

Evaluation 记录：

- tenant；
- target type/id/version；
- inputHash；
- ruleSetVersion；
- status；
- started/completed time；
- engine version。

Finding 记录：

- ruleCode/ruleVersion；
- category；
- severity/decision；
- message；
- medicationRequestIds；
- evidence snapshot/reference；
- overridePolicy。

## 3.5 第一条垂直规则

推荐优先使用当前最有数据基础的规则完成链路：

```text
DuplicateMedicationRule
```

或选择：

```text
AntimicrobialOutpatientRule
```

第一条规则的目标不是展示复杂医学能力，而是验证：

```text
Clinical Snapshot
 -> Quality Adapter
 -> Rule
 -> Finding
 -> Evaluation Persistence
 -> Decision
```

## 3.6 测试

必须增加：

- engine unit test；
- aggregator test；
- Evaluation/Finding persistence test；
- module boundary/ArchUnit test；
- tenant isolation test；
- UNAVAILABLE 不被转 PASS 的回归测试。

## 3.7 验收标准

- `rhn-quality` 不再只是骨架，有完整首条纵向链路；
- Clinical 不直接依赖 Quality 内部包；
- Evaluation/Finding 可审计；
- 同一输入 + 同一规则版本结果可重复；
- 模块依赖门禁通过。

# 4. QMED-2：迁移现有安全规则

## 目标

把已经散落在临床服务中的合理用药规则逐条迁移，但始终保留业务安全。

## 4.1 首批迁移对象

按建议顺序：

1. Drug Allergy；
2. Allergy Status Unknown；
3. Antimicrobial Outpatient Permission；
4. Antimicrobial Max Days；
5. Skin Test Requirement；
6. Exact Generic Duplicate。

## 4.2 Shadow Run

每条迁移规则都经历：

```text
旧逻辑仍是权威
 +
Quality 新规则 Shadow 执行
 ↓
记录结果差异
 ↓
分析差异原因
 ↓
回归通过
 ↓
切换权威实现
 ↓
删除/降级旧重复逻辑
```

Shadow 期间新规则不得额外阻断医生，避免重复告警。

## 4.3 差异记录

至少记录：

```text
legacyResult
newResult
inputHash
ruleVersion
mismatchType
resolvedReason
```

用于证明迁移不是“看起来差不多”。

## 4.4 药物过敏重点

复用现有 MedicationTerminology 能力，但逐步向 Canonical Ingredient/Class 关系演进。

需要覆盖：

- 精确药品过敏；
- 成分过敏；
- 药理/过敏原类别关联；
- drug allergy 未记录；
- active allergy；
- 覆盖原因。

## 4.5 验收标准

- 每条迁移规则都有 Shadow 证据；
- 不出现同一风险双重弹窗/双重阻断；
- 迁移后历史行为差异有明确记录；
- 旧逻辑只有在 Quality 成为权威并回归通过后才删除。

# 5. QMED-3：医生 Safety Check 工作流

## 目标

建立显式的“检查 → 处理 → 提交”流程，并保证检查后处方被修改时结果自动失效。

## 5.1 API

建议由 Clinical 暴露处方语义 API，例如：

```text
POST /api/outpatient/.../prescriptions/{id}/safety-check
POST /api/outpatient/.../prescriptions/{id}/submit
```

`safety-check` 返回：

```text
evaluationId
prescriptionRevision
inputHash
decision
findings[]
```

submit 至少携带：

```text
evaluationId
expectedPrescriptionRevision
overrides[]
```

## 5.2 最终服务端门禁

submit 时：

1. 检查 Evaluation 属于当前 tenant/处方；
2. 检查 prescription revision；
3. 重算/校验 inputHash；
4. 验证 override 是否满足 Finding 的 overridePolicy；
5. 必要时重新评价；
6. 通过后再库存冻结；
7. 激活 MedicationRequest；
8. 提交处方。

前端安全检查结果不能成为唯一安全依据。

## 5.3 事务边界

不要让 BLOCK 后直接抛异常导致 Evaluation/Finding 与业务事务一起回滚。

推荐：

- 用户显式 safety-check 独立持久化；
- submit 在业务事务中验证已持久化评价；
- 若需最终重评，明确其持久化事务语义，避免“阻断证据被回滚”。

## 5.4 UI

以“处方安全检查面板”代替大量弹窗。至少展示：

- Severity；
- Decision；
- 涉及药品；
- 风险说明；
- Evidence；
- Suggested Action；
- 修改处方/确认/覆盖理由入口。

## 5.5 验收标准

- safety-check 后修改任一关键药品字段，旧 evaluationId 不能继续提交；
- BLOCK 无法提交；
- REQUIRE_OVERRIDE 没有合规理由无法提交；
- WARN 可继续但有审计；
- UNAVAILABLE 行为按策略可验证；
- 检查发生在库存冻结前。

# 6. QMED-4：Medication Knowledge Base

## 目标

从“规则代码中硬编码知识”演进到“规则逻辑 + 版本化药学知识”。

## 6.1 首批知识域

先做：

```text
DoseConstraint
AgeRestriction
TherapeuticClass
DuplicateTherapyGroup
DrugInteraction
RouteRestriction
FrequencyConstraint
Contraindication
```

## 6.2 绑定策略

优先级：

```text
Ingredient / Generic Medication
    ↓
Product-specific Override（仅确有必要）
```

不要把通用相互作用和剂量知识绑定到每个厂家产品。

## 6.3 版本和有效期

所有药学知识都必须：

- 有知识版本；
- 有证据来源；
- 有生效/失效时间；
- 发布后不可原地改；
- 能被具体 RuleVersion 引用。

## 6.4 Rule 测试数据

每条知识/规则建立最小测试集：

```text
Positive
Negative
Boundary
Missing Data
Conflict
```

发布新版本时自动跑回归。

## 6.5 验收标准

- Max dose/age/DDI 等规则不依赖散落常量；
- 历史 Evaluation 能定位当时知识版本；
- 换厂家不会无理由导致通用知识失效；
- 知识变更能触发受影响规则测试。

# 7. QMED-5：AI Knowledge Factory

## 目标

让 AI 解决“没有大规模药学知识工程团队”的效率问题，但把生产风险控制在 Candidate/Review/Publish 边界内。

## 7.1 Source Registry

建立：

```text
KnowledgeSource
SourceDocument
SourceDocumentVersion
```

记录：

- source type；
- title；
- publisher；
- version；
- effective period；
- source locator；
- license/usage scope；
- content hash；
- import status。

## 7.2 AI Pipeline

建议最小流水线：

```text
Document Import
 -> Chunk / Section Parse
 -> Entity & Terminology Link
 -> Knowledge Extraction
 -> Candidate Rule
 -> Evidence Binding
 -> AI Critic
 -> Schema Validation
 -> Conflict Detection
 -> Test Generation
 -> Review Queue
```

每一步保存运行记录和 prompt/model/version，便于追溯。

## 7.3 Candidate 状态

候选对象建议：

```text
DRAFT
AI_REVIEWED
NEEDS_HUMAN_REVIEW
REJECTED
APPROVED_FOR_SHADOW
```

Candidate 不能直接变成生产 ACTIVE Rule；必须经过明确发布动作生成不可变 RuleVersion。

## 7.4 抽取置信度与证据等级分开

分别保存：

```text
extractionConfidence
clinicalEvidenceLevel
```

前者是模型对抽取质量的估计，后者是来源/医学证据的治理结论。

## 7.5 首批 AI 任务

从低歧义、高结构化、高价值任务开始：

1. 说明书章节识别；
2. 药品/成分对齐；
3. 明确年龄禁忌；
4. 明确单次/日剂量上限；
5. 给药途径限制；
6. 明确禁忌症；
7. 证据原文定位；
8. 测试用例草拟。

不先做开放式“根据医学知识自动生成所有规则”。

## 7.6 AI Critic 验证集

建立固定错误类型回归集：

- 慎用 vs 禁用；
- 推荐剂量 vs 最大剂量；
- 单次 vs 每日；
- 成人 vs 儿童；
- 肾功能分层条件；
- 孕妇/哺乳条件；
- 成分 vs 复方药 vs 商品；
- 单位换算；
- 来源冲突。

## 7.7 验收标准

- AI 不能直接修改 PUBLISHED RuleVersion；
- 任一生产规则都可追溯到 SourceDocumentVersion；
- 任一 AI 候选都能追溯模型/prompt/input/output；
- Critic 能检测预设错误集；
- 生成测试必须通过确定性 Rule Engine 才能进入 Shadow。

# 8. QMED-6：药师反馈闭环

## 目标

把机器 Finding 与现有 PharmacyReview 关联，用真实药师行为衡量规则价值。

## 8.1 药师工作台

展示：

- 当前处方安全评价；
- Finding 列表；
- Evidence；
- 医生 Override；
- Evaluation/Rule 版本。

药师继续使用现有审核状态，不另建平行审方流程。

## 8.2 关联数据

建立：

```text
PharmacyReview ↔ QualityFinding
```

可多对多，但必须保留当时 Finding 快照/ID。

## 8.3 规则效果指标

至少统计：

```text
triggerCount
doctorAcknowledgeRate
doctorOverrideRate
prescriptionChangeRate
pharmacistInterventionRate
pharmacistAgreementRate
```

这些指标用于提出规则优化建议，而不是自动更改规则动作。

## 8.4 验收标准

- 药师可以看到医生此前如何处理风险；
- 可以按 ruleCode/ruleVersion 统计干预效果；
- 新规则可以通过真实反馈判断告警疲劳。

# 9. QMED-7：高级临床规则

## 前置条件

只有在 Health Core/Clinical 提供可靠、版本化的临床事实 API 后才开始。

需要的事实包括：

- 肌酐/eGFR；
- 肝功能；
- K+/Mg2+ 等电解质；
- INR；
- QT/QTc 或相关心电事实；
- 妊娠/哺乳状态；
- 关键诊断/Condition；
- 相关检验的时间与版本。

## 禁止事项

Quality 不得为了赶进度：

- 直接查 diagnostics repository；
- 直接 JOIN 其他领域交易表；
- 从病历自由文本临时猜关键临床事实后进行 BLOCK。

## 规则范围

依次实施：

1. renal dose adjustment；
2. hepatic dose adjustment；
3. pregnancy/lactation；
4. electrolyte risk；
5. QT risk；
6. diagnosis/indication and disease contraindication。

# 10. 推荐 PR 切分

避免一个巨大 PR，建议：

### PR-QMED-0A：现状盘点与标准模型 ADR

- 数据映射文档；
- Frequency/Route/Unit 目标模型；
- 不改变业务行为。

### PR-QMED-0B：临床语义版本化基础设施

- 版本/状态模型；
- 发布流程；
- 维护权限；
- 首批映射迁移。

### PR-QMED-0C：处方快照补齐

- MedicationRequest/Prescription snapshot；
- 历史兼容；
- 回归测试。

### PR-QMED-1A：Quality 基础领域模型

- RuleDefinition/RuleVersion；
- Evaluation/Finding/Override；
- Flyway；
- Repository/test。

### PR-QMED-1B：MedicationSafetyPort + Engine

- Clinical Port；
- Quality Adapter；
- Engine/Aggregator；
- 一条纵向规则。

### PR-QMED-2x：每条现有规则单独迁移或小批迁移

每个 PR 带 Shadow/回归证据。

### PR-QMED-3：医生 Safety Workflow

- safety-check；
- evaluationId/revision/inputHash；

### PR-QMED-4x：药学知识域按类别落地

### PR-QMED-5x：AI Knowledge Factory

Source Registry → Extractor → Critic → Candidate → Review/Publish 分阶段，不一次性做“大而全 Agent”。

# 11. 第一阶段两条并行工作流

当前最推荐马上启动两条线：

## Stream A：Semantic Baseline

```text
A1 现状数据盘点
A2 药品三层模型确认
A3 Frequency/Route/Unit 标准语义
A4 本地映射
A5 版本/发布治理
A6 Runtime Snapshot
```

## Stream B：Quality Foundation

```text
B1 Rule/Evaluation/Finding 模型
B2 MedicationSafetyPort
B3 Engine/Aggregator
B4 一条纵向规则
B5 Evaluation 持久化
B6 模块边界和回归测试
```

两条线汇合点：

```text
标准化 PrescriptionSafetySnapshot
        ↓
MedicationSafetyEngine
```

在此之前不批量生成 AI 规则。

---

# 12. 第一可演示闭环

第一阶段结束时，系统至少应完整演示：

```text
医生开具某药
    ↓
处方保存标准化 Medication/Frequency/Route/Unit 快照
    ↓
执行 Safety Check
    ↓
Quality Engine 使用版本化规则
    ↓
发现 Allergy / Duplicate / Antimicrobial 风险
    ↓
形成 Evaluation + Finding + Evidence
    ↓
医生修改处方或填写合规 Override
    ↓
提交时验证 evaluationId + revision + inputHash
    ↓
库存冻结和正式提交
    ↓
药师工作台看到系统 Finding + 医生处理结果
```

这条链路成立后，后续大部分合理用药能力应通过“增加知识 + 增加规则”扩展，而不是继续侵入处方主流程。

---

# 13. Definition of Done

任何合理用药规则进入生产前至少满足：

- [ ] 有稳定 ruleCode；
- [ ] 有不可变 RuleVersion；
- [ ] 有 Evidence；
- [ ] 输入全部来自公开、可版本化事实；
- [ ] 没有 Repository/Entity/Table 越界访问；
- [ ] 有 Positive/Negative/Boundary 测试；
- [ ] 定义 Missing Data 行为；
- [ ] 定义 Severity 和 Decision；
- [ ] 定义 OverridePolicy；
- [ ] 有 Shadow/回归记录（迁移规则）；
- [ ] 有审计字段和 inputHash；
- [ ] `UNAVAILABLE` 不会被当作 PASS；
- [ ] 通过模块边界测试；
- [ ] 对医生端告警频率和可操作性完成验收。

AI 生成规则额外满足：

- [ ] Source 在白名单 Registry 中；
- [ ] SourceDocumentVersion 可追溯；
- [ ] Candidate 与 Production Rule 分离；
- [ ] extractionConfidence 与 clinicalEvidenceLevel 分离；
- [ ] AI Critic 已执行；
- [ ] 人工/策略审核达到该 Decision 所需等级；
- [ ] 没有由 AI 直接修改既有 PUBLISHED RuleVersion。

---

# 14. 暂不做的事情

为了控制第一阶段复杂度，明确暂不做：

- 通用可视化规则设计器；
- 任意脚本/Drools 式动态执行平台；
- 自动让 LLM 直接判定 BLOCK；
- 全量药物知识图谱；
- 一次性导入成千上万条未经验证的规则；
- Quality 直接读取其他领域数据库表；
- 为高级肾/肝/QT 规则临时复制检验数据；
- 自动让生产规则根据反馈自我修改。

这些能力只有在基础数据、评价模型和反馈闭环稳定后再评估。
