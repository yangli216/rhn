# 标准目录与用药语义运行契约

更新日期：2026-09-20。工程版本：`rhn-medication-standards-v1`；默认规则集：`qmed-standard-shadow-v2`。

## 本轮交付与原则

建立“标准参考目录 → 本院药品档案 → 厂家产品 → 医嘱事实快照 → 确定性规则”的依赖链。AI 使用同一组标准事实生成受限候选规则，不能另建药品身份、猜测换算关系或直接发布临床拦截规则。

| 层级 | 本轮行为 | 标准身份 / 来源 |
| --- | --- | --- |
| 参考目录 | 沿用现有只读目录，保留原始来源核验状态 | catalogId、catalogVersion、contentHash、entryId、specificationId |
| 药品档案 | 新建及导入必须提供标准规格；类型、剂型、规格、已定义单位与含量须匹配 | `RHN_BD_MED_STD_SOURCE` 显式关联 |
| 厂家产品 | 新建必须挂在有效关联的本院药品下 | 产品 → 本院药品 → 标准规格 |
| 给药途径 | 复用受控途径概念、别名解析及版本记录 | conceptId、system、systemVersion、semanticVersion |
| 频次 | 由结构化规则形成标准计算身份，展示名不参与识别 | `RHN.CLINICAL.FREQUENCY` + 语义版本 |
| 剂量 | 使用临床单位维度及标准含量关系计算，禁止从库存包装推断 | UCUM 单位子集、标准规格含量 |
| 医嘱快照 | 冻结标准来源、频次解释及剂量换算结果 | `clinicalSemantics`；历史事实不被当前主数据改写 |
| 规则 / AI | 新版重复规则使用冻结标准规格；AI 候选限定已关联规格 | 版本化执行器、候选快照、试跑记录 |

参考目录的 `sourceVerificationStatus` 当前仍是 `UNVERIFIED`。结构化关联表示身份已对齐，不表示目录已经完成权威核验、适应证审核或临床知识审核。`CAPTURED` 仅表示事实已留痕。

## 建档与存量治理

1. 在“基础数据 → 药品 → 标准参考目录”选定标准条目和规格，关联相符的旧档案或建立本院档案，再建立厂家产品。
2. 普通创建接口与批量导入执行相同校验；导入模板增加必填“标准规格编码”。同租户、同目录版本、同标准规格只能对应一条来源关联，不允许通过另一个本院编码重复新建。
3. 标准规定的类型、剂型、规格和制剂单位不能改成另一标准规格；含量允许同维度等值表达，例如 0.25 g 与 250 mg。院内显示名称和别名可保留，不参与标准身份判断。
4. 旧档案保留查询和维护；新产品及 AI 候选须先建立有效标准关联。名称相似仅用于提示候选，最终关联必须显式提交。
5. 来源缺失、多重关联、来源版本不可用、档案与标准身份/含量不符分别呈现 `UNMAPPED`、`AMBIGUOUS`、`STALE`、`MISMATCH`；这些状态不能伪装成有效 `LINKED`。
6. 本轮不自动批量关联存量药品，也不创建未经审核的目录外条目。现有参考目录未覆盖的中药饮片具体规格、疫苗等需要先完成标准目录扩充，再进入新建链路。

## 频次、用法和用量

新增“用药标准”视图和 `GET /api/platform/master-data/clinical-semantics/standards`，展示当前工作上下文的可用频次、受控途径和临床单位。

- 周期次数通过约分形成身份，例如 BID 的 `TIMES_PER_DAY:2/1:DAY`；固定间隔 Q12H 为 `INTERVAL:2/1:DAY`。平均次数相同，不等于执行安排相同。
- 常见保留编码 QD、BID、TID、QID、Q4H、Q6H、Q8H、Q12H、Q24H、PRN、ONCE、ST 的结构化配置不得与编码含义冲突。院内自定义编码按结构化规则解释。
- 按需、单次、日历安排不推算固定日剂量；日历安排须有日期上下文，持续输注须有速率语义，不能降级为每日一次。
- 质量和体积只做同维度换算。片、粒等只有在标准规格明确 `AMOUNT_PER_PRESENTATION` 且含量可计算时，才换算成临床质量/体积。
- 复方、浓度、IU 等本轮未支持的组合换算明确标记不可计算。包装盒数、库存数量不参与推断。
- `standardDose.singleDose` 为规范单位下的单次量，`averageDailyDose` 为按频次计算的平均每日量。二者都不是临床推荐量、24 小时最大实际暴露量或安全上限。
- 默认剂量单位必须属于临床单位、制剂单位或参考规格明确记载的含量单位；“默认剂量”仍是录入辅助配置，不作为审查证据。

## 标准规格重复规则

默认规则集升级到 `qmed-standard-shadow-v2`，执行器版本为 `qmed-engine-2`。`QMED.EXACT_GENERIC_DUPLICATE` 的新实现为 `java:standard-reference-duplicate:1`。

规则只读取已保存医嘱中的 `clinicalSemantics.standardReference`，使用目录标识、目录版本、内容哈希和标准规格 ID 分组。同一处方中相同版本标准规格的多条有效医嘱产生核对提示，不依赖本院药品 ID、名称或厂家。缺少有效冻结标准关联时返回 `UNAVAILABLE`，不将其解释为安全通过。

这条规则检查同规格重复，不声称覆盖不同规格同成分重复、复方交叉成分或同药理类别重复。规则编码保留以延续追踪，新版本的实际边界以本契约和执行器为准。

原 `qmed-foundation-shadow-v1` 和旧执行器保留用于回放；迁移只新增规则版本。其余六条规则仍沿用既有实现，尚未全面迁移为标准成分/证据驱动。所有规则继续处于 SHADOW；本轮没有启用新的临床强制拦截。

## AI 边界

- 生成前核对全部选中药品的标准关联，未关联时拒绝调用模型；候选保存当时的目录身份及版本。
- 支持四种受限模板：标准规格重复、抗菌药疗程核对、年龄阈值核对、显式选中规格组重复。类别文字只作显示名称，不代表已经建立临床分类本体。
- 服务端验证模板参数，按确定性模板生成实际展示表达式；不执行模型自由生成的规则代码或表达式，不接受模型生成的 BLOCK 决策。
- 模拟测试使用候选冻结事实，HIS 旁路读取历史医嘱的标准关联和用药事实；不回填当前主数据来替代历史缺失字段。
- 审批状态仅为 `APPROVED_FOR_SHADOW`，不等于正式规则发布。AI 生成的年龄等阈值仍需要外部证据及专业审核，不能因试跑通过就成为临床结论。

## 统一在行规则目录与发布治理

“在行规则目录”现在承担规则全生命周期管理，不再只展示当前有效规则。目录按规则根编码聚合系统内置规则、AI 候选规则和人工起草规则，版本、审核、发布、运行观察和历史操作都在同一条记录中管理。列表可按来源、审核状态和运行状态筛选，便于区分“审核通过但尚未发布”“已暂停”“已替换”和“历史结束”等状态。

规则状态和运行状态分开保存：审核状态经历 `DRAFT → IN_REVIEW → APPROVED/REJECTED → RETIRED`，发布记录另行记录 `SHADOW/ENFORCED`、范围、生效期和发布状态。审核通过只代表版本具备发布资格，不会自动改变处方行为；启用旁路后才开始记录真实处方观察，正式发布要求先有旁路观察记录。暂停、回滚和废止均产生操作审计事件，旧版本不会被原地改写。

运行时只消费已冻结的 `RuleVersion`、标准参考身份和处方事实快照。旁路评价写入运行记录但不改变提交结果；正式版本才参与处方提交校验。标准规则没有显式发布时仍保持默认旁路基线，机构可以在目录中暂停该默认旁路；显式发布后，目录范围内的版本接管对应规则，避免同一规则在基线和发布版本中重复执行。AI 只能形成候选版本，旧的 `APPROVED_FOR_SHADOW` 兼容标记不会越过目录审核和发布流程。

目录治理数据落在租户隔离的 `RHN_AUD_MED_GOV` 和运行记录表 `RHN_AUD_MED_GOV_RUN` 中。命令提交携带目录修订号，发生并发修改时拒绝写入并要求刷新；每次审核、发布、暂停、回滚和废止都保留操作人、原因、时间和目标版本。正式审核必须确认标准身份和临床证据，证据需包含来源、版本、定位、支持条款及 `CLINICAL_EVIDENCE` 用途。

## 验证方式

使用 `test` profile 与随机 H2 数据库验证建档/导入约束、存量关联、标准冲突、单位转换、频次一致性、历史快照、规则版本及 AI 边界；前端验证标准预填与只读字段、用药标准展示及工作台流程。不运行真实系统浏览器自动验证，不将测试写入人工验收 Oracle 库。

2026-09-20 验证结果：相关后端测试类共 96 项通过（含规则目录审核、旁路发布生命周期用例）；前端全量 95 个测试文件共 541 项通过；后端打包及前端构建通过。新增标准接口、规则目录接口及相关请求/响应已同步到 OpenAPI 和前端生成类型。

全局检查另有本轮范围外的存量问题：`ArchitectureTest.persistent_model_does_not_reintroduce_uuid_identifiers` 因分析模块 `QueryPlanner.java:46` 使用 UUID 失败（该代码存在于本轮改动前）；`ui:check` 仍报告多个已有页面的规范问题，新增用药标准面板未报告违规。前端构建仍有已有的大分包提示。本轮不修改这些无关模块，不将相关测试通过表述为全仓检查通过。

人工验收后端已使用 `oracle-local` 更新，Oracle 的 `V1_58_0`、`V1_59_0` 迁移均已成功，规则治理表已建立。验收建议：从标准目录关联一个已有档案 → 查看标准身份 → 建立厂家产品；在“用药标准”对比 BID、Q12H 与 PRN；在 AI 工作台确认未关联药品无法选入候选、已关联药品可以试跑；在规则目录完成审核、旁路和正式发布前置校验。真实浏览器操作由人工完成。
