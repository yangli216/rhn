# QMED-0 运行基础与 QMED-1 接入

更新：2026-09-16。分支：`docs/rational-medication-blueprint`。

已快进接入同事提交 `6bfbb04`，并完成本轮 QMED-0 开发与 QMED-1 接入。遵循本轮约定：优先贯通业务，暂不建设资料核验、发布审批、医生检查后才能提交等工作流。

## 1. 可以使用的功能

- 基础数据中心 → 药品目录 → 通用药品 → **成分与含量**：建立本院成分，关联单方/复方成分，填写分子含量和分母基准量，记录来源。支持 `100 mg / 2 mL`，不把浓度压成单一剂量。
- 成分可先关联、含量留空；资料缺失不阻止既有开药链路。含量填写时仍检查数值、单位配对等数据结构，防止保存不可解释的半条记录。
- 单位词表明确区分质量、体积与包装/制剂计数。支持 kg/g/mg/ug/ng、L/mL/uL 的同维度换算；片、盒、支和 IU 不会被当作质量换算。IU 等原文可保存，但标记尚不能计算。
- 药品及频次维护追加不可变记录。药品显示名称/别名或本院码变化不改变其语义内容版本；临床字段、成分映射、执行频次变化生成不同版本。
- 门诊直接开立、处方草稿/批量开立，以及住院开立，都保存开立时的语义快照。住院同时补存频次 ID、名称和完整频次规则。
- QMED-1 可通过独立旁路接口接收完整处方、产生重复药品提示，并保存 Evaluation / Finding。旁路评价不提交处方、不冻结库存、不改变既有药师审核策略。

## 2. 版本与历史约定

`RHN_BD_CLIN_SEM_VER` 是只追加的版本/审计记录，API 不提供覆盖或删除历史的操作。

- `HASH_SEM_VER`：规范化 JSON 的 SHA-256 内容版本；数值小数位数、对象键顺序不影响版本。不是 JPA revision。
- `ID_CLIN_SEM_VER`：审计记录主键。成分映射维护使用这个值检查页面是否过期；并发维护先锁定当前租户药品，禁止后保存者覆盖先保存者。
- `SD_CHANGE_TYPE`：首次记录、显示变化、映射变化、临床语义变化。频次定义和机构/科室配置分别留存。
- 成分身份包含租户、来源体系、来源版本、成分编码；名称、过敏原 ID、分类 ID 均不用于猜测成分。
- 临床单位使用独立版本词表。途径沿用受控概念 ID，运行版本包含来源体系、体系版本和执行类型。频次版本包含机构/科室实际解析后的规则、执行时点和首日策略。
- 版本状态为 `CAPTURED`，表示已留存可复现资料，不表示医学正确性已审核。`versionRecordedAt` 是留存时间，`businessDate` 是医嘱业务日期，不冒充无法恢复的历史生效时间。
- 重复使用相同内容可引用相同语义哈希；审计记录仍可因显示更新、来源更新或不同配置观察产生多条。不以全局自增序号替代临床语义版本。
- 历史医嘱不回填当前主数据；没有新增快照的历史条目仍为 `LEGACY`。已持久化快照不会因资料维护而重写。

这覆盖本轮“立即维护、历史可复现”的基础。原路线图的审批发布状态机、预约生效/退役管理不在本轮实现。

## 3. 快照合同

保留原 `MedicationRequest.medicationSnapshot` 字段和原有顶层属性（皮试等消费者继续读取），新增 `clinicalSemantics`：

- `schemaVersion = qmed-medication-semantics-v1`
- `status = VERSIONED / VERSIONED_PARTIAL` 与 `unknownReasons`
- medicationId、medicationSemanticVersion、productId、资料来源及留存时间
- ingredientIds、成分来源记录、结构化 strengths（分子/分母和临床单位维度）
- 实际 dose / 临床单位概念与词表版本
- 实际 route / frequency 的稳定概念标识、语义内容版本和解析结果
- durationValue / durationUnit；缺失值保留空，不推导疗程

QMED-1 顶层升级为 `qmed-prescription-v2`；语义状态从已保存 JSON 读取，不回查最新目录。引擎继续接受 v1 历史输入。保存不完整或无法解析的新增语义标为 `UNKNOWN`，不能冒充完整版本。完整药品 JSON 已参与处方输入哈希。

`VERSIONED` 表示本轮所支持的字段已结构化，不代表处方医学审核通过。当前唯一规则仍只按相同 medicationId 判断重复，尚不做跨药品成分重复、剂量上限或相互作用判断。

## 4. 接口与调试

需已登录，并携带现有租户/工作机构/科室上下文。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET / POST | `/api/platform/master-data/medication-ingredients` | 查询/建立本院成分；写操作需要 MASTER_DATA.MANAGE |
| GET / PUT | `/api/platform/master-data/medications/{id}/composition` | 查询/保存成分与含量，revision 原样回传，首次为空 |
| GET | `/api/platform/master-data/medications/{id}/semantic-history` | 最近 100 条药品版本记录 |
| GET | `/api/platform/master-data/clinical-semantics/impact?kind=MEDICATION&conceptId={id}` | 当前工作范围医嘱、基础规则集引用及覆盖范围 |
| POST | `/api/encounters/{encounterId}/prescriptions/{prescriptionId}/safety-evaluations` | 对已保存处方进行独立 SHADOW 评价 |
| GET | 上述评价路径加 `/{evaluationId}` | 读取历史评价，校验租户、处方归属和机构/科室范围 |

影响分析由各模块通过公开贡献接口查询本模块事实。支持药品、途径、频次在当前科室的 DRAFT/ACTIVE 使用计数。模板没有统一公共引用查询、单位没有在用索引时明确返回 UNAVAILABLE；不能把尚未覆盖解释为“没有影响”。规则分析仅覆盖当前基础规则集。

旁路接口用于当前业务联调，还未加入医生端面板、自动开方触发或提交门禁。评价输入来自已提交的数据库记录，持久化沿用 QMED-1 的独立事务。

## 5. 数据库与兼容

- 已有 `V1_43_0` 保持不变。
- 同事的 `V1_44_0` 建立用药评价基础表。
- 新增 `V1_45_0` 建立语义版本记录表，提供 PostgreSQL/H2 与 Oracle 脚本及物理表映射。
- 不清理现有业务记录；不伪造旧医嘱版本，不推断真实成分和药学结论。
- 验证测试使用隔离 test/H2 随机库；人工环境仍使用 oracle-local。

## 6. 验证项目

- 单位同维度换算、包装单位排除、PRN/ONCE/日历语义的不可计算表达。
- 显示变化不改变语义版本；强度、频次配置变化改变版本；历史内容不被覆盖。
- 复方浓度、空含量、未知单位、过期页面冲突、租户隔离和业务回滚。
- 已保存处方 → SHADOW → 评价及提示落库；修改主数据后重新评价旧处方，输入哈希仍一致；评价不改变处方状态和库存。
- 门诊标准目录到收费/发药/退药/退款，以及住院医嘱执行回归。
- 成分维护页面保存失败后保留输入，重试使用原精确 revision。
