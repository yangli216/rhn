- 评估日期：2026-09-15

## 2. 实施前必须补齐的约束

### 2.1 门禁要覆盖所有生效入口，并区分皮试阶段

总体方案第 11 节把门禁放到 `PrescriptionService.submit()` 库存冻结前，位置正确。但当前 `MedicationRequestService.create()` 在未关联处方时会直接创建 ACTIVE 请求（约第 229 行），对应独立的药品请求创建 API。只改处方 submit 会使该路径无法获得完整的新评价保障。

应在 QMED-0A 盘点直接开立、批量分方、住院开立等生效入口，明确首期范围。范围内的每个入口均须进入公共门禁；范围外入口明确保留原安全行为，不宣称已由新引擎覆盖。

此外，`TreatmentExecutionService` 第 296 行起、`TreatmentExecutionTask` 第 60 行起已有执行前皮试判断。路线图将 Skin Test Requirement 列为迁移对象，但应明确：开立阶段识别皮试要求/豁免，执行阶段仍验证结果、阳性和适用性。不能把“尚未做皮试”一律提前变成不能开处方，也不能因开立检查通过就撤掉执行门禁。

### 2.2 评价失效条件不能只看处方头 revision

路线图第 5 节已有 revision、inputHash 和阻断证据独立持久化要求，方向正确，但并发和时效协议尚未落细。

现有药品请求独立新增/取消，处方头 revision 不能单独代表全部子项变化。过敏等事实也可能在检查后变化；当前 `AllergyDirectory.AllergySnapshot` 未暴露事实版本/有效时间。

实施时需明确：

- 对有效药品项、各项 revision、临床事实、标准语义及机构策略构造规范化快照和稳定 hash；明确排序、数值、单位、空值、时区的规范。
- 增删改子项与 submit 使用同一并发控制协议，确保最终校验与库存冻结/激活之间不能插入未检查的变化。
- 定义检查有效期、事实变化、规则紧急撤回后的重评策略；旧处方快照用于历史解释，提交时的事实新鲜度另行校验。
- Override 绑定 tenant、机构权限、操作者、evaluation、finding、规则版本和处方版本，防止跨评价复用。
- 延续文档已提出的事务隔离要求，验证 BLOCK 后审计仍存在，并覆盖重复提交的幂等性。

### 2.3 剂量计算需要成分与给药方案，不能仅靠单位换算因子

路线图第 2.2 节的 dimension/canonicalUnit/conversionFactor 可支持 g 与 mg 等同维度换算，但不足以支持完整剂量规则。

现有 Medication 的单组 strengthValue/strengthUnit 不能完整表达复方多成分及每成分强度。应增加明确的成分强度分子/分母、剂型和必要的浓度信息。片、支、瓶转换成 mg 需要该药品的已验证强度或浓度；mL 与 mg、IU 与质量均不能使用全局固定系数。

`mg/kg/day` 是依赖体重和给药计划的剂量表达。PRN 缺少最大频次时不能得到确定日剂量，Q8H 的计算也要定义统计窗口。首期限制到语义完整的简单剂型、固定频次和确定性单位转换；无法计算时显式报告，不得按 0 或默认剂量放行。

复用现有频次快照，但需区分数据库乐观锁 revision 与可长期引用的不可变语义版本；两者不能混用。

### 2.4 “整张处方”是必要范围，但不等于患者全部用药

总体方案第 2.1 节要求整张处方检查，能够改善逐药检查的盲区。但现有 `batchOrder()` 会自动分方；DDI、重复治疗和总日剂量可能跨越多张处方、长期有效医嘱及院外用药。

首期可明确只承诺本张处方的确定性规则，并在评价中记录覆盖范围。进入 DDI/总日剂量等规则前，应定义同次就诊、活动用药时间窗、停药排除、院外用药可信度及缺失数据策略，并通过 Clinical 公共快照提供输入。不能把单张处方 PASS 显示为患者总体用药安全结论。

### 2.5 同时保存“临床动作”和“执行完整性”

路线图第 3.3 节列出了 BLOCK、REQUIRE_OVERRIDE、WARN 的优先级，以及输入缺失时 UNAVAILABLE，但缺少它们同时发生时的组合结果。例如一条规则 BLOCK、另一条超时，不能丢失已知阻断，也不能隐藏检查不完整。

建议分别保存 `decision` 与 `executionStatus`，逐条记录成功、失败、跳过及原因；只有必需规则成功执行、覆盖范围满足且无风险时才可 PASS。定义每类规则/场景的超时、降级、人工处理路径和验收矩阵。同步延迟、最大规则量、处方药品数及批量取数要求也应进入验收，数值由首轮基准测试确定。

### 2.6 首期就需要可复现的规则集清单和回滚机制

总体方案第 13 节把 `quality_rule_set` 放在后续，但第一阶段 Evaluation 已要求 ruleSetVersion。可以暂缓独立表或管理界面，不能暂缓不可变的规则集发布清单。

一次评价必须固定规则清单、各规则版本、参数/知识版本、机构适用范围以及 Java 实现的构建标识。否则即使记录了 ruleCode/version，代码升级或运行中发布仍可能产生不可复现结果。早期可以使用随构建发布的受治理清单，无需先做完整动态发布平台。

补充原子发布、机构灰度、停用/紧急撤回和回退策略；已绑定旧规则的待提交评价如何处理，需与第 2.2 节一致。

### 2.7 提前建立药师反馈，落实审核资源

路线图把完整药师反馈放在 QMED-6、AI 工厂之后，但“第一可演示闭环”已要求药师查看 Finding 和医生处理结果。建议将最小展示和反馈关联提前到 QMED-3，QMED-6 保留分析看板和效果指标扩展。

ADR 已明确缺少完整药学团队。技术可以支持候选抽取与审阅提效，但不能替代合格的临床/药学审核责任。新增高风险规则启用前，需明确实际审核人、授权、证据许可及维护安排。审核资源不足时，首期优先迁移既有已认可规则，新增知识保持候选或经过批准的提示级范围，不以 AI confidence 代替专业审核。

## 3. 建议的首期边界与顺序

1. **QMED-0A 盘点和测试基线**：确认已有模型、所有生效入口、首期适用场景、数据缺失比例，修复下述 403 测试失败。
2. **最小语义基线与 Quality 骨架**：复用频次/途径快照，增加必要的不可变版本、发布清单、Evaluation/Finding 和公开 Port。仅建设首条规则所需语义，无需等待全量成分图谱或全字典治理完成。
3. **一条纵向规则**：可从现有抗菌药门诊限制开始，或以 WARN 验证同药重复检查；先 Shadow，保存证据和差异。相同药品多行未必是不合理重复，应考虑疗程、分次和适用策略。
4. **最终门禁和最小药师闭环**：检查、处理、提交、并发失效、审计保留、库存冻结、药师查看连通后，再逐条迁移现有规则。
5. **知识扩展与 AI 工厂**：用一小批有许可、有审核负责人的药学来源验证抽取和发布流程；剂量/年龄/DDI 按各自数据就绪程度推进，高级肝肾/QT 等规则继续等待事实平台成熟。

先完成前三步可验证工程可行性；完成第四步并通过相应验收，才具备首期受控试用条件。当前信息不足以承诺完整平台工期或临床覆盖率。
