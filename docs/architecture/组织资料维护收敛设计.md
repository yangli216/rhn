# 组织资料维护收敛设计

状态：已废弃（2026-10-19）。阶段一前端实现经用户查看后撤回，改为把组织与人员拆成两个独立功能重新开发，见 [组织与人员拆分重建设计](组织与人员拆分重建设计.md)。本文的字段取舍分析仍可参考。

适用范围：设置 → 组织与人员 → 组织架构 →「资料维护」。人员任职页签、调岗/离职流程不在本次重做范围。

## 1. 结论

保留后端领域模型和人员流转，重做「资料维护」前端，收敛资料模型。不整体废弃。

| 部分 | 处理 | 理由 |
| --- | --- | --- |
| 机构/科室/任职/聘用领域、停用影响校验、乐观锁、变更快照 | 保留 | 与业务规则一致，且被执行科室路由、药房场所同步、开立校验等运行模块消费 |
| 调岗/离职/入职弹窗 | 保留，只做规范对齐 | 流程已符合业务，无需重做 |
| 资料维护页（`OrganizationProfileEditor` 等） | 重做 | 把 6 类档案平铺成一张长表，每条记录重复生效/结束/状态；UI 违反共享组件规范；多数档案无运行消费者 |
| 6 类资料档案（能力/标识/联系/地址/负责人/协作） | 收敛，不是全保留 | 见第 3 节：代码核查显示 `*ProfileStore` / `*ProfileView` 只在 organization 模块内被引用，其他运行模块不读取这些档案 |

## 2. 现状问题

### 2.1 UI 与规范不符（来自截图与源码）

1. 日期用原生 `<input type="date">`（`OrganizationProfileEditor.tsx` 的 `text()` 辅助函数），未用共享 DatePicker，所以样式和高度与下拉框不一致。
2. 提示文字加「含待生效…」复选框被塞进 `ui-query-filters`（本是列表查询栏样式），复选框文案被挤成三行小字。
3. 「虚拟组织」是带边框卡片里的复选框，与相邻输入框高度、样式不同；应使用共享 Switch。
4. 组织代码只读框是灰底输入，其他是白底；只读信息应作只读展示而不是禁用输入。
5. 入口重复：顶部「编辑资料」、「资料维护」页签、底部「返回人员与任职」指向同一处；顶部概览条和表单重复展示类型/性质；组织说明在提示条和文本框重复出现。
6. 底部固定栏暴露「重新加载资料选项」（字典加载细节），不应让用户操作。
7. 样式位置错乱：`.master-form--unit`、`.organization-profile-editor` 定义在 `dashboard-analytics.css`，窄屏断点在 `treatment-skintest.css`；PC-only 约定下不应有移动断点。
8. 地址分区要手工输入国家/省/市/区行政区划代码，未使用共享 GridAddressInput。

### 2.2 维护信息冗余

- 每条资料记录都带 生效日期 / 结束日期 / 记录状态 / 展示顺序 / 主要记录，普通用户无需理解。
- 服务能力文档已写明「当前作为能力登记；不自动授予业务操作权限」，目前没有运行消费者。
- 协作关系、机构标识的签发机构/体系 URI/确认结果同样没有消费者。

## 3. 字段取舍清单

判定标准：必须是系统运行依据，或法定/业务必须登记；否则不在日常维护界面出现。

### 3.1 基本信息（机构 / 科室）

| 字段 | 决定 | 新处理 |
| --- | --- | --- |
| 组织代码 | 保留 | 创建时填写；之后只读展示 |
| 名称 | 保留 | 必填 |
| 组织类别 | 保留 | 只读展示（创建后不变） |
| 组织结构类型 | 保留 | 机构类型 / 科室类型，必填，字典下拉 |
| 科室业务属性、具体科室类型 | 保留，突出 | 科室的核心字段：属性决定排班/转科/护理识别，类型决定检验检查路由和药房库存场所；放在表单最前并给一句运行用途提示 |
| 上级组织 | 保留 | 树选择，必填规则不变 |
| 虚拟组织 | 保留 | Switch；运行中被执行科室路由排除，说明其作用 |
| 时区 | 保留，降级 | 仅法定机构显示，默认 Asia/Shanghai，下拉选择（统计/体温单等读取） |
| 简称 | 保留，可选 | 一行，不强调 |
| 机构性质 | 待确认 | 当前无运行消费者；若仅用于展示可折叠到「更多」 |
| 同级排序 | 移出表单 | 在左侧树内上移/下移调整，字段保留 |
| 生效日期 | 移出表单 | 新建默认当天；编辑只读展示；需要计划启用日期时放「更多设置」 |
| 结束日期 | 移出表单 | 由「停用」操作承担：停用对话框中填写停用日期，并展示现有的依赖影响检查 |
| 组织说明 | 保留，可选 | 只出现一次 |

注意：生效/结束日期在后端是运行条件（`ServiceRequestService`、`ServiceExecutionDepartmentPolicy`、药房同步都判断有效期），所以后端字段和规则不动，只改变维护方式。

### 3.2 资质与联系（仅机构；科室只保留联系方式和负责人）

| 分区 | 决定 | 新处理 |
| --- | --- | --- |
| 机构标识（统一社会信用代码、执业许可证号等） | 保留，仅法定机构 | 行内表格：标识类型 + 编码；体系 URI 由类型字典推导；去掉签发机构和确认结果 |
| 地址 | 保留，仅法定机构 | 一个地址：GridAddressInput + 详细地址；去掉手填行政区划代码 |
| 联系方式 | 保留 | 行内表格：类型 + 内容 + 主要联系；使用场景用默认值，不展示排序 |
| 负责人 | 保留 | 行内表格：负责人 + 职责类型；默认内部任职人员，「外部负责人」用开关切换为姓名输入；有效期仍由后端按任职覆盖规则校验 |
| 服务能力 | 保留，简化，待确认 | 行内表格：能力类型 + 范围说明 + 确认结果；资质依据编码放行展开项。运行规则页继续说明其不授予权限 |
| 协作关系 | 从维护界面移除，待确认 | 无消费者。数据和接口保留，仅在变更记录里可见；有转诊/协作场景消费它时再恢复 |

所有分区的统一规则：
- 去掉每行的 生效/结束/记录状态/展示顺序。新增记录生效日默认当天，结束日为空。
- 「作废」改为行内「移除」操作并确认；后端仍按作废保留历史，不物理删除。
- 「含待生效、已结束与作废」开关取消；历史可在「变更记录」页签查看。

## 4. 新页面布局

模板：`MasterDetailPage`（左树右详情，不变）。详情区页签调整：

```
[人员与任职]  [基本信息]  [资质与联系]  [运行规则]  [变更记录]
```

- 页头操作：只保留「新增科室」「更多（停用/恢复）」。删除「编辑资料」按钮，因为它与页签重复。
- 概览条：保留任职人数、状态；类型/性质不再重复展示。
- 基本信息：表单分两组，「基本信息」「运行属性」，3 列，使用 FormField + Select/DictionarySelect/FormSelect/Switch；只有一个固定底部「保存」。
- 资质与联系：每个分区一个 PanelHead + 共享 EditableTable，分区标题右侧「新增」。法定机构显示全部分区，科室只显示联系方式、负责人、服务能力。底部「保存」固定。
- 两个页签各自保存，各自带 expectedRevision；有未保存修改时切换页签提示。（需确认后端维护接口能否只提交该页签的变更，见第 5 节。）
- 取消「重新加载资料选项」，字典加载失败时在分区内给重试提示。
- 样式迁移：表单样式从 `dashboard-analytics.css` 移到组织页自己的样式文件，只用语义令牌，不覆盖共享控件外观。

## 5. 迁移与兼容影响

| 项目 | 影响 |
| --- | --- |
| 数据库 | 阶段一无结构变更。所有资料表保留；被隐藏的协作关系数据保留 |
| 后端接口 | 阶段一不改。阶段二让资料项的 `validFrom` 可省略（缺省为当天或所引任职起始日）、机构标识 `identifierSystem` 缺省由类型推导；这是向后兼容的放宽，需要更新 OpenAPI 和 generated.ts |
| 权限 | 不变，仍用 IAM.MANAGE |
| 存量数据 | 已有的已结束/作废/待生效记录不丢失，在变更记录和只读历史中可见；已有的带有效期记录保存时保持原值，不被默认值覆盖 |
| 前端测试 | `OrganizationPersonnelManagement.test.tsx`（1483 行）中资料编辑相关用例需要重写；`organizationProfileForm.ts`、`OrganizationProfileEditor.tsx`、`OrganizationProfileRecords.tsx` 重构 |
| 文档 | 更新 `docs/ai/organization-personnel.md` 的「维护闭环」；删除不再需要的 ui-policy 基线条目 |
| 验证 | `./scripts/verify-scope.sh organization`；阶段二涉及契约则加 `api-contract`；1280/1440/1920 人工视觉验收 |

### 分阶段

1. 阶段一（仅前端）：基本信息/资质与联系两个页签、字段取舍、共享组件替换、样式整理。不改后端。
2. 阶段二（后端小改）：日期/标识体系缺省值、确认只提交变更项的接口行为、更新契约。
3. 阶段三：人员任职页签和入职/调岗/离职弹窗按 UI 规范做一轮对齐检查，同样先走小范围整改；本轮尚未逐项检查该页，发现问题再单列。

## 6. 需要你确认的取舍

1. 协作关系：从维护界面移除（推荐），还是保留？
2. 服务能力：简化保留（推荐），还是先整体隐藏到有消费者再恢复？
3. 机构性质、简称：保留为可选并折叠，还是去掉？
4. 生效/结束日期：按「新建默认当天、停用时填停用日期」处理，是否符合你的运营习惯？是否存在需要提前录入的未来启用机构/科室？
5. 两个页签各自保存，还是仍保持一次保存？
