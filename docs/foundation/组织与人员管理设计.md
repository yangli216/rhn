# 组织与人员管理设计

## 1. 最新审计结论

以“表结构梳理”最新版 `nextgen-core.dbml` 和组织人员差异报告为权威依据，机构与科室是两个独立聚合：机构维护法人及医疗机构主体，科室维护机构内部的业务、行政、医技和护理单元。二者各有自己的层级、状态、合并关系、联系方式、业务关系、能力和负责人，不再把科室保存为机构表中的一种节点。

人员继续拆分为从业人员、聘用、标准岗位和任职。聘用关联机构，任职必须同时保存机构和科室，便于权限、参数、审计和临床业务直接取得明确上下文，不通过组织树反推机构。

## 2. 权威关系

```text
租户
 ├─ 机构树：上级机构 → 下级机构
 │    └─ 科室树：机构 → 一级科室 → 下级科室
 └─ 从业人员 ──< 聘用 >── 机构
                      └──< 任职 >── 机构 + 科室 + 标准岗位
```

| 目标逻辑表 | 当前物理表 | 责任 |
|---|---|---|
| `sys.organization` | `organizations` | 医疗机构主体及机构上下级关系 |
| `sys.department` | `departments` | 机构内科室及科室上下级关系 |
| `sys.practitioner` | `practitioners` | 与账号、机构无关的人员主档 |
| `sys.employment` | `employments` | 人员与机构之间的聘用关系 |
| `sys.position` | `positions` | 租户内可复用的标准岗位 |
| `sys.assignment` | `staff_assignments` | 某段聘用下的机构、科室和岗位任职 |
| 机构档案组件 | `organization_*` | 机构标识、联系、地址、机构关系、能力和负责人 |
| 科室档案组件 | `department_*` | 科室联系、科室关系、能力和负责人 |

`GET /organization-units` 仅将机构和科室组合成便于管理界面展示的兼容树。新建、修改、档案和任职接口会按节点类型写入各自权威表；任何新业务都不得把该兼容树当作统一物理模型。

## 3. 机构与科室边界

机构承担主体资格和对外治理信息：多标识、执业/通信地址、机构间关系、机构级服务能力，以及法定代表人、主要负责人、业务负责人和安全负责人。

科室承担机构内部运行信息：具体科室类型、科室属性、虚拟标志、科室上下级、科室间业务管理/临床支持/协作/转诊关系、科室能力，以及科主任、副主任、护士长、业务负责人和安全负责人。科室没有机构标识和机构地址；服务位置后续由 `location` 单独表达。

机构和科室均保留有效期、状态、合并去向、排序、审计字段和乐观锁版本。变更快照表属于后续治理能力，不阻塞当前业务主流程。

## 4. 核心约束

1. 所有主键使用 Snowflake `BIGINT`，API 和前端一律按十进制字符串处理。
2. 所有关系通过 `(tenant_id, id)` 复合外键防止跨租户串联。
3. 机构上级只能是同租户机构；科室上级只能是同一机构内的科室，两棵树都禁止自引用和循环。
4. 科室代码在机构内唯一；相同代码允许在不同机构复用。
5. 聘用只能指向机构；任职中的机构必须与聘用机构一致，科室必须属于该机构。
6. 同一人员在重叠有效期内最多存在一个启用的主聘用。
7. 同一聘用在同一科室、重叠有效期内最多存在一个启用的主任职。
8. 任职有效期必须位于聘用有效期内，停用人员、聘用、科室或岗位不能建立新的下游关系。
9. 可修改聚合使用 `revision` 乐观锁，编码创建后不修改、不复用。
10. 机构和科室责任记录可关联当前任职，也可登记尚未建档的外部负责人，但两者只能取其一；科室责任所关联任职必须属于该科室。
11. 药库、药房和科室库存点必须绑定一个真实科室；只有纯路由或汇总用途的 `VIRTUAL` 库存站点允许不绑定科室。
12. 审方、配药、发药、复核和退药确认必须使用 `PHARMACY` 标准岗位任职，任职科室、当前工作科室与库存站点所属科室必须一致。

### 4.1 推荐药学组织结构

```text
医疗机构
└─ 药学部（MED_PHARMACY）
   ├─ 中心药库（MED_PHARMACY_WAREHOUSE） → WAREHOUSE / MIXED
   ├─ 门诊药房（MED_PHARMACY_OUTPATIENT） → PHARMACY / OUTPATIENT
   ├─ 住院药房（MED_PHARMACY_INPATIENT） → PHARMACY / INPATIENT
   └─ 中药房（MED_PHARMACY_TCM） → PHARMACY / MIXED
```

急诊药房和制剂室按机构实际业务选建，不要求所有机构机械复制。库存站点是科室下的业务执行与库存核算对象，不替代科室；窗口、货位、库区等更细粒度物理位置继续由站点、货位及后续 `location` 模型表达。

## 5. 字典与枚举

机构类别、机构结构类型、状态、人员性别、人员状态、聘用类型、岗位类型和任职类型继续使用平台系统枚举投影。具体科室类型改用独立普通字典 `DEPT_TYPE`，覆盖国家诊疗科目以及常见行政、医疗辅助、护理、跨学科和自定义类型。V35 在原有 `MED_PHARMACY` 基础上补充 `MED_PHARMACY_WAREHOUSE`、`MED_PHARMACY_OUTPATIENT`、`MED_PHARMACY_INPATIENT`、`MED_PHARMACY_EMERGENCY`、`MED_PHARMACY_TCM` 和 `MED_PHARMACY_PREPARATION`，使药学部、药库、不同服务场景药房和制剂室都能以正式科室建档，而不是继续使用“其他”类型或另建一棵孤立目录。

科室字典统一为：

- `DEPT_TYPE`：具体科室类型；
- `DEPT_PROPERTY`：临床、行政、医技、护理、其他；
- `DEPT_RELATION_TYPE`：业务管理、临床支持、协作、转诊；
- `DEPT_CAPABILITY_TYPE`：科室能力类型；
- `DEPT_RESPONSIBILITY_TYPE`：科主任、副主任、护士长、业务负责人、安全负责人。

机构继续使用 `ORG_*` 字典。`ORG_RESPONSIBILITY_TYPE` 只保留机构责任类型，不能再保存科主任或护士长。API 响应中的 `sdXxx` 字段继续由字典翻译底座批量补充 `sdXxxText`。

## 6. 兼容迁移策略

V13 将旧 `organizations` 表中 `ORG_UNIT` 数据按原 ID 迁移到 `departments`，同步迁移可归属的联系、关系、能力和负责人，并为任职补齐 `department_id` 和真实机构 `organization_id`。保留原 ID 可以避免外围引用和历史业务数据整体换号。

旧 `ORG_UNIT` 行暂时作为只读兼容影子保留，应用查询机构时必须只读取法定机构，新科室写入只进入 `departments`。待所有存量模块和外围引用切换完成后，再通过单独、可审计的数据清理版本移除影子数据，不能在本轮迁移中直接删除。

## 7. 当前实现范围

当前已覆盖机构与科室独立建模、组合树浏览、科室完整属性、机构/科室档案组件、人员、标准岗位、聘用、任职、状态维护、有效期与重叠校验，以及字典文本翻译。权限和参数目录对科室 ID 的解析改为读取 `departments`，就诊、临床文档和用户角色范围的科室外键随迁移切换到科室表。V35 同步提供药学组织演示基线：药学部、中心药库、门诊药房、住院药房、中药房，三个药学标准岗位、示范药师任职、科室工作上下文授权和四个对应库存站点。

以下能力保留在设计边界内，但暂不提前建设空壳：

- 机构和科室档案组件的修改、停用和批量导入；
- 机构/科室追加式变更快照和合并拆分工作流；
- 诊室、病区、床位组、窗口等 `location` 服务位置；
- 执业证书及其他 `credential` 资质；
- 持续数据质量扫描和由任职驱动的岗位权限建议。

### 7.1 新增人员与入职配置

人员管理页的“保存并完成入职配置”调用 `POST /api/platform/practitioners/onboarding`，机构、科室、岗位和聘用日期均为必填。服务端在同一事务中建立人员、正式主聘用、主任职与 100% 工作量配置；这些固定业务选项在表单中明确展示。聘用和任职代码分别由持久化人员 ID 生成 `EMP_{id}`、`ASN_{id}`，不拼接可能已达长度上限的人员代码。

停用或不存在的机构、科室、岗位以及其他任一步校验失败，均回滚本次全部记录。前端不再串行调用三个独立创建接口并吞掉后续异常；仅在返回的三类记录及其关联与本次提交一致后显示成功。失败时保留输入，用户清空聘用日期后禁止提交，不在保存时补成今天。

此接口尚无请求码幂等重放协议。网络中断或响应不完整只能说明结果未确认，不能据此宣称未落库；页面提供重新核实目录入口，用户应先核实记录。重复人员代码仍由服务端拒绝。原有单独创建人员、聘用、任职接口继续用于各自独立的维护场景。

### 7.2 目录与档案的未确认状态

组织、人员、岗位、任职查询在进入页面前校验必要字段、状态、版本和层级；人员详情必须包含完整的聘用与任职数组，且人员身份、聘用归属、任职关联和有效期一致。缺失数组不能按空数组展示，只有成功返回且校验通过的空数组才能显示“暂无”。

请求失败和重新加载期间不展示旧缓存为当前事实，不显示零数量或无记录结论，并提供常驻重试入口。人员编辑与聘用、任职表单在依赖数据未确认时保留草稿、禁止保存。查询缓存按 API 实例隔离，避免切换工作上下文后继续使用上一实例的目录或详情。

组织页面展示“任职记录数”，不把历史、停用或同一人员的多条任职记录计为当前在岗人数。概览只展示唯一一条明确标记为主要的关系；存在多条时提示查看明细，无主要关系时不取第一条替代。岗位和聘用关系不等同于职称、执业注册或处方资质。

### 7.3 人员维护的保存确认

人员编辑、停启用、岗位创建、聘用和任职创建均校验服务端返回的完整记录。编辑与停启用必须返回同一人员、更新后的版本以及本次要求的字段和目标状态；岗位、聘用、任职必须匹配本次提交的代码、类型、关联 ID、标志、日期及可选内容。创建不能用已知旧记录冒充新结果，未指定的工作量也不能擅自补为 100%。

响应缺项、关联错人、旧版本或内容不一致时显示“结果未确认”，保留表单并提供重新核实入口。保存期间禁止重复提交和关闭；切换 API 上下文后忽略旧请求的成功或错误反馈。停启用重试保留原目标状态与原版本，不能依据刷新后的状态重新计算相反动作。这些接口没有幂等重放协议，结果未确认时应先核实目录；既有版本冲突与代码重复校验仍由服务端执行。

### 7.4 治理档案按登记事实展示

机构治理档案必须包含标识、联系、地址、关系、能力和负责人六类数组；科室治理档案必须包含联系、关系、能力和负责人四类数组。查询结果需与所选对象的 ID、代码和版本匹配，并校验每条记录的类型、标志、状态和有效期。缺项、重复记录或错误对象不能降级为空档案。科室性质在后端为可选字段，返回 `null` 时保持未维护状态，不生成默认性质。

页面逐条显示联系方式、地址和负责人及其类型、主要标志、状态、有效期，不再取第一条联系方式当作电话、第一条地址当作执业地址，或只显示一个负责人。历史和停用记录保留状态标识，不推断为当前有效业务资格；服务能力与机构标识同时展示核验状态。

刷新期间隐藏旧档案内容，读取失败使用常驻提示与重试入口。已打开的扩展信息表单绑定原组织，查询未确认时保留草稿并禁止提交，不能随着目录选择变化把草稿转存到另一个组织。

### 7.5 扩展信息新增结果确认

保存标识、联系方式、地址、关系、服务能力或负责人后，返回档案必须仍属于原对象、保留此前已确认的记录，并包含恰好一条与本次提交字段一致的新增记录。仅返回旧档案、记录缺项、对象不符或字段不一致时，不关闭表单、不显示成功。科室关系按 `targetDepartmentId` 核对，机构关系按 `targetOrganizationId` 核对；科室不支持标识和地址写入。

保存中锁定表单与关闭操作，迟到响应不能关闭其他表单或影响已切换的 API 上下文、组织节点。失败时提供常驻提示与重新核实入口；若查询已发现完全一致的记录，阻止重复创建并提示核实，不把它冒充本次重试的成功响应。接口仍没有请求码幂等重放协议。

地址和服务能力的后端模型没有“主要记录”标志，因此其表单不再显示该选项。其余四类记录按真实布尔值提交并核验返回结果。

### 7.6 组织节点保存确认

机构、科室创建与编辑需核对回执的完整字段、节点身份、归属、类型、日期、排序和标志；创建必须是新 ID，编辑与停启用必须推进原版本。停启用不能顺带修改名称、归属或属性。异常回执与网络失败均保留草稿、提供常驻核实入口，不显示成功；保存期间禁止重复提交和关闭，切换上下文或所选节点后忽略旧响应。重试状态操作沿用原版本和原目标，不因刷新后已停用就反向启用。

兼容树中一级科室的 `parentId` 为所属机构；提交科室编辑时转换为未设上级科室，真实科室父节点保持原 ID，禁止移动到其他机构。创建重试前若已查到同一代码（科室按所属机构区分），阻止重复请求并提示核实。

科室不提供后端不存储的时区和独立结构类型输入；结构类型按后端的业务属性投影提交，业务属性与具体科室类型须明确选择。编辑机构的空时区保持为空，不擅自补为上海时区。只有通过核验的服务端结果可触发成功反馈；这些接口仍不提供请求码幂等重放。

### 7.7 扩展资料草稿与字典事实

机构标识、联系方式、地址、关系、能力和负责人分别保存表单草稿；切换类别不能把标识 URI、详细地址、关系说明或字典代码带入其他类别。标识体系与核验状态须由用户明确填写或选择，不预填自造标识体系。

组织字典加载需校验数组、编码、名称、排序与编码唯一性。失败、刷新中及返回结构无效时不使用缓存作为当前选项；只有成功读取的空数组可表示当前无可用选项。扩展资料只依赖本类别所需的字典，提供常驻失败/空选项提示与重新加载入口，保留已输入草稿。提交前再次核对所选编码仍存在于当前字典，不能用已经移除的旧值保存。

人员证书、医保代码、CA 资料、身份证与电话等尚未接入读取的字段，显示“尚未接入”，不能以“未维护”暗示已经查询并确认无记录。主要聘用、人员代码和性别仍显示真实接口数据。

### 7.8 组织人员表单选项确认

系统枚举读取需验证定义和条目的编码、名称、说明、排序及编码唯一性。响应缺项、失败或刷新中，不再由前端补出性别等枚举选项，也不使用旧缓存代表当前可用类型。

人员性别、岗位类型、聘用类型和任职类型分别检查其实际依赖；缺少某种定义或定义没有条目时，相应表单保留草稿、禁止保存并提供重新加载入口。提交前检查所选代码仍存在于已确认的枚举中，预置值也不能绕过此检查。其他已确认的表单不因无关定义缺失而被禁用。

组织表单同时确认类别、机构结构类型和机构性质字典；机构性质允许不选择，但读取失败不能视为空字典。科室需确认真实业务属性与具体科室类型字典，原值失效时要求重新选择。表单刷新选项不覆盖已有草稿。

## 8. 回归基线

核心回归必须覆盖：创建机构和多级科室、校验科室归属与类型、分别维护机构和科室档案、创建人员与岗位、建立主聘用和科室主任职、返回机构与科室双重任职上下文、字典文本自动翻译，以及主聘用/主任职有效期重叠冲突。药事回归还必须覆盖库存站点科室必填、当前工作科室隔离和非药学岗位拒绝。后续业务模块只能引用明确的 `organization_id` 与 `department_id`，不得用单个“组织单元 ID”代替二者。

## 9. 多类型工作上下文

同一账号可以同时保留不同业务类型的活动上下文，但同一类型只能激活一个科室。当前稳定类型为：

- `CLINICAL`：诊疗类科室；内科、全科等多个有效任职在运行时只能选择一个；
- `PHARMACY`：药房调剂、审方与发药；
- `INVENTORY`：药库与库存管理；
