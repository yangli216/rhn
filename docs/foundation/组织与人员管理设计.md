# 组织与人员管理设计

## 1. 最新审计结论

以“表结构梳理”最新版 `nextgen-core.dbml` 和组织人员差异报告为权威依据，机构与科室是两个独立聚合：机构维护法人及医疗机构主体，科室维护机构内部的业务、行政、医技和护理单元。二者各有自己的层级、状态、合并关系、联系方式、业务关系、能力和负责人，不再把科室保存为机构表中的一种节点。

人员继续拆分为从业人员、聘用、标准岗位和任职。聘用关联机构，任职必须同时保存机构和科室，便于权限、参数、审计和临床业务直接取得明确上下文，不通过组织树反推机构。

## 2. 权威关系

```text
租户
 ├─ 机构树：上级机构 → 下级机构
 │    └─ 科室树：机构 → 一级科室 → 下级科室
 └─ 从业人员 ──< 聘用 >── 机构
                      └──< 任职 >── 机构 + 科室 + 标准岗位
```

| 目标逻辑表 | 当前物理表 | 责任 |
|---|---|---|
| `sys.organization` | `organizations` | 医疗机构主体及机构上下级关系 |
| `sys.department` | `departments` | 机构内科室及科室上下级关系 |
| `sys.practitioner` | `practitioners` | 与账号、机构无关的人员主档 |
| `sys.employment` | `employments` | 人员与机构之间的聘用关系 |
| `sys.position` | `positions` | 租户内可复用的标准岗位 |
| `sys.assignment` | `staff_assignments` | 某段聘用下的机构、科室和岗位任职 |
| 机构档案组件 | `organization_*` | 机构标识、联系、地址、机构关系、能力和负责人 |
| 科室档案组件 | `department_*` | 科室联系、科室关系、能力和负责人 |

`GET /organization-units` 仅将机构和科室组合成便于管理界面展示的兼容树。新建、修改、档案和任职接口会按节点类型写入各自权威表；任何新业务都不得把该兼容树当作统一物理模型。

## 3. 机构与科室边界

机构承担主体资格和对外治理信息：多标识、执业/通信地址、机构间关系、机构级服务能力，以及法定代表人、主要负责人、业务负责人和安全负责人。

科室承担机构内部运行信息：具体科室类型、科室属性、虚拟标志、科室上下级、科室间业务管理/临床支持/协作/转诊关系、科室能力，以及科主任、副主任、护士长、业务负责人和安全负责人。科室没有机构标识和机构地址；服务位置后续由 `location` 单独表达。

机构和科室均保留有效期、状态、合并去向、排序、审计字段和乐观锁版本。变更快照表属于后续治理能力，不阻塞当前业务主流程。

## 4. 核心约束

1. 所有主键使用 Snowflake `BIGINT`，API 和前端一律按十进制字符串处理。
2. 所有关系通过 `(tenant_id, id)` 复合外键防止跨租户串联。
3. 机构上级只能是同租户机构；科室上级只能是同一机构内的科室，两棵树都禁止自引用和循环。
4. 科室代码在机构内唯一；相同代码允许在不同机构复用。
5. 聘用只能指向机构；任职中的机构必须与聘用机构一致，科室必须属于该机构。
6. 同一人员在重叠有效期内最多存在一个启用的主聘用。
7. 同一聘用在同一科室、重叠有效期内最多存在一个启用的主任职。
8. 任职有效期必须位于聘用有效期内，停用人员、聘用、科室或岗位不能建立新的下游关系。
9. 可修改聚合使用 `revision` 乐观锁，编码创建后不修改、不复用。
10. 机构和科室责任记录可关联当前任职，也可登记尚未建档的外部负责人，但两者只能取其一；科室责任所关联任职必须属于该科室。
11. 药库、药房和科室库存点必须绑定一个真实科室；只有纯路由或汇总用途的 `VIRTUAL` 库存站点允许不绑定科室。
12. 审方、配药、发药、复核和退药确认必须使用 `PHARMACY` 标准岗位任职，任职科室、当前工作科室与库存站点所属科室必须一致。

### 4.1 推荐药学组织结构

```text
医疗机构
└─ 药学部（MED_PHARMACY）
   ├─ 中心药库（MED_PHARMACY_WAREHOUSE） → WAREHOUSE / MIXED
   ├─ 门诊药房（MED_PHARMACY_OUTPATIENT） → PHARMACY / OUTPATIENT
   ├─ 住院药房（MED_PHARMACY_INPATIENT） → PHARMACY / INPATIENT
   └─ 中药房（MED_PHARMACY_TCM） → PHARMACY / MIXED
```

急诊药房和制剂室按机构实际业务选建，不要求所有机构机械复制。库存站点是科室下的业务执行与库存核算对象，不替代科室；窗口、货位、库区等更细粒度物理位置继续由站点、货位及后续 `location` 模型表达。

## 5. 字典与枚举

机构类别、机构结构类型、状态、人员性别、人员状态、聘用类型、岗位类型和任职类型继续使用平台系统枚举投影。具体科室类型改用独立普通字典 `DEPT_TYPE`，覆盖国家诊疗科目以及常见行政、医疗辅助、护理、跨学科和自定义类型。V35 在原有 `MED_PHARMACY` 基础上补充 `MED_PHARMACY_WAREHOUSE`、`MED_PHARMACY_OUTPATIENT`、`MED_PHARMACY_INPATIENT`、`MED_PHARMACY_EMERGENCY`、`MED_PHARMACY_TCM` 和 `MED_PHARMACY_PREPARATION`，使药学部、药库、不同服务场景药房和制剂室都能以正式科室建档，而不是继续使用“其他”类型或另建一棵孤立目录。

科室字典统一为：

- `DEPT_TYPE`：具体科室类型；
- `DEPT_PROPERTY`：临床、行政、医技、护理、其他；
- `DEPT_RELATION_TYPE`：业务管理、临床支持、协作、转诊；
- `DEPT_CAPABILITY_TYPE`：科室能力类型；
- `DEPT_RESPONSIBILITY_TYPE`：科主任、副主任、护士长、业务负责人、安全负责人。

机构继续使用 `ORG_*` 字典。`ORG_RESPONSIBILITY_TYPE` 只保留机构责任类型，不能再保存科主任或护士长。API 响应中的 `sdXxx` 字段继续由字典翻译底座批量补充 `sdXxxText`。

## 6. 兼容迁移策略

V13 将旧 `organizations` 表中 `ORG_UNIT` 数据按原 ID 迁移到 `departments`，同步迁移可归属的联系、关系、能力和负责人，并为任职补齐 `department_id` 和真实机构 `organization_id`。保留原 ID 可以避免外围引用和历史业务数据整体换号。

旧 `ORG_UNIT` 行暂时作为只读兼容影子保留，应用查询机构时必须只读取法定机构，新科室写入只进入 `departments`。待所有存量模块和外围引用切换完成后，再通过单独、可审计的数据清理版本移除影子数据，不能在本轮迁移中直接删除。

## 7. 当前实现范围

当前已覆盖机构与科室独立建模、组合树浏览、科室完整属性、机构/科室档案组件、人员、标准岗位、聘用、任职、状态维护、有效期与重叠校验，以及字典文本翻译。权限和参数目录对科室 ID 的解析改为读取 `departments`，就诊、临床文档和用户角色范围的科室外键随迁移切换到科室表。V35 同步提供药学组织演示基线：药学部、中心药库、门诊药房、住院药房、中药房，三个药学标准岗位、示范药师任职、科室工作上下文授权和四个对应库存站点。

以下能力保留在设计边界内，但暂不提前建设空壳：

- 机构和科室档案组件的修改、停用和批量导入；
- 机构/科室追加式变更快照和合并拆分工作流；
- 诊室、病区、床位组、窗口等 `location` 服务位置；
- 执业证书及其他 `credential` 资质；
- 持续数据质量扫描和由任职驱动的岗位权限建议。

## 8. 回归基线

核心回归必须覆盖：创建机构和多级科室、校验科室归属与类型、分别维护机构和科室档案、创建人员与岗位、建立主聘用和科室主任职、返回机构与科室双重任职上下文、字典文本自动翻译，以及主聘用/主任职有效期重叠冲突。药事回归还必须覆盖库存站点科室必填、当前工作科室隔离和非药学岗位拒绝。后续业务模块只能引用明确的 `organization_id` 与 `department_id`，不得用单个“组织单元 ID”代替二者。

## 9. 多类型工作上下文

同一账号可以同时保留不同业务类型的活动上下文，但同一类型只能激活一个科室。当前稳定类型为：

- `CLINICAL`：诊疗类科室；内科、全科等多个有效任职在运行时只能选择一个；
- `PHARMACY`：药房调剂、审方与发药；
- `INVENTORY`：药库与库存管理；
- `GENERAL`：暂未归入专门业务槽的综合上下文。

类型由服务端根据权威科室类型和属性投影，前端不得按科室名称猜测。工作门户为每种类型保存一个活动槽，模块请求使用独立的不可变 API 客户端携带对应机构和科室；切换诊疗科室只重建诊疗槽，不覆盖药房或库房槽。同一类型存在多个授权科室时保留上次选择，只有一个时自动进入。

该约束限制的是运行时活动上下文，不限制同一人员建立多条有效任职。所有写操作仍由后端校验请求科室、人员任职、岗位类型和业务对象归属，前端分槽不能替代权限门禁。
