# 门诊病历签署流程

## 目标与边界

门诊病历签署复用 `healthcore.clinicaldocument` 的不可覆盖版本和密码证据能力，并接入科室任务队列。它负责证明“谁在什么时间以作者身份确认了哪一版内容”，不在业务模块内实现具体密码厂商、个人证书或可信时间戳协议。

生产环境必须通过统一密码适配层接入合规签名和时间戳服务；开发环境生成的 JCA 证据仅用于验证状态机、原文绑定和失败关闭行为。

## 状态与门禁

1. 接诊记录保存后形成 `OUTPATIENT_NOTE` 的 `DRAFT` 当前版本，并为当前机构科室建立 `CLINICAL_DOCUMENT_SIGN` 待办。
2. 再次保存会新增不可覆盖版本，取消旧版本的开放待办，只保留最新版本待签署。
3. 签署前先验证当前版本的完整性证据；验证失败时不得签署。
4. 签署生成绑定文档、版本、模式和 `AUTHOR` 签署含义的不可否认证据，状态切换为 `SIGNED`，对应待办自动完成。
5. 通用任务接口不能人工完成签署待办，必须执行文档签署业务动作。
6. 完成就诊前必须存在已签署的当前门诊病历；缺少文档、仍为草稿或处于修订中均失败关闭。
7. 已签署版本不能直接覆盖。后续更正必须发起新版本修订并重新签署，历史签署证据保持不变。

## 接口契约

| 接口 | 用途 |
|---|---|
| `GET /api/clinical-documents?encounterId={encounterId}` | 按当前工作上下文查询本次就诊文档、当前内容和版本证据 |
| `POST /api/clinical-documents/{documentId}/sign` | 按当前业务版本签署；请求必须提供期望版本和签署含义 |
| `PUT /api/encounters/{encounterId}/clinical-record` | 保存接诊记录并生成新的待签署文档版本 |
| `POST /api/encounters/{encounterId}/complete` | 仅在当前门诊病历已签署时完成就诊 |

所有文档读取、签署和就诊完成操作均按租户、机构、科室工作上下文校验。前端不能以隐藏按钮代替后端门禁。

## PC 工作台规范

接诊工作区将病历编辑与正式签署分为两个面板。签署面板同时展示患者当前就诊下的主诉、血压、诊断、内容模式、当前版本、版本历史、摘要和证据标识；签署弹窗再次确认就诊号、版本和关键内容，并要求操作者显式勾选核对声明。

当前版本签署后，普通编辑控件不可继续保存，完成就诊按钮才可用。需要修订时必须进入独立修订流程，不能把已签署内容重新变成普通可编辑表单。

任务中心对签署待办仅提供“查看业务”和“认领”，不提供通用“完成”按钮。签署成功后由领域事件自动关闭待办并刷新门户汇总。

## 验收场景

- 连续保存两版病历时，任务队列只有第二版待签署；
- 直接调用通用任务完成接口返回 `TASK_BUSINESS_ACTION_REQUIRED`；
- 未签署完成就诊返回 `DOCUMENT_SIGNATURE_REQUIRED`；
- 签署后当前版本包含签署人、时间、含义和签名证据标识；
- 签署待办自动消失，完成就诊成功；
- 跨机构或跨科室工作上下文不能读取或签署文档。
