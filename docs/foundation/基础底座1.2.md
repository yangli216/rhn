# RHN 基础底座 1.2：工作门户与任务协同

## 1. 定位

Foundation 1.2 在 1.1 的组织、IAM、Outbox、参数、MPI 与临床文档基础上，补齐后续业务主页共同依赖的工作上下文、可靠事件消费、任务、站内通知和门户聚合能力。

本轮目标不是增加静态主页卡片，而是保证用户看到的待办、消息和指标具有真实来源、明确数据范围、可追踪状态和稳定跳转目标。

## 2. 受信工作上下文

- 会话接口返回当前账号在有效期内可用的机构、科室、数据范围和角色集合。
- 前端通过 `X-Organization-Id` 与 `X-Department-Id` 传递当前选择；服务端依据用户角色授权重新校验，不信任前端选择。
- `ExecutionContext` 同时承载租户、用户、机构、科室、数据范围和可访问组织集合。
- 门诊写入及读取在提供工作上下文时执行机构、科室范围校验。
- 任务、通知和门户聚合接口强制要求有效工作上下文。

## 3. 可靠事件与幂等

- 领域事实继续与业务事务同时写入 `outbox_events`。
- 调度器使用悲观锁批量领取待发布事件，记录尝试次数、工作节点、重试时间和最终失败状态。
- 事件消费者通过 `event_consumptions` 记录 `(consumer_name, event_id)`，确保重复投递不会重复创建任务或通知。
- `IdempotencyService` 将已有 `idempotency_records` 表正式开放为写请求幂等预留与完成接口，校验同一幂等键的请求摘要。
- 模块化单体阶段使用数据库 Outbox；不提前引入外部消息中间件。

## 4. 任务与通知边界

任务表示必须处理的工作单元，包含来源对象、机构科室、分配对象、优先级、截止时间、状态和业务跳转路径。首个投影规则由门诊挂号创建科室待接诊任务，开始接诊或完成就诊后自动结束。

通知表示需要告知的信息，不代替任务状态。通知独立维护未读、已读、归档、严重程度、接收人或科室范围以及业务跳转路径。

## 5. 门户聚合与用户工作区

- `/api/portal/summary` 按当前工作上下文汇总任务、未读消息、今日挂号、接诊中、今日完成和活跃居民数。
- 前端主页只消费聚合接口，不自行拼接多个领域仓储或使用静态指标。
- `portal_user_workspaces` 独立保存默认上下文、收藏、Tab 和布局状态；高频用户交互状态不写入运营参数表。

## 6. 新业务接入规则

1. 需要进入个人或科室工作队列的业务必须发布稳定、版本化领域事件。
2. 任务投影必须提供唯一去重键、业务来源、跳转目标和完成条件。
3. 通知必须明确接收人或机构科室范围，不能以全租户广播替代授权判断。
4. 事件消费者必须通过消费幂等服务，不得只依靠先查后写。
5. 门户指标必须定义时间口径、数据范围和下钻目标。
6. 写请求需要重试语义时使用统一幂等服务，并通过 `Idempotency-Key` 对外暴露稳定契约。
7. 所有新增表必须同时提供 PostgreSQL/H2 与 Oracle 19c 迁移。

## 7. 当前边界

- 不包含通用工作流编排器；任务状态机先服务真实业务。
- 不包含短信、微信、邮件等外部通知渠道。
- 不包含通用全文搜索与BI平台。
- Outbox最终失败目前通过数据库状态和运行指标运维，后续上线阶段再接告警平台。
