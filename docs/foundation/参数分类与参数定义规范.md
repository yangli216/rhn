# 参数分类与参数定义规范

- 状态：草案 v0.1
- 日期：2026-08-27
- 适用范围：RHN 平台底座及门诊、住院、药事、公卫、家医、收费、接口等业务模块

## 1. 目的

本规范统一参数分类、参数键、定义属性和评审要求，使不同业务模块创建的参数能够被稳定识别、正确继承、安全展示并长期复用，避免出现同义不同名、作用域滥用、代码内隐藏默认值和各模块自行实现配置逻辑。

本规范中的“必须”是新增或修改参数时的强制要求，“建议”是当前阶段的默认实践；确需偏离时，应在参数定义说明和评审记录中写明原因。

## 2. 基本边界

参数中心只承载“当前执行时可运营、可能因上下文而不同”的配置。以下判断顺序必须在新增参数前完成：

| 内容 | 应进入 | 示例 |
|---|---|---|
| 少量、稳定、只解释代码含义的选项 | 普通字典或系统枚举 | 就诊来源、证件类型 |
| 需要版本、值域、映射或标准语义的编码 | 术语服务 | 诊断、检验项目、药品编码 |
| 机构、科室、人员、药品等独立对象 | 主数据 | 科室、人员、供应商 |
| 可按租户、机构、科室或用户覆盖的运行策略 | 参数中心 | 预约提前天数、队列阈值 |
| 诊断、处方、费用、库存、签署结果等已发生事实 | 业务表或不可变业务版本 | 实收金额、处方审核结论 |
| 权限边界、业务状态机、临床规则版本 | 专门的策略或规则模型 | 越权访问规则、处方状态流转 |
| 数据库地址、端口、启动参数、密钥明文 | 部署配置或密钥服务 | JDBC 地址、私钥、第三方密码 |

启动前必须可用的基础设施配置不能依赖参数数据库；高频变化的业务状态、计数器、任务进度和临时会话也不能作为参数。

## 3. 参数分类规范

### 3.1 分类职责

`parameter_categories` 是全平台共享的管理目录，只决定参数在管理界面中的归属、层级和排序，不参与参数解析、继承或权限判断。

分类按“稳定业务域 → 业务能力”组织，不按租户、机构、科室、用户、环境、菜单页面或配置属性组织。一个参数只能归属一个最贴近其责任主体的分类。

### 3.2 分类层级

分类建议不超过三级：

```text
一级：稳定业务域或平台域
 └─ 二级：业务能力或子域
     └─ 三级：仅在二级参数过多且存在稳定职责边界时增加
```

系统技术上允许更深层级，但新分类原则上不得超过三级。不得为了对应前端菜单或组织架构创建空分类。

### 3.3 分类编码

分类编码必须满足：

- 使用大写字母、数字和下划线，必须以字母开头；
- 正则为 `^[A-Z][A-Z0-9_]{0,63}$`，最长 64 个字符；
- 一级分类使用领域编码，如 `OUTPATIENT`、`PHARMACY`；
- 子分类使用父级前缀，如 `OUTPATIENT_REGISTRATION`；
- 编码创建后不可修改、复用或赋予新语义；
- 不得包含租户、机构、科室、用户 ID、年份、版本号和部署环境；
- 排序号建议以 10 为步长，便于后续插入分类。

分类名称使用简洁、稳定的中文业务名，不添加“参数”“配置”等无区分度后缀。分类说明应明确责任边界，并指出容易混淆但不属于本分类的内容。

### 3.4 建议的一级分类

以下为项目级候选基线；只有出现实际参数时才创建，不提前建设空目录：

| 分类编码 | 分类名称 | 主要范围 |
|---|---|---|
| `PLATFORM` | 平台底座 | 租户、组织、身份、字典、参数和审计等平台可运营行为 |
| `PORTAL` | 工作门户 | 工作台、导航和非关键用户体验偏好 |
| `HEALTHCORE` | 健康核心 | 居民主索引、临床文档、健康时间轴 |
| `OUTPATIENT` | 门诊业务 | 预约、登记、排队、接诊和门诊业务策略 |
| `INPATIENT` | 住院业务 | 入出转、床位、住院医嘱和病区业务策略 |
| `EMERGENCY` | 急诊业务 | 分诊、急诊队列和急救协同策略 |
| `NURSING` | 护理业务 | 护理任务、执行和护理文书策略 |
| `PHARMACY` | 药事管理 | 审方、调剂、发药和药房运营策略 |
| `LABORATORY` | 检验业务 | 检验申请、采集、执行和报告策略 |
| `IMAGING` | 检查影像 | 检查申请、预约、执行和报告策略 |
| `PUBLIC_HEALTH` | 公共卫生 | 公卫档案、随访和专项服务策略 |
| `FAMILY_DOCTOR` | 家庭医生 | 签约、履约和团队服务策略 |
| `BILLING` | 收费结算 | 计费、结算、票据和支付策略 |
| `INSURANCE` | 医保业务 | 医保交互、结算和审核策略 |
| `SUPPLY` | 物资库存 | 库存、批次、效期和供应保障策略 |
| `INTEGRATION` | 接口集成 | 外部系统路由、超时、重试和消息交换策略 |
| `OPERATIONS` | 运营质控 | 质量、绩效、运营预警和管理分析策略 |

二级分类示例：`OUTPATIENT_SCHEDULING`、`OUTPATIENT_REGISTRATION`、`OUTPATIENT_QUEUE`、`PHARMACY_REVIEW`、`INTEGRATION_HIS`。排班管理模式、简易排班默认人数和生成天数归入 `OUTPATIENT_SCHEDULING`；跨域参数归属实际拥有该行为和代码的模块，不建立含义模糊的 `COMMON`、`OTHER`、`MISC` 分类。

## 4. 参数键命名规范

### 4.1 基本格式

参数键全局唯一，采用小写语义分段：

```text
<domain>.<capability>.<subject>.<attribute>
```

其中 `subject` 可在语义足够清晰时省略。示例：

- `outpatient.registration.advance-time`
- `outpatient.queue.max-wait-time`
- `pharmacy.review.enabled`
- `integration.his.request-timeout`
- `portal.workspace.page-size`

实现允许的正则为 `^[a-z][a-z0-9]*(?:[._-][a-z0-9]+){1,15}$`，最长 160 个字符。规范层面进一步约定：

- 点号只用于分隔语义层级；
- 同一语义段内的复合词使用连字符；
- 不使用下划线、驼峰、中文、缩写堆叠或无意义编号；已登记的行业缩写如 `his`、`lis`、`pacs` 可以使用；
- 第一段必须与责任领域一致，不能省略领域前缀；
- 布尔参数采用正向语义，优先使用 `enabled`、`required`、`allowed`；
- 参数键创建后不可修改、复用或改变含义，语义变化应创建新键并停用旧键。

### 4.2 禁止写入参数键的内容

以下信息已有独立定义字段或运行上下文，不得编码到参数键中：

- 租户、机构、科室、用户 ID 或名称；
- `dev`、`test`、`prod` 等环境名；
- `v1`、`2026` 等版本或时间；
- `string`、`boolean` 等值类型；
- 秒、分钟、元等单位；
- `system`、`business` 配置属性；
- 密钥值、患者信息或其他敏感内容。

例如应使用 `outpatient.registration.advance-time` 并将单位定义为 `min`，不能创建 `outpatient.registration.advance-minutes-30`。

## 5. 参数定义规范

### 5.1 必填定义清单

每个新参数必须完整登记以下内容：

| 定义项 | 规范要求 |
|---|---|
| 参数分类 | 选择实际责任域下最具体、稳定的分类 |
| 参数键 | 全局唯一、稳定的小写分段键 |
| 参数名称 | 使用可直接理解的中文名，不重复领域前缀堆砌 |
| 参数说明 | 写清控制对象、执行效果、缺值行为和修改风险 |
| 值类型 | `STRING`、`NUMBER`、`BOOLEAN` 或 `JSON` |
| 控件类型 | 必须与值类型兼容 |
| JSON Schema | 对范围、长度、格式或结构进行机器校验；无额外约束时可空 |
| 默认值 | 设置安全的产品默认行为，或明确采用“无默认值、缺值失败”；不允许代码再维护第二套默认值 |
| 示例值 | 非密钥参数提供一个合法且不含敏感数据的示例；密钥参数留空 |
| 单位 | 数值或度量参数必须声明；无单位时留空 |
| 绑定字典 | 仅 `SELECT` 控件填写，必须使用系统枚举或普通字典编码 |
| 允许作用域 | 只选择业务确实允许维护的最小作用域集合 |
| 配置属性 | 明确 `SYSTEM` 或 `BUSINESS` |
| 继承开关 | 明确缺值时是否允许向父级及更宽作用域查找 |
| 缓存开关 | 根据一致性和读取频率明确，不机械使用默认值 |
| 显式空值 | 只有“空”具有独立业务语义时才启用 |
| 敏感级别 | `NORMAL`、`SENSITIVE` 或 `SECRET` |
| 展示策略 | `PLAIN`、`MASKED` 或 `HIDDEN`，并符合敏感级别约束 |
| 状态 | 完成定义校验和接入测试后才能启用 |

默认值、示例值和当前值都使用合法 JSON 表达：字符串写为 `"value"`，数值写为 `30`，布尔写为 `true`，对象或数组写为标准 JSON。

### 5.2 配置属性

配置属性描述参数的治理责任，不等同于参数分类、作用域或敏感级别：

| 属性 | 适用范围 | 示例 |
|---|---|---|
| `SYSTEM` | 平台运行机制、跨业务公共技术行为，只能由平台责任人定义 | 幂等窗口、接口默认超时、门户分页上限 |
| `BUSINESS` | 由业务制度或运营策略决定的行为，由对应业务域负责 | 预约提前天数、审方开关、随访提醒周期 |

业务参数可以具有平台默认值，系统参数也可以允许租户或机构覆盖，不能仅根据作用域判断配置属性。

### 5.3 值类型与控件

必须使用以下兼容组合：

| 值类型 | 允许控件 | 使用建议 |
|---|---|---|
| `STRING` | `TEXT`、`TEXTAREA`、`SELECT`、`SECRET_REFERENCE` | 短文本、长文本、字典代码或密钥引用 |
| `NUMBER` | `NUMBER`、`SELECT` | 数量、阈值、比例和时长 |
| `BOOLEAN` | `SWITCH`、`SELECT` | 开关优先使用 `SWITCH` |
| `JSON` | `JSON_EDITOR` | 仅用于确有整体原子配置语义的小型对象或数组 |

`SELECT` 必须绑定字典，非 `SELECT` 不得绑定字典。固定少量选项优先使用字典，不使用 JSON 数组模拟下拉选项。

能够拆成独立、可继承、可校验参数的配置，不得为了减少定义数量合并成大 JSON。JSON 参数建议控制在单一责任、低频修改的小型结构内。

### 5.4 JSON Schema

当前底座支持并校验以下 Schema 关键字：

- `type`；
- `enum`；
- `minimum`、`maximum`；
- `minLength`、`maxLength`；
- `pattern`；
- 对象顶层的 `required`。

Schema 的 `type` 必须与参数值类型一致。不得依赖当前底座尚未执行的复杂 Schema 关键字形成关键业务约束；复杂结构约束应由业务适配器再次转换为强类型并校验。

### 5.5 单位

数值参数必须使用稳定、无歧义的单位编码。时间优先使用 `ms`、`s`、`min`、`h`、`d`，比例使用 `%`，数量可使用 `count`，金额使用明确币种编码如 `CNY`。参数名称和说明可以展示中文单位，但代码读取必须以定义中的单位为准。

同一参数不得在不同作用域使用不同单位。需要改变单位时创建新参数键并完成迁移。

## 6. 作用域与继承规范

### 6.1 作用域选择

| 作用域 | 使用场景 | 约束 |
|---|---|---|
| `PLATFORM` | 所有租户共享的产品基线 | 仅平台级责任人维护 |
| `TENANT` | 医共体或客户整体策略 | 最常用的业务覆盖层 |
| `ORGANIZATION` | 医疗机构差异 | 机构 ID 必须属于当前租户 |
| `DEPARTMENT` | 科室及父科室差异 | 必须同时提供所属机构并校验归属 |
| `USER` | 用户个人偏好 | 不得承载授权或关键业务规则 |
| `PRODUCT` | 同租户不同产品上下文 | 使用稳定产品编码，不使用 ID |
| `MODULE` | 同租户不同模块上下文 | 使用稳定模块编码 |
| `ENVIRONMENT` | 确需参数化的部署环境差异 | 启动级配置仍应留在部署配置中 |

只允许选择必要作用域，禁止无依据地勾选全部作用域。常见集合建议：

- 租户级策略：`PLATFORM + TENANT`；
- 机构级策略：`PLATFORM + TENANT + ORGANIZATION`；
- 科室级策略：`PLATFORM + TENANT + ORGANIZATION + DEPARTMENT`；
- 用户偏好：`PLATFORM + TENANT + USER`；
- 仅要求本级显式维护的参数：只选择所需精确作用域并关闭继承。

### 6.2 继承开关

启用继承时，底座按以下顺序短路解析：

```text
用户
 → 当前科室 → 父科室 → ...
 → 当前机构 → 父机构 → ...
 → 租户
 → 模块 → 产品 → 环境
 → 平台
 → 参数定义默认值
```

只查询定义允许的作用域，遇到第一个有效且不是 `INHERIT` 的当前值立即停止。

以下情况通常启用继承：下级未维护时可以安全沿用上级政策，且各层值具有完全相同的语义和单位。

以下情况必须关闭继承：每个目标作用域都必须明确配置、错误沿用上级值可能导致接口串接或安全风险，或者业务明确禁止跨层复用。关闭继承后只查找当前上下文中允许的最具体作用域，不查询父级、其他层级和定义默认值；缺值时返回 `PARAMETER_VALUE_NOT_FOUND`。

### 6.3 当前值模式

| 模式 | 语义 |
|---|---|
| `OVERRIDE` | 当前作用域保存并使用明确值 |
| `INHERIT` | 当前作用域明确继续向更宽作用域查找 |
| `RESET_DEFAULT` | 当前作用域明确使用定义默认值并停止查找 |
| `EXPLICIT_NULL` | 当前作用域明确返回空并停止查找 |

`EXPLICIT_NULL` 仅在定义启用显式空值时可用。布尔“关闭”应使用 `false`，不能使用空值；没有清晰业务含义时不得启用 `nullableValue`。

### 6.4 默认值与缺值

默认值必须是安全、可解释的产品行为。以下两种策略必须二选一并写入参数说明：

1. 有默认值：未维护任何覆盖时由定义默认值兜底；
2. 无默认值：当前上下文缺值时失败关闭，由业务明确处理 `PARAMETER_VALUE_NOT_FOUND`。

代码、前端和业务数据库中不得再维护同一参数的隐藏默认值。对收费、签署、外部路由等高风险行为，优先采用失败关闭或保守默认值。

## 7. 缓存与安全规范

### 7.1 缓存

以下情况建议启用缓存：参数读取频繁、变更较少、短时间旧值不会产生安全或资金风险。

以下情况建议关闭缓存：紧急控制开关、密钥引用、资金或安全关键参数，或者在多实例跨节点失效机制尚未启用时要求变更立即一致。

业务模块不得在参数底座之外增加第二级参数缓存。参数也不能替代实时状态和计数器。

### 7.2 敏感与展示策略

| 敏感级别 | 允许展示策略 | 要求 |
|---|---|---|
| `NORMAL` | `PLAIN`、`MASKED`、`HIDDEN` | 一般参数默认 `PLAIN` |
| `SENSITIVE` | `MASKED`、`HIDDEN` | 禁止明文展示 |
| `SECRET` | `MASKED`、`HIDDEN` | 必须使用 `STRING + SECRET_REFERENCE`，不得设置默认明文 |

`SECRET` 当前值只能保存外部密钥服务引用。参数说明、示例、变更原因、日志和错误信息中均不得出现真实密钥或个人敏感数据。

参数值不能授予权限；前端参数开关也不能作为安全控制的唯一依据。关键判断必须在后端完成。

## 8. 生命周期与治理

1. 参数需求提出时，先完成“参数、字典、术语、主数据、规则或业务事实”归类。
2. 业务域负责人提交完整参数定义清单和至少一个合法示例。
3. 平台负责人审查参数键、分类、作用域、继承、缓存和安全边界。
4. 新参数进入对应模块测试，覆盖默认值、覆盖、继承、禁止继承和缺值场景。
5. 参数定义启用后，业务只能通过 `ConfigurationDirectory` 读取。
6. 参数键不可修改或复用；已有当前值后不得修改值类型。
7. 不再使用的参数先停用，确认所有消费者移除后仍保留历史变更记录，不物理删除或改作他用。
8. 定义和值修改必须提交期望修订号、全局唯一请求编码和有意义的变更原因。

系统级参数定义和跨模块公共参数应随产品发布统一初始化，避免不同环境手工创建出不一致的定义。当前模型不提供审批、计划发布、灰度和历史时点重放；出现这些需求时应扩展模型，不能把变更日志当成业务版本。

对收费、签署、处方、消息发送等需要事后解释的关键业务，业务事实应记录最终采用的参数值、参数键及必要的来源作用域或修订号，不能依赖未来再次解析当前值还原历史。

## 9. 定义示例

### 9.1 可继承的科室业务参数

| 定义项 | 示例值 |
|---|---|
| 分类 | `OUTPATIENT_REGISTRATION` |
| 参数键 | `outpatient.registration.advance-time` |
| 名称 | 允许提前登记时间 |
| 值类型 / 控件 | `NUMBER` / `NUMBER` |
| Schema | `{"type":"integer","minimum":0,"maximum":1440}` |
| 默认值 / 示例值 | `30` / `60` |
| 单位 | `min` |

## 10. 评审检查表

- [ ] 内容确实属于参数，而不是字典、术语、主数据、规则、部署配置或业务事实；
- [ ] 分类按责任域和业务能力建立，未复制菜单、组织或作用域结构；

- [ ] 敏感级别、展示策略和密钥引用符合安全边界；
