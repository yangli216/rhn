# 权限体系设计与接入指南

## 1. 当前边界

本阶段采用“最小 RBAC + 工作上下文数据范围”。权限决定账号在当前机构/科室可以执行什么动作，租户、机构和科室共同限定动作在哪个范围内生效。菜单可见性只是前端体验，后端方法鉴权和领域数据校验才是最终安全边界。

当前已提供角色、权限、用户角色授权、有效期、撤销和授权变更审计的管理闭环；暂不引入策略表达式、字段级权限、紧急访问和外部 IAM 工作流。这些能力应在出现真实业务规则后通过授权策略端口扩展，不能堆入菜单配置。

## 2. 权威模型

- `management_modules`：功能目录和路由元数据，用于组织权限与前端菜单，不直接授予访问能力。
- `access_permissions`：原子动作，编码统一为 `RESOURCE.ACTION`，例如 `TASK.READ`、`TASK.MANAGE`、`PHARMACY.REVIEW`。
- `access_roles`：一组岗位或职责权限；业务代码不得直接判断角色名。
- `role_permission_assignments`：角色与权限的时效绑定。替换权限时关闭旧绑定并新增绑定，不覆盖历史。
- `user_role_assignments`：用户在租户、机构或科室范围内的时效角色授权。
- `iam_authorization_events`：角色、角色权限、用户授权与撤销的追加式审计事件。

作用域约束如下：

| 作用域 | organization_id | department_id | 含义 |
| --- | --- | --- | --- |
| `TENANT` | 空 | 空 | 整个租户有效 |
| `ORGANIZATION` | 必填 | 空 | 指定机构有效 |
| `DEPARTMENT` | 必填 | 必填 | 指定科室有效 |

## 3. 运行时判定

1. 认证适配器只解析当前租户内的有效账号和不带机构/科室范围的全局授权。
2. 请求携带 `X-Organization-Id`、`X-Department-Id` 时，安全过滤器先验证账号是否拥有该工作上下文，再按当前时间重新解析全局、机构和科室授权。
3. 解析结果替换本次请求的 Spring Security authority，并进入 `ExecutionContext.authorities`。
4. Controller 使用 `@PreAuthorize` 做动作门禁；应用服务通过 `ExecutionContextProvider` 获取权限和范围；Repository 或领域服务仍需按租户和业务对象归属收敛数据。
5. 无工作上下文访问业务权限接口时返回 `WORK_CONTEXT_REQUIRED`；伪造或无权上下文返回 `WORK_CONTEXT_FORBIDDEN`；权限不足返回 `ACCESS_DENIED`。

授权和角色有效期在每次请求解析，角色停用、授权撤销或过期后不依赖重新登录即可生效。

## 4. 管理能力

`/api/platform/iam` 提供当前租户内的角色、权限、用户和用户角色授权管理。所有接口要求 `IAM.MANAGE`：

- 查询角色、权限、用户及用户的授权记录；
- 创建自定义/业务角色，使用版本号更新名称和状态；
- 原子替换角色权限；
- 在允许范围内为用户分配带有效期角色；
- 撤销尚未失效的角色授权。

管理者不能授予自己不具备的权限或角色，也不能从当前科室上下文查看、授权或撤销其他机构/科室的用户授权。科室级账号候选人来自本科室当前有效任职；平台级管理员应通过全局授权和受控运维流程管理更大范围。角色定义是租户共享资产，本阶段的 `IAM.MANAGE` 只授予受信 IAM 管理员，尚不向普通科室负责人开放独立的授权入口。

前端入口为 `/settings/access-control`。它负责角色与授权的日常维护，但不能在线创建权限编码或业务模块；权限目录必须随业务代码和数据库迁移发布，避免界面配置出后端从未执行的“伪权限”。

### 4.1 角色权限读取与保存确认

角色与权限目录必须返回完整、唯一的身份编码、类型、状态及版本；角色的 `permissionCodes` 必须明确返回，缺失时不能按空权限处理。目录失败或刷新中隐藏旧目录、显示待确认和重试入口，禁止保存权限。只有成功校验后的空目录才能显示“暂无权限”。

权限勾选草稿保留其原角色版本，重新加载不会静默覆盖；服务端版本变化时必须明确放弃草稿并载入最新权限。角色已有但目录未包含的权限不能被过滤掉，需提示核实并阻止提交；停用权限不能新增。明确取消全部勾选仍可提交真实空集合。

提交冻结原角色、版本与完整权限 ID 列表。回执必须为同一角色、推进版本、保留名称和状态，并返回与本次提交完全相同的权限集合，否则不提示成功、不覆盖草稿。提交期间禁止重复保存和修改勾选；切换角色、API 实例或机构/科室上下文后，旧请求不再修改当前页面反馈与草稿。相关读取缓存按 API 实例与工作范围隔离。

### 4.2 角色创建与状态回执

新建业务角色仅在服务端返回新 ID、规范化后的相同编码和名称、正确角色类型、启用状态、初始版本及空权限集合后提示成功并清空表单。失败、缺项或不一致的回执保留原输入，提供核实入口。若重新查询已找到相同编码，阻止再次创建，不能把既有角色当作本次成功结果。

停启用使用共享确认框冻结原角色、原版本和目标状态，校验返回身份、推进后的版本、实际状态以及未被修改的权限集合。失败保留确认框；重新加载后的状态不改变本次目标，重试继续携带原版本，由服务端处理版本冲突。请求期间禁止重复提交、关闭确认框和并发修改角色权限；上下文或角色选择改变后忽略迟到反馈。

### 4.3 用户授权事实与撤销核验

账号列表需包含真实账号身份和状态；授权列表必须为所选用户、当前机构和科室的完整记录，包含角色信息、范围名称、有效期、创建时间及有效标志。返回缺项或其他范围时整体视为未确认，不用“租户范围”替代缺失信息，不显示缓存记录为当前事实。只有确认的空列表可显示无账号或无授权。

创建授权前确认账号、启用角色和现有授权；回执必须包含新 ID、相同用户、角色、科室及请求有效期。成功提示“授权记录已保存”，不能据此推断所有业务权限已经生效。重查发现相同角色已有有效授权时阻止重复请求并提示核实，重叠授权的最终判断仍由服务端完成。

撤销接口返回无正文，前端必须随后读取原用户的授权，确认原记录保持身份和起始信息、已结束且不再有效后才提示撤销成功。读取失败、记录缺失或仍有效均提示结果未确认并提供重新核实入口；操作失败后刷新目录，避免旧记录继续被当作当前事实。写入冻结原用户与工作范围，保存中锁定重复操作；切换 API 或范围后的迟到结果不会影响当前页面。

## 5. 新业务接入规则

新增功能时按以下顺序接入：

1. 将功能挂入 `management_modules`，并为每个独立动作登记 `access_permissions`；编码使用大写英文 `RESOURCE.ACTION`，读写分离时至少区分 `READ` 与 `MANAGE`。
2. 在所属模块公开权限常量，Controller 的 `@PreAuthorize` 引用常量，不散落角色名或兼容权限字符串。
3. 服务层从 `ExecutionContextProvider` 取得当前租户、机构、科室和权限；涉及具体患者、单据或库存站点时继续校验对象归属。
4. 本地演示迁移把新权限绑定给演示角色；生产租户由初始化/升级流程显式绑定，不默认扩大既有角色能力。
5. 前端菜单节点声明同一个 `requiredAuthority`，无权时隐藏入口；直接访问路由仍显示无权限状态，不能代替后端鉴权。
6. 测试至少覆盖：有权成功、无权 403、伪造工作上下文 403、跨租户失败、不同科室权限隔离、授权过期/撤销立即失效，以及授权管理审计。
7. API 变化后更新 `docs/api/openapi.json` 并重新生成前端类型。

## 6. 后续演进触发条件

只有出现下列真实需求时才进入下一阶段：需要根据患者关系、访问目的或敏感等级动态判定时增加策略授权端口；需要紧急救治越权时建设 Break Glass、强理由和事后复核；需要统一身份源时接入 OIDC/MFA 与账号生命周期同步；需要合规取证时把授权拒绝和敏感数据访问接入统一审计证据。上述能力继续复用当前角色、权限、工作上下文和执行上下文，不改变业务模块的接入方式。
