# M3 药房接方与审方契约

## 1. 本批目标

M3.1 至 M3.4 纵向切片承接已提交的门诊处方，完成药房接方、具体产品与包装选择、追加式审方、发药任务形成、批次入账、余额投影、FEFO 原子预留、普通门诊药品的配药复核、部分发药、患者退药和批次追溯，并以实际发退药事实形成计价、应收、收退费和日对账闭环。库存预留不是已发药事实，只有不可变发药事件与 `DISPENSE` 库存分录才表示实际发药；费用预览也不是应收事实，只有不可变收费事项与借贷分录才进入费用账。

## 2. 业务边界

- `ex.medication_request` 继续保存临床用药意图；临床按通用名开立后，药房选择的具体产品不回写并覆盖原请求快照。
- 药房选择结果进入 `sup.dispense_task_line`，引用具体 `stock_item` 与发药包装；由此同时保留“开了什么”和“实际准备发什么”。
- 自备药不进入药房接方队列。
- 已撤销请求保留历史，但不得新建审方或发药任务；已有未完成任务进入取消/释放流程。
- `pharmacy_review` 是追加事实，不更新上一条审方记录；任务只保存最新审方引用作为当前态加速。
- `PASS` 允许进入配药，`REJECT` 终止当前任务，`INTERVENE` 等待临床处理，`OVERRIDE` 必须保留理由并纳入高风险审计。
- 发药任务是过程当前态，实际发药进入不可变 `medication_dispense + line`；不得把“已配药”伪装为库存出库事实。

## 3. 接方与选品

药房队列读取机构范围内 `ACTIVE`、非自备的药品请求：

1. 请求已指定产品时，所选库存经营项目必须指向同一目录产品，包装必须有效且可发药。
2. 请求仅指定通用药品时，药房可从同一通用药品下的机构已采用、可发药且有效产品中选择；不允许替代时仍必须满足原请求已指定产品。
3. 任务行固化产品、包装、申请量、计划发药量、基本单位换算、拆零与追溯要求。
4. 产品选择不得重新解析并覆盖开立时扩展属性；发药上下文如需新增解析，必须保存独立发药快照和与开立快照的差异。
5. 同一药品请求只能存在一个有效发药任务行；接口重试返回原任务，不重复接方。

### 3.1 基础数据扩展属性门禁

`item-attribute-configuration-model.md` 是本轮 M3 使用的基础数据横切契约，不在药房模块复制一套属性表或解析算法：

- M3.1 直接复制药品请求在开立时生成的规范化属性快照和哈希，配置后续修改不得改变已接方任务的解释；
- 药房选品不得用当前配置重算并覆盖开立快照，具体产品、包装、拆零、追溯和批次关系仍使用强类型字段；
- 将来确有 `DISPENSING` 或 `STOCKING` 上下文属性时，由基础数据公开解析服务生成独立的发药/库存快照，并保存与开立快照的差异，不能原地替换；
- 回归测试必须覆盖“开立后修改租户/机构属性，既有药品请求及发药任务快照和哈希保持不变”。

## 4. 计划状态

### 发药任务

`PENDING_REVIEW → READY_TO_PICK → PICKING → READY_TO_DISPENSE → PARTIALLY_DISPENSED → COMPLETED → PARTIALLY_RETURNED/RETURNED`

异常分支：

- `PENDING_REVIEW → INTERVENTION`
- `PENDING_REVIEW/INTERVENTION → REJECTED`
- 未完成状态可因处方撤销进入 `CANCELLED`

### 任务行

`PENDING → READY → PICKING → READY_TO_DISPENSE → PARTIAL/COMPLETED → RETURNED`，撤销时进入 `CANCELLED`。任务头状态由行状态、累计发退量和最新审方结果确定，页面不得直接提交任意目标状态。

## 5. 权限与数据范围

- 接方队列按租户与当前工作机构隔离；药房科室可跨开方科室处理本机构处方，因此不以开方科室等于当前科室作为条件。
- 非虚拟库存站点必须绑定科室；库存、接方、审方、配药、发药和退药操作要求当前工作科室与站点所属科室一致。
- 审方、配药、发药、复核和退药确认还需绑定药师人员及 `PHARMACY` 标准岗位任职；临床或行政岗位不能仅凭人员名称冒充药师。
- 机构发药路由决定库存站点；前端不得自行传入任意库房绕过路由。
- 后续引入岗位权限码：`PHARMACY_INTAKE`、`PHARMACY_REVIEW`、`PHARMACY_DISPENSE`、`PHARMACY_OVERRIDE`。

## 6. 与目标表结构的对应

| 能力 | 目标表 | 说明 |
|---|---|---|
| 药房与发药路由 | `sup.stock_site`、`sup.dispense_route`、`sup.dispense_station` | 机构/科室/就诊场景确定药房与窗口 |
| 可经营产品 | `sup.stock_item` | 具体目录产品在某药房的库存与发药规则 |
| 追加式审方 | `sup.pharmacy_review` | 每次决策独立保存 |
| 发药任务 | `sup.dispense_task`、`sup.dispense_task_line` | 当前过程态与具体选品结果 |
| 库存预留 | `sup.inventory_reservation` | 直接关联药品请求，任务沿请求关联；释放和消费责任独立留痕 |
| 数量账与余额 | `sup.inventory_transaction*`、`sup.inventory_balance` | 已记账分录不可变，余额为带并发版本的可重建投影 |
| 批次与货位 | `sup.stock_lot`、`sup.stock_bin` | 批号、效期、质量与站点内实际存放位置分立 |
| 实际发退药 | `sup.medication_dispense`、`sup.medication_dispense_line`、`sup.stock_return`、`sup.stock_return_line` | 原批次、库存流水行、退药处置和责任证据 |

## 7. 分批实施

1. M3.1（已完成）：药房站点/经营项目最小主数据、接方队列、选品、审方和任务工作台。
2. M3.2（已完成）：批次、余额、不可变库存事务、FEFO 预留及并发门禁。
3. M3.3（已完成普通门诊纵向切片）：配药复核、批次发药、部分发药、退药与追溯。
4. M3.4（已完成普通门诊纵向切片）：计价、应收、收费、退费、冲正和日结对账；受控/高警示药品仍需独立双身份会签后才能进入发药与收费联动。

## 8. M3.1 实施与验收结果

- V29 落地 `stock_sites`、`stock_items`、`dispense_tasks`、`dispense_task_lines` 和 `pharmacy_reviews`，PostgreSQL/H2 与 Oracle 脚本保持对应；
- 药房公开接口覆盖站点、经营项目、机构收件箱、接方、任务查询和追加式审方；多类型工作上下文纳入后的 OpenAPI 版本为 1.21.0；
- PC 端“药事管理”已进入正式导航，采用药房上下文工具栏、处方收件箱和任务详情双栏工作台，支持选品接方、当前任职选择、干预/驳回/通过和审方历史；
- 接方按药品请求幂等，同一请求不重复生成任务行；包装换算、整包装/拆零、追溯标志和具体产品快照进入任务行；
- 自动化跨模块验收覆盖开立后属性覆盖值变化、接方快照哈希不变、重复接方、`INTERVENE → PASS` 追加式审方、任务与行状态推进及收件箱最新结论；
- M3.1 不伪造库存余额或已发药事实，库存事实由后续切片独立承接。

## 9. M3.2 实施与验收结果

- V31 落地 `stock_bins`、`stock_lots`、`inventory_periods`、`inventory_transactions`、`inventory_transaction_lines`、`inventory_balances` 和 `inventory_reservations`，PostgreSQL/H2 与 Oracle 脚本保持对应；
- 显式入账以租户内 `request_code` 幂等，相同编码和相同内容返回原事务，不同内容失败关闭；操作数量、操作单位、包装换算因子、基本数量增量和成本快照进入不可变事务行；
- 批次必须通过质量和效期门禁才能进入 `AVAILABLE` 库存；货位同时控制收货、拣货和默认库存状态，前端不能通过任意参数绕过；
- FEFO/FIFO 自动分配使用数据库悲观行锁和余额乐观版本，先锁定全部候选余额并校验整单可用量，再一次性形成直接关联药品请求的预留；不足时整单回滚，不留下部分占用；
- 重复预留返回现有有效分配，不重复占用；手工释放必须填写原因，超时扫描则以 `SYSTEM_EXPIRY` 自动将分配标记为 `EXPIRED`，两种路径都在同一事务内恢复余额投影、预留状态和任务状态；预留与释放不写库存数量分录，避免伪造出入库事实；
- PC 药房工作台展示批号、效期、货位、在手量、预留量、可用量和分配组，支持 FEFO 一键预留与有理由释放；
- 自动化验收覆盖两批次 FEFO 顺序、入账幂等冲突、重复预留、手工释放、自动过期恢复，以及两个任务并发争抢不足库存时恰好一个成功；H2 56 个迁移已执行至 V31；
- M3.3 已按下一节承接实际发药：消费既有预留并生成不可变 `DISPENSE` 库存事务，不直接覆盖余额。

## 10. M3.3 实施与验收结果

- V32 落地 `medication_dispenses`、`medication_dispense_lines`、`stock_returns` 和 `stock_return_lines`，并扩展发药任务的配药责任与部分发退药状态；PostgreSQL/H2 与 Oracle 脚本保持对应；
- 配药完成动作要求完整、未过期的库存预留覆盖剩余计划量，登记配药药师、账号、任职和说明后，任务才从 `PICKING` 进入 `READY_TO_DISPENSE`；
- 实际发药按操作单位数量消费既有批次预留，同一事务内同时减少在手量与预留量；每个批次发药行一对一引用对应的不可变库存事务行，部分发药保留剩余有效预留并进入 `PARTIALLY_DISPENSED`；
- 发药请求编码全租户幂等，相同编码与相同任务/数量返回原事件，不同内容失败关闭；任务悲观锁、预留行锁和余额版本共同防止重复发药及超量消费；
- 患者退药必须选择原发药批次行，累计数量不得超过原实际发药量；退药新增 `RETURN` 发药事件、患者退药事实和正向库存分录，`RESTOCK`、`QUARANTINE`、`DESTROY` 分别进入可用、隔离和待销毁库存状态，原发药事实不修改；
- 追溯接口按任务返回发药/退药事件、原事件关联、批号、效期、货位、库存事务行、总发量、总退量和净发量，PC 工作台同步支持部分发药、原批次退药和事件时间线；隔离/待销毁数量不计入工作台的“当前可用”；
- 普通接口明确拒绝受控或高警示药品，不以“录入另一名药师姓名”冒充独立身份会签；此类药品必须在后续双账号/双身份确认切片验收后开放；
- 自动化验收覆盖配药门禁、特殊药品失败关闭、两次部分发药、预留逐步消费、发药幂等冲突、同一任务并发最终发药恰好一个成功、按两个原批次事件退药、可用/隔离处置和端到端批次追溯；H2 57 个迁移已执行至 V32。

## 11. M3.4 实施与验收结果

- V33 落地患者费用账户、收费事项及组成、结算凭证及明细、支付事实和不可变借贷分录；PostgreSQL/H2 与 Oracle 脚本保持对应，收费事项按实际发退药来源唯一，反向事项显式引用原收费事实；
- 实际发药形成正向收费事项和借方分录，患者退药沿用原收费事项的项目、价格版本、币种和名称快照，形成负向收费事项及贷方冲正分录，不按退药日当前配置重新计价；分次退药的最后一笔吸收金额尾差；
- 结算凭证归集尚未结算的收费事项，支付与退款只追加新事实；退款同时受原支付剩余额度和当前账户退费余额约束，原支付、原收费和原分录均不修改；
- 患者费用账户使用悲观锁串行化收款与退款，同一业务编码相同内容幂等返回，不同内容失败关闭；并发全额收款只允许一笔成功；
- 日对账按机构和业务日逐笔核对发退药来源、收费数量、历史价格金额和账务借贷，并识别未计费、金额不符及孤立收费事项；
- PC 端“费用结算”已进入正式导航，采用收费队列、费用账户和收退操作三栏工作台，支持发退药计费同步、结算凭证、收款、退款和日对账；
- OpenAPI 版本升级为 1.17.0，公开收费工作队列、计费同步、账户对账单、结算、支付、退款及日对账接口；自动化验收覆盖同步/结算幂等、并发支付、退药冲正、退款上限、逐笔对账和最终平账；H2 58 个迁移已执行至 V33。

### 11.1 扩展属性与收费门禁

- 收费默认使用开立、选品和发药时已经固化的项目与价格快照，不读取当前动态扩展属性重新解释历史事实；
- 影响计价、库存、医保、医疗安全或高频统计的属性必须先晋升为强类型字段或受控 `PROJECTED` 投影，动态 JSON 值不得直接驱动核心计价规则；
- 后续确需按执行或收费上下文重新解析属性时，必须另存解析快照、来源证据和与开立快照的差异，不得覆盖原快照。

普通门诊 M3 纵向闭环完成后，路线进入 M4 医防一体化证明；受控和高警示药品的双身份会签、医保结算、财政票据、跨币种和月结继续作为独立切片验收，不伪装为本轮已完成能力。

## 12. V35 药学组织语义补强

- `DEPT_TYPE` 新增药库、门诊药房、住院药房、急诊药房、中药房和制剂室类型，药学部继续作为上级管理科室；
- `stock_sites.department_id` 对除 `VIRTUAL` 外的站点成为数据库与应用双重必填约束；库存站点不再游离于组织人员体系之外；
- 人员任职响应显式返回 `sdPositionType`，药事服务据此校验药学岗位，不依赖岗位名称字符串；
- 本地演示结构预置“药学部—中心药库/门诊药房/住院药房/中药房”、药学能力、标准岗位、示范药师、用户工作上下文和一一对应的库存站点；生产环境应通过实施数据建立自身结构，不直接复制演示主键。
