# 字典与术语命名规范

## 1. 目的与适用范围

本规范统一 RHN 各业务条线的编码体系、概念、值域和映射命名，作为数据库种子、管理接口、业务代码、接口契约和外部适配的共同门禁。

“字典管理”是统一的用户入口，但设计、代码和表结构中必须区分以下对象：

| 对象 | 定义 | 典型用途 |
|---|---|---|
| 系统枚举 SystemEnum | 与代码分支、数据库约束或基础设施协议绑定的封闭枚举，只读发布 | 并发策略、日志目标、字典底座自身状态 |
| 普通字典 Dictionary | 无业务有效期和发布版本、只需维护当前枚举集合的轻量代码表 | 简单类型、来源方式、非临床展示选项 |
| 编码体系 CodeSystem | 定义一组代码及其稳定语义 | 性别、就诊状态、医嘱状态 |
| 概念 Concept | 编码体系中的一个代码项 | `MALE`、`ACTIVE` |
| 值域 ValueSet | 某业务语境在指定版本允许使用的概念集合 | 居民建档可选性别 |
| 映射 Mapping | 来源代码与目标概念之间的版本化对应关系 | 本地诊断码映射到标准诊断概念 |

核心原则是“概念只定义一次，业务场景通过值域复用”。不同条线不得为了显示方便复制语义相同的概念。

系统枚举、普通字典与术语资源采用不同生命周期：系统枚举在代码中封闭定义并通过只读目录发布；普通字典只保存当前定义和当前字典项，通过追加式日志追溯变化；CodeSystem、ValueSet 和 Mapping 继续采用版本、发布和有效期治理。三类资源不得共用同一聚合或表结构，详细边界见[普通字典管理设计](普通字典管理设计.md)。

## 2. 不应建成字典的数据

以下内容不得以普通字典替代领域模型：

- 租户、机构、科室、人员、药品、收费项目、供应商等具有独立属性和生命周期的主数据；
- 全局、租户、机构、科室、用户级参数，应进入参数中心；
- 仅有真/假语义的技术标志，应使用布尔类型；
- 业务状态机的迁移规则，应由领域代码控制；状态编码体系只能提供稳定编码和显示语义，不能决定合法迁移；
- 国家、省市或外围系统的大型目录，应作为带来源、版本和映射的标准或主数据导入，不能复制成无来源的本地字典。

## 3. 资源登记键

本节及第 4 至 8 节只适用于版本化术语资源。普通字典使用第 3.0 节的轻量编码规则。

### 3.0 普通字典编码

普通字典定义编码使用：

```regex
^[A-Z][A-Z0-9_]{0,63}$
```

编码应表达明确业务对象或属性，例如 `APPOINTMENT_SOURCE`、`CONTACT_RELATION_TYPE`。禁止使用 `TYPE`、`STATUS`、`CATEGORY` 等无业务对象的万能名称。唯一性范围为 `scopeCode + dictionaryCode`，其中平台作用域固定为 `PLATFORM`，租户作用域固定为 `TENANT:<tenantId>`；租户 ID 不得拼入字典编码。

RHN 自定义普通字典项编码使用：

```regex
^[A-Z0-9][A-Z0-9_.-]{0,127}$
```

字典和字典项编码创建后不可修改或复用；名称、说明、排序和启停状态可通过带父字典修订号的命令调整。普通字典没有版本号、草稿和发布状态，不得使用术语资源的 `<OWNER>.<DOMAIN>.<KIND>...` 登记键伪装成普通字典编码。

### 3.0.1 系统枚举编码与引用

只有同时满足“值集合封闭”“代码逻辑或数据库约束直接依赖”“不允许运行期增删改”三个条件的枚举，才登记为系统枚举。系统枚举编码使用普通字典定义编码的字符规则，但必须带明确的子系统对象，禁止 `STATUS`、`TYPE` 等泛化编码；字段规范中的引用写为：

```text
SYSTEM_ENUM:<SYSTEM_ENUM_CODE>
```

例如 `SYSTEM_ENUM:DICT_SCOPE_TYPE`。系统枚举项编码必须与后端枚举常量、数据库约束和接口取值完全一致，显示名称和说明由同一代码目录集中维护，通过只读接口发布。需要作为基础数据交付或供数据库侧查询的系统枚举，可以在 `dictionary_definitions`、`dictionary_items` 建立 `system_managed=true` 的平台级只读投影；投影只能随版本迁移维护并通过启动一致性校验，不得通过普通字典管理接口修改，也不得创建同编码的普通字典。

业务模块不得为了省略字典治理而把开放式业务选项声明为系统枚举。只要业务人员需要在不停机的情况下新增、停用或调整选项，就应使用普通字典；涉及标准、版本、值域或映射时使用术语资源。

### 3.1 格式

CodeSystem、ValueSet 以及后续具有独立身份的 Mapping 使用：

```text
<OWNER>.<DOMAIN>.<KIND>.<SUBJECT>[.<ATTRIBUTE>]
```

示例：

```text
RHN.COMMON.CS.GENDER
RHN.PI.VS.RESIDENT.GENDER
RHN.VIS.CS.ENCOUNTER.STATUS
RHN.EX.VS.OUTPATIENT_PRESCRIPTION.ROUTE
LOCAL.VIS.CS.DIAGNOSIS
```

结构校验规则：

```regex
^(?=.{1,100}$)[A-Z][A-Z0-9_]*\.(COMMON|SYS|BD|META|PI|SC|VIS|EX|HPL|BIL|INS|SUP|INT|AUD)\.(CS|VS|MAP)\.[A-Z][A-Z0-9_]*(\.[A-Z][A-Z0-9_]*)?$
```

附加规则：

1. 全部使用大写 ASCII 字符；层级使用 `.`，单个分段内的复合词使用 `_`。
2. 总长度不超过 100 个字符，只允许四段或五段。
3. `KIND` 必须与实际资源类型一致：CodeSystem 使用 `CS`，ValueSet 使用 `VS`；`MAP` 预留给后续独立映射集。
4. 四段形式的主题不得只写 `STATUS`、`TYPE`、`CATEGORY` 或 `KIND`，必须带业务对象，例如 `RHN.VIS.CS.ENCOUNTER.STATUS`。
5. 登记键不得包含中文、空格、租户或机构 ID、部署环境、菜单页面、数据库表名和版本号。
6. 登记键发布后永久不变、不得复用；语义发生实质变化时创建新资源，并建立替代或映射关系。

### 3.2 OWNER

| OWNER | 规则 |
|---|---|
| `RHN` | RHN 产品统一维护的编码体系和值域 |
| `LOCAL` | 租户拥有的本地编码体系或私有值域 |
| 外部标准简称 | 使用登记后的标准发布者或标准体系简称，例如诊断、医保或地方交换标准的批准简称 |

外部 OWNER 由术语治理人员统一登记，业务模块不得临时创造缩写。OWNER 只是 RHN 内部登记键的一部分，不替代官方标识。

### 3.3 DOMAIN

| DOMAIN | 责任范围 |
|---|---|
| `COMMON` | 跨条线且语义完全一致的公共概念 |
| `SYS` | 租户、组织、人员、身份与权限 |
| `BD` | 术语底座自身的管理对象，通常不承载业务概念 |
| `META` | 表单、规则、流程和元数据 |
| `PI` | 居民主索引、标识与人口学 |
| `SC` | 排班、预约、登记和队列 |
| `VIS` | 就诊、诊断、观察和临床文档 |
| `EX` | 医嘱、执行、处方、检验检查和任务 |
| `HPL` | 照护计划和健康目标 |
| `BIL` | 费用、发票、支付和账本 |
| `INS` | 保障、医保和理赔 |
| `SUP` | 库位、批次、库存和发药 |
| `INT` | 外部接口、适配和消息交换 |
| `AUD` | 审计、血缘和数据质量 |

出现新的独立业务条线时，必须先在本规范和模块目录中登记 DOMAIN，随后才能创建该域的术语资源。

## 4. 公共与条线归属

只有同时满足以下条件才进入 `COMMON`：

- 被两个及以上业务域实际复用；
- 各业务域中的语义完全一致；
- 生命周期可以由平台统一管理；
- 不含某个业务流程特有的状态迁移或统计口径。

公共 CodeSystem 可以被多个条线的 ValueSet 复用。例如：

```text
RHN.COMMON.CS.GENDER
  ├─ RHN.PI.VS.RESIDENT.GENDER
  └─ RHN.VIS.VS.ENCOUNTER.GENDER
```

若仅允许值不同，应新增条线 ValueSet；若概念语义不同，才新增条线 CodeSystem。禁止建立 `RHN.COMMON.CS.STATUS` 这类没有业务对象的万能字典。

## 5. Concept 代码

RHN 自定义 CodeSystem 中的 Concept 代码必须符合：

```regex
^[A-Z][A-Z0-9_]{0,63}$
```

推荐使用稳定的英文语义代码，例如 `DRAFT`、`PENDING_REVIEW`、`ACTIVE`、`CANCELLED`。禁止使用显示顺序、中文名称、数据库 ID、年份版本或含义不明的 `ZT01` 作为 RHN 概念代码。

外部标准及本地历史系统导入的 Concept 代码必须按来源原样保存，包括其大小写、点号、连字符或纯数字形式。不得为了满足 RHN 自定义代码风格而改写来源代码；如需统一使用，通过 Mapping 关联到目标概念。

显示名称允许按版本修订，概念代码不得改名或复用。显示名称不能作为业务判断条件。

## 6. 内部登记键与 canonicalUri

- 资源登记键用于 RHN 内部查找、权限、配置绑定和代码常量。
- `canonicalUri` 用于唯一标识 CodeSystem；外部标准必须保存官方 URI，不得根据 RHN 登记键伪造。
- RHN 自有体系可使用稳定的受控 URI 或 URN，但发布后不得随名称、版本或部署地址改变。
- 同一个登记键的不同版本共享同一 canonicalUri；版本放在 `versionCode`，不能拼入登记键或 URI。

## 7. 版本、发布与历史

本节只适用于 CodeSystem、ValueSet 和 Mapping，不适用于普通字典。

1. RHN 和 LOCAL 资源使用 `YYYY.MM`，同月修订使用 `YYYY.MM.N`，例如 `2026.08`、`2026.08.1`。
2. 外部标准保留官方版本标识，不转换为 RHN 日历版本。
3. `DRAFT` 可编辑；`ACTIVE` 发布后不得原地改变成员语义；调整内容必须形成新版本。
4. 已停用代码保留历史，禁止物理删除和重新分配。
5. 业务记录保存 Concept 稳定 ID，并保留发生时的系统、版本、代码和显示名快照。
6. 历史数据始终按发生时版本解释，新版本不得改变历史含义。

## 8. 作用域和租户覆盖

作用域是独立维度，不编码进登记键：

| 场景 | 作用域 | 登记键规则 |
|---|---|---|
| 产品公共或条线资源 | `PRODUCT` | `RHN` 或登记后的外部 OWNER |
| 租户覆盖产品 ValueSet | `TENANT` | 与产品 ValueSet 使用同一个 `RHN...VS...` 登记键 |
| 租户新增私有 ValueSet | `TENANT` | 使用 `LOCAL.<DOMAIN>.VS...` |
| 租户本地 CodeSystem | `TENANT` | 使用 `LOCAL.<DOMAIN>.CS...`，并映射到产品或标准概念 |

租户不得通过创建同名 CodeSystem 覆盖 RHN 概念语义。租户使用 `RHN` OWNER 创建值域时，底座必须确认同名产品值域已经存在，禁止租户凭空创建 RHN 资源。机构或科室需要选择不同值域时，由参数中心保存 ValueSet 登记键并使用参数继承能力，不在登记键中拼接机构、科室或用户 ID。

## 9. 代码使用门禁

1. 业务模块只能通过 `platform.dictionary.api` 读取普通字典或只读系统枚举目录，通过 `platform.terminology.api` 查询和校验版本化值域，禁止直接访问底层数据表。
2. 每个业务模块集中声明自己使用的 ValueSet 登记键，禁止在多个服务中散落字符串字面量。
3. API 和领域事件传递概念时至少包含 `system`、`systemVersion` 和 `code`；显示名只作为快照。
4. 创建 CodeSystem 和 ValueSet 时必须经过统一命名策略校验，不能只依赖前端表单。
5. 导入任务同样调用领域校验；确需兼容的不合规历史键必须先迁移或建立别名，不能绕过门禁。
6. 普通字典或系统枚举的响应字段统一使用 `sd<字典编码大驼峰>`，由序列化底座生成只读的 `sdXxxText`；无法准确推导时必须通过 `@DictionaryBinding` 显式绑定，详见[字典字段自动翻译设计](字典字段自动翻译设计.md)。
7. `sd` 前缀属于内部 JSON 展示契约保留命名。签名原文、密码证据、审计快照和外部交换合同不得无意使用该约定，也不得把自动生成的文本纳入稳定代码或业务判断。

## 10. 首批基线

当前居民性别基线统一为：

```text
CodeSystem：RHN.COMMON.CS.GENDER
ValueSet：RHN.PI.VS.RESIDENT.GENDER
Concept：MALE、FEMALE、UNKNOWN
Version：2026.01
```

本次只规范资源归属和类型，不把“性别”擅自改名为“行政性别”或其他临床含义。后续采用明确的国家、行业或互操作标准时，应新建对应标准 CodeSystem 和版本化 Mapping，不能直接改变现有概念语义。

机构字典使用 `ORG_` 前缀：`ORG_PROPERTY`、`ORG_IDENTIFIER_TYPE`、`ORG_CONTACT_TYPE`、`ORG_CONTACT_USE`、`ORG_ADDRESS_TYPE`、`ORG_RELATION_TYPE`、`ORG_CAPABILITY_TYPE`、`ORG_RESPONSIBILITY_TYPE`、`ORG_VERIFY_STATUS`、`ORG_DETAIL_STATUS`。科室作为独立聚合使用 `DEPT_` 前缀：`DEPT_TYPE`、`DEPT_PROPERTY`、`DEPT_RELATION_TYPE`、`DEPT_CAPABILITY_TYPE`、`DEPT_RESPONSIBILITY_TYPE`。`DEPT_TYPE` 是可维护、可扩展的具体科室目录；描述封闭结构的 `ORG_TYPE` 仅作为机构分类和兼容展示枚举，二者禁止混用。旧 `ORG_DEPARTMENT_TYPE` 只服务存量兼容，不得被新业务引用。
