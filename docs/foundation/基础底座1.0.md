# RHN 基础底座 1.0

> 持续开发所需的工程底座增量见 [基础底座 1.1](基础底座1.1.md)，目标数据库约束对齐见 [目标表结构与基础底座对齐](目标表结构与基础底座对齐.md)。

## 1. 目的

Foundation 1.0 是所有门诊、药事、收费、公共卫生、家医和医共体协同模块共同依赖的产品与工程契约。其目标不是建设通用低代码平台，而是在业务规模扩大前稳定身份、组织、数据标准、配置、事件、居民身份和临床记录的基本语义。

## 2. 本阶段范围

### 实际建设

1. 模块目录、依赖规则、统一错误和执行上下文。
2. 租户、机构、科室、人员、任职关系等组织主数据。
3. 只读系统枚举、平台/租户普通字典，以及术语编码、值域、概念和本地映射。
4. 分层参数的当前定义、当前值、可控继承、缓存和追加式变更追溯。
5. 具有固定信封、事务 Outbox 和幂等投影的领域事件。
6. MPI 多标识、来源记录、重复候选、合并和拆分基础。
7. 临床文档版本、签署、归档和更正基础。
8. 数据库迁移、架构测试、模块测试和前端工程结构。

### 本阶段不实际建设

- 监控、告警和运维驾驶舱；
- 备份、恢复和灾备系统；
- 发布平台、部署流水线和制品推广；
- 正式身份源、授权策略、加密、等保和安全运营。

上述事项保留接口边界和约束说明，但不作为当前实现任务。现有开发认证仅用于本地和自动化测试。

## 3. 基础完成标准

Foundation 1.0 完成必须同时满足：

- 每个模块都有明确责任、数据归属、公开 API 和事件；
- 业务模块不能直接依赖其他模块的内部实现；
- 机构、科室、人员、居民、术语均使用稳定内部 ID，外部编码作为可版本化标识；
- 所有参数都有明确作用域、缺值和继承策略，当前值变化写入不可覆盖的变更记录；需要版本、生效区间和发布语义的政策规则进入独立版本化领域；
- 跨模块业务事实先写入事务 Outbox，再形成查询投影；
- 事件具有事件 ID、版本、聚合版本、来源、关联和因果标识；
- MPI 能处理多标识、来源冲突、人工复核、合并和拆分；
- 正式临床文档不能被覆盖修改，历次版本可追溯；
- PostgreSQL 迁移和模块边界进入自动化测试；
- 现有居民—接诊—健康时间轴切片迁移到新基础后仍完整通过。

## 4. 非目标

- 不建设微服务体系；
- 不建设通用工作流、规则或低代码平台；
- 不将内部领域模型完全等同于 FHIR 资源；
- 不采用全系统事件溯源；
- 不为尚未出现的客户差异设计任意脚本扩展点；
- 不在 Foundation 中放置门诊、药品、费用或公卫专用规则。

## 5. 变更原则

1. 基础契约先通过当前纵向切片验证，再成为强制基线。
2. 数据库迁移只向前追加；已发布迁移不可修改。
3. 对外 API 和领域事件采用兼容性演进，删除字段必须经过弃用周期。
4. 参数只承载可运营行为和展示差异，强事务状态、权限和需要历史解释的规则仍由领域代码或版本化领域控制。
5. 所有基础能力必须提供最小但真实的业务用例，拒绝孤立平台演示。
