# 居民中心与门诊接诊边界

- 状态：业务基础能力基线 v1.0
- 日期：2026-08-28
- 适用范围：居民主索引、患者档案、门诊挂号、候诊和门诊接诊

## 1. 页面职责

“居民中心”“门诊挂号”和“门诊接诊”是三个独立入口，不以同一页面承担档案、窗口和临床三类任务。

| 入口 | 主要用户目标 | 本轮能力 |
|---|---|---|
| 居民中心 | 找到正确居民并维护相对稳定的个人资料 | 建档、检索、核心人口学、地址、联系人/监护人、保障信息、死亡标记 |
| 门诊挂号 | 为已识别居民建立一次当日门诊服务入口 | 居民检索、当日排班选号、临时接诊、挂号回执、今日挂号记录 |
| 门诊接诊 | 处理已经挂号并进入候诊队列的患者 | 今日候诊队列、开始接诊、病历与医嘱、完成就诊 |

居民中心不得隐式创建就诊；挂号页不承载完整档案维护；接诊页不再作为日常挂号主入口。三者通过稳定的 `residentId`、挂号事务和候诊队列协作。居民中心可以显式跳转到挂号页，但跳转本身不产生业务数据。

## 2. 权威数据

- `residents`、`resident_identifiers` 继续作为统一居民身份与标识权威数据。
- `resident_demographic_profiles` 保存当前人口学补充资料。
- `resident_addresses`、`resident_related_persons`、`resident_coverages` 保存带有效期的地址、联系人和保障事实；本轮界面以整组维护为主。
- `service_schedules` 与 `schedule_slot_pools` 是实际排班和号源库存权威数据。
- `appointments` 保存现场挂号时确认的服务、医生和时间快照。
- `patient_registrations` 保存挂号业务事实，其状态只表达 `REGISTERED`、`CANCELLED` 等挂号生命周期；`queue_tickets` 与 `queue_ticket_events` 独立保存 `WAITING`、`IN_SERVICE`、`COMPLETED` 等候诊状态和事件。
- `encounters` 保存临床就诊上下文，并显式关联挂号、排班和预约快照。

## 3. 现场挂号事务

当用户选择当天排班确认挂号时，后端按固定顺序完成：

1. 锁定并校验居民，拒绝已登记死亡居民及同科室活动就诊重复登记。
2. 校验排班属于当前机构科室、处于可预约状态且日期为今天。
3. 锁定共享号源池并占用一个号源，追加号源占用事件。
4. 固化预约快照，创建挂号记录和科室候诊票。
5. 创建并关联就诊，发布门诊挂号事件。

以上步骤处于同一数据库事务。任一步失败均整体回滚，不留下“扣号未挂号”或“有就诊无候诊票”的中间状态。同一幂等编码重复请求返回原结果；候诊号按租户、科室队列和业务日期独立递增。

无可用排班时，基层机构可以使用“临时接诊”。该入口创建挂号、候诊和就诊，但不虚构排班或扣减号源；后续是否允许普通门诊长期使用该入口由参数策略收紧。

当前窗口入口为 `/outpatient/registration`。挂号成功后页面显示挂号单号和候诊号，并立即刷新今日挂号摘要与候诊顺序；“去接诊”只负责进入接诊工作台，不重复创建挂号。第一阶段确认即登记，因此挂号状态直接进入 `REGISTERED`，开始接诊和完成就诊只推进候诊及临床状态，不覆盖挂号事实。

## 4. 字典与接口约定

居民档案受控字段统一使用现有普通字典：

- `PI_MARITAL_STATUS`：婚姻状况
- `PI_BLOOD_TYPE`、`PI_RH_TYPE`：血型
- `PI_ADDRESS_USE`：地址用途
- `PI_RELATED_PERSON_RELATIONSHIP`：联系人关系
- `INS_COVERAGE_TYPE`：保障类型

接口响应遵循全局字典翻译约定，字段使用 `sdXxx`，JSON 序列化时自动增加 `sdXxxText`。业务页面显示文本而不是编码，字典解析继续使用平台/租户覆盖和统一缓存。

所有 BIGINT 主键在 JSON 中仍以十进制字符串传输。档案更新携带居民版本号，过期版本返回冲突并要求刷新；挂号写接口携带不超过 128 位的幂等编码。

## 5. 当前边界与后续顺序

本轮完成基层日常主链，不提前建设复杂预约中心。后续按以下顺序迭代：

1. 证件、医保号、电话和地址的密文存储、检索哈希与脱敏展示，在进入真实居民数据前完成。
2. 居民重复候选处理工作台、标识新增/停用以及合并拆分操作界面。
3. 患者端提前预约、临时锁号、过期释放、取消改约和爽约管理。
4. 候诊叫号、过号回队、优先级调整和诊室大屏。
5. 专业模式的分时号、渠道额度、模板例外和停替诊影响闭环。

后续功能不得绕过现有居民、库存、挂号、候诊和就诊事务边界另建平行主链。
