# RHN 基础底座 1.1

## 1. 定位

Foundation 1.1 在 Foundation 1.0 的领域底座上补齐“持续开发平台”。它解决的不是某个业务页面，而是后续门诊、药事、收费、公卫、家医等模块都会重复遇到的身份上下文、ID、JSON、错误、接口契约、请求状态、表单和交互组件问题。

这轮建设遵循两个边界：共性能力只抽取已经由当前纵向切片验证的部分；居民、就诊、处方、收费等领域语义仍归各业务模块，不能进入 `shared`。

## 2. 已落地能力

### 后端

- `ExecutionContext` 和 `ExecutionContextProvider`：统一提供租户、账号主体、操作者、关联号与权限集合，业务模块不再直接读取 Spring Security 静态上下文。
- `GlobalIds`：新数据统一生成正数 Snowflake BIGINT；数据中心/工作节点显式配置，编号随机后缀与数据库主键生成分离。
- `JsonCodec`：以 Jackson 3 作为唯一 JSON 语义入口，领域服务不直接持有 `ObjectMapper`。
- `BusinessErrors`：集中常用业务异常构造，保留稳定错误码、关联号和字段校验契约。
- OpenAPI 3：后端发布 `/v3/api-docs`，统一声明 Basic 开发认证、必填 `X-Tenant-Id` 和可选 `X-Correlation-Id`。
- 身份访问模型：账号、角色、管理模块、权限、时效授权、机构/科室数据范围和幂等记录已进入 Flyway 迁移；当前请求按工作上下文动态解析有效权限，并已形成角色、角色权限、用户范围授权、撤销和审计的最小管理闭环。
- 组织人员主数据：机构与科室分别进入独立权威表和层级，管理端通过兼容组合树统一浏览；机构维护主体标识、地址和机构治理组件，科室维护类型、属性、虚拟标志、层级及科室治理组件；人员、聘用、岗位和任职分离，任职同时保存机构与科室，支持有效期、主聘用/主任职重叠校验和乐观并发。
- 租户完整性：当前纵向切片所有租户拥有表补齐租户根外键；组织树、人员聘用任职、居民、就诊、文档等父子关系补齐复合租户外键。
- 架构守卫：禁止业务模块绕过执行上下文直接读取安全上下文，禁止在 JSON 适配层之外直接使用 `ObjectMapper`。
- 密码证据底座：统一关键数据摘要、版本化签名声明、提供者适配、证据链、验证和生产合规门禁；业务模块只能依赖公开 API。
- 临床文档验证接入：每个版本自动生成完整性证据，签署前验证原文，签署时生成绑定签名含义的不可否认证据。
- 字典管理底座：区分只读系统枚举、平台/租户普通字典和版本化术语；组织与参数的系统枚举形成平台级只读持久化投影，普通字典维护当前定义、当前字典项和追加式变更日志，业务响应支持 `sdXxx` 到 `sdXxxText` 的批量自动翻译。
- 参数管理底座：以分类、定义当前状态、作用域当前值和追加式变更日志为权威模型，支持平台、租户、机构、科室、用户及产品/模块/环境上下文，同类型父级优先的可控继承、四种值模式、乐观锁、幂等变更、人工恢复和一致性缓存。
- 基础数据中心：疾病使用带版本、有效期和别名的标准术语模型；诊疗项目使用统一目录项加服务强类型明细；药品按知识、生产企业、厂家产品和包装分层，并把机构采用和有效期价格从主数据定义中分离。
- 多数据库持久化：PostgreSQL 与 Oracle 19c 使用独立 Flyway 方言迁移，实体长文本按数据库方言映射为 `text`/`CLOB`，主键仍统一为 `BIGINT`/`NUMBER(19)`，布尔值在 Oracle 中统一为 `NUMBER(1)`；开发连接凭据只从环境变量读取。

### 前端

- `ApiClient`：统一认证、租户头、关联号、JSON 和错误解析；业务 API 按 session、organization、residents、encounters、timeline 分包。
- OpenAPI 类型：版本化保存后端契约，并由 `openapi-typescript` 生成类型；手写的 UI 领域视图类型以生成契约为基类收紧。
- 应用 Provider：统一挂载路由、React Query 缓存与全局错误边界。
- 表单：React Hook Form + Zod 统一输入模型、校验和字段错误展示。
- 通用交互：Button、PageHeader、PanelHead、Alert、LoadingState、EmptyState、Dialog、FormField、PlannedPage。
- 组织上下文：登录后从服务端加载当前机构和科室，不再在页面或请求层写死。
- 权限管理：`/settings/access-control` 维护角色权限和当前工作上下文内的用户角色授权；菜单按当前上下文权限过滤，后端仍是最终安全边界。
- 字典选项：共享 `DictionarySelect` 统一加载启用项、处理租户覆盖、缓存、加载失败和重试；业务页面保存编码、展示服务端生成的 `sdXxxText`。
- 参数管理：`/settings/parameters` 统一维护分类、定义、作用域当前值和变更记录；业务页面不得复制参数继承和缓存逻辑。
- 组织与人员管理：`/settings/organization` 统一浏览机构—科室组合树，并分别维护机构档案、科室档案、人员主档、标准岗位、聘用和科室任职；具体科室类型使用可扩展的 `DEPT_TYPE` 普通字典，`/organization-units` 仅作为管理界面兼容聚合接口。
- 基础数据中心：`/settings/master-data` 按疾病、诊疗项目、药品三个工作区维护主数据；机构上下文用于展示机构采用状态和价格，所有分类中文由字典翻译提供。

## 3. 字典与参数统一接入规则

后续模块必须先区分系统枚举、普通字典、版本化术语、参数和领域模型，随后只依赖相应平台模块的公开 API：

- 封闭且被代码或数据库约束依赖的集合使用系统枚举；可在线维护的扁平选项使用普通字典；有标准来源、版本、有效期或映射的集合使用术语服务；
- 业务写入通过 `DictionaryDirectory.resolveActiveItems` 校验当前可选编码，响应通过 `sdXxx` 命名或 `@DictionaryBinding` 自动增加文本，前端通过 `DictionarySelect` 加载选项；
- 上下文相关的可运营行为使用参数，后端通过 `ConfigurationDirectory.resolveCurrent` 传入真实租户、用户、机构、科室及附加上下文解析；
- 字典只保存稳定编码，参数只表达当前可配置行为；需要历史重放的关键业务必须在业务事实中固化当时采用的值或来源修订；
- 禁止业务模块直接访问字典/参数表、Repository 或管理接口，禁止自行实现租户回退、父级继承、文本映射和二级缓存。

完整的选型表、前后端示例、错误语义、测试要求和合并检查见[字典与参数接入指南](字典与参数接入指南.md)。

## 4. Hutool 使用规则

Hutool 作为 Java 通用工具的优先选择，但不是新的基础框架。本项目只引入 `hutool-core`，避免 `hutool-all` 扩大依赖面。

允许直接使用的场景：字符串判空与规范化、集合等无状态纯工具，以及没有医疗领域语义的局部便利方法。

以下能力必须走项目自己的稳定接口：

- ID 使用 `GlobalIds`，业务代码不直接实例化 Hutool Snowflake，也不使用数据库自增或随机 UUID；
- JSON 使用 `JsonCodec`，不用 `JSONUtil` 形成第二套序列化规则；
- 时间使用 `java.time` 和注入的 `Clock`，避免不可测试的隐式当前时间；
- 密码、个人标识和密钥加密使用经过评审的 JCA/密钥管理方案，不直接用便捷加密方法；
- HTTP 调用通过后续统一集成客户端，不在领域代码中散落 `HttpUtil`；
- 领域对象映射保持显式，不用反射式属性复制掩盖字段演进。

## 5. 新业务模块接入清单

每个新模块开始开发时必须：

1. 通过 `ExecutionContextProvider` 获取租户和操作者。
2. 通过 `GlobalIds.next()` 生成数据库 `BIGINT` 主键；所有接口和前端把 ID 当作 1 至 19 位十进制字符串。
3. 通过 `JsonCodec` 处理持久化 JSON，通过 `BusinessErrors` 返回稳定错误。
4. 为写请求定义幂等语义；跨模块事实与事务 Outbox 同事务提交。
5. 为租户拥有表创建 `(tenant_id, id)` 唯一键，并以 `(tenant_id, parent_id)` 建父子外键。
6. 明确并发策略：乐观版本、继承父版本、追加写或不可变版本，不允许默认“最后写入覆盖”。
7. 在 OpenAPI 中声明请求校验和响应；更新保存的契约并重新生成前端类型。
8. 前端请求进入对应 API 模块，服务端状态进入 React Query，业务表单进入 RHF + Zod；优先复用现有 UI 组件。
9. 补充模块测试、跨租户失败测试、幂等/并发测试和架构边界测试。
10. 对照《关键数据密码保护目录》定义精确受保护原文和保护策略；签署、发布、冲正等关键动作只接统一密码证据服务。
11. 新枚举选项按接入指南判定系统枚举、普通字典、术语或领域模型；业务只通过 `DictionaryDirectory`/`SystemEnumDirectory` 读取，响应使用 `sdXxx` 自动翻译，前端复用 `DictionarySelect`。
12. 新参数声明系统/业务分类、允许作用域、缺值、继承、缓存和安全策略；业务只通过 `ConfigurationDirectory` 解析，不自行访问参数表或缓存。
13. 新增或修改表结构时，同步提供 PostgreSQL/H2 与 Oracle 方言迁移并保持版本号、语义和约束一致；长文本使用方言感知映射，不在实体中硬编码数据库类型。
14. 新业务引用疾病、诊疗项目或药品时，遵循标准术语/租户主数据/机构采用/运行价格/业务事实五层边界；业务事实固化必要快照，不复制或反写基础数据权威表。
15. 新功能登记 `RESOURCE.ACTION` 权限并通过迁移发布；Controller 使用权限常量鉴权，服务层继续校验租户、工作上下文和业务对象归属，前端菜单只做同码可见性控制。

密码能力的详细边界见 [ADR-003](../architecture/架构决策-003-密码证据.md) 和 [关键数据密码保护目录](关键数据密码保护目录.md)。本地 `development-jca` 只验证开发流程，不能用于真实医疗数据或作为密评证据。

参数数据模型、解析顺序、禁止继承语义和缓存一致性见 [参数管理设计](参数管理设计.md) 与 [ADR-004](../architecture/架构决策-004-分层参数配置.md)。

主键位布局、节点配置、外部字符串和数据库重建边界见 [ADR-005](../architecture/架构决策-005-雪花算法标识.md)。

Oracle 开发库的连接、迁移、初始数据和使用边界见 [Oracle 持久化开发环境](Oracle持久化开发环境.md)。

疾病、诊疗项目和药品的分层、接口使用及后续扩展边界见[基础数据中心设计与接入指南](基础数据中心设计与接入指南.md)。

## 6. 契约更新流程

后端启动后更新契约：

```bash
curl http://localhost:8080/v3/api-docs -o docs/api/openapi.json
cd frontend
npm run api:generate
npm run build
```

`docs/api/openapi.json` 和 `frontend/src/shared/api/generated.ts` 都需要随 API 变更提交。契约发生不兼容变化时必须先给出弃用周期，不能只修改前端手写类型。

## 7. 仍然明确不属于通用层的内容

- 处方审核、收费结算、库存批次、公卫随访等业务规则；
- 面向任意业务的万能 CRUD、万能表单或全量 EAV；
- 将所有 DTO、Repository 或 Service 塞入单一 `common` 包；
- 为尚未出现的差异预建脚本扩展平台。

底座允许持续演进，但新增抽象至少要被两个真实业务用例需要，或属于安全、租户、审计、契约等系统级强约束。
