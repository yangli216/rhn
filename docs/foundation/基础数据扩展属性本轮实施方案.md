# 基础数据扩展属性本轮实施方案

## 1. 结论

`item-attribute-configuration-model.md` 列入本轮正式计划，并作为药品、检验、检查及其他诊疗项目扩展能力的模型基线。本轮采用混合模型，不把现有基础数据改造成通用 EAV：

- 稳定、关键、强关联、高频检索字段保留为强类型列或关系表；
- 类型特有且结构稳定的数据进入一对一扩展表或多值关系表；
- 低频、差异化、允许配置的属性进入元数据扩展层；
- 租户、机构、科室差异通过覆盖表表达；
- 医疗请求使用解析后的不可变快照，不在历史查询时重新计算。

上游模型依据：`/Users/yangl/Documents/研发资料/数据库相关/表结构梳理/nextgen/model/item-attribute-configuration-model.md`。

## 2. 本轮范围

### 2.1 强类型主干

- 项目类型树：`item_type`；
- 平台公共项目：`item_master`；
- 药品类型扩展：西药、中药、疫苗；
- 检验扩展及标本关系；
- 检查扩展；
- 服务变体及强关联对象。

当前系统已有 `catalog_items`、`service_items`、`medications`、`medication_products` 等物理表，实施时保持现有物理命名，并建立与上游逻辑模型的一一映射，不为追求同名重复建表。

### 2.2 可配置属性闭环

本轮落地以下职责对象：

| 逻辑对象 | 职责 |
|---|---|
| `item_attr_definition` | 定义属性编码、数据类型、控件、校验、默认值和投影策略 |
| `item_type_attribute` | 把属性装配到项目类型，声明必填、排序和类型级默认值 |
| `item_attribute_subject` | 将可挂载对象统一为稳定属性主体 |
| `item_attribute_value` | 保存平台或租户公共属性值 |
| `item_attribute_override` | 保存租户、机构、科室覆盖值 |
| `item_attribute_change` | 保存属性定义、装配和值变更日志 |

不在本轮预建缓存表、发布版本表、通用审批表、任意 EAV 检索表，也不允许动态属性代替标本、部位、适应症、药品成分等强关系。

## 3. 固定解析规则

属性解析输入至少包含项目主体、租户、机构、科室和业务时间。候选值按以下优先级取第一个有效值：

1. 科室覆盖；
2. 机构覆盖；
3. 租户覆盖；
4. 租户公共值；
5. 平台公共值；
6. 类型装配默认值；
7. 属性定义默认值。

解析结果必须返回最终值、值类型、来源层级、来源记录、属性定义版本和解析时间。写入和解析共用同一套 Schema 校验，包括类型、枚举、范围、长度、正则、必填和有效期。

## 4. 业务快照契约

正式接入医疗请求时，业务事实至少固化：

- `json_item_attr_snapshot`：最终解析属性集合及来源摘要；
- `hash_item_attr_snapshot`：规范化 JSON 的哈希；
- `dt_item_attr_resolved`：解析完成时间。

业务执行、审计和历史回放读取快照；只有明确的重新解析动作才允许生成新快照。当前门诊诊疗申请和药品请求已经在创建时持久化属性快照、哈希和解析时间，M3 发药任务行复制开立快照而不按当前配置重解释。后续执行或库存上下文确需重新解析时，必须另存新快照及差异，不能覆盖原快照。

## 5. 服务边界

基础数据模块对外提供以下能力：

- 查询项目类型和可配置属性 Schema；
- 维护公共值和作用域覆盖值；
- 校验单个或整组属性；
- 按上下文解析最终属性；
- 生成规范化快照和哈希；
- 查询属性变更记录。

当前公开接口：

| 接口 | 用途 |
|---|---|
| `GET /api/platform/master-data/item-attributes/schema` | 获取按项目类型合并后的表单 Schema |
| `GET /api/platform/master-data/item-attributes/maintenance` | 获取当前租户公共值和有效覆盖值 |
| `PUT /api/platform/master-data/item-attributes/base-value` | 新增或按修订号更新租户公共值 |
| `PUT /api/platform/master-data/item-attributes/override` | 新增或按修订号更新租户、机构、科室覆盖值 |
| `POST .../base-value/disable`、`POST .../override/disable` | 停用值或恢复继承 |
| `POST /api/platform/master-data/item-attributes/resolve` | 按业务上下文解析最终属性 |
| `POST /api/platform/master-data/item-attributes/snapshot` | 生成规范化不可变快照及 SHA-256 哈希 |
| `GET /api/platform/master-data/item-attributes/changes` | 查询最近 100 条属性变更日志 |
| `GET /api/platform/master-data/item-attribute-configurations` | 查询当前租户可见的项目类型、属性定义和类型装配 |
| `POST/PUT .../definitions`、`POST .../definitions/{id}/status` | 在租户命名空间内维护属性定义及状态 |
| `POST/PUT .../assignments`、`POST .../assignments/{id}/status` | 维护属性与项目类型的装配、控件、条件和排序 |
| `GET .../item-attribute-configurations/changes` | 查询定义与装配的追加式审计记录 |

写入接口要求变更原因、全局幂等请求码和更新修订号，校验数据类型、单/多值基数、枚举、范围、长度、正则、ISO 日期时间、字典有效编码、有效期重叠及组织数据权限。`PROJECTED` 属性为只读，只能通过对应强类型字段维护。

业务模块只能依赖公开 API，不得访问属性 Repository 或表，也不得复制解析优先级。用于列表筛选、医疗安全、计费、库存或统计的动态属性必须先升级为 `PROJECTED`，再由受控投影列或索引承载查询。

## 6. 当前覆盖与本轮交付状态

### 6.1 已完成底座

- V19/V20 已落地项目类型树、平台公共项目预留、药品类型扩展、检验标本、检查部位方式和属性配置全套物理表；
- 已提供 Schema、公共值、作用域覆盖、确定性解析、快照与变更记录接口；
- 已支持租户公共值、机构/科室覆盖、恢复继承和 `EXPLICIT_NULL` 的 PC 端维护；
- 已提供租户属性定义和类型装配的受控接口与 PC 管理界面，平台定义只读，租户编码固定使用 `TNT.<TENANT-CODE>.` 命名空间；
- 字典单选/多选、枚举、布尔、数值、日期时间等使用结构化控件，动态属性启用检索前强制要求受控强类型投影；
- 门诊诊疗申请、药品请求已经持久化不可变快照，M3 发药任务行已经预留并承接同一快照契约；
- 自动化测试已覆盖类型继承、租户隔离、值校验、乐观锁、幂等请求、机构/科室覆盖、显式空值、来源证据、稳定哈希和历史快照不变；
- V30 已移除跨租户的全局排序唯一约束，改为租户内冲突校验和稳定排序，避免不同租户装配同一平台项目类型时互相影响。

### 6.2 本轮已完成

1. 属性定义和类型装配的受控配置接口及 PC 管理界面已经上线到基础数据中心“属性配置”页签；
2. 科室覆盖、恢复继承、`EXPLICIT_NULL`、字典引用单选/多选已经进入扩展属性维护流程；
3. 定义和装配变更已纳入追加审计，写操作带修订号、变更原因和幂等请求码；
4. M3 跨业务回归已验证：开立后修改有效属性覆盖值，既有药品请求与发药任务继续持有原快照和哈希；
5. OpenAPI 已随 M4.1 升级至 1.18.0 并重新生成前端类型；61 个 H2 迁移、77 项后端测试、架构检查、UI 规范检查和生产构建均通过；PostgreSQL、Oracle 迁移脚本已同步，需在对应数据库联调环境执行最终运行验证；
6. M3.4 收费只消费业务发生时已固化的项目、价格和属性快照；影响计价、库存、医保或医疗安全的动态属性必须先晋升为强类型字段或受控 `PROJECTED` 投影，不允许运行时扫描 JSON 值驱动核心规则。
7. M4.1 可以把已固化的项目属性快照作为辅助证据，但成人筛查范围、血压阈值、显著升高分流和确诊/转诊边界属于版本化临床规则，不建成项目动态属性，也不通过当前 JSON/EAV 配置运行时改写。

### 6.3 本轮明确不做

- 解析结果权威缓存表、属性发布版本、通用审批流；
- 允许按任意 JSON/EAV 值进行高频业务检索；
- 用动态属性替代药品产品/包装/批次、标本、检查部位方式、计费和医疗安全等核心强类型关系。
