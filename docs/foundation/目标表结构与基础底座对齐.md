# 目标表结构与基础底座对齐

## 1. 评审范围

本轮已阅读“表结构梳理”中的下一代独立模型、设计规范、并发设计和核心 DBML。核心模型目前包含 13 个逻辑域、99 张目标表：

| 逻辑域 | 表数 | 主要职责 |
|---|---:|---|
| SYS | 14 | 租户、机构、位置、人员、账号、角色、权限、模块 |
| BD | 11 | 编码系统、概念、值集与映射 |
| META | 14 | 定义包、实体字段、表单、规则、流程与扩展 |
| PI | 8 | 患者主索引、标识、人口学、关系与合并 |
| SC | 4 | 排班、预约、登记与队列 |
| VIS | 11 | 照护周期、就诊、诊断、观察和临床文档 |
| EX | 12 | 医嘱请求、执行、处方、检验检查与任务 |
| HPL | 2 | 照护计划与目标 |
| BIL | 8 | 账户、费用、发票、支付与账本 |
| INS | 4 | 保障、理赔与响应 |
| SUP | 6 | 库位、批次、库存流水、余额与发药 |
| INT | 2 | 事务 Outbox 与外部消息 |
| AUD | 3 | 数据血缘、访问审计与数据质量问题 |

该模型是后续业务数据库的设计目标，不是要求本轮提前创建 99 张空表。基础阶段要先把所有业务表都会依赖、且事后修改代价极高的规则固化。

## 3. 必须作为后续业务表的建模门禁

这些规则不需要现在创建空业务表，但第一张相关业务表出现时必须同步完成：

1. 每个聚合明确并发策略：`OPTIMISTIC_VERSION`、`INHERIT_PARENT`、`APPEND_ONLY`、`IMMUTABLE_VERSION` 或 `SERIALIZED_COMMAND`。
2. 诊断明细、处方明细、发票行等子实体若继承父聚合并发令牌，不独立暴露更新接口。
3. 费用、支付、库存和状态迁移使用追加流水与冲正/替代关系，不原地覆盖历史事实。
4. 每个自然业务键、外部报文键和写接口都明确幂等范围、请求摘要、冲突行为和过期策略。
5. 所有高频访问路径以 `tenant_id` 为首要隔离条件，索引必须来自实际查询与执行计划。
6. 核心患者、就诊、诊断、医嘱、费用和库存保持强类型；仅长尾表单与地方扩展进入版本化元数据。
7. 发布后的标准术语、表单、规则、流程定义不可就地改写；普通字典允许修改当前展示属性和启停状态，但编码不可修改/复用且每次变化必须写入追加式快照日志；需要按历史版本解释的业务不得使用普通字典。
8. 跨模块写入只写本模块数据，通过 Outbox 传播事实，禁止共享表写入。
9. 排班与号源模块必须遵循《基层排班与号源双模式设计》：简易模式不另建表、不绕过库存，专业模式是同一模型上的能力展开。

## 4. 在真实数据进入前必须关闭的 P0 项

以下项目需要密钥、身份平台或合规范围决策，本轮不能用默认实现代替，但必须在接入真实居民数据前完成：

- 身份证件、医保号和外部原始报文的密文存储、受控精确查询哈希、掩码展示与密钥轮换；
- OIDC/OAuth2、MFA、账号停用/锁定、会话撤销和正式密码策略；
- RBAC 之外的机构/科室/辖区/医患关系、用途限制与紧急访问策略执行器；
- `AUD.provenance` 级字段/版本血缘，查询、导出、打印和 AI 调用的完整访问审计；
- 生产密码产品/服务、SM2/SM3、CA 与个人证书、可信时间戳、密钥轮换、历史验证和防篡改归档；当前仅完成可替换证据底座和失败关闭门禁；
- 审计防篡改、留存、归档与查询性能策略，并接入统一密码证据底座；
- 数据分类分级、个人信息保护影响评估、测试数据脱敏和密钥托管。

当前 `national_id` 与居民标识字段仍为开发切片的明文兼容结构。因此仓库中的本地账号和样例数据库不得承载真实医疗数据。

## 5. 暂不前置的内容

- META 全量定义仓库和通用工作流引擎：等待至少 SOAP、生命体征和一种公卫随访表单共同验证后再固化。
- EX/BIL/INS/SUP 等业务域物理表：随纵向业务切片建设，不提前生成空壳。
- 目标模型中尚未落地业务域的更多数据库方言适配：当前已落地基础表具备 H2/PostgreSQL 与 Oracle 19c 迁移；后续新增业务表仍需同步提供两套方言并在真实数据库验证。
- FHIR 物理表：FHIR 是互操作契约，不直接复制为内部存储模型。

## 6. 结论

目标表结构对当前项目最重要的影响不是“现在建完所有表”，而是把 Snowflake BIGINT、字符串 ID 契约、租户复合关系、IAM、并发、幂等、Outbox、不可变版本、审计血缘和元数据边界变成开发门禁。本轮已完成其中可独立落地的系统级能力；剩余事项已经按“首个相关业务同步完成”与“真实数据前必须完成”分开，避免后续返工或形成虚假的通用平台。
