# 居民基本信息模型审计与建档迭代

## 审计结论

本轮对照 `nextgen-core.dbml` 的 `pi.patient`、`pi.patient_demographic_profile`、
`pi.patient_identifier`、`pi.patient_address`、`pi.related_person`、`pi.patient_employment`
及 `ins.coverage`，并结合基层门诊接诊时“姓名 + 至少一个其他身份要素”的核验要求完成审计。

现有“居民主索引 + 可拆分从表”的总体设计合理，能够作为居民中心、门诊接诊、公共卫生和医保业务的共同身份底座。
本轮补齐常住类型和工作单位模型，并将首次建档扩展为一次事务内保存多标识、人口学、地址、联系人、保障和工作单位。

## 本轮固化范围

- 居民主索引：健康档案号、姓名、性别、出生日期、电话、死亡状态、合并关系和乐观锁版本。
- 多标识：身份证、社保卡、居民健康卡、医保人员编号、护照、出生医学证明、机构病案号及其他标识。
- 人口学资料：国籍、民族、常住类型、婚姻状况、文化程度、职业类别、ABO/Rh 血型。
- 有效期资料：地址、联系人/监护人、保障信息和工作单位；地址、保障和工作单位各自最多一个主要记录。
- 首次建档：必要字段保持精简，扩展资料按需追加；身份证可自动带出出生日期和性别。
- 受控值：新增 `PI_IDENTIFIER_TYPE`、`PI_RESIDENCY_TYPE`、`PI_EDUCATION_LEVEL`、
  `PI_OCCUPATION_TYPE`，继续复用既有居民和保障字典。

## 明确不放入静态基本信息的内容

- 过敏史不是一个“是否过敏”标志，应形成独立、可追溯、可失效和可核验的临床安全记录。
- 孕产状态具有时间性，应归属妇幼/临床观察或健康事件，不作为长期人口学属性覆盖保存。
- 暴露史需要结构化记录暴露类型、期间、来源和证据，不以一段当前文本替代历史记录。

## 后续演进边界

- 证件号、电话、详细地址和医保个人编号目前先跑通业务流程；接入真实患者数据前，按密码应用方案切换为“密文 + 检索哈希”，接口继续只返回脱敏值。
- 国籍、民族和行政区划后续接入标准术语/区域数据，不把大规模国家标准代码复制为普通业务字典。
- 当前保障信息是居民中心的轻量视图；正式医保对接后由保险域维护支付方代码、待遇有效期与参保状态，居民中心只引用和展示。
- 标识新增、停用、核验、补发等生命周期应使用独立的主索引维护流程，不在普通档案编辑中直接覆盖。
