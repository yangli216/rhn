# 基础数据中心设计与接入指南

## 1. 建设目标

基础数据中心为门诊、住院、药事、收费、检验检查和公共卫生提供统一的疾病、诊疗项目、药品等可复用主数据。首版依据《PHIS基础数据中心原生需求说明书》和“表结构梳理”的下一代模型落地，优先跑通维护、机构采用、定价和业务读取主流程，同时保留标准版本、产品包装和后续对照映射的扩展边界。

本模块管理的是可复用定义，不管理处方、医嘱、费用、库存批次等业务事实。

## 2. 分层模型

| 层次 | 当前对象 | 使用规则 |
|---|---|---|
| 外部标准/平台术语 | 编码体系、疾病概念、别名 | 必须保存标准来源、版本、有效期和稳定编码；业务事实需要固化当时使用的编码体系与版本 |
| 租户主数据 | 诊疗项目、药品知识、生产企业、药品产品、包装 | 租户内统一编码；项目/产品共用目录项能力，强类型属性分表保存 |
| 机构目录 | 机构采用关系、院内码/院内名称、可开立/可执行/可收费/可库存等开关 | 机构差异不能反写平台或租户主数据 |
| 运行规则 | 有效期价格、包装用途 | 价格与项目定义分离；药品价格可精确到产品及包装 |
| 业务事实 | 诊断、医嘱、处方、收费、库存流水 | 由各业务模块拥有，只引用基础数据并固化必要快照，不进入本模块 |

## 3. 已落地范围

### 疾病

- 疾病编码体系可按版本登记，并明确区分西医诊断、中医病名和中医证候；首批提供 ICD-10 以及中医病名、证候示例版本；
- 疾病、症状、体征、健康问题、综合征使用受控概念类型；
- 支持标准编码、名称、简称、章节、定义、检索码、别名、有效期、状态和替代概念；
- 检索同时匹配编码、标准名称、简称、章节和别名；
- 公共卫生慢病、传染病/疾病报卡等属于独立的“疾病管理分类”，不复制疾病条目，也不固化为普通字典；数万级疾病目录以规则覆盖为主，精确疾病例外为辅；
- 管理分类可配置触发动作、报卡类型、时限、有效期和状态。医生选择诊断时同步展示命中的管理提示，并在诊断事实中固化当时的管理规则快照；
- 疾病识别规则支持按诊断体系、编码体系、疾病类型、章节和编码区间组合匹配。同一规则内条件取交集，多条纳入规则取并集，排除规则优先；精确疾病纳入/排除例外具有最高优先级；
- 疾病候选查询由服务端分页完成，包含别名和检索码匹配，管理界面不得预加载全量术语或在浏览器端筛选全量疾病；
- 标准概念由 `platform.terminology` 负责，不复制到普通字典。

### 诊疗项目

- 统一目录编码、名称、单位、有效期、状态、可开立和可收费属性；
- 强类型维护项目类型、子类型、用途、医疗技术标志、组合/单开、标本/检查/核算分类、重复开立规则、多部位计价、互认编码、孕期提醒和注意事项；
- 支持机构采用和按有效期维护机构价格；
- 检验、检查、治疗、手术、护理、材料、药事服务、床位、挂号及其他服务可使用同一模型。

### 药品

- 药品知识维护通用名、别名、药品类型、剂型、制剂规格、含量、储藏方式、处方药/基药/抗菌药分级/皮试、默认剂量与给药信息；
- 生产企业独立维护，并保留生产地分类；
- 药品产品关联药品知识与生产企业，维护商品名、批准文号、注册有效期、上市状态、生产地、进口标志、产品有效期、说明书和追溯拆零等属性；
- 包装独立表达单位、换算数量、条码和采购/销售/发药用途；
- 机构采用、价格挂在可经营的药品产品上，避免把知识定义、厂家产品、包装和机构目录混为一张表。

### 管理界面

入口为“系统设置 / 基础数据中心”，页面分为疾病、诊疗项目和药品三个工作区。疾病工作区再分为“疾病术语”和“管理分类与规则”：前者维护西医诊断、中医病名、中医证候，后者维护慢病、疾病报卡等业务分类及识别范围。识别范围以可审查的批量规则为主，只对少量特殊疾病维护精确纳入/排除例外，不提供全量疾病勾选器。支持查询、新增、编辑或状态变更，以及药品产品、包装、机构采用、价格、扩展属性和标准映射。生产企业与药品供应商统一在“平台管理 / 基础设置 / 厂商与供应商”中独立维护：生产企业按租户共享，供应商按机构隔离；基础数据中心和药库作业只保留快捷入口与业务引用，不再内嵌完整档案维护。诊疗项目与通用药品可在同一宽屏工作台按业务日期查看当前映射、建立国家/医保/监管/地方映射、替代旧映射并追溯历史。诊疗项目和药品产品另提供机构目录与价格宽屏工作台，集中展示业务日期快照、采用历史、价格历史和批量处理结果。

## 4. 模块接入规则

1. 疾病诊断选项从术语公开 API 获取，保存概念标识、编码、编码体系、版本和诊断体系；不得使用普通字典代替疾病库。保存诊断时必须由服务端按概念标识重新解析权威名称和有效管理分类，不得信任前端回传的名称或慢病/报卡标志。
2. 诊疗项目和药品必须保存目录项标识。业务单据还应固化当时的编码、名称、规格、单位和价格等必要快照，以保证历史重放。
3. 机构业务使用前必须检查当前机构采用关系、状态和有效期，再检查相应能力开关；不能仅凭租户主数据为有效就直接开立、收费或发药。
4. 价格按业务日期、机构、目录项、包装和价格类型解析。费用事实必须固化最终单价、数量、金额和价格来源，不能在历史查询时重新取当前价格。
5. 业务模块只能依赖 `platform.terminology.api` 和 `platform.masterdata.api`，不得访问其 Repository 或数据表。
6. `sdXxx` 状态和分类字段由普通字典校验与自动翻译；业务响应使用服务端返回的 `sdXxxText`，前端不自行维护中文映射。
7. 所有标识继续使用 Snowflake BIGINT，JSON 中按十进制字符串传递；写接口使用修订号控制并发。
8. 业务模块通过 `ItemStandardMappingDirectory` 按项目主体、映射用途和业务日期解析标准编码；不得读取当前映射表后自行判断有效期，也不得把医保码、国标码直接固化为主数据单值列。
9. 业务模块通过 `CatalogLifecycleDirectory` 解析机构采用关系和有效价格。价格解析优先级为机构指定包装、机构默认单位、租户指定包装、租户默认单位；调用方不得自行用“最新一条”代替有效期解析。

## 5. 数据库对象

本轮新增或扩展以下权威对象：

- 术语：`code_systems`、`concepts`、`concept_aliases`、`organization_concepts`；
- 疾病管理：`disease_management_programs` 保存管理项目，`disease_management_rules` 保存批量纳入/排除规则，`disease_management_members` 仅保存精确疾病例外；诊断事实通过快照字段留存概念版本、诊断体系和命中的管理规则；
- 类型与统一目录：`item_types`、`item_masters`、`catalog_items`、`item_aliases`；
- 诊疗项目：`service_items`、`laboratory_services`、`laboratory_service_specimens`、`examination_services`、`service_variants`；
- 药品：`medications`、`medication_western`、`medication_herbal`、`medication_vaccine`、`manufacturers`、`medication_products`、`item_packages`；
- 机构与价格：`organization_catalog_items`、`catalog_prices`、`catalog_change_batches`、`catalog_change_batch_rows`。
- 扩展属性：`item_attribute_definitions`、`item_type_attributes`、`item_attribute_subjects`、`item_attribute_values`、`item_attribute_overrides`、`item_attribute_changes`。
- 标准映射：版本化 `code_systems`、`concepts` 以及 `item_term_mappings`。

`item_types` 是项目类型树的权威来源，`item_masters` 提供平台公共项目锚点；现有目录项继续通过强制类型边界防止跨类型装载。检验标本、检查扩展、药品子类型等稳定结构以强类型表为权威来源，不能退化为动态属性。扩展属性表仅承接低频、差异化配置，并统一通过基础数据服务解析。

## 6. 首版字典

首版初始化 `BD_MASTER_STATUS`、`BD_CONCEPT_TYPE`、`BD_ALIAS_TYPE`、`BD_ITEM_TYPE`、`BD_SERVICE_TYPE`、`BD_SERVICE_USE`、`BD_MEDICATION_TYPE`、`BD_DOSE_FORM`、`BD_MANUFACTURER_TYPE`、`BD_PACKAGE_USE`、`BD_PRICE_TYPE`。本轮补充 `BD_DIAGNOSIS_DOMAIN`、`BD_DISEASE_MANAGEMENT_TYPE`、`BD_DISEASE_TRIGGER_ACTION`、`BD_STORAGE_TYPE`、`BD_ANTIMICROBIAL_LEVEL`、`BD_SERVICE_DUPLICATE_RULE`、`BD_PRODUCT_MARKET_STATUS`、`BD_PRODUCTION_PLACE`、`BD_SHELF_LIFE_UNIT`，并统一归入“基础数据”字典分类。诊断体系和管理类型字典只描述稳定枚举；具体疾病、慢病名单和报卡名单仍由术语与疾病管理关系表维护。这些字典用于界面选择、服务端写入校验和 `sdXxxText` 自动翻译。

## 7. 扩展属性能力

本轮纳入“强类型核心字段 + 类型化扩展表 + 元数据扩展属性 + 租户/机构/科室覆盖”的混合模型。扩展属性只承接低频、差异化、允许配置的属性；医疗安全、计费、库存、强关联和高频检索字段继续使用强类型列或关系表。

最终值必须由基础数据公开服务按固定优先级解析：科室覆盖、机构覆盖、租户覆盖、租户公共值、平台公共值、类型装配默认值、属性定义默认值。业务模块不得自行拼接覆盖层级，也不得直接读取属性表。

医疗请求在正式接入属性解析后必须保存最终属性 JSON、属性哈希和解析时间，确保历史业务不被后续配置变更污染。详细边界见《基础数据扩展属性本轮实施方案》。首个门诊诊疗请求切片已按该边界落地，没有提前预建空业务事实表。

业务模块通过 `ItemAttributeSnapshotDirectory` 获取规范化快照，必须把 `jsonItemAttrSnapshot`、`hashItemAttrSnapshot`、`resolvedAt` 与业务事实同时提交并持久化。快照哈希不包含解析时间，包含契约版本、主体、项目类型、业务日期、最终值、来源层级、作用域、定义修订和来源记录，因此同一配置与上下文可稳定复算。业务模块不得只保存属性值而丢弃来源证据，也不得在历史查询时重新解析当前配置。

## 8. 后续迭代顺序

首版有意暂缓批量导入预检、审批工作流、变更集、医保/国家标准对照、项目分组、复杂互斥规则和完整药品知识库。建议后续按真实业务切片依次补充：

1. Excel/标准文件导入、重复识别、错误回执和可恢复批次（诊疗项目与药品知识已完成）；
2. 国家、医保与地方标准映射及映射有效期（诊疗项目与通用药品已完成）；
3. 机构采用与价格的变更、停用、历史查询和批量操作（已完成）；
4. 门诊开立与收费预览场景验证目录解析契约（诊疗项目与药品产品首个切片已完成）；
5. 药品采购、库存、处方和发药验证包装换算与机构能力；
6. 在真实数据进入前补齐分类分级、敏感字段保护和关键发布动作密码证据。

这些能力应继续落在现有分层上扩展，不回退为按条线复制疾病表、项目表或药品表。

## 9. 批量导入能力

诊疗项目与药品知识支持 `.xlsx` 和 UTF-8 `.csv` 文件导入。导入采用“上传预检—行级修正—重新预检—显式提交”的可恢复批次模型，不允许上传后直接写入正式主数据。

- `master_data_import_batches` 保存租户、导入类型、文件 SHA-256、全局请求码、批次状态和各类行数；
- `master_data_import_rows` 保存原始行、规范化强类型数据、结构化错误、行状态和最终目标标识；
- 单批限制为 5 MB、2,000 行和 100 列，拒绝加密工作簿、公式单元格、重复表头和非模板文件类型；
- 预检复用诊疗项目与药品的字典、领域规则和租户存量编码校验，同时识别文件内重复编码；
- 错误行可以按修订号反复修正，已成功导入行不会被重试；运行时失败保留为 `PARTIAL` 批次；
- 请求码与租户组成唯一约束，相同请求码只有在导入类型和文件哈希一致时才返回原批次；
- 错误回执使用 UTF-8 CSV，并对电子表格公式前缀做转义，避免回执文件形成公式注入入口。

管理界面位于“系统设置 / 基础数据中心”的诊疗项目和药品目录工作区。用户可下载 XLSX/CSV 模板、上传预检、查看最近批次、修正错误、下载错误回执以及提交或取消批次。

## 10. 国家、医保与地方标准映射

本轮对齐上游 `bd.code_system`、`bd.code_release`、`bd.term` 和 `bd.item_term_mapping` 的语义边界。当前物理表 `code_systems` 已经以 `(scope_type, scope_id, code, version_code)` 唯一标识一次版本化发布，因此继续由一行承载“编码体系发布版”，不再建立内容重复的 `code_release` 表；`concepts` 保存该发布版中的标准条目。

编码发布版补充以下来源证据：

- `authority_type`：`NATIONAL`、`INSURANCE`、`REGULATORY`、`LOCAL`、`INTERNAL`、`OTHER`；
- `publisher`：权威发布机构；
- `source_uri`：发布文件或权威来源地址；
- `content_hash`：导入发布内容摘要；
- `version_code`、`effective_from`、`effective_to`：发布版本和有效区间。

项目映射使用 `item_term_mappings`，通过 `item_attribute_subjects` 的复合租户外键挂接诊疗目录项目或通用药品，同时直接外键关联 `concepts`。这一结构复用统一项目主体，但不会让动态扩展属性承担高频查询和外键完整性职责。

每条映射维护用途、等价关系、主要映射标志、限制范围、有效期、状态和替代来源：

- 用途：`CLINICAL`、`INSURANCE`、`REGULATORY`、`LOCAL`；
- 等价关系：`EXACT`、`EQUIVALENT`、`WIDER`、`NARROWER`、`RELATED`；
- 生命周期：`ACTIVE`、`SUSPENDED`、`RETIRED`、`SUPERSEDED`；
- 替代映射会把原记录截止到新记录生效前一天，原记录仍保留并可按历史业务日期解析；
- 同一项目、标准体系和用途在重叠有效期内只能有一个主要映射；同一标准条目不能建立重叠映射；
- 医保用途只能选择医保权威来源，监管用途只能选择国家或监管来源，本地用途只能选择地方或院内来源；
- 映射有效期必须位于编码发布版和标准条目的共同有效区间内。

公开接口如下：

| 接口 | 用途 |
|---|---|
| `GET /api/platform/master-data/standard-mappings/code-systems` | 按业务类型、权威类型、日期和关键字查询标准发布版 |
| `GET /api/platform/master-data/standard-mappings/terms` | 查询指定发布版的有效标准条目 |
| `GET /api/platform/master-data/standard-mappings/{subjectType}/{targetId}` | 返回业务日期下的有效映射和完整历史 |
| `POST /api/platform/master-data/standard-mappings/{subjectType}/{targetId}` | 新增映射或按修订号建立替代映射 |
| `POST /api/platform/master-data/standard-mappings/mappings/{mappingId}/status` | 暂停、恢复或停用映射 |

管理端采用 PC 宽屏双区布局：左侧展示所选业务日期的有效映射，右侧维护新映射，下方以宽表追溯全部历史。发布版与条目选择器统一支持名称、编码和拼音检索，并在选项右侧显示浅色编码。

## 11. 机构采用与价格生命周期

机构采用和价格继续复用原有效期表，不建立重复的“历史表”。`organization_catalog_items` 增加 `replaces_adoption_id`，`catalog_prices` 增加 `replaces_price_id`：变更时关闭原版本并建立新版本，原记录标记为 `REPLACED` 且截止到新版本生效前一天。暂停和恢复保留原有效期；停用必须指定截止日期。

核心约束如下：

- 同一机构和目录项目的采用版本有效期不得重叠；
- 相同目录项目、机构、包装和价格类型的价格有效期不得重叠，数据库中可空机构/包装不承担冲突判断，统一由领域服务按空值等价规则校验；
- 替代版本必须晚于原版本生效日期，并提交原版本修订号；
- 指定包装必须属于当前目录项目；机构和科室必须属于当前租户；
- 历史业务日期可解析已被替代或已停用版本，暂停版本不参与运行时解析；
- 价格解析按机构范围和包装范围择最具体记录，费用事实仍须固化最终价格和来源版本。

批量采用、停用和调价使用 `catalog_change_batches` 与 `catalog_change_batch_rows`。批次保存业务日期、请求编码、SHA-256 请求摘要、操作类型、成功/失败数量和操作人；明细保存来源 JSON、目录项、逐行结果、目标版本或错误。相同请求编码和相同摘要返回原批次，相同请求编码用于不同内容时拒绝执行。

管理接口如下：

| 接口 | 用途 |
|---|---|
| `GET /api/platform/master-data/catalog-lifecycle/catalog-items/{catalogItemId}` | 按机构和业务日期返回当前采用、当前价格及完整历史 |
| `POST /api/platform/master-data/catalog-lifecycle/catalog-items/{catalogItemId}/adoptions` | 新增机构采用版本 |
| `POST /api/platform/master-data/catalog-lifecycle/adoptions/{adoptionId}/replace` | 建立机构采用替代版本 |
| `POST /api/platform/master-data/catalog-lifecycle/adoptions/{adoptionId}/status` | 暂停、恢复或停用采用版本 |
| `POST /api/platform/master-data/catalog-lifecycle/catalog-items/{catalogItemId}/prices` | 新增有效期价格 |
| `POST /api/platform/master-data/catalog-lifecycle/prices/{priceId}/replace` | 建立调价版本 |
| `POST /api/platform/master-data/catalog-lifecycle/prices/{priceId}/status` | 暂停、恢复或停用价格 |
| `POST /api/platform/master-data/catalog-lifecycle/adoption-batches` | 批量采用或停用 |
| `POST /api/platform/master-data/catalog-lifecycle/price-batches` | 批量生效价格 |
| `GET /api/platform/master-data/catalog-lifecycle/batches/{batchId}` | 查询可审计批次及逐行结果 |

管理端使用面向 PC 的双区布局：左侧是业务日期快照，右侧是采用/价格版本编辑器，下方两张宽表分别追溯采用史和价格史。页面级批量工作台提供多项目选择、统一能力配置、统一调价和逐行结果，不使用移动端纵向长条表单代替桌面工作台。

## 12. 门诊诊疗项目开立接入样板

门诊开立使用 `care_requests` 保存请求公共事实，使用 `service_requests` 保存诊疗项目专有数量和临床说明。开立服务只依赖 `outpatient.api` 与三个基础数据公开契约，不读取基础数据 Repository 或表：

- `CatalogLifecycleDirectory` 返回目录定义、可选包装、机构采用和最具体有效价格；
- `ItemAttributeSnapshotDirectory` 按开立、执行机构科室上下文返回属性 JSON、稳定哈希和解析时间；
- `ItemStandardMappingDirectory` 按业务日期解析医保映射。

开立成功前必须同时满足：就诊处于接诊中、项目类型为诊疗服务、目录项目在业务日期有效且可开立、机构已采用且可开立；需要计价时，目录与机构均须可收费并存在有效销售价。执行机构科室必须属于当前租户及可访问工作上下文。

请求事实固化目录编码/名称/单位、机构本地编码/名称、采用标识及修订、价格标识及修订、单价/数量/金额/币种、属性快照及哈希、医保映射快照。后续改名、调价或属性调整不得改变历史请求。当前切片只形成费用预览；正式收费、退费和冲正仍由后续 `billing` 模块拥有不可变账务流水，不能把门诊请求表当作收费台账。

| 接口 | 用途 |
|---|---|
| `POST /api/encounters/{encounterId}/service-requests` | 校验目录契约并开立诊疗项目 |
| `GET /api/encounters/{encounterId}/service-requests` | 返回开立时固化的历史快照 |
| `POST /api/encounters/{encounterId}/service-requests/{requestId}/cancel` | 按修订号撤销请求并保留轨迹 |

PC 端入口位于居民中心的接诊工作区。项目下拉框按当前机构筛选已采用且可开立项目，支持名称、编码和拼音首字母检索，左侧显示名称、右侧显示机构编码；开立列表同时展示数量、单价、金额、属性哈希和状态。

## 13. 门诊药品处方与包装换算接入样板

处方头由 `request_groups` 归纳，药品明细复用 `care_requests` 公共请求事实，并由 `medication_requests` 保存处方专有语义。处方必须选择通用药品，具体产品与发药包装可选：临床可以仅按通用名形成请求，由药房后选产品；若临床已选具体产品，则继续提供包装换算与费用预览。产品路径会反向校验产品所属通用药品，不能形成通用名与产品不一致的请求。

新建处方处于 `DRAFT`，药品明细先以草稿加入；提交处方时至少需要一条有效草稿明细，并在同一事务内将处方和明细切换为 `ACTIVE`。草稿或已提交处方均可整单撤销，撤销原因和动作轨迹必须保留。已提交或已撤销处方不能继续新增药品。

通用名路径解析通用药品扩展属性和标准映射，不强制机构已选定某个产品，也不生成价格快照。产品路径同时解析产品目录、机构采用、可选包装和有效价格；普通处方要求机构目录可开立且可发药，自备药仍要求产品被机构采用并可开立，但跳过发药能力和价格要求。剂量、剂量单位以及疗程、疗程单位必须成对出现；未提交剂量、途径和频次时使用通用药品默认值。

包装换算遵循 `基本数量 = 申请数量 × 包装换算因子`。若命中包装级价格，计价数量使用申请包装数量；若回退到产品基本单位价格，计价数量使用基本数量。请求中固化包装单位/规格/因子、基本数量、计价数量和最终金额，后续包装或价格调整不得重算历史处方。

| 接口 | 用途 |
|---|---|
| `POST /api/encounters/{encounterId}/prescriptions` | 建立门诊处方草稿 |
| `GET /api/encounters/{encounterId}/prescriptions` | 返回处方组及其药品明细 |
| `POST /api/encounters/{encounterId}/prescriptions/{prescriptionId}/submit` | 按修订号提交整张处方并激活明细 |
| `POST /api/encounters/{encounterId}/prescriptions/{prescriptionId}/cancel` | 按修订号撤销整张处方及未撤销明细 |
| `POST /api/encounters/{encounterId}/medication-requests` | 向草稿加入通用名药品；产品、包装与价格按需校验 |
| `GET /api/encounters/{encounterId}/medication-requests` | 返回药品请求及开立时固化的完整快照 |
| `POST /api/encounters/{encounterId}/medication-requests/{requestId}/cancel` | 按修订号撤销单条药品请求并保留轨迹 |

PC 端入口位于居民中心接诊工作区的“门诊处方”。工作台先选择或新建处方草稿，再选择通用药品；具体产品和包装为同一行的渐进式可选项。各下拉支持名称、编码和拼音首字母检索，编码在选项右侧浅色显示。选择包装后即时展示包装数量到基本数量的换算预览；处方卡片并排展示通用药品/产品、用法、申请与换算、金额、安全提示、状态和单条/整单操作，宽表在自身容器内横向滚动，不撑破页面或弹窗。
