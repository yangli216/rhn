# 基层排班与号源双模式设计

- 状态：基础能力基线 v1.1
- 日期：2026-08-30
- 适用范围：基层门诊排班、号源预约、窗口挂号和候诊衔接
- 权威模型：`表结构梳理/nextgen/model/scheduling-slot-appointment-model.md`

## 1. 产品原则

本系统首先服务社区卫生服务中心、乡镇卫生院、村卫生室等基层医疗机构。默认使用简易排班模式，确保常规操作只需要回答四个问题：谁出诊、哪天出诊、上午还是下午、可以预约多少人。

需要分时预约、专家号、渠道额度、检查设备或复杂停替诊时，再由管理员启用专业模式。两种模式共用相同的数据表、库存事务和事件记录，不复制功能、不迁移历史数据，也不因界面简化而绕过租户、并发和库存校验。

## 2. 模式能力

| 能力 | 简易模式（默认） | 专业模式 |
|---|---|---|
| 建排班入口 | 单页快速排班 | 模板、例外、生成和调整 |
| 必填信息 | 科室、人员、日期/星期、时段、人数 | 资源、服务、地点、模板、号源及规则 |
| 资源 | 根据人员任职自动创建或复用 | 医生、团队、地点、设备和复合资源 |
| 号源 | 池号源、共享额度 | 池号源、顺序号、分时号及渠道独立额度 |
| 规则 | 采用平台和机构默认值 | 支持范围绑定、优先级和规则试算 |
| 停替诊 | 单班次暂停、恢复和取消 | 影响分析、审批、通知、改约、退款 |

简易模式不是“另一套简化数据库”。其一次保存由后端编排为资源补齐、模板发布、实际排班生成和共享号源池创建。自动生成的对象在切换为专业模式后可以继续维护。

## 3. 简易排班主流程

1. 用户进入排班页，系统根据工作上下文自动带出当前机构、科室和可排班人员。
2. 用户选择日期范围或星期，勾选上午、下午或全天；系统带出科室默认起止时间。
3. 系统带出默认可约人数；用户可直接修改。
4. 用户点击“保存并发布”。系统以一次幂等命令生成实际排班和共享号源池。
5. 返回结果按“已生成、已存在、失败”分组，失败项给出具体日期、时段和原因，不要求用户查看技术日志。

简易模式页面不展示资源成员、版本号、渠道额度、回收策略、规则 JSON 等专业概念。

## 4. 预约、加号和挂号

- 患者端、电话和窗口预约都必须携带渠道来源，并使用同一套锁号和确认预约事务。
- 简易模式默认所有已授权渠道共享号源池，不要求基层机构先分配渠道额度。
- 窗口“直接挂号”在后端自动完成锁号、预约确认和挂号，不能绕过库存。
- 只有明确配置为“纯现场接诊”的排班允许无预约挂号；此时挂号必须关联实际排班。
- 急诊无排班挂号使用独立来源标识，不混入普通门诊号源统计。
- 同一预约只能产生一条挂号记录；重复点击或网络重试返回原结果。

## 5. 模式参数

以下参数通过通用参数中心解析，允许继承，当前机构或科室未配置时向上短路获取：

| 参数键 | 类型 | 默认值 | 建议作用域 | 用途 |
|---|---|---|---|---|
| `outpatient.scheduling.management-mode` | 字符串/字典 | `SIMPLE` | 租户、机构、科室 | 排班管理入口模式 |
| `outpatient.scheduling.simple.default-capacity` | 数值 | `50` | 租户、机构、科室 | 简易班次默认可约人数 |
| `outpatient.scheduling.simple.generate-days` | 数值 | `28` | 租户、机构 | 默认生成未来排班天数 |
| `outpatient.scheduling.simple.default-service` | 字符串 | 无 | 机构、科室 | 默认诊疗服务项目标识 |
| `outpatient.scheduling.simple.default-location` | 字符串 | 无 | 机构、科室 | 默认诊室或服务位置标识 |
| `outpatient.scheduling.simple.morning-period` | JSON | `08:00-12:00` | 机构、科室 | 上午班次起止时间 |
| `outpatient.scheduling.simple.afternoon-period` | JSON | `14:00-17:00` | 机构、科室 | 下午班次起止时间 |

模式和默认人数属于业务参数。具体服务、位置必须解析为当前租户中的有效主数据；不能把失效对象或其他租户标识作为默认值使用。

与代码分支和数据库约束绑定的封闭取值登记为系统枚举，首批至少包括 `SC_SCHEDULE_MANAGEMENT_MODE`、`SC_BOOKING_POLICY`、`SC_SLOT_MODE`、`SC_QUOTA_MODE`、`SC_QUOTA_ROLE`、`SC_APPOINTMENT_STATUS`、`SC_REFUND_STATUS` 和 `SC_REGISTRATION_SOURCE`。基层操作界面只显示中文含义，不直接暴露枚举编码。

## 6. 升级和降级

- `SIMPLE -> PROFESSIONAL`：允许原地升级。既有模板、排班和号源继续使用，只增加专业编辑能力。
- `PROFESSIONAL -> SIMPLE`：只有未来排班不存在编号/分时号、渠道独立额度、复合资源和自定义规则时才允许。否则提示需要先处理的项目，不自动删除配置。
- 参数切换只影响新建入口和后续编辑方式，不批量改写已发布排班的模式快照。

## 7. 开发门禁

首个业务切片必须同时满足：

1. 同一幂等请求不会重复生成排班、预约、挂号或候诊票。
2. 并发抢最后一个号时最多一个请求成功，池计数、锁号、预约和事件一致。
3. 共享额度模式不要求渠道配额行，专业独立额度模式才校验渠道额度。
4. 窗口加号与患者预约共用库存事务，不存在绕过号源的普通挂号分支。
5. 预约取消后退款状态独立变化，不能用“已退款”覆盖预约取消事实。
6. 候诊按优先级和稳定队内序号排序，重复叫号命令可幂等重放。
7. Oracle 下完成资源时间重叠检测、固定加锁顺序、非负库存条件更新和过期锁号扫描验证。

## 8. 分阶段交付

第一阶段只实现简易排班、共享池、预约、窗口加号、挂号和候诊主流程。第二阶段增加模板例外、顺序号和分时号。第三阶段再开放渠道独立额度、复杂规则、复合资源和批量停替诊。

专业能力可以从第一阶段开始保留底层字段和服务边界，但不得提前暴露给普通基层用户或要求其完成无必要配置。

## 9. 2026-08-28 实现基线

本轮已交付第一阶段的“简易排班、窗口挂号与候诊衔接”主切片：

- 门诊医疗下新增“排班与号源”入口，默认只要求选择医生、服务、日期、星期、上午/下午和号源数。
- 后端一次幂等命令完成资源复用、模板及班次生成、实际排班发布、共享号源池和事件记录。
- 简易模式固定采用 `POOL + SHARED`，专业字段、渠道配额和分时能力保留在统一模型中，但不进入基层日常页面。
- 门诊医疗下新增独立“门诊挂号”工作台；窗口人员检索居民、选择当天可用排班或临时接诊，确认后在同一事务内占用共享号源、固化预约快照、生成挂号记录和科室候诊票，并关联就诊。
- 挂号成功即时展示挂号单号、候诊号和今日挂号记录，居民中心可携带 `residentId` 显式跳转办理，接诊工作台继续消费同一候诊队列。
- 未建立排班时保留“临时接诊”入口，只生成挂号和候诊记录、不伪造号源占用；普通排班挂号不允许绕过库存。
- 候诊号按租户、科室队列和业务日期独立编号。开始接诊和完成就诊推进候诊票、预约及临床状态；挂号记录保持 `REGISTERED`，仅在撤号时进入 `CANCELLED`，避免用候诊状态覆盖挂号事实。
- 同一幂等编码重复提交返回原挂号结果；同一居民在同一科室已有活动就诊时拒绝再次挂号。
- 模式、默认号源数、生成天数和上午/下午时段接入通用参数中心；模式与状态文本接入全局字典翻译。
- PostgreSQL/H2 与 Oracle 19c 均已建立迁移脚本；挂号状态分离迁移版本为 `49`。H2 已完成主链测试，Oracle 19c 开发库已从 `41` 连续升级到 `49` 并通过应用启动和真实查询验证。

当时的 `appointments` 仅用于现场挂号时形成确认快照；该阶段边界已由第 11 节的独立预约管理基线替代。临时锁号与过期释放、停替诊影响分析以及专业排班页面仍按后续阶段推进，不在基层简易入口提前增加操作成本。

## 10. 2026-08-30 简易排班日常维护基线

本轮在不增加专业排班配置成本的前提下，补齐基层机构最常用的班次维护闭环：

- 未来且尚未结束的班次允许直接调整起止时间、号源上限和诊室；号源上限不得低于已锁定、已占用和冻结数量。
- 班次已有锁号或占用时仍可增加号源和修改诊室，但不允许改变时间，避免既有预约失去有效时段。
- 已发布班次支持暂停、恢复；状态变化同步冻结或激活共享号源池。无任何锁定、占用或冻结记录时允许取消班次并关闭号源池。
- 医生冲突从“完全相同时间”提升为真正的时间区间重叠检测，同一医生跨服务项目也不能生成相互覆盖的班次。
- 修改、暂停、恢复和取消均要求业务命令号与原因，重复命令安全返回当前结果，并留下排班事件；号源容量变化同时记录号源事件。
- 简易排班页面只提供“修改、暂停/恢复、取消”四类日常动作，并在取消前直接提示已有使用量，继续隐藏模板版本、渠道额度和规则 JSON。
- 数据库迁移版本为 `66`。H2 已通过迁移和排班回归；Oracle 19c 开发库已从 `55` 连续升级到 `66`，并通过应用启动、健康检查、排班参数和真实排班查询验证。

本基线仍不开放有预约班次的批量停替诊、患者改约与退款编排，也不开放专业模式的分时号、顺序号和渠道独立额度；这些能力进入下一阶段，并复用当前事件、号池和锁号事务继续建设。

## 11. 2026-08-30 独立预约管理基线

本轮将预约从“窗口挂号的附属快照”提升为可独立管理的业务事实，并保持基层操作入口简洁：

- 门诊医疗下新增独立“预约管理”工作台，按日期、状态和居民关键词查询预约；支持检索居民、选择未来班次后新建预约，以及取消和改期。
- 预约状态从 `BOOKED` 开始，转挂号后进入 `REGISTERED`，后续接诊完成可进入 `VISITED`；取消保留原预约记录、取消时间和原因，不物理删除业务事实。
- 新建预约直接占用共享号源；取消释放原号源；改期在同一事务内占用目标号源并释放原号源，原预约转为取消、新预约记录 `rescheduledFromId`，避免覆盖历史。
- 新建、取消和改期均要求业务命令号并支持幂等重放；预约事件和号源事件同时追加，便于追踪一次操作对预约与库存的双重影响。
- 预约改期按号源池主键固定顺序加锁；目标号源不足、班次不可用或并发冲突时整笔事务回滚，不留下“双占号”或“原号已释放但新号未成功”的中间状态。
- 当日已预约居民可从预约工作台进入门诊挂号。收费登记意向和最终挂号显式携带 `appointmentId`，复用预约已占用的号源，不再次锁号或扣减库存；同一预约最多生成一条挂号记录。
- 预约状态与来源纳入系统枚举 `SC_APPOINTMENT_STATUS`、`SC_APPOINTMENT_SOURCE`，接口继续使用统一字典文本翻译；数据库迁移版本为 `71`，PostgreSQL/H2 与 Oracle 使用等价表结构和约束。

当前基线聚焦人工预约主流程，暂不加入患者自助认证、临时锁号超时、批量爽约判定、短信/微信通知、停替诊批量改约、预约取消退款和专业模式渠道配额。后续能力必须继续复用本轮预约台账、号源事务和事件，不另建平行预约表或独立扣号逻辑。

## 12. 2026-09-01 专业排班最小可用基线

本轮开放专业模式的第二阶段最小闭环，但仍以基层机构能理解和维护为边界：

- `outpatient.scheduling.management-mode` 在当前科室解析为 `PROFESSIONAL` 时，排班页默认进入专业工作区；未启用时明确显示“科室尚未启用”并提供参数管理入口，不再用“按需启用”暗示功能已经可用。
- 专业模板一次维护名称、医生、门诊服务、有效日期、每周出诊日、固定起止时间、号源方式和诊室。保存模板时以幂等生成任务发布实际班次，并沿用原有医生时间冲突检测。
- 号源方式首批支持 `POOL` 和 `TIMED`。`POOL` 为整个时段的共享总量；`TIMED` 按 5 至 120 分钟的固定时间片生成可独立预约的班次，每个时间片拥有独立库存，预约、挂号和改约继续调用既有号源事务。
- 日期例外首批支持 `CLOSED` 和 `OVERRIDE`。停诊日期不生成班次；临时调整可以覆盖当天起止时间、号源数和分时时长，也允许为固定规则之外的日期临时加班。
- 模板规则和日期例外作为长期配置保存，实际排班继续固化医生、服务、地点、管理模式和容量快照；后续修改规则不能静默改变已经发布且可能被预约的班次。
- 前端保留简易排班切换入口。即使科室启用了专业模式，日常临时增加上午或下午班次仍可使用简易表单，避免为简单操作强制维护模板。

当前分时实现以“一个时间片对应一个实际班次和一个 `TIMED` 号源池”为最小模型，因此可直接复用现有预约库存、事件和并发控制，也能让预约端精确选择时间。它暂不等同于完整专业号源平台：渠道独立额度、顺序号、规则引擎、复合资源、模板修订后批量重生成，以及有预约班次的停替诊影响分析、通知和改约仍属于后续迭代，界面不得提前标注为已支持。

本轮数据库迁移版本为 `125`，新增专业模板分时时长和日期例外表；后端集成测试覆盖分时拆分、停诊、临时调整及幂等重放，前端测试覆盖科室启用后的专业模板创建入口。

## 13. 2026-09-02 科室号与挂号费治理基线

本轮在简易、专业两种排班方式上统一补齐“按科室挂号”和“按医生挂号”，并把挂号费纳入医疗服务目录价格治理：

- 排班模板、实际班次和号源资源显式保存挂号对象 `DEPARTMENT` 或 `PRACTITIONER`。科室号不再伪造医生，患者先占用科室号源，到科后由分诊或接诊流程分配实际接诊医生；医生号仍保留人员任职校验和跨服务时间冲突检测。
- 简易排班默认使用科室号，适合普通门诊、全科门诊和基层分诊场景；需要锁定专家、专病或指定医生时再切换为医生号。专业模板同样支持两类挂号对象以及总量号源、分时号源和日期例外。
- 挂号收费不再由前端按“普通/专家”写死金额，也不在选号阶段假算年龄减免或医保报销。排班返回对应门诊服务在服务日期、当前机构下生效的 `SALE` 目录价；正式医保基金支付、个人账户、自付、优待减免和退费继续由结算规则按患者待遇计算。
- 普通门诊诊查费、专家门诊诊查费、急诊诊查费、中医辨证论治费、基层一般诊疗费和便民门诊等差异应建成独立服务目录项目，分别维护机构适用价，而不是把职称或机构等级写成排班字段。
- 每个机构价格版本保留生效日期、失效日期、政策文件或价格文号、调价原因和历史版本。没有当前有效价格的收费项目会明确标记“未定价”，并阻止排班挂号直接出单，避免用临时默认价收费。
- 基层启用“一般诊疗费”时，应按当地政策停用同一诊疗场景下的门诊诊查费及被合并项目，避免一般诊疗费与诊查、注射等费用重复收取；具体互斥范围由当地价格目录和结算规则配置。
- 专业模式的日期例外、模板列表、排班列表和挂号费列表均提供独立的纵向或横向滚动区域，表头保持可见，窄屏下不再裁掉操作列和右侧内容。

本轮数据库迁移版本为 `128`，PostgreSQL/H2 与 Oracle 脚本同步维护。既有医生排班自动回填为医生号，旧接口未传挂号对象但传入医生时继续按医生号解释，保证存量调用平滑升级。
