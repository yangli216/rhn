# 门诊主流程验收基线

## 1. 目的

本基线把门诊主流程的分散测试收敛为一条可重复执行的验收门禁。验收运行在每次随机创建的 H2 内存数据库中，完整执行 Flyway 迁移，进程结束后数据自动销毁，不写入 Oracle 持久化开发库。

## 2. 一键执行

在项目根目录运行：

```bash
./scripts/verify-outpatient-main-flow.sh
```

等价 Maven 命令：

```bash
cd backend
mvn -Dgroups=outpatient-main-flow test
mvn -Dtest=ArchitectureTest test
```

ArchUnit 使用独立的 JUnit Platform 引擎，当前 Maven 标签过滤不会把它计入第一条命令，因此脚本显式执行第二条架构门禁。

## 3. 当前覆盖

| 主流程阶段 | 验收内容 |
|---|---|
| 预约与号源 | 预约、锁号、改约、取消及重复提交 |
| 挂号与收费 | 现场挂号、挂号费、支付回调、最后一个号源并发、退号退款与号源返还 |
| 接诊 | 候诊、开始接诊、暂挂、恢复、诊毕及接诊后终止 |
| 连续接诊保护 | 切换患者前识别未保存病历、诊断和待确认医嘱；诊毕不得静默丢弃草稿 |
| 病历与诊断 | 结构化病历、主要诊断、临床文档签署与诊毕门禁 |
| 科室结构病历 | 简易/结构化书写模式切换、科室表单版本发布、字段校验及文书定义快照 |
| 受控打印 | 已签署门诊病历、生效处方生成正式 PDF，输出完整性摘要、按就诊查询、历史下载及重打留痕 |
| 命令重试 | 开始、暂挂、恢复、病历保存和诊毕在响应不确定时使用原命令号安全重试 |
| 病历模板 | 个人/科室模板、受控段落 Schema、专科分类、使用计数及软停用 |
| 常用诊疗方案 | 个人/科室方案结构化持久化、诊断规则、主数据快照解析、使用计数及软停用 |
| 医嘱与结算 | 诊疗项目、药品医嘱自动计费，未结算执行拦截，结算后放行 |
| 药房 | 接方、审方、库存预留、配药、发药、退药、费用冲正与退款 |
| 检查检验 | 待结算、登记、采集、执行、结果发布及门诊流转状态 |
| 治疗 | 待结算、待执行、执行中、完成及门诊流转状态 |
| 科室协同 | 院内会诊发起、接收、意见回传、拒绝与撤回；未完成会诊阻断诊毕 |
| 院内转科 | 转科前身份、病历、主诊断和签署门禁；原就诊暂挂、目标科室接收后自动生成新挂号与就诊，原就诊标记已转科 |
| 全程协同 | 从接诊到收费、药房、医技、治疗和可以离院的患者去向聚合 |
| 复合门诊闭环 | 同一就诊同时开立药品、检验、检查和治疗，统一结算后依次完成发药、两类医技报告与治疗，最终五个阶段全部完成并允许离院 |
| 架构边界 | 业务模块无循环依赖，跨模块调用只经过公开 API |

## 4. 数据隔离规则

- 自动化验收只使用 `test` profile，数据库地址为 `jdbc:h2:mem:rhn-${random.uuid}`。
- 每个 Spring 测试上下文使用独立数据库；不连接 Oracle，不需要清表脚本。
- 用例内业务编码和幂等键带随机后缀，允许同一命令连续执行。
- Oracle 仅用于人工运行态验收；人工验收记录必须走到诊毕、取消或终止，不留下候诊或接诊中记录。
- 不允许提供跨业务表直接 `DELETE` 的验收清理脚本，以免绕过账务、库存、号源和临床事实的状态机。
- 常用诊疗方案只负责带入诊断和医嘱草稿；模板药品必须重新核对患者过敏事实，正式开立仍经过目录、机构采用、价格及过敏规则校验。
- 病历模板只允许保存主诉、现病史、既往史、查体所见和诊疗计划，内容模式固定为 `RHN.OUTPATIENT_NOTE_TEMPLATE.V1`；不得复制患者标识、生命体征、诊断或医嘱，带入后仍须由医生核对、保存并签署。
- 病历模板默认只填充空白段落；覆盖既有病历草稿必须由医生在本次带入操作中显式选择，模板使用本身不得产生正式临床文档版本。
- 默认使用“基础门诊病历（简易）”，不能因为科室存在结构表单而强迫基层医生增加录入步骤；只有医生主动选择科室结构时才展示扩展字段。
- 科室结构表单采用不可变发布版本；发布新版本会退役旧版本，新病历只能选择当前发布版本。临床文书必须同时保存表单编码、版本、完整字段定义和填写值，历史病历展示与打印不得依赖后来被修改的配置。
- 结构字段由服务端校验允许字段、必填、数据类型、文本长度、数值范围和选项范围；前端校验只用于即时提示，不能代替服务端规则。
- 模板及历史病历带入、病历字段编辑、诊断调整和待确认医嘱都必须计入当前患者的未保存状态；切换患者、暂挂或终止时显式确认放弃，诊毕时必须先处理完草稿。
- 开始接诊、暂挂、恢复、病历保存和诊毕必须携带稳定命令号；相同命令和相同载荷返回首次结果，相同命令换用不同载荷返回 `IDEMPOTENCY_KEY_REUSED`，不得重复生成临床事实或状态事件。
- 医生站只对已签署病历和药品明细全部生效的处方开放打印；首次生成形成不可变 PDF 输出及 SHA-256 摘要，后续重打复用原输出并单独记录重打任务，不得绕过签署状态直接打印草稿。
- 历史病历必须按来源文书版本展示正式输出、模板版本、用途和原打/重打次数；补打只能复用同一不可变输出，当前签署版本没有正式输出时才允许首次生成。
- 复合门诊验收必须使用同一个 `encounterId` 贯穿临床、费用、药房、医技和治疗，不能把几个独立模块用例拼接后宣称主流程闭环；流程完成时五个阶段都必须为 `COMPLETED`、账户余额及未开票金额均为零。
- 药房接方必须按当前机构和药房经营目录解析实际 `stockItemId`，测试及业务代码不得假定本地体验数据、Oracle 存量数据和新建数据库使用相同库存主键。
- 院内会诊不切换原就诊归属：会诊期间原就诊保持诊疗中，目标科室只接收并回传意见；存在 `REQUESTED` 或 `ACCEPTED` 会诊时不允许原科室诊毕。
- 院内转科必须创建新的目标科室挂号和就诊，不直接改写原就诊科室；接收前原就诊暂挂，接收成功后原就诊与原队列号标记 `TRANSFERRED`。
- 转科接收命令必须可重试，重复提交不得多建挂号、队列号或就诊；目标科室拒绝后原就诊保持暂挂，由原医生明确恢复，避免系统悄然改变医生工作状态。
- 基层简易模式首期只开放同机构科室选择，保持“类型、目标科室、紧急程度、原因和摘要”的最小录入；跨机构转诊、会诊医师指定和时限策略留给专业模式。

## 5. 完成判定

只有以下条件同时满足，才视为门诊主流程回归通过：

1. `outpatient-main-flow` 标签下全部测试通过；
2. `ArchitectureTest` 通过，业务模块不存在循环依赖；
3. 后端完整 `mvn verify` 通过；
4. 前端 `npm run check` 通过；
5. Oracle 正式开发实例健康检查通过，关键接口契约与 H2 验收一致。
