# RHN 数据库设计与协作规范

适用范围：当前 RHN 代码库。上游模型的设计规范作为参考；发生差异时以项目已确认的领域契约、物理映射和迁移为准。

## 1. 结构、业务语义与统计语义

- Flyway 迁移定义预期结构，Oracle 元数据快照反映开发库实际结构；存在差异时先评审原因。
- `docs/foundation/rhn-physical-schema-map.json` 维护逻辑名、物理名、中文注释和字段映射。
- `docs/database/annotations` 维护业务用途、一行粒度、责任人、写入入口、字段解释和业务关联。
- `backend/rhn-analytics/src/main/resources/semantic/outpatient-ontology.v1.yaml` 继续作为统计实体、维度、指标、白名单关系的来源。
- 工作台的图、AI 资料和检查报告是派生产物。业务说明审核和建议审核不等于统计资产发布，也不会自动执行 DDL。

## 2. 表与字段命名

- 物理表采用 `RHN_<DOMAIN>_<ENTITY_ABBR>`，标识符不超过 30 字符。上游规范的 `HI_` 在本项目使用 `RHN_`。
- 逻辑表采用 `domain.entity`；沿用已登记的逻辑名称，不通过工作台自动重命名。
- 主键和引用字段使用 `ID_`；状态和受控代码使用 `SD_`；业务编码使用 `CD_`。
- 名称、说明、布尔、日期时间、金额、数量分别使用项目登记的 `NA_`、`DES_`、`FG_`、`DA_ / DT_`、`AMT_`、`QTY_` 语义。
- 表注释说明“一行代表什么”，字段注释说明业务含义，避免只有缩写解释。
- 物理字段按 `_` 分词，每段最多 7 个字符；完整标识符最多 30 个字符，不允许空词段。仅完整名称 `REVISION` 作为乐观锁契约例外，`SN_REVISION` 等组合不享有例外。
- 长词必须在 [统一字段缩写词典](physical-column-naming.md) 登记完整词与缩写，保持唯一含义；优先复用已有同义缩写，禁止按长度截断或逐表另起缩写。逻辑名、Java/API 属性和枚举值保留业务可读性。
- 字段改名同步所有主外键引用、JPA 映射、原生 SQL、统计 YAML 和目录映射，通过新增迁移原位改名；历史 SQL 保留原文。表名与索引/约束名按各自规则管理，不随字段词段替换。

## 3. 主键、租户与关系

- 可独立引用的实体使用 Snowflake 正数 BIGINT；API 中以十进制字符串传输。
- 租户拥有关系按项目约定包含 `ID_TNT`。父子引用使用完整的租户复合条件。
- 唯一约束明确全局范围或租户范围。业务编码、证件号和外部流水不能替代内部主键。
- 物理外键、人工确认的业务关联、候选关系分开登记。候选关系不进入默认 AI 查询上下文。
- 关系需记录字段顺序、基数、业务依据与确认状态。数据库基数由主外键和唯一约束判断；统计聚合安全性继续由语义计划与验证器负责。

## 4. 业务粒度、历史与并发

- 主档与多值明细、请求与执行、收费与支付、当前状态与历史事实应明确边界。
- 可修改聚合按项目契约使用 `REVISION`；由父聚合管理的明细不独立暴露并发修改入口。
- 费用、支付、库存及关键状态使用追加事实与冲正/替代关系；已签署或发布的版本保留历史。
- 核心临床事实、金额、库存和租户关系保持强类型；JSON 与扩展字段需明确版本化契约。
- 写操作由所属模块负责，跨模块通过公开契约与事件协作。

## 5. 字典、金额、时间与索引

- 区分系统枚举、普通字典、标准术语与业务实体；字段补充说明中记录绑定目录及依据。
- 金额和数量明确精度、单位与舍入规则；日期与时间点分别建模。
- 索引来自实际查询路径与执行计划，并保留租户隔离条件。外键存在不代表索引已经满足查询需求。
- H2 兼容结构与 Oracle 物理类型不同。跨方言检查对常见类型进行归一化；默认值、函数索引和检查表达式须结合原始约束人工确认。

## 6. 变更与验证

- 新变更使用新的配对 PostgreSQL / Oracle 迁移；不修改已发布基线、不清空迁移历史。
- 同步维护表字段映射、业务说明和受影响的统计实体、维度、指标。
- 自动验证使用 `test` 和随机 H2 数据库；工作台采集 Oracle 仅读取结构元数据，不读患者业务行。
- 工作台「规范检查」与后端 `RhnPhysicalSchemaGovernanceTest` 执行字段词段门禁。新增未知长词须先登记缩写；已登记词会给出目标字段名。命名变更须验证升级前后的行数据、字段类型/默认值/注释、复合外键、唯一键和索引均保留。
- AI 提交建议、依据和影响范围；开发人员评审业务语义。建议审核后仍经代码评审、测试和原有发布流程落地。
- 规范与业务知识属于代码资产，纳入 Git 评审。工作台不会自动提交或推送。
