# 下一代基层信息系统表结构设计规范

> 版本：1.11（医疗项目扩展属性与作用域治理）  
> 适用范围：下一代逻辑模型、元数据仓库和后续物理模型  
> 设计目标：同一逻辑模型可适配 Oracle、达梦、人大金仓、OceanBase、TiDB 等目标数据库  
> 当前阶段：规范逻辑语义和建模质量，不直接产生生产 DDL

## 1. 规范定位

本规范由 `RBMH_PHIS_SHOW` 原始快照的 377 张表、44 个视图、10,110 个字段及下一代 DBML 模型反向提炼；当前已确认排除 13 张备份、测试、废弃或旧版副本，活动审计范围为 364 张表、44 个视图、9,889 个字段。它重点解决现结构中已经反复出现的问题：

- 门诊、住院、家床复制诊断、医嘱、处方、费用和结算表；
- 关系只存在于应用约定，父子字段类型和索引意图不一致；
- 租户、ID、金额、数量、时间、状态和标志没有统一语义域；
- 接口镜像、日志、读模型、审批副本和业务事实混在同一模型；
- 动态扩展通过增加列、复制表或自由大字符串实现；
- 设计直接绑定某一种数据库的物理类型，难以支持国产数据库。

本规范不是旧命名的格式化清单，也不是 Oracle DDL 规范。它先定义稳定的业务语义和结构契约，再由数据库适配器编译为各目标数据库的物理实现。

本项目不从旧数据库迁移数据。旧库采集结果只用于识别业务术语、能力覆盖和结构反模式，不构成目标模型的字段兼容、主键映射、双写、对账或切换要求。新系统必须从业务场景独立定义实体、字段、关系、标识和生命周期。

## 2. 规则语言与审计口径

### 2.1 约束级别

- **MUST**：不满足时不得发布，除非形成有期限、有责任人的书面例外；
- **SHOULD**：默认必须满足，偏离时需要说明业务理由和替代控制；
- **MAY**：根据业务量、数据库能力和运行指标选择。

### 2.2 风险级别

- **P0**：可能造成跨租户、敏感数据、资金或核心事实不可逆错误；
- **P1**：可能造成主键、关系、类型、业务粒度或模型一致性错误；
- **P2**：可能造成状态解释、查询性能、生命周期或长期维护问题；
- **P3**：文档、命名和一般可理解性问题。

### 2.3 证据层级

| 证据 | 能确认的事项 | 不能单独确认的事项 |
|---|---|---|
| 静态元数据 | 名称、字段、类型、可空、主键、索引、注释 | 数据是否合法、约束是否会阻断现有写入 |
| 数据剖析 | 空值、重复、孤儿、长度、非法金额和时间 | 目标业务访问路径与容量假设 |
| 运行证据 | 目标执行计划、写入责任、容量和最后使用时间 | 业务语义和合规要求 |
| 业务确认 | 粒度、状态机、来源权威性、留存责任 | 物理变更对性能和锁的影响 |

规则命中表示“存在待确认或整改的证据”，不是直接执行 DDL 的指令。

## 3. 模型分层与对象归属

### 3.1 每张表必须有明确结构角色

每张表必须且只能声明一个主要角色：

| 角色 | 定义 | 设计要求 |
|---|---|---|
| 主数据 | 相对稳定的业务对象 | 自然键、有效期、发布状态、变更责任 |
| 交易事实 | 一次实际业务发生 | 明确粒度、患者/机构/时间和来源 |
| 明细/关联 | 父事实的组成或多对多关系 | 父引用、顺序、复合唯一性或稳定 ID |
| 不可变流水 | 财务、库存、状态、审计事件 | 追加写、顺序、冲正/替代关系 |
| 元数据 | 表单、字段、规则、流程和字典定义 | 包、版本、发布、签名、有效期 |
| 集成镜像 | 外部报文或第三方目录 | 来源、批次、原文、解析状态、留存期 |
| 读模型 | 面向查询的投影或聚合 | 可重建、刷新点、来源版本，不反向写核心 |
| 归档 | 只用于历史追溯 | 只读、留存期、访问责任、退出日期 |

交易事实、集成镜像、读模型和归档对象不得用同一张表同时承担。

### 3.2 单一事实粒度

表定义必须说明“一行代表什么”。同一行不得混合：

- 请求与执行结果；
- 当前状态与完整状态历史；
- 费用事实与支付事实；
- 外部原始报文与规范业务字段；
- 患者主档与联系人、证件、地址等多值对象。

已确认的业务语义参考决策必须进入独立登记表，并高于自动合并建议。本项目患者基本信息只参考 `HI_PI`，`MS_BRDA` 不参与下一代患者模型设计。`HI_PI` 也不是待迁移表，不约束新系统字段或主键。

### 3.3 共享核心优先

门诊、住院、家床、家医等场景记录同一种业务事实时，必须进入共享核心，并通过 `encounter_type`、`episode_type`、来源和类型扩展表达差异。禁止继续复制 `*_DIAG`、`*_ORDER`、`*_PRES`、`*_FEE`、`*_SETTLE` 表族。

### 3.4 动态扩展边界

- 患者、就诊、临床请求、诊断、金额、库存和审计等核心属性必须强类型建模；
- 长尾表单字段可以进入版本化元数据和结构化快照；
- 需要搜索、统计、质控或规则计算的动态字段必须形成类型化索引投影；
- 禁止用自由 EAV、逗号分隔 ID、未声明 Schema 的 JSON 代替核心关系。

## 4. 命名与命名空间

### 4.1 逻辑名称

- 第一段必须是已登记的业务域代码，后续段表达业务对象；权威逻辑名称采用 `<domain>.<entity>`，例如 `pi.patient`、`bil.payment`；
- 业务域代码以 `SYS/BD/PI/SC/VIS/HPL/BIL/EX` 为基线，并按现状扩展 `INS/SUP/META/INT/ANL/AST/AUD/ARC`；完整目录见 `domain/domain-catalog.csv`；
- 目标数据库不适合使用 Schema 命名空间时，由适配器按已登记的物理命名策略扁平化；本项目默认预览为 `HI_<DOMAIN>_<ENTITY_ABBR>`，例如 `sys.organization_capability → HI_SYS_ORG_CAP`，但元数据仍保留完整逻辑名、域和实体；
- 物理名缩写必须来自项目统一词典，默认单词段不超过 7 个字符；缩写必须全局唯一、稳定、可逆，禁止按字符数自由截断；
- 表、字段和约束逻辑名使用 ASCII `lower_snake_case`；
- 普通业务属性优先使用可理解的业务词；实体标识可使用公司内已形成统一认知的受控缩写，但必须登记于 `model/entity-key-catalog.csv`，禁止同一缩写多义或同一实体多种缩写；
- 能被多个同域对象误解的通用名称必须补足业务限定词，例如 `service_schedule`、`patient_registration`、`execution_task`、`patient_account`；
- 可被其他表引用的实体主键必须采用来源型标识 `id_<entity_abbr>`，例如 `pi.patient.id_pi`、`sys.organization.id_org`、`bd.dict_def.id_dict`；目标模型禁止新增无来源语义的单独 `id`；
- 外键必须保留被引用主键的完整名称；同一表多次引用同一实体时，在目标主键后追加角色后缀，例如 `id_org_issuer`、`id_pract_author`、`id_wf_state_from`；禁止使用后缀式 `<entity>_id`；
- 与父实体一对一且不可独立存在的从属表可共享父主键，并继承其来源名，例如 `pi.patient_demographic_profile.id_pi`；
- 状态、类型、类别和其他受控枚举字段使用 `sd_*`，且必须绑定字典或标准术语；
- 时间点与日期时间使用 `dt_*`，不含时刻的业务日期使用 `da_*`，区间两端还必须保留明确角色语义；
- 严格二值布尔字段使用 `fg_*` 并采用肯定语义；存在未知、未采集或不适用时改用 `sd_*` 显式枚举。

### 4.2 禁止用名称表达生命周期

生产命名空间不得出现 `BAK`、`OLD`、`TEST`、`FIXED`、数字版本后缀。版本、环境、修复批次和归档状态必须进入元数据或独立命名空间。

### 4.3 物理名称适配

逻辑名称是权威名称。命名元数据必须区分三层：

1. `logical_name`：跨数据库稳定的 `<domain>.<entity>`，例如 `sys.organization`；
2. `physical_name`：按项目和数据库适配策略生成；当前项目默认 `HI_SYS_ORG`；
3. `source_name`：采集快照中的旧物理表名，仅用于设计证据追溯。

`HI` 是当前项目的可配置物理前缀，不得写入业务实体代码。数据库适配器可以因 Schema 能力、标识符长度、保留字和大小写规则生成 `SYS.ORG`、`SYS_ORG` 或 `HI_SYS_ORG`，但必须登记命名策略并保留可逆的 `logical_name → physical_name` 映射，禁止人工为不同数据库维护多套语义名称。

同一审计视图不得把来源物理名与目标逻辑名当成同一层展示。界面默认显示当前项目物理名，并允许切换逻辑名；详情必须同时给出逻辑名、默认物理名和设计参考来源。

#### 4.3.1 公司受控字段前缀

目标逻辑字段使用跨数据库稳定的 `lower_snake_case`，并保留公司内已形成统一认知的受控前缀。当前项目默认物理名为对应逻辑名的大写形式。受控前缀是公司级统一语言，不按旧模不透明缩写处理：

| 前缀 | 唯一语义 | 示例 | 禁止用法 |
|---|---|---|---|
| `ID_` | 系统内部标识或实体引用 | `ID_PI`、`ID_ORG`、`ID_DICT` | 不得承载挂号号、发票号等业务编码；不得单独命名为 `ID` |
| `CD_` | 业务对象编码、业务单据编码 | `CD_REG`、`CD_INVOICE`、`CD_STAFF` | 不得用 `NO_`、`SD_` 代替业务编码 |
| `SD_` | 状态、类型、类别及其他受控字典代码 | `SD_GENDER`、`SD_STATUS`、`SD_ORG_TYPE` | 不得保存自由文本；必须绑定普通枚举字典或标准术语 |
| `NA_` | 名称、标题或显示文本 | `NA_DICT`、`NA_DICT_ITEM` | 不得代替可计算的代码或标识 |
| `DES_` | 说明、备注或变更原因 | `DES_DICT`、`DES_CHANGE_REASON` | 不得保存状态或关系 |
| `FG_` | 严格二值布尔 | `FG_PRIMARY`、`FG_ACTIVE` | 不得表达未知、未填、不适用等多状态语义 |
| `DT_` | 时间点或日期时间 | `DT_CREATE`、`DT_UPDATE` | 不得仅凭数据库物理类型判断时区语义 |
| `DA_` | 不含时刻的业务日期 | `DA_BIRTH`、`DA_SERVICE` | 不得存储时间点 |
| `SN` / `SN_` | 行号、排序号、批次内序号、版本序号 | `SN`、`SN_VER`、`SN_LINE` | 不得表示可对外引用的业务编码 |

业务编码字段必须使用 `CD_`。例如逻辑字段 `registration_no` 的当前项目默认物理名为 `CD_REG`，不得生成 `NO_REG`；逻辑字段 `invoice_no` 默认生成 `CD_INVOICE`。业务编码、内部标识和标准代码的判定以字段语义域及元数据绑定为准，不以旧字段名称或 `varchar` 类型推断。

字段前缀不替代语义域：`DT_` 仍须在元数据中区分 `Instant`、`OffsetDateTime` 与 `LocalDateTime`，`SD_` 仍须登记普通枚举字典或标准术语，`CD_` 仍须登记编码规则、唯一范围、签发方和有效期。乐观锁字段是受控例外：统一命名为 `revision`，Java 使用同名属性并标注 JPA/MyBatis-Plus 的 `@Version`，同时绑定专用 `LockVersion` 语义域。

### 4.4 临时、备份和废弃对象

- 采集快照是不可变证据，不直接删除对象记录；
- 名称含 `BAK/BACKUP/TEST/TMP/TEMP/OLD/FIXED` 或注释明确标记备份、测试、废弃的对象只能作为排除候选；
- 自动排除必须同时满足高置信命名/注释证据和已确认的排除登记，登记至少包含对象、类型、证据、理由、确认人和日期；
- `_1`、日期或数字后缀以及名称中间出现 `OLD` 不足以自动排除，必须结合表说明、字段相似度、行数、依赖和业务使用情况确认；
- 已确认排除对象不得进入活动业务域参考、并发证据和新模型归纳，但必须保留在排除清单和原始快照中以供追溯。

## 5. 键、租户与关系

### 5.1 内部主键

- 每个可独立引用的实体必须有稳定主键；
- 默认使用可跨节点生成的有序 `GlobalId`；
- 主键逻辑名为 `id_<entity_abbr>`，其中缩写必须在 `model/entity-key-catalog.csv` 唯一登记；修改缩写等同于修改全域关系契约，必须连同外键、索引和元数据引用一并评审；
- 引用字段必须与目标主键同名或以目标主键名加角色后缀，从字段名可直接回溯至来源实体；
- 可变业务编码、身份证、医保号、外部流水号不得作为内部主键；
- 纯关联表可以使用复合主键，但必须证明不会被其他实体独立引用；
- 日志和流水也必须具备稳定定位键或明确的复合定位契约。

### 5.2 外部标识

新系统需要承载的外部业务标识至少包含 `system/source`、值、签发方、有效期和验证状态。旧数据库主键不是新系统外部业务标识，不进入目标运行模型，也不建立 `legacy_id_map`；只有真实业务协议中的外部编号才按本节建模。

### 5.3 租户边界

- 所有租户拥有的业务表必须有 `id_tnt`，逻辑上必填，并明确引用 `sys.tenant.id_tnt`；
- 平台级对象必须显式声明作用域；按公司字典命名规则建模时使用 `sd_scope_type`，不得用空租户代替“全局”语义；
- 唯一性必须说明是全局唯一还是租户内唯一；
- 子表关系必须验证父子属于同一租户；
- 物理数据库支持复合约束时，优先编译为 `(id_tnt, <source_identifiable_id>)` 租户安全关系；否则由访问层、写入校验和持续数据质量检查共同实现。

### 5.4 关系契约

每条关系必须在元数据中声明：

- 父子实体和对应字段；
- 基数、必填性、所有权与删除策略；
- 是否跨租户、跨上下文或多态；
- 强物理外键、逻辑外键或异步校验的执行方式；
- 延迟检查、历史保留和孤儿隔离策略。

父子字段必须绑定同一语义域。物理外键可以因目标数据库或分布式架构受限而不创建，但不能没有关系契约和替代控制。

## 6. 逻辑类型与语义域

### 6.1 先选语义域，再选物理类型

字段必须先绑定逻辑类型、语义域、必填性、长度/精度、值域、单位、敏感级别和时区语义。数据库适配器根据目标数据库及版本选择物理类型。

第一版语义域基线见 `cleaning/semantic-domains.csv`。关键域包括：

- `GlobalId`、`TenantId`、`PatientId`、`OrganizationId`；
- `Money`、`Quantity`、`Percentage`、`IntegerCount`；
- `LockVersion`；
- `BusinessDate`、`LocalDateTime`、`Instant`、`Duration`；
- `BooleanFlag`、`StatusCode`、`CategoryCode`、`TerminologyCode`；
- `EncryptedPersonalIdentifier`、`PasswordHash`、`SecretCiphertext`；
- `JsonDocument`、`BinaryContent`。

### 6.2 跨数据库保守适配

| 逻辑域 | 物理能力要求 | 兼容策略 |
|---|---|---|
| GlobalId | 16 字节或等价稳定表示 | 原生 UUID 能力经版本认证后使用；否则定长二进制或受约束字符表示 |
| BooleanFlag | 二值且不可出现第三状态 | 有原生布尔则使用；否则整数/字符加合法值约束 |
| Money | 精确十进制、明确精度和小数位 | 禁止浮点与字符串；币种独立保存 |
| Instant | 统一绝对时间线和精度 | 优先可靠的带时区类型；否则保存 UTC 语义并固定会话时区策略 |
| JsonDocument | Schema、版本、规范序列化 | 原生 JSON 能力不足时用大文本保存，并由应用校验及类型化投影索引 |
| LargeText/Binary | 大对象生命周期和哈希 | 大对象可外置，核心表保存定位、摘要、大小、类型和血缘 |
| LockVersion | 非空、可比较、原子更新 | 字段名统一为 `revision`；默认映射为整数修订号；数据库原生行版本仅在适配器认证后使用 |

达梦、人大金仓、OceanBase、TiDB 等必须按具体产品、兼容模式和版本完成适配器认证，不能仅凭“兼容 Oracle/MySQL/PostgreSQL”作假设。

### 6.3 数值

- 金额使用精确十进制并保存币种；
- 数量必须说明计量单位，数值与单位共同构成语义；
- 比例必须说明采用 `0..1` 还是 `0..100`；
- 序号、次数和计数使用明确范围的整数；
- 禁止未说明精度的通用数值承载金额或关键计算值。

### 6.4 时间

- `BusinessDate` 不含时区；
- `LocalDateTime` 必须能确定所属机构时区；
- `Instant` 表示绝对时刻，统一可信时钟与精度；
- 持续时间必须包含单位；
- 外部接口时间原文可保留，但必须和解析后的规范时间分列。

### 6.5 状态、代码与标志

- 二值标志逻辑必填，存在未知/未采集时改为显式枚举；
- 普通状态和分类必须绑定普通枚举字典；字典只维护当前项并以追加日志追踪变更，不引入业务版本表；
- 普通枚举字典可归入独立、可分层的管理分类；分类只服务管理导航、检索和责任划分，不参与字典项值域解释，也不得替代行业标准术语层级；
- 已使用的普通字典项不得物理删除或复用编码；确需历史时点解释时，在业务事实保存显示快照或升级为独立的版本化标准术语体系；
- 字典项确需携带业务适用性时，应使用受属性定义约束的类型化扩展配置：属性定义必须声明数据类型、基数、引用值域、最低自定义层级和覆盖策略；最低层级采用平台、租户、机构、科室的累计层级，不允许每个属性自行改变继承顺序；作用域值必须使用来源型租户、机构和科室外键，不得使用无约束 `scope_id`；多值字典引用必须按行保存，禁止以逗号字符串或不可检索 JSON 代替；
- 字典项属性按“科室→机构→租户→平台”固定优先级解析；下级无配置时继承，显式空集用于停止继承。业务事实使用配置结果时必须保存所选字典项、使用场景及必要显示快照，不得根据当前配置反向重解释历史交易；
- 生命周期状态必须有允许流转规则；
- 诊断、药品、服务等标准术语必须同时保存编码系统、代码和版本策略；
- 禁止只在字段注释中描述合法值。

### 6.6 医疗基础数据分层

疾病、手术操作、诊疗服务、药品和医用耗材不得继续压缩为一张通用目录表，也不得把国家或行业标准目录当作普通枚举字典。目标模型必须同时满足以下分层：

1. **标准术语层**：编码体系、不可变发布版、术语项、术语关系和跨体系映射分别建模；诊断和手术等临床事实保存标准术语引用及编码、名称、体系、发布版快照。
2. **本地业务目录层**：可开立、可收费或可库存对象共享稳定目录项目身份；诊疗服务、药品产品和医用耗材的专有属性使用强类型从属表。
3. **药品分层**：通用药品与具体厂家产品分开；包装换算、批准文号、注册信息、处方与抗菌毒麻皮试属性不得混在同一行。
4. **机构运营层**：机构启用、可执行科室、开立/收费/库存权限和价格有效期独立于平台或租户公共目录；历史价格不得被当前价格覆盖。
5. **组合与分类层**：检验、检查和医嘱组套保存成员关系；面向科室和业务选择的分类树与组套分开，不用字符串列表表达成员或适用科室。
6. **监管与追溯层**：医保、卫健、药监等外部目录通过标准发布版进入本地；源系统扩展属性可使用受发布版 Schema 约束的 JSON，但进入开立、收费、库存、质控或统计的字段必须投影为强类型；药品追溯码和 UDI 生产标识按可独立扫码单元建模。

旧系统成熟字段必须逐字段给出 `RETAIN/NORMALIZE/DERIVE/EXTERNAL_STANDARD/REMOVE/PENDING` 取舍。`REMOVE` 只允许用于旧技术状态、重复快照或已有明确替代控制的历史包袱；不得因目标模型追求表少而静默丢失业务能力。

### 6.7 医疗项目扩展属性与作用域覆盖

- 药品、诊疗项目的稳定公共字段使用强类型主表；西药、草药、疫苗、检验和检查等稳定专有字段使用一对一类型扩展表。
- 标本、部位方式等多值关系必须独立建表，不得保存为自由 JSON、逗号分隔字符串或单值兼容字段。
- 客户长尾属性必须先定义数据类型、基数、值域、单位、Schema、适用项目类型、可覆盖范围和业务上下文，再允许保存值。
- 扩展属性挂载必须具有可校验的真实外键，不得使用没有关系契约的任意 `subject_type + subject_id`。
- 项目公共值与租户、机构、科室覆盖必须分表；作用域编码由后端确定性生成，最终值使用全系统唯一的固定优先级解析。
- 跨租户共享的具体药品或诊疗项目必须有独立平台公共身份；租户业务交易仍引用租户运营主档，解析时允许本地值继承平台公共项目值。
- 医疗安全属性必须声明是否允许覆盖以及覆盖是否只能加强；显示条件不得代替服务端安全校验。
- 进入开立、执行、发药、收费或库存规则的最终属性值必须在业务发生时保存来源和定义修订快照，后续配置变更不得重新解释历史事实。
- 动态属性成为高频检索、统计、质控或核心规则条件后必须投影或晋升为强类型字段，扩展值不得与强类型权威字段双写为两个可修改来源。

## 7. 可空、默认值与约束

- 必填性来源于业务语义，不来源于旧数据是否有空值；
- 主体、租户、业务时间、状态和事实核心值原则上逻辑必填；
- 不使用 `NULL` 同时表达未知、未采集、不适用和已删除；
- 默认值只能表达确定的业务默认，不得掩盖调用方漏传；
- 自然键、幂等键和关联表组合必须声明唯一性；
- 范围、互斥、单值列、起止时间等约束应进入逻辑约束目录，再由适配器决定数据库约束或应用校验。

存量表增加非空、唯一或外键前，必须先完成空值、重复和孤儿数据剖析。

## 8. 索引与访问路径

### 8.1 索引是访问契约的实现

设计索引前必须记录查询目的：租户过滤、父子加载、自然键查找、状态队列、时间范围、幂等写入或对账。不得根据字段名称机械增加单列索引。

### 8.2 一般顺序

组合索引通常按以下意图组织，但必须用目标业务访问场景和执行计划验证：

1. 强制隔离条件，如 `id_tnt`；
2. 等值条件，如父引用、机构、患者、状态；
3. 范围或排序条件，如业务时间；
4. 必要的覆盖列。

外键或逻辑父引用在高频加载、删除检查和数据质量巡检中使用时，应具备可用的前导索引。上线前必须检查重复索引、写放大和执行计划回归。

## 9. 状态历史、审计与不可变事实

### 9.1 通用审计

- 可修改主数据和交易表必须保存可信的 `created_at/created_by`；
- 更新责任使用统一策略保存，不能只保存最后更新而丢失关键业务历史；
- 临床签名、审批、发布、结算、支付和库存动作必须保存业务操作者、系统账号、时间和来源；
- 技术审计日志不得替代业务状态历史。

### 9.2 版本语义与并发控制

业务版本、来源版本和乐观锁版本是三种不同语义，必须在字段元数据中分别标记：

- `BUSINESS_VERSION`：标识文档、定义包或业务事实的不可变版本；
- `SOURCE_VERSION`：保存新系统实际对接的外部系统版本水位，仅用于接口幂等、增量同步或来源追踪；
- `LOCK_VERSION`：只用于检测并发覆盖，不表达业务版本顺序。

每张逻辑实体必须声明并发策略：`NONE`、`OPTIMISTIC_VERSION`、`APPEND_ONLY`、`IMMUTABLE_VERSION`、`SERIALIZED_COMMAND` 或 `INHERIT_PARENT`。策略与结构角色共同决定是否需要乐观锁版本，禁止给所有表机械复制通用版本字段。`DB_NATIVE` 只能登记为目标数据库适配实现，不能成为逻辑策略。

采用 `OPTIMISTIC_VERSION` 时：

- 必须绑定且只能绑定一个名为 `revision`、逻辑类型为 `LockVersion` 的非空字段；Java 实体对应同名属性必须标注 `@Version`；
- `revision` 必须有确定初值，并在同一更新语句中比较和递增；影响行数为零表示并发冲突；
- 跨数据库默认使用整数版本号，不使用可空字符串、更新时间或随机文本模拟版本锁；
- 数据库原生行版本只属于已认证的物理适配策略，不得泄漏为跨数据库业务契约；
- 通常不为 `revision` 单独建索引，实体应先由租户边界和主键定位。

追加写、不可变发布版本和可重建读模型不通过修改旧记录解决冲突，分别依赖幂等键、版本唯一性或投影水位。旧库 `REVISION` 的字符值、全表复制方式和运行实现不迁移；新模型中的 `revision` 依据业务粒度、结构角色、生命周期和写入场景重新生成，并采用整数语义。

聚合内明细采用 `INHERIT_PARENT`：明细不设置独立版本锁，其增删改必须在聚合根的同一命令和并发边界内完成。若明细已成为可独立引用、独立流转的业务事实，应升级为独立聚合并重新选择策略。

### 9.3 追加写领域

- 财务、支付、库存、状态历史、审计和已签名临床事实采用追加写；
- 错误通过冲正、撤销、替代或新版本修复；
- 反向记录必须引用原记录；
- 当前余额、当前状态和统计值是可重建投影，不是唯一事实来源。

### 9.4 生命周期

主数据使用状态和有效期；业务事实使用撤销/更正；归档使用独立生命周期。禁止用一个通用 `deleted_flag` 代替所有领域生命周期。

## 10. 安全与敏感数据

- 每个字段必须声明敏感级别、用途、访问角色、留存期限和脱敏策略；
- 密码只保存合格的慢哈希，不得可逆；
- 私钥、令牌和对称密钥优先进入外部密钥服务，确需入库时保存密文和轮换元数据；
- 身份证、医保号、手机号等个人标识保存密文；需要等值检索时使用独立、受控的检索哈希；
- 接口原文、日志和读模型同样执行敏感分级，不因“技术表”豁免；
- 敏感字段不得进入普通错误日志、索引键或无保护导出。

## 11. 元数据、表单和工作流

- 定义必须属于可发布的版本包；
- 草稿可修改，发布版本不可原地修改；
- 实例绑定确切版本和 Schema 哈希；
- 规则、工作流、表单和扩展使用统一版本生命周期；普通枚举字典只保留当前值和追加式变更日志；
- 动态引用必须限制目标实体类型；
- 类型化动态值一行只能有一个值列生效；
- 高频动态字段晋升为核心字段或专用投影，不能长期依赖全量 JSON 扫描。

### 11.1 统一管理门户边界

统一管理门户是组织机构、人员账号、权限和普通枚举字典等治理能力的操作入口，不是独立的业务事实域：

- 机构、人员、账号、管理模块和权限仍归属 `SYS`；普通枚举的字典定义、当前字典项和追加式变更日志归属 `BD`，不引入业务版本表；
- 门户菜单或管理模块只能描述入口、路由和授权资源，不得复制组织、字典等权威业务数据；
- 机构多编码、地址和联系方式拆为组织聚合内明细，组织主表不增加重复列或拼接字段；
- 机构与科室分别使用 `sys.organization` 和 `sys.department` 权威树；科室必须归属一个机构，任职、权限、参数、排班和临床业务需要科室上下文时显式使用 `id_dept`；
- 诊室、物理病区、床位组和药房窗口使用 `sys.location`，位置可选归属科室，但不得以物理位置代替科室主档；
- 组织简称、说明、性质、虚拟标志和同级排序等高频单值可进入组织主表；业务管理、医联体、协作和转诊等非权威关系必须进入有效期化关系明细，不得改变权威父树；
- 组织服务能力、科室负责人和人员联系方式均是多值且带有效期的组成明细；内部负责人必须引用有效任职，账号表不得复制人员姓名、电话、机构、科室或角色；
- 人员主档、机构聘用、标准岗位、科室任职、执业资质和登录账号必须分别建模；原 `practitioner_role` 式混合表禁止进入新模型；
- 人员证件、人事主索引和外部身份源标识统一保存密文及受控检索哈希，并登记标识体系、绑定状态、核验状态和有效期；人员主表不得保存明文证件或单值手机号；
- 租户级人员主档编码与机构聘用编码分离；同一人员跨机构不得因员工编码相同或不同而自动合并，必须基于受控标识和人工治理结论；
- 一人多任职时必须选择当前 `assignment` 工作上下文，权限计算和关键业务审计同时携带账号、人员、任职、机构和服务位置；不得将全部任职权限无条件合并；
- 组织移动、合并、拆分、暂停和停用必须追加不可覆盖的前后快照、原因、操作者和生效时点；已发布组织不得物理删除；
- 账号/任职/岗位—角色和角色—权限必须分别建模并声明规范作用域与有效期；角色绑定使用稳定来源型主键，不允许可空作用域字段参与主键；页面可见性不能替代服务端授权；
- 普通枚举字典使用独立分类树进行管理归类，字典定义必须归属一个同作用域分类；分类树不改变字典项的平面枚举语义；
- 普通枚举字典只维护稳定定义和当前字典项，不建立独立业务版本；已使用编码不得复用，分类、字典及字典项的新增、修改、移动、启用和停用必须追加变更日志；
- 管理门户的查询列表属于可重建投影，不得成为 `SYS/BD` 权威写入来源。

### 11.2 系统参数管理

当前项目参数管理只维护当前定义、当前值和修改记录，不建设审批、发布或业务版本流程。必须满足：

- 参数分类、参数定义、作用域当前值和追加式变更日志分表建模；
- `cd_param` 全局唯一，退役后不得复用；
- 参数定义必须声明强类型、JSON Schema、默认值、单位、普通字典绑定、敏感级别和允许作用域；
- 参数当前值以 `(id_param, cd_scope)` 唯一，`cd_scope` 必须由作用域类型和上下文标识确定性生成；
- 作用域值明确区分 `INHERIT`、`OVERRIDE`、`RESET_DEFAULT` 和 `EXPLICIT_NULL`；
- 密钥类参数只保存受控密钥引用，明文不得进入当前值、变更快照、日志或导出文件；
- 参数分类、定义和当前值使用 `revision` 乐观锁；Java 同名属性标注 `@Version`；
- 每次参数定义或当前值修改必须在同一事务追加变更日志，保存目标、动作、作用域、前后快照、原因、幂等请求编码、操作人和时间；
- 变更日志只追加，不允许更新或删除；人工回退必须作为一次新修改记录；
- 已留痕的参数当前值不得物理删除，停用和恢复默认都必须修改当前行并追加日志；
- 最终值和缓存是可重建运行结果，不建立可人工维护的权威表。

### 11.3 收费、结算、支付与票据

- 收费事实、结算交易、异步支付指令、成功资金事实、患者账务分录和财政票据必须分层；结算单不得以 `invoice` 命名并同时承担财政票据职责；
- 待支付、失败、超时、查询和重复回调保存在支付指令及事件中，只有成功资金移动才能写入支付事实；
- 已记账收费、支付和分录只追加，退款、补收和冲正必须生成反向事实并引用原记录；
- 同一账务事务必须按币种借贷平衡；账户余额和结算分类汇总只能作为可重建投影；
- 结算明细必须固定收费事实、结算数量和各付款方金额；资金来源合计必须等于结算净额；
- 票据开具、作废、红冲、打印和交付必须追加业务事件；票据文件保存对象引用，不保存大对象或长期有效访问地址，打印次数不得同时作为主表权威字段；
- 收费员日结只固定成功支付或退款事实作为金额成员，不得同时累计关联结算和票据金额；
- 外部支付存在时应启用逐笔渠道对账；未接外部支付的项目可不启用对账表族，不得为低频异常预建通用审批或工单系统；
- 可修改聚合统一使用 `revision` 并映射 Java `@Version`；价格等业务修订快照使用 `sn_*_revision`，不得声明为 `lock_version`。

## 12. 集成、读模型与归档

### 12.1 集成边界

原始报文与解析后的业务事实分层保存。集成记录至少包含来源、消息类型、业务关联、校验状态、重试、幂等键、接收/发送时间、保留期和敏感策略。

### 12.2 读模型

视图、统计宽表、搜索索引和监管报表必须声明来源模型、刷新点和重建方式。读模型不得成为核心业务写入来源。

### 12.3 归档与退役

备份、旧版、测试、修复批次表不得留在核心 Schema。退役前必须确认应用依赖、任务、视图依赖、最后写入、合规留存和恢复方式。

对已经确认退役的对象，审计动作以依赖解除、历史留存和访问收口为主，不再投入字段级标准化整改；其静态字段问题仅作为退役风险证据保留。

## 13. 表设计交付模板

每张新表在字段评审前先提交以下表级信息：

| 项目 | 必填内容 |
|---|---|
| 逻辑名称 | `context.entity` |
| 中文名称 | 业务一致的实体名称 |
| 一行粒度 | 一行代表的业务事实 |
| 结构角色 | 主数据/交易/明细/流水/元数据/集成/读模型/归档 |
| 权威来源 | 创建和更新该事实的系统或流程 |
| 租户范围 | 平台级、租户级及共享规则 |
| 生命周期 | 创建、状态流转、撤销、归档和保留期 |
| 修改与并发策略 | 修改策略、并发策略、令牌字段、冲突处理和适配实现 |
| 主键和自然键 | 稳定 ID、幂等键及唯一范围 |
| 关键关系 | 基数、所有权、删除和跨租户策略 |
| 敏感级别 | 用途、加密、脱敏、访问和留存 |
| 主要访问路径 | 关键查询、排序、队列和对账 |
| 数据量级 | 初始量、增长率、冷热和归档 |

字段级信息至少包含逻辑名、中文定义、语义域、必填性、长度/精度、单位、字典或标准术语绑定、默认值、敏感级别、来源和派生规则。

目标逻辑表的表级信息统一登记在 `model/table-catalog.csv`，字段级信息统一登记在 `model/field-catalog.csv`。两份目录必须与 `model/nextgen-core.dbml` 一一对应；中文名称、业务定义、语义域、敏感级别、审计状态和来源缺失，或存在重复、孤立登记时不得通过逻辑模型门禁。规则生成字段说明只能标记为草稿，未经领域负责人确认不得升级为已固化元数据。

## 14. 发布门禁

### 14.1 逻辑模型门禁

- 表级粒度、角色、权威来源和生命周期已确认；
- 核心关系和唯一性已定义；
- 字段已绑定语义域、值集、单位和敏感级别；
- 动态字段与核心字段边界明确；
- 关键状态机、不可变事实和修订方式明确。

### 14.2 物理模型门禁

- 目标数据库适配器已通过类型、约束、时间和标识符认证；
- 关系执行方式与替代控制已确定；
- 索引有真实访问路径和执行计划证据；
- 分区、归档、统计信息和容量策略已确认；
- 新系统初始化数据、接口样例和测试数据已完成空值、重复、孤儿、非法值及业务不变量验证。

### 14.3 例外管理

例外必须记录规则编号、对象、原因、替代控制、责任人、批准人和到期日。例外到期后自动回到阻断状态，不能形成永久口头豁免。

## 15. 当前审计产物

本规范对应的机器可读规则和走查结果位于 `nextgen/audit/`：

- `generated/rule-catalog.csv`：规则编号、约束级别、风险和验证方式；
- `generated/legacy-findings.csv`：现有表结构按本规范归类后的证据；
- `generated/table-compliance.csv`：逐表规则命中和整改优先级；
- `generated/schema-audit-summary.json`：机器可读汇总；
- `schema-design-audit-report.md`：管理和评审用报告。

规范、规则目录和审计脚本必须同版本发布，防止“文档是一套、检查器是另一套”。
