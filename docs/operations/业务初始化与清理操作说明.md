# 业务初始化与清理操作说明

入口：系统设置 → 业务初始化与清理（`/settings/business-maintenance`）。数据库迁移、账号授权与部署是独立步骤；按实际运行制品和迁移记录核对验收版本，不能把开发区测试通过当作 Oracle 已升级或生产已上线。

## 权限和环境

通过已有“角色与权限”功能分配独立权限：`MAINTENANCE.VIEW` 查看、`MANAGE` 登记来源和预览、`EXECUTE` 执行、`TENANT` 整租户范围、`BACKUP` 下载恢复快照、`LIFECYCLE` 确认上线状态和上线前重置。新增权限定义没有自动赋给既有角色。基础配置和机构目录、库存操作仍要求原有领域权限；维护权限不代替这些权限。

物理清理在 `test`、`local`、`oracle-local` 开发环境默认可用；其他环境默认关闭，由部署配置 `rhn.maintenance.physical-cleanup-enabled` 显式控制。启用前须完成对应部署和恢复验收。初始化不受物理清理开关影响。

机构状态默认“未确认”。有生命周期权限的账号可填写原因并确认“上线前”；须核对没有真实诊疗、收付款或药品交付。确认“正式上线”后不能回退。上线前重置只枚举指定机构的门诊根对象，不会把机构目录、患者主档、采购和住院记录自动纳入重置。

## 基础初始化

1. 选择机构或整个租户；“包含下属机构”按真实组织层级展开，展开后的每个机构都重新检查授权。
2. 基础配置补齐：勾选允许初始化的参数；已有机构值保留，只新增缺失的默认值。
3. 机构目录与价格：下载模板，填写既有平台目录、目标科室及价格信息，上传 CSV / XLSX，最大 5 MB。既有采用和价格保留，重复行、非法金额或不明确的包装阻断预览。
4. 填写原因，生成影响预览，核对新增、保留和跳过内容。输入预览实际展开的机构名称（按预览顺序用“、”连接）或租户名称，启动任务。

初始化和清理分别记录任务。清理成功后才另外发起初始化；初始化失败不会自动撤销已完成的清理。

## 测试清理与任务状态

使用业务清理页签，选择门诊、收费、药房模块及来源批次。已有测试业务须由授权账号逐个核对就诊号，填写批次依据并确认没有真实交付；登记后来源不可转移。批次标记不等于永久可删，执行前还会检查最新引用和外部业务证据。

拆零与追溯清理按原核销历史恢复所选业务消耗，保留开包、入库和流转历史，并将已清理单据的当前追溯引用绑定维护任务；共享包装中其他业务的消耗保持。缺少核销历史、包装已被其他不可闭合业务使用或状态不能恢复时阻断。

库存补偿沿用原流水数量和精确金额；撤销隔离退药时按原入账价值扣除，重新计算剩余库存均价，不覆盖其他业务的库存和成本。原成本未知时保留未知语义；回补后数量不足、剩余价值为负或数量净额为零而金额不为零时阻断。

预览存在阻断项时不能执行。真实或未知的外部支付、医保、财政票据、跨范围引用、受保护单据及未接入业务均阻断清理。模块依赖需要显式勾选，不会静默扩大删除范围。单批次及单次上线前重置最多 1000 个就诊，关系快照还有行数上限；超限应缩小范围。

预览 15 分钟有效。数据、规则、权限或上线状态变化后重新预览。界面切换机构或修改条件会使旧预览失效；重复执行同一预览只能产生一个任务。

执行状态：等待 → 隔离与备份 → 数据库处理 → 派生核验 → 完成。任务期间**整个租户暂停业务写入**，所选机构仍是实际数据处理范围，读取保持可用。等待中的任务可以取消；进入处理后不能按等待任务取消。

数据库处理失败时同库业务事务回滚并释放屏障；范围快照和审计保留。数据库已经提交但派生核验失败时，屏障保持，使用“重试派生数据校验”；该操作不重复删除或库存补偿。不应手动清空屏障来跳过失败核验。

原库存流水保留，测试发药及退药按原库存维度产生维护任务补偿流水，释放所选冻结和预留。已删除身份永久留痕，迟到或重新编号的事件不能重建这些业务记录。

## 重启及在途写入恢复

正常请求/事务结束时精确移除自己的写入凭据。后台重启后根据持久任务阶段继续处理。同一 OS 进程命名空间中，只有确认原 PID 已结束、或 PID 对应的启动时刻改变，才自动回收原凭据；回收记录进入任务审计。活跃进程的旧时间戳不会成为回收依据。

多实例部署应设置稳定且唯一的 `rhn.maintenance.process-namespace`，不同宿主或 PID 命名空间不能复用。无法证明的其他节点、缺少进程身份的凭据保持阻断，由运维核对所属节点和数据库事务后受控处理；不能靠超时删除或同时开放业务写入。

## 范围恢复快照及恢复验收

执行记录中具有 `MAINTENANCE.BACKUP` 的账号可下载已生成的范围快照。下载重新校验租户和完整机构范围，并记录 `EXPORT_BACKUP` 审计。文件含业务明细，按现有诊疗数据访问及存储要求管理。

导出格式 `RHN_MAINTENANCE_BACKUP_V1` 包含租户、任务、数据集、规则版本、实际范围、原始 `snapshotJson` 字符串及其 SHA-256。校验指纹时对**原始字符串的 UTF-8 字节**计算，不先重排或格式化 JSON。数据库内部使用绑定租户和任务身份的加密快照；内部临床文书密文还需对应的原加密密钥，导出文件不能替代密钥管理。

第一期交付恢复数据和核对依据，不提供跨文件、缓存、账务及共享库存的一键回滚。范围回灌必须先在隔离副本演练：

1. 保存任务、预览、审计、维护补偿流水和原范围导出，核对格式、版本、范围和指纹；使用同版迁移及原密钥建立隔离副本。
2. 按领域恢复清单核对新增/删除对象与原关联。临床快照中的表定义区分清理对象与保留对象；不能把保留的共享患者、目录、库存余额整行覆盖回生产。
3. 核对事务是否提交。未提交失败仅需验证回滚结果；已提交清理若需恢复，须按库存网关处理反向补偿，重新建立冻结/预留与业务履约状态，核对数量和成本，不能覆盖或删除已记账流水。
4. 对已解除的受保护档案引用、文书密文/签名、开包/追溯、排班占用及事件身份逐项核对；保留原事件处理回执，不能简单把全部弃用事件改回待发布。
5. 在隔离副本验证患者、门诊、收费、药房、库存和派生结果，形成领域确认与回灌清单。生产回灌需隔离相同范围的所有写入口，由运维按现有发布/恢复流程执行并追加审计；验证完成后才恢复服务。

整库备份恢复到隔离副本可辅助核对，但不能把恢复整库描述为不影响其他机构的定向恢复。首次开放实际环境前，必须记录所采用的备份引用、密钥可用性、隔离演练结果及未解决项。
