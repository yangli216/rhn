# 机构直连付款码支付

本期范围：收费窗口扫描患者支付宝／微信付款码，机构使用自有直连商户。沿用 `PaymentChannelAdapter`、支付指令、资金事实、账务分录及支付恢复工作台。不提供服务商模式、患者主扫收款码或公开支付回调端点。

## SDK 与通道

- 支付宝：官方 `com.alipay.sdk:alipay-sdk-java:4.40.1036.ALL`，当面付 `alipay.trade.pay`（`bar_code`）、交易查询、退款及按退款请求号查询。支持 RSA2 公钥模式或三证书模式。
- 微信：`com.github.binarywang:weixin-java-pay:4.8.0`（WxJava），API v2 `micropay`、交易查询、双向证书退款及退款查询。需要开通付款码支付、API v2 密钥和商户退款证书；API v3 密钥不能替代 API v2 密钥。本期没有同时引入另一套微信官方 SDK。
- 版本固定在后端父 POM，渠道只在 `rhn-clinical` 的 `infrastructure/payment/` 依赖 SDK。

SDK 来源：[支付宝官方 SDK](https://github.com/alipay/alipay-sdk-java-all)、[WxJava](https://github.com/binarywang/WxJava)。升级时重新验证验签、错误状态、部分退款和依赖兼容性，不能只更新版本号。

## 配置和启用

复制 [payment-direct.example.yml](payment-direct.example.yml) 到受部署管理的外部配置目录，填写租户／机构 ID 和对应商户应用信息，使用 Spring Boot `spring.config.additional-location` 加载。不要将实际密钥、证书、私钥文件或含秘密的配置提交到 Git。证书和密钥文件应为部署进程可读、其他用户不可读的挂载文件；API 密钥由部署密钥系统注入。

支付宝与微信各自以 `rhn.billing.payment.alipay`、`rhn.billing.payment.wechat` 绑定强类型商户配置，分别设置 `enabled` 和 `merchants`；不再使用混合的 `direct.merchants`。渠道专属配置拒绝未声明字段，不能把微信密钥放进支付宝商户记录。直连适配器默认启用；商户缺失、重复或凭证不可用时，本次收款在调用通道前失败，不返回模拟成功。商户严格按**支付单的租户、机构、支付方式**匹配，不按操作员当前机构或配置列表的第一项回退。每个商户使用独立 SDK 客户端；配置或证书轮换后重启应用以刷新客户端。移除某商户前先清理该机构所有在途收退款；商户号／应用变更需保留原商户的查询、退款能力，不能直接覆盖配置后处理历史交易。

`rhn.billing.payment.aggregated-adapter.enabled=true` 仅用于显式模拟环境，与直连适配器互斥；生产必须保持 false。`direct.enabled=false` 可关闭本期直连渠道。独立外部适配器的消息交接须另行显式开启 `routing.external-handoff-enabled=true`；缺省无路由直接拒绝，不再隐式转发。消息交接不接受一次性付款码，也不代表支付已成功。隔离测试默认关闭直连，不访问真实渠道。

支付宝 `merchant-id` 为收款商户 PID，应用须拥有该商户当面付能力。`private-key-path` 指 PKCS8 RSA 私钥（PEM 或原始 Base64），公钥模式填写 `public-key-path`；证书模式填写 `app-cert-path`、`alipay-cert-path`、`root-cert-path` 三项。网关只允许官方生产地址或示例列出的官方沙箱地址。

微信 `api-key` 为 32 位 API v2 密钥；`certificate-path` 为商户 `.p12` 证书；`client-ip` 为部署侧合法业务终端／服务出口 IPv4（不能把未经信任的前端字段作为来源）。商户退款证书在本期收款前一并校验可读，证书内容／密码的有效性仍需联调退款确认。

## 收款与资金事实

1. 收款 API 新增可选、仅写入的 `authorizationCode`。数字直连必须提供与所选渠道匹配的有效付款码；现金和已有外部适配路径兼容原请求。
2. 付款码仅在当次调用内存中使用；不进入支付单、事件、终端编号、可靠消息、异常文本或响应。前端输入遮蔽、提交后清空；移除模拟扫描与占位二维码。SDK 协议日志和 Apache HTTP wire 日志默认关闭，支付宝 SDK 自带日志也关闭；生产代理／APM 必须对该接口请求体作同等脱敏。
3. 金额必须为正人民币并精确到分，禁止按渠道精度自动舍入；微信同时检查整数分范围。最终账务继续用现有六位金额语义，渠道只转换单位。
4. 供人阅读的 `orderNo` 按租户生成，不能直接用作跨租户共用商户的渠道单号。渠道收款号为 `P` 加支付指令全局 ID，退款号为 `R` 加退款指令全局 ID，稳定、可恢复、长度不超过 20。查询根据同一 ID 派生原渠道单号；已保存的外部号不一致时拒绝混用。
5. 成功必须有真实渠道流水及报告金额；金额缺失／不匹配由既有账务内核拒绝，不借用申请金额补齐。微信额外核验 appid、商户号及订单身份；支付宝核验订单号，退款核验原交易号和退款请求号。签名／网络／身份异常保留待确认状态，不重复下单或当作已失败释放额度。
6. 相同幂等键的重复收款不会再次发送一次性付款码。前端网络异常后的重试复用原幂等键；重新打开窗口后由后端在途金额预占阻止重复收款，并应从支付恢复工作台查询原单。
7. 支付单先提交事务，再调用 SDK，通道结果仍通过现有原子入账服务落账；不在持有患者账户／结算行锁时调用远程接口。

## 查询、关闭与退费

付款码首期采用同步结果和主动查单，不新增公开回调或放开认证。弹窗串行查询，最长自动查询 60 秒；仍待确认时停止自动轮询并提示手动核验／恢复工作台。超时、订单不存在、未知通道状态均不能据此断定未扣款。

关闭弹窗只关闭界面。直连订单的已有取消 API 改为先查单，不调用本地取消释放资金预占，也不把按钮关闭解释为渠道撤销。首期**不开放主动渠道撤销**：它可能把已扣款交易退款，与并发查询入账产生竞态；若要支持，需要另做持久化撤销状态与查询／入账协调。已付款使用正式退款指令处理。

退款必须使用原支付渠道流水；微信部分退款同时发送原支付总额和本次退款额。退款受理先保持待确认，随后按精确退款请求号查询；只在确认退款完成且报告金额与申请一致后生成退费资金事实。退款异常／处理中保留预占，不重建退款请求。退款查询和原收款查询不能混用。

## 验证和上线验收

自动检查覆盖渠道请求构造、商户隔离、回执身份／金额、异常脱敏、部分退款、幂等、防重复、取消不释放未知资金，以及前端切换结算单防串结果。收费 scope 另覆盖现金、结算、挂号、住院消费者、架构与 API 契约。

上线前用各机构已签约的商户完成：一笔真实付款码收款、用户需输密、通信超时后查单、部分退款、重复退款查询、重启恢复和实际渠道账单核对。没有凭证的本地测试不能代替真实商户验收。当前未实现渠道账单自动下载；现有对账端口继续保留。

## 新增支付渠道的扩展步骤

1. 新增独立的适配器，实现 `PaymentChannelAdapter`，通过 `paymentMethods()` 声明规范支付方式编码，通过 `capabilities(method)` 声明稳定适配器编码、交互、付款码规则和查询／退款／取消确认能力。SDK、错误映射、签名及验签留在该适配器。付款码规则应使用 Java 与浏览器均支持的正则语法；规则和长度只在适配器定义，前后端共用该声明。
2. 在新渠道自己的 `@Configuration` 中注册适配器、客户端和 `@ConfigurationProperties` 强类型配置。新增渠道只增加自己的文件，不修改支付宝／微信配置或任何中央 SDK 工厂。按租户、机构选择商户并覆盖 `configured`；不能回退到另一个机构。密钥配置继续脱敏，接口不返回凭证或商户路径。
3. 维护 `PAY_METHOD` 字典及现有 `TENDER_TYPE`、可用场景、金额精度等属性。已有共享收款弹窗通过 `GET /api/billing/payment-methods/{paymentMethodCode}/capabilities` 读取当前工作机构的能力，选择交互；前端不判断微信、支付宝等品牌编码。
4. 注册表在应用启动时拒绝同一支付方式的多个适配器、重复适配器编码、空支付方式集合和缺失能力声明。收款、退款、查询、取消均使用同一注册表，业务流程没有 `findFirst` 渠道选择。未注册路由默认拒绝，避免误发到其他服务商；外部可靠消息交接仅为显式开关下的既有集成边界。
5. 为新适配器补充真实回执金额、身份、验签、超时、重试和退款测试。现有扩展测试使用 `NEW_BARCODE`／`NEW_CARD_PROVIDER` 等测试渠道证明复用路径，不把不存在的渠道伪装成可上线能力。

当前已实现的通用交互为 `DIRECT`（无需患者付款码的发起确认）和 `AUTHORIZATION_CODE`（按声明规则录入付款码）。新增使用这两类交互的渠道无需修改收款弹窗、支付编排或账务逻辑。首次增加主扫二维码、跳转支付等全新交互时，仍需扩展类型、结果载荷和对应通用交互组件；不能只声明一个未实现类型就宣称支持。能力加载失败、类型未知、商户未配置或机构切换后的迟到结果均禁止发起收款。

能力中的 `available` 表示该机构具有唯一的商户配置声明，不代表商户凭证、网络、签约产品已通过真实联调；提交前仍验证凭证和金额。能力端点只返回交互元数据，不接受机构 ID 覆盖当前工作上下文，也不暴露商户号、密钥或文件路径。

每个支付方式编码必须稳定绑定同一渠道身份；注册表不支持同一编码同时挂多个收单服务商。已有在途支付和历史退款处理完之前，不得移除、重指向原渠道或覆盖原商户凭据。新支付方式可以追加适配器和配置；替换历史渠道的路由属于单独迁移，不能依靠 Bean 顺序切换。
