# 收费结算模块演进设计

版本：1.3
基线：`nextgen/model/billing-settlement-model-audit.md`、`nextgen/model/nextgen-core.dbml`
目标：统一支撑挂号预付、门诊收费、诊间结算、住院/家床扩展，以及医保、聚合支付和财政票据接入。

## 1. 当前实现审计

V33 是早期 8 表收费基线。当前运行实现已演进到 V65：保留兼容 `Invoice` 的同时，增加正式结算、支付编排、挂号计费意图、财政票据、医保申请、收费员日结和渠道对账持久化。

与 nextgen 完整逻辑模型相比，当前仍缺少：

- `charge_adjustment`：折扣、减免、补贴、加收和舍入的追加事实；
- `account_balance`：患者账户余额的高频投影；
- 患者账户余额当前由不可变分录实时聚合，高并发规模下仍需增加可重建的高频投影。

因此，现有 `Invoice` 只可视为早期结算凭证，不能继续兼任财政票据，也不能作为外部支付状态载体。

## 2. 主流 HIS 必备能力

结合 nextgen 覆盖矩阵和国家医保、财政医疗票据要求，收费模块至少需要以下闭环：

1. 费用生成：挂号、处方、检查、检验、治疗、材料和人工补收均形成不可变收费事实；
2. 费用确认：支持撤销、退费、折扣、减免、补贴和舍入，原记录不覆盖；
3. 结算：支持部分结算、混合支付、医保预结算/结算、个人账户和第三方承担；
4. 支付：同步现金与异步数字支付统一建单，成功资金事实与支付过程分离；
5. 退款：原路、部分、多次退款受累计上限约束，并形成反向账务；
6. 票据：结算成功后独立申请财政票据，失败可重试，作废/红冲可追溯；
7. 日结：按收费员、终端和固定支付成员结账，各支付方式与收退类型均须明确录入实际核对金额，逐项差异必须说明；
8. 对账：支持本地单边、渠道单边、金额差异、状态差异和重复交易；
9. 审计：关键状态、外部报文、操作者、工作上下文和幂等命令全链留痕；
10. 安全：患者证件、医保编号、渠道敏感报文和票据文件按最小权限访问。

## 3. 统一结算支付组件

通用组件不感知具体页面，只接受下列上下文：

- `settlementId`：待支付结算聚合；
- `businessScene`：`REGISTRATION`、`OUTPATIENT`、`INPATIENT`、`HOME_BED`、`PHARMACY`；
- `terminalScene`：`CASHIER`、`DOCTOR_STATION`、`SELF_SERVICE`、`MOBILE`、`ONLINE`；
- `settlementMode`：自费结算或医保结算，决定是否先执行医保预结算及资金分摊；
- `paymentMethod`：患者实际付款工具，来自普通字典 `PAY_METHOD`，按 `AVAILABLE_SCENE` 在服务端再次校验；
- `amount/currency`：定点金额，不接受前端自行推导的最终应付额；
- `idempotencyKey/correlationId`：调用方业务幂等和全链路关联标识；
- `terminalCode/operatorContext`：日结、权限和问题追踪所需上下文。

统一流程：

`创建支付指令 → 通道提交 → 待支付/处理中 → 回调或主动查询 → 成功资金事实 → 平衡分录 → 结算完成 → 票据申请`

现金适配器可以同步成功；数字支付、银行卡、医保移动支付等适配器必须允许返回待处理。外部网络调用不得发生在持有患者账户或结算行锁的数据库事务中。

`settlementMode` 与 `paymentMethod` 不得合并为一个字段。医保基金和医保个人账户通过
`InsuranceSettlementAdapter` 写入结算资金来源；医保返回的个人自付金额再通过现金、银行卡、
微信或支付宝等支付方式收取。`MEDICAL_INSURANCE` 不得作为支付指令的支付方式。

### 支付舍入调整校验

支付面板从当前工作上下文的 `PAY_METHOD` 属性读取 `PAYMENT_PRECISION`、`ROUNDING_MODE`；缺失或非法配置不能默认补为分级精度或四舍五入。金额为空、非有限数或超出六位小数精度时也不能替换为零。

直接收款和统一支付指令提交非零 `roundingAdjustment` 时，服务端共用 `PaymentRoundingPolicy` 校验：调整基数是扣除已支付及医保等资金来源后的真实未付余额，差额必须等于按当前机构、科室配置舍入后的差额；本次付款必须覆盖舍入后的全部余额，且不能存在在途支付。差额叠加到已有舍入累计额，不能覆盖之前的调整。空或零表示本次不改变结算金额，并不表示服务端自动选择舍入规则。非舍入的折扣、减免及加收不能借用此字段。

## 4. 外部系统适配边界

核心域只接收已规范化的通道结果，不直接依赖微信、支付宝、银联、医保或地方财政 SDK。

```text
收费核心
  ├─ PaymentChannelAdapter     支付下单、查询、撤销、退款、验签
  ├─ InsuranceSettlementAdapter 医保预结算、结算、撤销、退费
  ├─ FiscalReceiptAdapter      财政票据开具、查询、作废、红冲
  └─ ReconciliationAdapter     渠道账单下载、解析和标准化
```

所有适配器通过 `external_messages` 保存出入站业务键、摘要、投递状态和关联资源。原始敏感报文由受控存储管理，收费业务表只保存业务快照、外部订单号、渠道交易号和错误摘要。

## 5. 状态与金额不变量

- 结算资金来源合计必须等于结算净额；
- 同一幂等键只能创建一个支付指令；
- 待处理支付金额与成功支付金额合计不得超过结算未付金额；
- 同一支付指令最多形成一个成功资金事实；
- 重复回调可追加接收轨迹，不得重复记账；
- 累计退款不得超过原支付金额；
- 每个账务事务按租户和币种借贷平衡；
- 已完成结算、成功支付、已开票据和已确认日结不得原地改金额；
- 外部调用在短事务之外执行，账户和结算锁按固定顺序获取。

## 6. 分阶段落地

### 阶段 A：支付编排内核

增加支付指令、支付事件、通道适配端口和统一支付面板；现金同步完成，外部通道进入可靠消息队列。保留原收款接口作为兼容入口，但新页面统一使用支付指令。

### 阶段 B：正式结算聚合

以 `settlement/settlement_line/settlement_tender/settlement_event` 替换早期 `Invoice` 语义，支持部分结算、混合支付和医保资金分摊。

### 阶段 C：挂号与诊间复用

费用账户允许 `REGISTRATION` 范围；挂号支付成功事件幂等触发就诊创建。医生站调用同一结算面板，不复制支付表和收款逻辑。

### 阶段 D：票据、日结和对账

补齐财政票据、收费员日结、渠道对账及异常处置工作台，并建立可观测指标和补偿任务。

## 7. 验收门槛

- 状态机迁移、金额守恒、退款上限和借贷平衡具备事务级测试；
- 并发支付只能有一笔成功，重复回调只记账一次；
- 支付超时后可主动查询并恢复，不把未知状态当失败；
- 挂号、收费处、医生站至少复用同一支付组件与服务端校验；
- 结算成功与票据失败解耦，票据可独立幂等重试；
- 外部适配器可以不修改收费领域模型而新增；
- PostgreSQL 外键列、常用工作队列和终态过滤均有匹配索引。

## 快捷医保预结算的业务资料来源

快捷入口不得创建患者保障记录、拼接医保项目或机构/医师编码，也不得用结算单号代替诊断摘要。其组装过程使用本次门诊实际接诊时间（按机构时区确定保障及目录生效日期）、接诊医师、已确认的当前就诊诊断、已有有效保障，以及标准目录维护中的 `INSURANCE` 映射。诊断摘要为排序后的实际结构化诊断 JSON 的 SHA-256；缺主诊断、未确认诊断、保障缺失/歧义、项目无唯一有效等价映射时均拒绝提交。

外部机构和医师注册号不能由内部 ID 推导。部署配置 `rhn.billing.insurance.quick-submission.registrations` 提供经核实的注册记录，每条包含：

- `tenant-id`、`organization-id`、`department-id`：对应本系统真实对象。
- `insurance-type-code`、`region-code`：对应保障险种与实际统筹区；不提供地区默认值。
- `organization-code`、`department-code`：医保平台登记的机构和科室编码。
- `insurance-system-code`：本系统维护的医保标准目录体系编码；仅使用该体系有效的 `EXACT` 或 `EQUIVALENT` 项目映射。
- `practitioner-codes`：本次接诊记录的医师账号到其真实医保注册号的映射。键含点等特殊字符时使用 Spring 配置映射的方括号键语法。收费员账号不替代接诊医师。

注册记录默认为空；需由部署维护者填写实际资料，不附带可被误用的示例业务值。未传统筹区时只有唯一匹配记录才可自动选择。保障选择同样只读取真实记录，存在多个候选且无唯一主保障时必须明确指定 `coverageId`。快捷请求必须提供 `idempotencyKey`，重试沿用原值。

这些校验同样适用于启用三方 Mock 客户端的环境：允许模拟外部响应，不允许因此向患者主档补造参保事实。标准网关未接入、外部人员标识及冲正报文仍需后续适配，不以本节的资料组装校验宣称整条医保链路已完成。

## CHS 适配与模拟边界

`NationalInsuranceClient.preparePreSettle/prepareSettle/prepareReversal` 负责提供有来源的外部人员标识、操作员和费用分类；默认实现明确拒绝，不能因为网络客户端可调用就推导为资料已接入。当前正式客户端仍不可用，不能将以下校验视为正式医保专网已经接通。仅显式启用的 `MockChsNationalInsuranceClient` 可构造模拟人员及分类，模拟待遇比例不代表真实政策。

通用 CHS 适配器核对准备报文与原结算的对象、明细及金额，缺少目录编码、人员标识、分类或原预结算流水时不得以本地编号补齐。请求发出后的回执缺失、流水错配或金额不完整属于结果待确认，不转为成功。成功回执须具备外部流水，资金分摊明确、非负且与原总额相等；大病补充基金与其他基金合并计入核心的其他基金资金来源。账务实体再次校验成功结果，禁止把缺失金额当成零。

完整冲正必须核对外部回执指向原结算，并保留已保存的原统筹、个账、自付及其他基金分摊。不能把原总额全部归入统筹基金。模拟客户端也不为不存在的预结算或原结算返回成功；真实查询协议未实现时仍保持待确认。


## 医保申请重试与就诊时间

普通预结算入口必须明确提交 `serviceStartedAt`，结束时间不得早于开始时间；不以服务器当前时间补齐。保障有效日期按费用账户所属机构维护的时区换算，机构时区缺失或无效时拒绝提交。

同一幂等编码只允许重放原业务请求：除结算单、保障、统筹区及险种外，还必须匹配机构、科室、医师、诊断摘要、就诊起止时间，以及全部结算行的医保目录编码和追溯属性。比较已保存的申请及明细快照，不使用后来变动的结算金额或目录重建原请求；行和追溯属性的排列顺序不影响相等判断，传输关联号可以变化。业务内容不同返回 `INSURANCE_IDEMPOTENCY_MISMATCH`，不得把旧申请的成功状态作为修改后请求的成功回执。重试仍检查原费用账户的机构访问权限。

历史缺少原始就诊时间的请求不能通过省略时间取得幂等成功；需要核实原业务资料。这些保护不代表重复外部回执、跨进程恢复和全流程账务去重已全部完成。


## 医保成功回执与资金入账去重

回执处理在医保申请行锁内执行。相同命令必须匹配原回执的业务阶段、状态、外部流水和各资金来源金额；成功结果还必须明确币种及所有金额，不得通过复用命令获得另一份结果的成功确认。传输消息编号变化不代表新增一次医保收款。

预结算、正式结算和冲正一旦确认，迟到的处理中或失败回执不能将其降级，重复成功回执也不能改变原分摊。相同外部消息编号再次到达时，先比对业务内容，一致则复用原回执，不一致则报冲突；不同外部消息携带相同成功结果时保留回执记录并标记重复。只有首次确认的状态转换才生成收款、账务或冲正记录；全额自付、医保资金为零时同样执行该规则，不依赖是否存在资金流水判断是否已确认。

查询发出前固定其实际业务阶段，结果回写时仍使用该阶段；不按回写时的当前状态重新解释结果。查询确认的回执保存为 `PRE_SETTLE`、`SETTLE` 或 `REVERSE`，以便后续冲正关联真正的原结算成功回执。旧数据只有 `QUERY` 而缺少可证明阶段的记录时须核实，不自动推断补造原入账事实。待处理冲正返回的受理号不能替换原医保结算流水，重复冲正不能刷新首次冲正时间。


## 医保回调币种、摘要与原子处理

已验签适配器调用 `VerifiedInsuranceResult` 边界时，成功回执必须明确携带 `currencyCode`，且与原申请一致。不得从申请反向补出回执币种。应用服务构造待确认适配器结果时保留未知币种和金额，不填入人民币或零金额。回执存储的空值与历史来源按下节 1.102.0 规则处理；历史零值不能作为资金已确认的依据。该边界约束不代表正式医保验签、网络或查询协议已接入。

入站消息摘要绑定本次申请、结算单、统筹区、业务阶段、状态、外部流水、四项资金分摊、币种、错误字段及脱敏报文；不能只对一个空的或无关的脱敏对象计算摘要。传输重试命令不属于回执事实，可以变化；同一外部业务消息号改变任何受保护内容时拒绝复用。历史只保存旧摘要的消息需核实来源，不自动改写其摘要以绕过冲突。

医保回调在申请行锁内将消息接收、回执核验、账务写入及处理标记纳入同一事务。标记失败时业务与消息一并回滚。已处理消息重试须有对应原回执及相同申请关联；原处理版本和时间保持不变，不用后来冲正或其他操作产生的新版本覆盖原处理事实。

共享交换消息重试还需检查原消息可访问性、消息类型及机构/科室；外发消息同时比对业务对象类型、标识和版本。身份字段先按存储规则去除首尾空格再检索。不能仅因报文摘要一致就返回另一个范围或业务对象的旧回执。


## 回执金额的缺失、明确零值与历史来源

从 1.102.0 起，回执四项金额允许保存空值。新回执标记 `amountSource=REPORTED`，表示按实际适配器结果保存字段是否存在；空值表示未返回，数字零表示明确返回零。`REPORTED` 不等于业务成功，仍须结合回执状态；成功回执必须具备四项非负且符合精度的金额，并通过业务总额校验。幂等比对严格区分空值和零，不再把二者当作相同结果。

旧记录保留原始金额列，统一标记 `LEGACY_UNVERIFIED`，不猜测原先的零是否由缺失值填充。接口对这些历史回执返回空金额及来源标识，原值仅保留供审计核实；历史未核实回执不能用来跳过金额重试校验。该迁移不改写患者费用、已入账金额、已确认申请分摊或收款流水，也不将历史来源自动升级为已核实。旧记录的核实与申请聚合金额来源仍需后续根据真实报文和账务证据治理。

## 支付回执事实与原子入账

统一支付的提交、主动查询及回调成功分支均须提供明确的正金额、外部订单号和交易流水，金额必须与对应收款或退款申请一致，并能精确表示为六位小数。成功但缺少金额时拒绝入账，不以申请金额补齐；也不通过自动舍入把不一致回执变成成功。现金主动查询没有外部凭证，不能根据申请金额生成成功结果，未确认指令需核对实际收退现金记录。

已验签支付回调必须提供业务消息号、处理命令和状态；成功回调还须明确返回与申请一致的币种。入站消息摘要覆盖支付指令身份、收退款类型、支付方式、状态、金额（区分空值与零）、币种、外部订单号、交易流水、错误字段及脱敏报文。传输重试命令可以变化，但同一业务消息号的业务事实不得变化。原命令已用于其他消息或存在未完成处理的历史事件时，不猜测为已成功重试。

回调在支付指令行锁下将消息接收、事件迁移、收退款事实、账务分录与处理标记纳入同一事务。同步适配器成功结果也将事件与账务一并提交；远程通道调用在事务外执行。已处理回调重试须有正确对象关联和原支付事件，并保留首次处理时间与对象版本；后续业务状态推进不能反向覆盖首次处理事实。门诊等业务完成协调在支付事务提交后执行，仍沿用独立的业务完成重试入口。

这些约束不表示正式支付通道已接入。三方适配器的 Mock 实现仍按环境能力独立配置；历史消息摘要不自动升级，旧回执和已入账金额的来源仍须根据真实记录核实。

## 财政票据回执的来源、重复处理与时间

出票及红冲成功必须由回执明确提供外部票据号、票据代码、号码及业务时间；作废成功须提供与原票据一致的外部票据号和操作时间。缺失时间不能填入当前时间，缺失票据身份不能从申请反向补齐。出票时间按数据库微秒精度保存，重复成功还需核对原票据代码、号码、校验码、凭证引用与时间。已确认出票不能用新的待处理或失败结果悄悄覆盖或假装已应用；红冲对象不能接收普通出票结果。

财政查询按平台明确返回的业务状态处理，不再把所有成功结果统一解释为普通出票；成功标志与业务状态冲突或状态无法识别时，不生成确定业务结果。本地票据的查询不能只凭申请号合成“已出票”。本地出票目前只保存票据业务记录，没有生成受控文件时，文件引用保持为空，不返回 `receipt-object:` 占位地址。

已验签财政回调直接按申请号加行锁，摘要绑定申请身份、财政平台、操作阶段、结果状态、票据身份、凭证引用、业务时间、操作原因、错误信息与脱敏报文；传输重试命令不属于业务事实。消息接收、票据变更、事件写入及处理标记在一个事务内提交。处理标记失败时整笔回滚；并发重复回调只生成一个事件。已处理消息重试必须找到对应原票据事件，保留首次处理时间和对象版本，即使票据后来作废也不改写原出票处理事实。

同步结果处理不再仅凭相同命令号直接返回成功。历史事件没有完整回执证据时拒绝推定为相同结果；正常应用命令重试仍通过原有已保存事件读取结果。历史来源不自动补证，既有票据时间不自动改写。正式财政平台对接能力、请求资金分摊来源和失败操作的后续恢复仍需分别核验，不能以本轮回调校验通过代替。

## 开票请求的实际资金分摊

开票资金分摊从正式结算的收款明细及其来源核验后生成，分别传递医保统筹、医保个人账户、患者实际支付和其他基金。结算聚合字段 `patientAmount` 包含个人账户，不能直接用作财政请求的患者实际支付；财政请求新增 `otherFundAmount`，同步适配器与外发消息均保留这一分项。

医保收款须能追溯到本结算、本账户和币种的正式成功结算／冲正回执，且金额来源为 `REPORTED`；每个回执的三类入账金额须与其报告金额和操作方向一致。历史未确认、预结算、待处理回执不能证明已收资金。支付收款须关联同机构、同账户、同币种的已完成支付和正确账单，不能超过退款后的有效金额；住院预交金仅使用实际抵扣部分。尚不能明确财政分摊的支付方式会阻止开票，不套用默认分类。

最终四项实收金额须非负，并与正式结算总额、统筹、其他基金以及个人账户加患者支付的聚合金额逐项一致。核验不通过时不创建新票据请求、不调用开票通道；重试开票也重新核验。查询已有票据仅使用原票据身份与平台信息，不依赖原结算后来的资金状态。

本轮未改写历史账务或自动补齐历史回执，也不代表正式财政通道已经接入。开票费用类别、跨事务并发变更与首次出站请求快照仍需继续核验。

## 开票费用明细与舍入差额

开票前同时核验正式结算行、原账单行和已入账收费项目：项目须属于同租户、机构、患者账户及币种；行号、原账单关联、收费项目不能重复或缺失；当前整单结算的数量与原收费数量一致，原额、优惠及净额逐项相符，且完整覆盖原账单。费用项目编码、名称和会计分类使用已保存快照，不读取当前目录替换历史事实，也不根据来源类型将空分类推定为药品、治疗或其他费。缺少证据时返回 `RECEIPT_LINES_UNVERIFIED`，在创建请求前拒绝开票；实际重试发送前也重新检查。

财政请求新增 `roundingAmount`，与正式结算已核准的舍入差额相同。项目明细仍保留原结算行净额，明细净额合计加舍入差额必须等于票面金额；不得通过虚构收费项目、修改最后一行金额或重新定价使合计看似一致。该差额同时传入财政适配器和外发消息，第三方正式协议对其如何表达仍由具体适配器明确实现。

这一核验不会自动补齐历史缺失分类。上游费用投影和分类汇总中仍存在来源类型推导及药品亚类默认值，需继续逐条核查其业务证据；非空的旧快照不因本轮校验而获得新的来源证明。首次外发快照及并发期间的变更一致性也仍待后续治理。

## 分类缺失的上游保存与汇总

药品医嘱事件、门诊发药同步和住院发药使用同一药品类型映射：明确的西药、中成药、饮片类型对应各自分类；已知的疫苗、民族药和院内制剂仅能证明属于药品大类。类型缺失或不认识时返回未确认，不默认为西药，也不根据处方分组替代药品自身类型。原医嘱查询异常必须传播，不能吞掉异常后写入一个分类。

诊疗事件、直接就诊费用和住院执行入账不再为缺少的会计分类补“治疗费”或“挂号费”。费用金额有证据而分类没有证据时，收费记录保留空分类快照；退药、挂号冲销及医嘱撤销沿用原分类，包括原记录的空值，不借冲销补造分类。明确的挂号业务收费和床日收费仍沿用其特定业务类别规则，本轮未修改这些业务定义。

归并分类对缺失快照使用 `UNCLASSIFIED / 分类未确认` 作为未确认状态，不依据来源类型猜测，也不混入真实 `OTHER / 其他费用`。该状态只表达缺失，不可作为已确认分类通过开票检查。自定义分类缺少名称时直接展示原编码；分类字典查询失败不再伪装成已成功解析。历史已经存储的非空默认分类及旧汇总不自动改写，仍需来源审计。

住院执行命令中分类字段的来源、临床事件其他身份与时间字段的补值、出站快照仍需继续核对；本轮不将已有非空分类一概认定为来源可靠。

## 临床医嘱计费事件的事实校验

门诊诊疗与药品医嘱的财务事件使用第 2 版契约，显式保存 `billingDisposition`：应收费、未定价、零金额、自备药和未提交草稿。未定价要求价格、金额、币种及价格来源均未提供；已定价要求价格来源完整、金额非负且数量乘单价与总额一致。自备药须有明确的原医嘱标记；草稿仅允许药品草稿撤销时跳过冲销。非收费决策如果与已入账记录矛盾，同样拒绝确认。正常业务没有价格时不自动生成零元价格或假项目。

收费投影先校验版本、患者与就诊、机构与科室、目录与价格来源、名称、编码、单位、单号、操作人及发生时间，再查重和入账。缺失字段不补“门诊医嘱”“次”、拼接单号、当前处理时间或原开立人。开立和撤销使用医嘱保存的真实时间；处方激活发生时间由发布时确定并保存到 Outbox，重试沿用该时间。新医嘱开立、撤销与事件时间统一到数据库支持的微秒精度，避免持久化舍入导致同一事实在重放时变化。金额沿用现行六位小数记账规则，分类仍允许保留未确认状态。

应收费医嘱撤销必须存在与原医嘱事实一致的收费记录及借方流水，冲销明确关联原收费和原流水，并记录实际撤销人。同一来源的重复事件会核对金额、身份和发生时间，不能仅因存在来源记录就吞掉矛盾事实。校验失败抛出 `CLINICAL_ORDER_BILLING_UNVERIFIED`，事务不保存收费、冲销和成功消费记录。

本轮不将缺少决策字段的旧版未消费事件自动升级为“已确认”，也不改写历史已消费事件或旧收费快照。旧事件需要核实源医嘱后按新契约重新投递；并发投影的唯一性、其他业务投影及首次对外请求快照仍需继续核查。

## 退药冲销的真实来源与统一计算

退药事件投影、手动收费同步和对账预期金额统一经过 `MedicationReturnChargeService`。事件必须与已保存的退药记录逐项匹配：发药任务、患者、就诊、原发药、医嘱、退药单号、数量、单位、实际处理人和发生时间。缺失字段不补原开立人、原单位、拼接单号或当前时间，也不直接保存成功消费记录。药房读取端使用实际发退药明细保存的换算系数，校验明细单位及数量汇总，不能以当前任务上的系数替代历史执行事实。

原收费只能由对应医嘱收费或对应原发药收费唯一确定；两者同时存在时须核实重复计费。缺少原收费时，只有可核实的自备药或零价医嘱允许不形成冲销。已存在原收费必须具备同患者、就诊、产品、币种和真实价格来源，并有匹配的借方流水。冲销保存真实退药处理人和发生时间，明确关联原收费和原流水，分类原样保留，包括空分类。

退药数量先依据实际发药单位换算为基本数量，再使用原医嘱或原发药计费依据精确换算为原计费单位；无法以数据库数量精度精确表达时拒绝自动冲销。金额按原总金额占比分摊，最后一笔结清已核对的剩余金额。原收费行在入账时加锁，累计冲销数量和金额不得超过原账。重放核对已有冲销及流水，不重复记账；业务时间倒填不会改变已入账冲销的先后顺序。

该整改不会改写历史异常冲销。历史缺少真实处理人、明细换算、原收费或流水的记录会明确报 `MEDICATION_RETURN_BILLING_UNVERIFIED` 或 `DISPENSE_BILLING_FACT_UNVERIFIED`，需核实来源；原始发药计费、医嘱撤销与退药交叉并发、其他业务投影仍需继续治理。


## 费用明细展示的字典与单位来源

收费明细和诊疗项目响应的 `accountingCategory` 通过 `@DictionaryBinding(BD_ACCOUNTING_CATEGORY)` 自动补充只读 `accountingCategoryText`。前端直接显示文本，缺少文本时保留原编码；分类缺失显示“分类未确认”，不按项目名或来源猜测。结算归并同样读取租户字典，未知编码不再使用本地标准中文名称兜底。历史停用项仍可解释，维护表单通过 `DictionarySelect` 选择当前启用代码。此能力解释当前显示名称，不修改已保存的分类编码或历史票据证据。

收费行的 `unitName` 优先使用与该行实际 `unitCode` 相符的医嘱包装名称快照；单位不一致或历史快照缺失时，由计量单位主数据公开 API 按租户批量解析，包括历史停用单位。实际发退药的基本单位不能套用申请包装名称。无法解析时前端显示原单位编码，且尊重服务端的英文名称；页面不再维护包装或计量单位中文映射。

## 收费工作台的开单信息与现金默认值

费用明细的单据分组标题展示“开单科室 / 开单医生”，来源为原医嘱的申请科室和开单用户关联的医务人员，不使用发药人、收费录入人或当前就诊科室代替。收费端通过门诊公开目录按租户批量查询原医嘱，并核对就诊关联；未记录来源时明确展示“科室未记录 / 医生未记录”。新药品医嘱保存就诊侧申请机构、科室，执行药房另行保留；不批量改写历史记录。

检验使用试管图标，检查使用扫描图标，按原诊疗医嘱的服务类型选择；费用归并分类不作为图标推断依据。待缴款状态仅在费用行展示，分组头保留小计和展开操作，避免重复标识。

收费工作台选择现金时，缴款金额默认当前应付金额；切换患者、结算或勾选费用导致应付变化时重新初始化，手动输入和清空不被普通重绘覆盖。默认值通过统一支付面板的可选开关启用，挂号、住院等既有调用保持原行为。
