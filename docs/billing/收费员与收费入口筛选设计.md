# 收费员与收费入口筛选设计

状态：P1、P2 已实现（收费员识别按岗位类型“收费”）；P3 随自助机、互联网缴费流程落地时再做。起因：收费查询页的“收费员”条件需要来自专门的收费员列表，且要覆盖诊间结算、自助机、互联网结算等渠道。

## 1. 现状

| 事实 | 位置 |
|---|---|
| 结算单记录“谁完成”：`finalizedBy`（登录账号 ID），不论哪个入口都是同一个字段 | `Settlement.finalizedBy` |
| 结算单记录“从哪完成”：`terminalScene`，取值 `CASHIER / DOCTOR_STATION / SELF_SERVICE / MOBILE / ONLINE`，库表有 CHECK 约束 | `V1_129_8` 迁移，字典名“收费入口” |
| 收费员筛选原来是文本框，后端按子串匹配；现已改为精确匹配，下拉选项取自“所选日期范围内最近 500 条记录里出现过的人” | `completedInRange`、`BillingQueryWorkspace` |
| 人员侧只有岗位类型 `PositionType`：临床、护理、药学、医技、行政；**没有收费/财务类**。收费权限靠权限点 `BILLING.ACCESS` 等授予 | `PositionType`、`RHN_SYS_ACC_PERM` |
| 代码里实际只有 `CASHIER` 和 `DOCTOR_STATION` 两个入口在写结算单；自助机、移动端、线上缴费只有字典与约束，尚无落地流程 | grep 结果 |

## 2. 要先说清的问题：“收费员”混了三件事

1. **收费员（人）**：在收费窗口办理的工作人员。
2. **办理人（操作账号）**：`finalizedBy` 指向的账号，不一定是收费员。
3. **收费入口（渠道）**：窗口、诊间、自助机、移动端、线上。

各入口下 `finalizedBy` 的含义不同：

| 入口 | 办理人是谁 | 是否“收费员” |
|---|---|---|
| CASHIER 收费处 | 收费窗口人员 | 是 |
| DOCTOR_STATION 医生站 | 接诊医生代为办理 | 否（临床人员） |
| SELF_SERVICE 自助机 | 设备或服务账号，患者本人操作 | 否 |
| MOBILE / ONLINE | 患者本人或系统回调，没有员工账号 | 否 |

所以把所有渠道都塞进一个“收费员”下拉框，语义是错的：诊间结算的“办理人”会是医生，自助机、线上则根本没有人。

## 3. 方案

### 3.1 筛选拆成两个条件

- **收费入口**（新增）：下拉，选项来自字典“收费入口”，多选或单选均可，对应 `terminalScene`。
- **办理人**（原“收费员”改名）：下拉，选项来自专门的列表（见 3.2），对应 `finalizedBy`，精确匹配。

选了入口为自助机、移动端、线上时，“办理人”置灰并提示“该入口无员工办理人”，避免出现空选项。
入口选“收费处”时，办理人只列收费员；入口为空或“医生站”时列全部办理过的人，医生站场景下会看到医生，标签带“医生站”以免混淆。

### 3.2 收费员列表从哪来

识别“谁是收费员”有三条路，建议组合使用：

| 路径 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 权限点 | 持有收费办理权限（`BILLING.ACCESS`，以及结算类权限）的账号 | 不改表；与实际能收费一致 | 权限不等于岗位；兼任人员、超级管理员会混入 |
| B 岗位类型 | `PositionType` 增加 `BILLING`（收费）。收费员 = 当前有效任职于收费岗位的员工 | 语义清晰；人事可维护；与排班、日结可复用 | 需改枚举、字典项、岗位维护页，并给存量数据补岗位 |
| C 历史办理人 | 日期范围内 `finalizedBy` 出现过的账号 | 离职、调岗人员历史记录仍可查 | 只能反映已发生的 |

**推荐 B + C 并集**：
- 候选 = 当前有效的收费岗位员工 ∪ 所选日期范围内实际办理过结算的账号。
- 每项带 `active`（当前是否仍在收费岗位）和 `channels`（范围内办理过的入口），离职人员标注“已离岗”。
- 在 B 落地之前，可用 A 作过渡：收费员 = 持有收费办理权限的账号，列表接口协议不变，后续换数据源即可。

### 3.3 接口

新增只读接口，替换“从记录里推导选项”：

```
GET /api/billing/settlement-cashiers?from=YYYY-MM-DD&to=YYYY-MM-DD&terminalScene=CASHIER
→ [{ userId, name, username, active, positionName?, terminalScenes: ["CASHIER", ...] }]
```

- 权限：`BILLING.ACCESS`；按当前工作机构过滤。
- `settlement-records` 的 `cashier` 参数保持“按人员 ID 精确匹配”，新增 `terminalScene` 参数。
- 需要同步 `docs/api/openapi.json` 与 `frontend/src/shared/api/generated.ts`。当前契约快照本身有历史差异，需单独确认是否一并对齐。

### 3.4 非员工入口的“办理人”

- `SettlementRecordView` 增加 `operatorKind`：`STAFF`（员工账号）、`DEVICE`（自助机设备或服务账号）、`PATIENT`（患者本人）、`SYSTEM`（回调、定时任务）。
- 展示：员工显示姓名；其余按入口显示“自助机（设备 SS-01）”“线上缴费（系统）”，不再出现“未记录收费员”。
- 这些入口真正落地时，需要约定 `finalizedBy` 写入什么：建议写专用服务账号 ID，而不是空值或某个员工 ID，避免日结、对账统计到员工头上。

### 3.5 与其他功能的口径一致

- **日终结账**：现按收费员（账号）汇总。需要明确：只汇总 `CASHIER` 入口的现金/刷卡；医生站代收的现金如何交接，需业务确认。
- **收费页底部“本人今日最近结算”**：现按登录工号精确匹配。若医生在诊间结算也想看到自己办理的，需要放开入口范围，目前只会列出本人在任意入口办理的，已满足。
- **电子票据开具渠道** `issueChannel` 与 `terminalScene` 的取值集合相同，可共用同一字典。

## 4. 分期

1. **P1（小）**：新增收费入口筛选；办理人选项改为“范围内办理过的人”，不再受 500 条上限影响（后端接口出列表）；非员工入口显示系统/设备标签。
2. **P2（中）**：`PositionType` 增加 `BILLING`，岗位与任职维护页、字典、存量数据迁移；列表加入“当前收费岗位员工”和 `active` 标记。
3. **P3（随渠道落地）**：自助机、移动端、线上缴费流程接入时，落实服务账号与 `operatorKind`；日结口径按入口拆分。

## 5. 需要你确认

1. 收费员的识别以**岗位类型（新增“收费”）**为准，还是先用**权限点**？
2. 诊间结算（医生代收）在“收费员”口径里是否算？日结是否包含医生站代收的现金？
3. 自助机、线上缴费的结算单，`finalizedBy` 是否统一用一个服务账号？
4. 离职人员是否仍出现在下拉框里（建议出现，标“已离岗”）？
5. 契约文件（`openapi.json`、`generated.ts`）是否一并对齐，还是只补新接口？

## 6. 已实现（P1、P2）

- **P2**：岗位类型新增 `BILLING`（收费），迁移 `V1_129_52` 补字典项并预置“收费员”岗位；`OrganizationDirectory.activeStaffByPositionType` 返回当日在岗的收费岗位人员。
- **P1**：
  - 新增 `GET /api/billing/settlement-cashiers`：收费岗位在岗人员（`active=true`）∪ 所选日期范围内实际办理过结算的人员（含已离岗）；传 `terminalScene` 时只返回该入口办理过的人。
  - `settlement-records` 增加 `terminalScene` 参数；`cashier` 按人员 ID 精确匹配。
  - 收费查询页：新增“收费入口”下拉，原“收费员”改为“办理人”并取自新接口；自助机、移动端、线上缴费无员工办理人，办理人置灰，列表中显示“自助机”“移动端（患者本人）”“线上缴费（系统）”。
- 存量人员需要人事在岗位与任职维护里把收费员调入“收费”类岗位后，才会作为“在岗”出现；此前办理过结算的人仍会以“已离岗”出现。
