# 基层住院主流程与首轮领域模型

## 1. 建设结论

当前“需求重建”未形成独立、完整的住院需求说明，“表结构梳理”已给出 `episode_of_care`、住院扩展、就诊和位置历史等通用骨架，但尚不足以直接支撑可运行的住院业务。

首轮按基层医疗机构的简易模式建设，冻结以下业务粒度：

- 一次住院对应一个住院周期（`care_episode`）。
- 一个住院周期首轮只建立一个覆盖全程的住院接触（`encounter`，`encounter_class = INPATIENT`）。
- 入院时直接分床；暂不把预入院、候床和床位预约暴露为基层用户的必经步骤。
- 转床仅改变床位占用和位置历史，不拆分住院周期或住院接触。
- 出院结束住院周期和住院接触，并将床位置为“待清洁”；床位清洁完成后才能再次分配。

该粒度保留了后续增加预入院、转科、请假、日间病房和多专业共同管理的空间，同时避免首轮把简单住院流程复杂化。

## 2. 首轮主流程

1. 在“入院登记”中搜索并确认居民主索引。
2. 选择空床、入院来源、护理级别和入院原因，直接办理入院。
3. 系统原子地创建住院周期、住院接触、住院扩展、当前床位占用、位置历史和入院事件。
4. 在病区床位板和在院患者列表中查看当前状态。
5. 医生开立长期或临时的药品、诊疗或护理医嘱；医嘱事实复用全院统一 `care_requests`，住院模块只追加流程和执行信息。
6. 医生签署后由护士核对，再按确定时点生成执行任务；非自备长期药品按机构时区和病区归入当日班次供药批次，再进入住院药房接方、审方、预留、配药和实际发药流程。
7. 药房按同一药房和同一病区建立配送交接批次，确认送出后进入在途；病区逐项核对，可正常签收或登记数量、破损、错药等差异，差异由药房确认处置结果。
8. 已进入配送交接的药品只有在病区签收或差异处置完成后才能给药；护士对每次任务记录已执行或跳过，并精确核销原发药批次。
9. 护士按六个常用时点录入生命体征和出入量，系统在体温单中同时展示入院、转床和出院事件。
10. 医生在住院患者上下文中完成入院记录、首次病程、日常病程和出院记录，签名和完整性证据由临床文书底座保存；同类日常病程通过实例键独立管理。
11. 转床时原子关闭原位置历史和原床位占用，将原床置为待清洁，并建立新床位占用和新位置历史。
12. 出院前集中核对长期/临时医嘱、待执行任务、出院记录签署和结构化主要出院诊断；诊断复用统一就诊诊断表，并与入院及门诊诊断按阶段隔离。
13. 住院期间可实时查看已记账与预计费用、收取预交金；财务风险提示不阻断临床出院。
14. 床日费用按住院周期、业务日期唯一记账，重复命令或并发请求不得形成重复床日；患者日清单必须分开展示实账与预计金额。
15. 诊疗类医嘱按每个实际执行任务形成一次住院实账，跳过任务不收费，重复执行命令不重复记账；药品费用仍以药房实际发退药事实为唯一来源。
16. 住院检查检验和治疗医嘱接入全院医技执行队列；检查检验完成后报告回到本次住院，治疗执行结果与住院医嘱任务保持关联，执行收费只保留一个来源。
17. 护士先完成基础入院护理评估，记录入院方式、沟通、自理、活动、皮肤、营养、疼痛及风险分层；日常护理记录继续按业务时间追加，正式交接班经过草稿、交班签署和接班确认，评估、记录与双方签署事实均不可覆盖。
18. 临床条件满足后关闭当前床位占用和位置历史，完成住院接触和住院周期，将床位置为待清洁；病区完成清洁消毒后释放床位。
19. 临床出院后进行最终费用核对；结算明确区分待补缴、待退余、待复核和已结清，只有差额处理完毕后才关闭财务账户。

## 3. 首轮状态与约束

### 3.1 住院周期状态

`PLANNED → PENDING_BED → ADMITTED → ON_LEAVE / DISCHARGE_PENDING → DISCHARGED`

首轮界面直接建立 `ADMITTED` 状态，其他状态作为后续专业模式的扩展点；`CANCELLED` 用于取消尚未实际入院的周期。

### 3.2 床位状态

- `AVAILABLE`：可分配。
- `OCCUPIED`：由当前床位占用事实推导，不单独写入床位维护状态。
- `CLEANING`：患者离床后待清洁消毒。
- `BLOCKED`：人工封床。
- `MAINTENANCE`：设施维护。

### 3.3 数据不变量

- 同一机构内住院号唯一。
- 同一患者同一时间只能存在一个当前在院周期。
- 同一床位同一时间只能有一个当前占用。
- 同一住院周期和住院接触同一时间只能有一个当前床位占用。
- 当前床位占用必须同时记录位置历史，转床和出院必须原子关闭两者。
- 所有改变住院状态的命令都使用 `command_code` 幂等；重复提交返回已有结果，不重复建档或占床。
- 关键写操作使用业务版本号做并发控制；数据库唯一约束负责最终并发兜底。

## 4. 已实现范围

### 4.1 后端与数据库

- 病区、病房、床位三级服务位置。
- 床位业务属性和床位维护状态。
- 住院周期、住院扩展、住院接触、当前床位占用和位置历史。
- 入院、转床、出院、床位释放/封床接口。
- 状态事件流水和幂等命令。
- H2 与 Oracle 两套迁移及本地演示数据。
- `INPATIENT.ACCESS/ADMIT/TRANSFER/DISCHARGE/BED_MANAGE` 权限点和住院模块菜单。
- 追加式生命体征事实：体温、降温后复测、脉搏、呼吸、血压、SpO₂、体重和出入量。
- 入院、转床、出院业务与体温单事件同事务生成，转床保存单条来源/目标快照。
- 住院医嘱复用 `care_requests`、`medication_requests`和 `service_requests`；仅新增住院流程、执行任务和追加事件，不存在第二套医嘱主事实。
- 长期/临时医嘱、签署、核对、确定时点计划、逐次执行/跳过、停嘱及未来任务取消。
- 出院就绪门禁：未停长期医嘱、未完成临时医嘱、待执行任务、未签出院记录和缺少主要出院诊断均在服务端强制校验。
- 结构化出院诊断复用 `encounter_diagnoses`，通过 `ENCOUNTER/ADMISSION/DISCHARGE` 阶段隔离，更新幂等且保留修订历史。
- 结构化入院诊断复用同一诊断事实与修订历史，支持主要/次要、初步/确认状态、幂等更新、住院并发版本校验和出院后只读；入院、门诊和出院诊断不会相互覆盖。
- 药品医嘱签署复用居民过敏底座：药物过敏状态未知时强制核对，存在有效药物过敏时要求显式确认，药品命中过敏原时必须记录临床覆盖理由；核对事实与理由进入不可覆盖的医嘱事件。
- 临床文书增加 `instance_key`，既保持入院记录等单实例语义，也支持多份日常病程独立版本、签署与更正。
- 住院费用汇总复用统一患者账户、支付与账本；支持已记账费用、预计医嘱和床日费用、预交金、预计待结与余额提示。
- 床日实账按实际床位占用历史逐日生成并固化计价版本、项目、单价和床位快照；同一住院周期同一业务日期使用数据库唯一约束和住院周期悲观锁共同防重，任一日期缺少有效床位价格时整批回滚。
- 患者日清单按业务日期归集床日、实际药品发退药和诊疗执行费用，并对每个费用分类分别返回实账、预计及合计金额；待执行医嘱的预计费用归属任务计划日期，不再归属开嘱日期。
- 非自备住院药品在护士登记给药前必须已完成药房履约；未发药、发药余量不足或已全量退药时服务端拒绝执行，自备药和跳过任务保留人工路径。
- 长期药品医嘱按“每次执行所需发药单位”固化药品供应快照；药品请求始终保存一次用量，不再被计划任务数改写。每天新增执行计划时，只为尚未归入供药的具体剂次生成当日供药行，因此首日接方后仍可安全追加次日计划。
- 滚动供药使用“供药批次—供药行—精确剂次映射”三级事实：批次唯一标识药房、病区和班次窗口；供药行汇总同一医嘱在窗口内的用量；剂次映射保证每个执行任务同一时间最多属于一个有效供药行。
- 药房履约唯一边界从“一个医嘱一条发药任务”调整为“一个供药行一条发药任务”。同一长期医嘱可以每天形成独立任务、库存预留、发药、配送和退药事实，给药时按当前执行任务精确定位对应供药行，不跨日误用药量。
- 基层默认按夜班、白班、晚班三个固定窗口一键生成并自动提交；同一业务请求号重放和同一窗口重复生成都返回原批次，不重复汇总剂次。
- 发药路由已将就诊场景作为必选维度，门诊、急诊、住院和家庭病床不会再共用一条模糊默认规则；住院综合病区默认路由到住院药房，目标药房能力与场景必须一致。
- V116 提供参数驱动的住院供药预生成：业务开关 `pharmacy.inpatient-supply.auto-generation.enabled` 默认关闭，提前量 `pharmacy.inpatient-supply.auto-generation.lead-time` 默认 120 分钟，均支持平台、租户、机构、科室范围继承与缓存。
- 自动任务按药房、病区、业务日期和班次生成确定性请求号，独立运行表保存路由版本、窗口、重试次数、下次执行时间和数据库租约；多实例并发和进程重启不会重复建批。无医嘱窗口只记录 `NO_DEMAND`，不产生空批次；自动路径不伪造普通用户，首轮仅生成并提交批次，不代替药师接方、审方、配药或发药。
- 住院药房支持对同一批次的待接方供药行一次性完成库存经营项匹配和接方；服务端在同一事务中锁定批次与全部明细，先完整校验再创建发药任务，跨批次、重复明细和非法状态不会留下部分结果。原请求重放返回原发药任务，变更库存经营项后重放会明确冲突。
- 接方完成后支持由药师一次触发整批常规审方和库存预留；服务端顺序锁定发药任务并按 FEFO/FIFO 占用库存，任一行缺货、需干预或已驳回时整批回滚。动作可安全重放，已进入备药中的任务不重复创建审方记录或库存预留。
- 常规供药批次已支持整批配药复核、整批全量发药和配送建单。发药号与配送号按批次确定性生成，发药、库存、预留、任务、配送和 outbox 处于同一事务；重放必须严格匹配人员、岗位和说明，不会静默吸收变更。受控、高警示、部分发药、停嘱和异常任务继续走逐行专业流程。
- 每次实际给药按先发先用关联到具体发药批次行，并写入不可变的 `inpatient_med_consumptions` 消耗账；执行命令重放不会重复核销，已核销数量不能再退药，未核销余量仍可按原批次退回。
- 住院药品以实际发药形成正向收费，以确认退药按原发药价格形成负向冲销；药品医嘱预计金额只用于提示，不作为实账来源。
- 病区配送使用独立的交接批次、交接明细和追加式事件，不把“药房发出”冒充“病区收到”；状态覆盖待送出、配送中、已签收、有差异和差异已处理。
- 停嘱后按药品实际位置冻结后续发药和库存预留；病区余药通过申请、实物交出、药房逐项验收形成反向交接，接收结果区分重新入库、隔离和待销毁。
- 出院门禁同时阻断待送出、配送中、交接差异和待退余药，避免患者已离院但药品保管责任仍悬空。
- 病区患者一览按当前机构、当前病区聚合在院患者、重点护理、待核对医嘱、未来 24 小时待执行/逾期任务、待送出/待签收药品和交接差异；聚合结果不另建重复事实表。
- 已纳入病区配送的药品在服务端同样执行签收门禁，直接调用给药接口也无法绕过；拦截失败与药品消耗处于同一事务，不会留下部分核销记录。
- 每条正向住院发药记录最多进入一个交接明细；批次只能包含同一药房送往同一病区的记录，签收必须覆盖全部明细，数量不能超过应收数量，差异必须说明原因。
- 建批、送出、签收和差异处置均使用请求号幂等，批次状态和版本号共同承担并发门禁；H2 与 Oracle V107 迁移保持一致。
- 住院诊疗医嘱执行后按执行任务写入统一 `charge_items`、费用明细与账本，`INPATIENT_ORDER_TASK` 受唯一约束保护；H2 与 Oracle V105 迁移保持一致。
- 已出院的体温单和医嘱仅可查询，服务端同步拒绝追加或执行。
- 住院检验、检查及治疗复用既有医技执行任务；住院医嘱激活后直接进入执行科室队列，不套用门诊先结算门禁。报告按本病区患者权限回流，其他病区不可读取；执行后仅产生一次 `INPATIENT_ORDER_TASK` 收费。
- 住院危急值从正式报告自动识别，在当前病区显示待办，支持确认、处置结果和关闭；超时升级与实时通知跳转到住院患者上下文，而不是门诊医生站。
- 护理记录使用追加式事实表，保留结构化观察摘要、记录人、业务时间、内容摘要与完整性证据；出院后只读。
- 基础入院护理评估复用同一追加式护理事实流，结构化保存入院/复评类型、入院方式、沟通、自理、活动、皮肤、营养、跌倒与压力性损伤风险、疼痛、风险标记、结论和即时措施；评估写入使用业务请求号幂等并纳入内容完整性证据，出院后只读。
- 当前风险等级属于基层简易模式的人工分层，不冒充 Morse、Braden 等专业量表。专业量表必须在机构确认题项、计分规则、阈值和发布版本后接入，客户端不得自行计算权威分值。
- 正式交接班保留班次范围、病区摘要、患者情况、待办与风险标记，按 `DRAFT → SUBMITTED → ACCEPTED` 形成交班和接班两次独立签署证据。
- 出院结算复用统一账户、发票、结算、支付、退款和账本；预交金按实际应付抵扣，少付走补缴，余额走原支付退余，命令重放不会形成重复支付或退款。
- 临床出院和财务结算状态独立；账户仅在结算无待付且无待退时关闭，零金额和预交金精确覆盖均可无新增支付地结清。
- Oracle 原生 JDBC 时间字段统一按带时区时间绑定，布尔字段按 `NUMBER(1)` 传参并增加数据库完整性约束。

### 4.2 前端

- 住院医疗按岗位和业务责任拆为四个独立入口：“入院登记”“病区护士站”“住院医生站”“住院费用”。旧 `/inpatient` 地址仅兼容跳转到入院登记，不再承载完整住院流程。
- 入院登记只负责居民确认、入院建档、床位分配和住院记录查询；不加载医嘱、护理、体温单、病历或费用工作面。
- 病区护士站按“病区总览、医嘱执行、护理与交接、体温单”切换，只加载当前护理任务所需工作区；住院医生站按“患者概览、诊断与医嘱、检查检验、住院病历”切换，临床出院从医生站发起。
- 四个入口复用统一的在院患者查询、患者上下文和后端住院事实，不复制住院周期、医嘱或护理数据；全局住院危急值直接进入住院医生站的对应患者上下文。
- 病区床位板，展示空床、占用、待清洁、封床和维护状态。
- 当前在院/历史住院查询。

## 6. 下一步优先级

1. **供药路由维度、迟到医嘱与异常履约**：可靠预生成、整批审方预留、配药复核、发药、配送和病区签收已完成主链路验收。下一轮将自动候选改为按真实计划剂次枚举“机构—病区—药品路由维度”，为通用、药品专项和缺路由建立可追踪事实；随后补预生成后迟到医嘱、缺药、替代药、部分供应和异常关闭。整包、病区基数药和更细时点继续作为专业模式。
2. **专业护理量表与护理计划**：基础入院评估已经落地；下一阶段选择一个经机构护理部门确认并发布版本的风险量表，补服务端确定性计分、签署/复评、护理问题、护理计划任务、执行和评价。评估叙事继续复用护理事实，问题、计划和任务状态使用强类型业务表，不从 JSON 或自由文本反推。
3. **病历归档闭环**：补文书完整性总览、缺项提醒、归档门禁、病案索引和受控打印；复杂病案首页及等级医院质控继续后置。
4. **住院票据与医保专业模式**：在统一结算事实之上接财政票据、医保结算、冲正和异步支付渠道；这些能力不阻断基层现金/移动支付主流程。
5. **专业住院管理**：预入院、候床、转科、请假、日间病房、会诊和多专业共同管理在基层主线稳定后逐步开放。

当前药品换算采用基层首轮约定：一次执行默认消耗一个药房准备单位。后续支持半片、按体重剂量、溶媒配制和多包装换算时，应在基础数据中引入可验证的“剂量—制剂含量—发药单位”换算规则，不在护理页面临时计算。

非关键路径如复杂病案首页、DRG/DIP、全量等级医院质控和精细成本核算不进入当前主线，待核心住院闭环稳定后再迭代。
