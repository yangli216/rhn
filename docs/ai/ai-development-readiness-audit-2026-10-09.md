## 判断

最优先的工作是修复门禁与协作流程，然后沿业务迭代拆分热点。继续增加长篇开发指令，不能替代这些工程约束。

## 需要优先处理的发现

### F1 / P0：CI 管道存在失败退出码被吞掉的风险

位置：`.github/workflows/ci.yml:24`、`:30`、`:56`、`:59` 等；后端验证、schema 检查、前端检查/测试/构建、API 构建等均使用 `command | tee logfile`。工作流没有显式设置 `shell: bash` 或 `set -o pipefail`。

GitHub Linux 未指定 shell 时的默认执行方式不应被当作已经启用了 pipefail。管道最后一个进程 `tee` 成功时，前面的检查失败可能无法让 step 失败。部分 API 比较步骤另有显式退出状态核对，这不能覆盖其他测试管道。

本地 shell 复现：

| 命令 | 退出码 |
| --- | ---: |
| `bash -e -c 'false \| tee /dev/null'`（表内反斜杠仅用于 Markdown 展示） | 0 |
| `bash -e -o pipefail -c 'false \| tee /dev/null'` | 1 |

建议统一声明运行 shell 并明确启用失败传播，再加入一个预期失败的工作流/脚本验证，确认检查失败会导致非零退出。分支是否要求这些 checks 通过，需要另行检查 GitHub 设置；本轮没有远程验证。

### F2 / P0：并行任务与共享资产的集成规则不完整

根 AGENTS 明确保护服务、测试库和 Git 操作，但没有定义独立任务的工作树、共享文件修改责任、迁移版本分配或集成顺序。当前 `git worktree list` 只登记主工作区；同时存在多个业务领域的未提交修改。这不能证明所有变更来自不同开发者，但现有规约无法保证并行隔离。

Module Catalog 的 owner 是能力组，不等于代码审查负责人。仓库未发现 CODEOWNERS、CONTRIBUTING 或 PR 模板。

风险不仅是合并冲突，还包括测试期间源码变化、不同任务反复重建相同 target、生成文件包含别人的未完成契约，以及持久服务的运行版本与验收记录不一致。

建议形成最小协作约定：

1. 独立业务任务使用独立分支/worktree；同一个任务可以共同处理该任务的工作区。
2. 共享 UI、API 生成资产、数据库迁移、权限和全局配置明确责任人或角色，由集成负责人协调同一资产的并发修改。
3. 合并前在集成工作区运行扩大范围的检查；记录提交/源码快照、制品指纹、验证时间和人工服务版本。
4. 主工作区的 Oracle 手工服务由明确的集成操作更新；普通任务不要互相重启服务或依赖另一任务的未提交改动。
5. 迁移编号在集成时核对，检查公共与 Oracle 脚本的对等变更；开发 profile 的 out-of-order 容错不能替代发布顺序管理。

不建议为了形式增加多层审批。小团队可以由一个人负责集成，AI 按同一任务约定工作。

| 文件/范围 | 结果 |

| `BasicDataManagement.tsx` | 4,059 行 |

| 非生成的生产前端 TS/TSX | 412 个，其中 47 个超过 500 行，22 个超过 1,000 行 |

| `MasterDataApplicationService` 构造协作者 | 25 个 |
| `ClinicalAssistantApplicationService` 构造协作者 | 21 个 |

前端文件中也有接口/数据声明，因此不能将所有长文件直接判定为上帝组件。不过医生站同一文件确实包含患者工作区、转诊、过敏、诊毕等多个职责；复杂服务也聚合了大量协作者。

既有审计记录中医生站曾降至约 3,900 行，当前已增长到 5,599 行。已有拆分并没有建立持续控制新增职责的约束。

建议先沿自然业务边界拆出患者上下文、诊毕、病历协调、医嘱和 AI 交互；保留患者切换、并发失效及草稿保存的统一契约。主数据按疾病/药品/产品/机构配置分离。每轮一个可验收边界，复用已有业务回归，避免同时重写状态、API 和事务。

对新增或修改部分增加复杂度提醒与拆分说明；存量逐步治理。单纯拆成大量透传函数或无职责的组件，不能降低理解成本。

### F4 / P1：契约生成与运行行为仍有差距

`MedicationRequest` 的 OpenAPI required 只有 `code`、`name`、`sdMedicationType`、`sdStatus`，但请求中含六个 primitive boolean。运行实例的负向抽样使用相同空名称：

| 请求 | HTTP / 错误 |
| --- | --- |
| 省略六个 primitive boolean | 400 / `MALFORMED_JSON` |
| 显式提供六个 primitive boolean | 400 / `VALIDATION_FAILED` |

两次请求都不能通过名称校验，不会创建档案。结果表明契约声明的可选性不能充分表达实际反序列化要求；只核对 OpenAPI 文件与生成类型一致，无法发现这种行为差异。

此外，`masterDataApi.ts`、`billingApi.ts` 中仍有大量手写接口，部分字段才继承生成类型。模型看到生成契约、手写类型与运行错误时，需要自行判断，增加返工成本。

建议让必填性、可空性和默认值在运行实现与 OpenAPI 中一致；请求/响应基础类型尽量派生自生成类型，业务视图明确投影和转换。补充契约行为测试，覆盖省略、null、空串、合法 false、金额精度、ID 类型和字典文本，优先处理新建药品等高频入口。

### F5 / P1：前端行为与依赖约束尚弱于后端

TypeScript 已开启 strict 和未使用声明检查；UI 门禁能约束部分结构/样式。但 package scripts 中没有 React Hooks lint 或前端依赖方向检查，本次也未发现 ESLint 配置。

静态 import 抽样发现住院复用门诊处方编辑器、药房复用合理用药反馈弹窗，共两处跨 features 导入。它们不一定不合理，本轮不据此判定架构违规；问题是尚未建立哪些复用允许、哪些应下沉为共享能力的自动约束。

建议增量加入 Hooks 规则、shared 不依赖 features、跨业务引用允许边界等检查。已有跨域复用先登记与评估，不要用目录级白名单掩盖所有新增引用。

### F6 / P1：新增 UI 约束有效，存量产品一致性仍需要治理

本轮 `npm run ui:check` 通过，UI policy 自测 10 项通过；新增违规 0、显式例外 0。当前静态规则命中仍有 2,588 处，包括共享按钮 202、共享下拉 30、共享表格 44、样式令牌 1,940 等。这些是代码规则命中，不等同于 2,588 个视觉缺陷。

这一结果说明新增约束已经落地，也说明门禁通过不能作为全站一致性验收。模板认可范围在文档中有说明，是优点；实际业务页面仍有逐步迁移和人工验收需求。

建议建立少量已人工验收的业务样板，按 1280/1440/1920 及标准/大字偏好维护验收清单；把重复交互修正回收到组件和模板。浏览器验证按项目约定由用户手工执行，除非另行明确请求自动 QA。

### F7 / P2：导航和验证入口需要跟随领域增长

四个 scope 主要围绕门诊、频次和知识面板；收费、主数据、库存、合理用药等任务仍较依赖开发者自行挑选测试。近期 `timings.tsv` 中有 backend stage 241 秒、228 秒的记录，前端约 32–34 秒、构建约 24 秒。这些属于不同开发快照，失败记录不能直接解释为当前代码仍失败，但能够说明扩大 scope 的时间成本。

入口链接抽查没有缺失，但存在内容滞后：数据库 README 仍称单次执行三个脚本，实际上已累积多个增量迁移；AI 耗时说明还将旧目录模型选择/决策路径与现行统一规则匹配混合描述。

建议扩展领域导航及明确的测试映射，为收费、主数据、库存、合理用药、AI 匹配分别提供维护 scope；危险变更仍扩大到契约/迁移/跨领域回归，完整 CI 保留。验证摘要增加源码快照与覆盖范围，避免同一快照重复跑宽范围测试。

当前规则及设计决策保留一个权威入口；历史审计明确标记为历史，运行统计和目录清单尽量由代码生成。不要让更多并行文档成为新的规则来源。

## 建议实施顺序与完成标准

| 顺序 | 工作 | 完成标准 |
| --- | --- | --- |
| 第一轮 | CI 失败传播、最小任务隔离/集成约定、高频请求契约修正 | 预期失败真正阻止检查通过；同一任务的验证/制品能对应明确源码；请求必填行为与 schema 一致 |
