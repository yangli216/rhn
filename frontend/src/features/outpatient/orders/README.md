# 门诊医嘱草稿

检验检查默认执行科室统一由服务端 `ServiceExecutionDepartmentPolicy` 计算，项目目录返回 `defaultExecutionDepartment`（科室身份、中文名称、来源），不覆盖机构采用记录中的手工配置。机构项目配置优先；未配置时按 `DEPT_TYPE` 的检验 30、影像 32 及具体检查专业匹配唯一有效、非虚拟、本机构科室。停用／过期配置、缺失或歧义不会回退到接诊科室。AI 建议、普通录入、临床模板及无科室参数的正式开立均使用该结果，明确选择的科室保留。正式开立按当前就诊验证开单权限，允许向同机构有效科室开申请，申请科室与执行科室分别保存；执行工作台的读取权限继续按原执行上下文校验。开发环境通过 local / oracle-local 的 V1_104_1 补齐检验、影像、超声与心电科室，仅清除未维护过的旧开发项目“全科门诊”默认值。

## 状态与依赖方向

- `medicationDraft.ts`：医嘱草稿类型与输液途径判定，不依赖 React 编辑器。
- `orderDraftTypes.ts`：项目草稿、AI 审核命令、录入类别。旧组件的类型和辅助函数导出保留兼容，新代码直接从小模块导入。
- `medicationEntry.ts`：尚未加入待确认列表的当前输入及默认值，和原子更新皮试免试状态的函数；不创建第二份录入状态。
- `medicationQuantity.ts`：剂量／疗程到包装数量的预览；频次必须来自结构化规则，不根据代码或名称猜测。
- `dispensableOptions.ts`、`administrationGroups.ts`、`orderEntries.ts` 为独立模型逻辑，不运行时依赖 React 编辑器；包装解析按当前机构、当地业务日期、真实产品单位和唯一有效价格提供整包装／拆零选项。
- `orderPresentation.ts`、`OrderRowDecorations.tsx`、`orderEditorControls.ts` 分别负责文字显示、行标识和连续录入焦点辅助，不承担提交职责。
- `../../../shared/clinical/frequencySemantics.ts`：与 Java ClinicalFrequencySemantics 对齐，双方测试读取 backend/src/test/resources/contracts/clinical-frequency-semantics.json。
- `persistOrderDrafts.ts`：医嘱整批保存与回执核实；唯一调用 `saveOrderDrafts`，不再按客户端分类分方或逐条兼容提交。
- `../UnifiedOrderListEditor.tsx`：保留连续录入状态、组方会话、目录选择／当前条目校验与加入草稿。跨区联动仍在这里协调；已保存和待确认列表的呈现进入对应 List 组件。
- `OrderComposer*` 是受控字段组件，只接收各自的输入字段、字典选项和回调，不拥有草稿副本，不接收完整工作站控制器。原 DOM 层级、ID 和回车流保持一致，草药确认阻止键盘事件向外重复提交。
- 待确认列表按类别连续展示，每类表头只出现一次；类别分组不是最终单据。药品审核预览与批量保存共用 `draftToBatchItem`（包括已选药房 ID）和后端分方引擎；检验检查当前逐项创建申请，不套用药品分方规则。
- `SavedOrderList` 与 `DraftOrderList` 用同一个 composer 插槽在指定组尾呈现录入区；位置由 `findGroupingComposerTarget` 决定。草稿药品保存后的输液会话同步仍回调父组件；整方修改仅回传整方字段，不传入整个录入状态 setter。
- `useDraftRowInteractions` 只管理交互和计时器。每个行编辑器负责自己的验证和单次保存保护，不能把失焦保存误当作向后端提交医嘱。
- `useAiOrderReview` 仍以命令 ID 驱动一次目录核对；完成时检查最新的就诊、忙碌和只读状态，卸载／换诊取消旧结果。只加入待确认草稿，正式开立仍由已有上层流程处理。
- `quantityManuallySet` 标记显式总量，同组频次变化不覆盖它。新模块不得运行时导入 UnifiedOrderListEditor 或 PrescriptionListEditor。

小时和分钟需要换算到日，周按 7 天；PRN、ONCE、CALENDAR、缺失／无效规则不提供固定日频次。自动预览失败返回 null，新开立时需明确填写数量；已有草稿的未知频次不参与比例重算。
药房使用已保存的 `frequencyRule` 快照，不能用当前目录替换历史规则或从 QD/TID 猜测数值。

每日平均次数不等于具体日期范围内的执行计划；精确排程属于后端 ClinicalFrequencySchedule。本轮没有扩展执行计划，也没有全面重写既有规格文字解析和单位换算。
验证：根目录 `./scripts/verify-scope.sh frequency`。修改处方提交协议时，还需扩大相应后端医嘱／处方主流程验证。

同时涉及医生工作站集成时运行 `./scripts/verify-scope.sh round1`（门诊草稿 + 频次组合范围）。后续拆分重点是主组件中的目录选择、当前条目校验／构建及组方会话；优先建立纯逻辑边界，避免整体迁入巨型 hook。

开立核查采用 `OrderDocumentReviewList` 的单一表头和局部滚动，每个 `OrderDocumentReviewCard` 输出独立单据分组；单头保留单号、执行科室、项目数、诊断摘要和缺项提示，编辑字段按需展开。分类统计按实际展示的分方预览与已保存单据计算，不以医嘱条数替代单据数。

检验、检查的检查目的为选填，允许留空或清空，不显示缺项警告。当前每个服务项目对应一个独立申请及执行任务；同一执行科室不自动合单，尚未实现按标本、执行流程及机构规则合单。

### 患者嘱托与临床说明

统一列表的“患者嘱托”用于药品的患者执行事项；检验、检查和治疗的 `clinicalDescription` 是临床说明，显示在执行信息中，并保留在申请单核查与保存数据中，不再混入患者嘱托列。当前服务申请没有独立患者嘱托字段，列表显示“—”，不自动生成空腹等准备要求。AI 方案的药品嘱托只能从明确的嘱托段提取，不能以适应证、治疗目的或医生审核事项补位；完整审核依据仍保留在方案任务中。

### 包装、价格与数量的事实边界

可发药选项要求产品及机构启用记录在当前业务日期内有效，开立、收费、发药标志明确为 true；包装单位、正数换算系数和有效期须完整。价格必须为非负有限数值，币种明确，机构作用域完整；同一包装的机构价优先于租户价，但所选层级只能有一条有效价格。机构价损坏时不回退到租户价，缺失金额不转换成零，缺失币种不补人民币。产品最小单位缺失时不借用知识库单位。已选择选项失效后阻止加入，不静默切换另一产品／包装。

数量预览只使用结构化含量及已知单位换算；不解析规格文本猜含量，不将未知单位等同于含量单位，不把缺失疗程或无效包装系数设为 1。含量换算须确认产品最小单位与制剂单位一致。不具备计算依据时返回空结果，统一录入和 AI 建议预览清空自动数量并要求补填；医生明确输入的数量保留。AI 药品建议不再自带一包装总量。单价按真实币种显示，未知价格显示待确认，小额单价保留精度。

本轮覆盖前端选项、数量预览及入草稿阻断；成组历史数量比例推算及服务端计价仍需各自核查，不能据此认定完整收费链已通过事实校验。

### 服务销售价与单据小计

手工诊疗录入、AI 建议预览和 AI 转草稿统一调用 `servicePricing.ts`：项目及当前机构采用记录须有效并允许开立与收费；只选择当前业务日期的销售价，当前机构价优先于明确的租户价，同层多条价格须先修正目录。缺失金额、币种、作用域、有效期以及药品包装价不能作为项目价格，也不能回退到列表第一条。普通服务开立默认要求计价，无有效价时保留输入并阻止加入；组套批量展开按下节重新核查目录后加入草稿。

`orderSubtotal.ts` 不将缺失单价或数量默认为零或一；任一有效明细缺少必要金额事实，小计显示待确认。草稿使用明确的数量和单价作十进制乘加，已开立单据只汇总后端 `totalAmount` 快照，不用当前价格或基础数量重算。按币种分别汇总并剔除已撤销明细，真实零元显示零，全部撤销显示无有效计价明细；小额正金额不显示为零元。草药明细价格也使用保存的币种。展示小计不替代后端实际计费结果。

### 组套导入与执行科室

已保存服务申请的执行科室名称按实际执行机构及科室 ID 查询组织目录；单头与明细使用同一解析结果，与草稿编辑共享目录缓存并按 API 会话和机构隔离。历史申请可显示已停用科室的名称，新开立的科室选项仍限制为当前可用科室。目录未确认、归属不符或 ID 不唯一时保留待确认提示，不按项目名称或当前就诊科室猜测执行去向。

`orderSetImport.ts` 先按 ID、编码、类型和版本重新读取组套，再校验机构、门诊适用范围、有效期及完整成员；缺失数量、类型和排序不再分别补成 1、检验或默认顺序。成员未指定单位（接口明确返回 null）时采用实时项目目录单位；明确配置的单位与目录不一致时要求先核实换算关系。每个成员必须查到唯一的当前项目，并通过 `servicePricing.ts` 核验真实销售价；所有成员成功后才整体加入，无部分导入后显示整套成功的路径。

`useOrderSetImport.ts` 管理核对中的禁用状态、持久错误及显式重试。切换患者、就诊、机构、科室、API、忙碌或只读状态，主动取消或卸载都会作废旧结果；重复点击不会重复加入。组套版本发生变化需重新检索核对。

执行科室取组套明确配置的科室，未配置时采用服务开立接口约定的就诊科室；两者都通过机构接口核实归属、状态、有效期和名称。真实科室随 `ServicePlanDraft` 展示并通过 `performerOrganizationId` / `performerDepartmentId` 传给既有开立接口，不丢弃组套配置。缺失成员临床说明不生成“门诊医生站诊疗方案”等文本。组套维护端及其他医嘱导入来源仍需继续审计。

### 历史处方续方

历史处方只提供医生明确选中的剂量、疗程、数量和嘱托。加入草稿前重新读取历史处方，核对患者、就诊、处方及明细归属和版本，再用**当前就诊**查询唯一的产品、药房、有效包装与销售价；不替换另一产品或包装，不把自备药改成院内发药，不补默认数量或疗程单位。缺少历史事实、包装换算变化、当前风险转为抗菌药／需皮试／输液时须重新评估。频次按保存的规则与当前有效规则比较，不因代码相同就认为用法未变化。库存按所选包装换算成基础数量，并校验同一产品的合计需求；库存核对不替代正式开立时的冻结。

全部所选明细核对成功才整体带入，不静默丢弃同药的其他剂量。与当前待确认医嘱重复时明确拒绝整批带入，避免只导入一部分仍提示成功。失败保留选择与持久错误；患者、就诊、机构、科室、过敏资料、API 或可编辑状态变化以及卸载会作废旧结果。历史面板的直接续方采用本节规则；临床模板、挖掘方案和成熟方案在模板抽屉带入时采用下节的当前目录核对。

### 临床模板回执与带入边界

临床模板抽屉的方案、配套病历、独立病历、成熟方案和挖掘方案创建回执都先核实身份、状态及请求中的临床明细。使用接口允许使用次数与版本前进，但不接受未经核对的内容变化；实际带入从核实后的回执按请求时的选择提取，不再优先复制请求前缓存。配套病历失败时不先带入方案医嘱。与当前医嘱草稿重复时整批拒绝，不静默跳过后报成功。

历史比较按明确的来源和索引保留全部所选明细，不按同一产品覆盖其他剂量；缺失来源、越界索引、重复差异或跨就诊比较均拒绝。异步带入统一防重入，切换患者、就诊、工作上下文、API、模板及勾选项，修改当前病历／医嘱草稿，或进入忙碌状态后旧结果不再修改草稿。查询缓存包含 API 与机构、科室作用域。错误持久显示，重新加载与再次带入由用户明确触发。

成功提示报告实际新增诊断、医嘱和病历段落；保留已有病历内容而没有变化时不会声称新增，也不会自动关闭面板。这些规则确认的是回执与本地草稿的一致性，不代表远端使用计数／模板创建已回滚，也不代替当前目录、库存和收费核查。独立 AI 方案入口已改为准备完整结果后整体带入，见 [病历边界](../record/README.md)；病历模板维护／保存入口仍需继续走查。

### 模板抽屉的当前目录核对

`resolveTemplateOrders.ts` 为已保存方案、合并的复诊成熟方案和挖掘方案提供相同的带入检查。药品名称、产品、包装、当前机构采用、销售价、用法、频次及风险标志来自当前目录；模板只提供明确选择的产品和用药输入。未选院内产品的通用药模板须先明确选品，不自动选择第一个产品。明确自备／不计价医嘱保留原业务语义，未知价格不补零，空过敏记录不标为已核验。

药房由后端分方预览确定，再按该药房及产品核对真实库存；按当前明确包装系数累计同产品的基础单位需求，不把另一药房的数量作为可用库存。项目重新核实类型、单位、当前价格以及执行科室的归属和有效期。任一失败都不带入诊断、配套病历或部分医嘱，保留选择及错误；核对中手工修改病历也会作废迟到结果。

单纯保存为个人模板无需当前库存，但带入当前草稿时必须通过以上检查。测试包含目录缺失、价格缺失、库存不足、后端分方遗漏、科室无权限、正式 API 模块请求路径及工作站晚到响应。库存预览不等于正式冻结；模板未保存历史包装系数或频次规则快照，不能据此证明历史语义未变。独立 AI 方案同样复用此解析器，保留医生明确的过敏核对和继续用药理由，不再保留旧 `stageTemplate` 复制路径。

### 执行去向展示

AI 检验检查推荐使用项目目录的 `defaultExecutionDepartment` 预填执行科室，机构项目明确配置优先；未配置时按本节开头的科室类型规则匹配，不再将接诊科室自动当作检验检查执行科室。推荐行与待确认行均可通过共享 Select 修改。科室选项只取当前机构有效科室；转入草稿时重新查询科室归属、状态和有效期，随保存请求保留医生选择。无有效默认值时要求明确选择，不按项目名称猜科室。AI 药品行显示可开药接口返回的路由药房，发药药房仍遵循库存路由，不以执行科室选择器覆盖。

明细、行编辑、录入预览、分类表头与开立核查弹窗不按药品类型生成西药房／中药房，不按项目名称猜测检验科、超声科或影像科，也不把当前开单科室冒充执行科室。草稿使用已确认的药房／科室名称，同分类存在多个去向时分别展示，缺失项保留待确认。已保存服务使用后端 `performerDepartmentId`；尚未取得名称时明确显示科室编号和名称待确认，不补通用科室名。已保存处方当前接口没有发药药房名称，显示发药药房待确认；执行科室 ID 不等同于发药药房。

服务执行说明仅展示真实项目类型，不生成“治疗室执行”等未配置流程。后续仍需接通已保存单据的真实名称查询，以及审计其他来源的医嘱执行去向。组套接口回归通过正式 `createRhnSessionApi` 验证目录与科室请求路径，测试替身的 API 模块键也受类型检查，不能仅靠自造同名方法证明接口接通。

### 门诊库存路由事实

`OutpatientPrescriptionInventoryService` 的可开药查询、精确库存查询及处方冻结统一通过 `DispenseRouteApplicationService` 按机构、科室、药品类型、门诊场景和有效日期解析已配置路由。缺少配置不再遍历机构药房兜底；目标停用、跨机构或不支持当前场景，以及同优先级路由冲突，都不能降级到另一药房。冻结逐个产品解析目标，不把整张处方发送到第一条路由；库存项目按准确产品 ID 查询，未命中或停用时停止，不拿通用药品 ID 或其他库存项目替代。以上行为由独立随机 H2 的提交／撤销集成测试及路由事实测试验证。

仍待审计：预览与正式提交间同药房内的配置变化，以及其他库存换算和冻结消费路径。不能据此认定整条药房链路已经完成治理。

### 库存换算与释放回执

库存可开药查询只使用库存项目明确配置的包装，不再选择第一个或默认销售包装替代缺失配置；精确可用量查询也必须确认包装 ID、基础单位、正数换算系数、状态和有效期。仅明确未选包装且库存与产品基础单位一致时，基础单位系数才为 1。缺失、零或负换算系数不作为 1 使用。

处方冻结通过内部 `PrescriptionItemFreezeRequest` 传递医嘱保存时的 `baseQuantity` 和 `baseUnit`，不按当前目录包装或库存默认包装重新推算。快照数量缺失、超出库存存储精度、单位与库存不一致时拒绝冻结。冻结后撤销先锁定并核对全部对应余额、维度、单位及合计冻结量；余额缺失或不足时保留 ACTIVE 冻结事实并回滚撤销，不能标记已释放。真实余额恢复后可重试原撤销请求，集成测试验证这一过程。


### 分方预览与开立事实

分方引擎从产品目录核实通用药品、分类与单列标志，从当前有效的门诊给药途径取得执行类型，并经统一库存边界核实实际药房。客户端分类、执行类型或药房 ID 与当前配置不一致时拒绝分方；客户端药房名称被实际名称替代。缺失分类、失效途径、未配置路由不再补西药、口服或默认药房；自备药保留空药房。非输液分组称为 `NON_INFUSION`，不将全部非输液途径标成口服。预览和批量开立共用该引擎，业务日期使用当前开立日期。

`usePrescriptionSplitPreview` 校验返回明细与当前请求一一对应；空结果、遗漏、重复或改变已明确输入的结果均报错。查询范围包含 API、就诊、居民、机构、科室及完整药品明细；加载／重新加载／失败时隐藏旧预览，不以本地分方估算补单据数。核查弹窗持续显示失败与重试，按钮及提交函数都要求预览已确认。自备药在预览中明确显示无需药房发药，未知单位不补盒或天。

本轮有随机 H2 的真实预览／批量接口测试、工作站失败重试测试及晚到结果隔离测试。预览仍不是最终开立成功凭据：正式创建继续执行目录采用、价格、临床和库存校验。尚需继续审计预览到开立之间同药房内其他配置变化，以及历史与模板导入事实，不能据此认定所有医嘱入口已完成治理。


### 整批医嘱保存与回执

`POST /api/encounters/{encounterId}/order-drafts` 接收必填命令编码、药品列表和项目列表。`OrderDraftSaveService` 在一个数据库事务中复用处方分方／创建和服务申请创建；任何明细失败都回滚整批及命令登记。重放命令先核实就诊访问和状态，再返回已提交回执；同命令更改载荷、就诊或操作者不能被当成新建。没有新增表，复用平台幂等记录及其现有 24 小时保留策略；不承诺跨清理周期的永久去重。

前端不再调用本地装箱和逐条创建的兼容路径，接口缺失或失败均停止。回执必须匹配命令、就诊、唯一单据／明细 ID、版本、真实状态及全部请求明细；药品产品、包装、数量、明确的剂量／疗程／嘱托，项目数量、执行科室和说明也须对应。空响应、漏行、重复、错误关联或已撤销记录均不能清空草稿。原分方容量和输液组规则由后端引擎测试覆盖，不再维护另一套前端保存规则。

保存协调器在当前编辑器内保留未确认医嘱命令；网络错误、异常回执及修改后重试都沿用该命令，服务端据此区分已提交重放和已回滚重试。病历仍先于医嘱独立保存，因此不能把整个病历加医嘱序列称为原子事务。关闭／重载页面后的未确认结果恢复、跨幂等记录清理周期的恢复，以及历史／模板导入仍需继续核查。

### AI 目录匹配与知识库调入

AI 共写与知识库检验检查调入统一使用 `ClinicalTreatmentCatalogResolver`；`treatmentRecommendations` 只包含唯一可靠匹配，`treatmentMatches` 保存未匹配意图、原因和可选候选。组合检验仅按明确的加号／顿号拆项；目录别名在 `clinical-catalog-aliases.json` 维护，不绑定机构或项目 ID，普通 CRP 与超敏 CRP 分别解析。已维护别名可纠正模型项目类型，未识别类型保留待确认。药品只允许精确质量单位等价换算，不移除剂型、浓度、包装或不同含量限制；规格冲突候选必须显式选择。

多候选由医生选择，目录异常可重试，不取搜索首项；选择产品后继续走已有用法、价格、库存与执行科室核对。知识库调入在草稿准备回调确认后才关闭；失败保留面板及原因，切换患者／就诊／临床上下文后丢弃迟到结果。逐项 `clinical_ai_catalog_match` 日志记录类型、名称、规格、机构、业务日期、候选与拒绝计数，不记录患者身份、病历或完整提示词。
