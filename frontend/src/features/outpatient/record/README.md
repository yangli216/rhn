## 状态与依赖方向

- `DiagnosisPanel` 持有搜索、弹层、拖拽等临时状态；诊断数组由父编辑器持有。常用诊疗方案入口位于医生站最右侧工具栏，方案池以宽抽屉呈现；`ClinicalRecordPanel` 通过 portal 将共享诊断和医嘱草稿接入抽屉，避免复制或上移整套草稿状态。
- `ClinicalVitalsFields` 持有参考来源查询和反馈状态；使用父编辑器的同一个 react-hook-form 实例，引用缺失字段时保留医生现值。卸载时清理反馈计时器。
- `StructuredNoteFields` 只负责呈现；`NoteTemplateBar` 负责模板查询和操作，通过回调修改父草稿。
- `useClinicalAiDraft` 负责普通病历／诊断的上下文订阅、采纳校验和撤销控制；父编辑器持有撤销快照。它拒绝含未经准备方案的直接请求，不再调用旧的医嘱快照复制回调。
- `useAiPlanApplication` 为独立 AI 方案入口先核对当前目录、价格、库存、执行科室和重复医嘱，返回仅能执行一次的本地带入函数。核对中不写病历、诊断或医嘱；最终执行时再次检查患者、工作上下文、API、草稿、过敏资料、可编辑状态及卸载状态。先修改又改回的表单也使旧结果失效。失败保留原草稿，成功整体写入，并保留病历撤销快照。
- `../ai/canonicalAiDiagnoses.ts` 在独立 AI 面板带入前核对唯一有效的目录身份。模型候选按其明确的 ICD-10 契约核对；保存的方案必须提供概念 ID 或编码体系＋诊断域，不能借用模型默认范围。概念、编码、体系或域不一致、有效期不符、目录结果歧义／不完整／查询失败均阻止带入和采纳留痕。核对后的诊断保留概念 ID、体系、域及真实管理规则证据；缺失管理证据保持未确认。勾选、合并和方案准备使用 `diagnosisIdentity.ts` 的身份键，跨体系同码不再互相覆盖；未知身份不与已确认概念暗中合并。`canonicalAiDiagnoses.test.ts` 与 `ClinicalAiPlanAdoption.test.tsx` 覆盖解析和实际页面到草稿的完整路径。
- 新模块不得运行时导入 `DoctorWorkstation`；模型不依赖 UI。新增同类行为直接进入对应模块，避免重新堆回工作站。

- `clinicalRecordDraft.ts`：病历 schema、结构化表单检查、诊断排序／指纹、提交内容投影。纯函数，不读网络、不依赖工作站 UI。
- `saveClinicalDraft.ts`：一个编辑器一个实例；按病历 → 医嘱草稿顺序保存，提交不可变快照并拒绝并发保存。相同就诊和病历内容失败重试复用病历 commandCode；回执核对通过且当前编辑器调用 `confirmApplied` 接受结果后才释放命令。原 API 会话存在未确认保存时，不能换新会话重复提交；应重新加载并核实远端结果。这是当前编辑会话的保护，不保证跨页面重载恢复。
- `clinicalRecordReceipt.ts`：保存病历后核对就诊回执，再读取真实文书；核对患者／机构科室、默认门诊文书身份与新版本、正文、生命体征、诊断、结构化表单和来源标记后才提交医嘱。查询失败、缺失、重复或内容不一致均保留本地草稿和重试命令，提示远端可能已保存；不能将失败解释为服务端回滚。成功后使用核实的文书更新缓存和标记，不再吞掉文书刷新失败并提前宣告全部保存。此读取核对只能证明当时的持久化状态，不提供跨病历／医嘱请求的事务保证。
- `clinicalDocumentWorkflow.ts`：独立签署、签署并诊毕、签署并打印及更正后签署共用文书身份、正文、版本和证据回执核对。签署前读取当前文书，签署后再确认持久化状态；已有签署必须具有当前版本的作者、时间、签署含义及证据引用，不能仅凭 `SIGNED` 字符串继续。前端核对的是服务端证据回执，密码学验证仍由服务端承担。
- 更正协调器保留当前编辑会话内已尝试的内容与版本。异常响应或签署失败后，显式重试先读取原文书：核实已提交的同一更正版后继续签署；再次修改正文时更新这份未签署更正版。并发更正、内容或历史证据不一致时停止，不另建替代文书。更正写入和签署仍为两个事务，不能宣称失败已回滚；页面重载后的恢复也不属于这份内存会话保证。
- `useClinicalDocumentSession.ts`：签署／更正的每个后续请求、成功缓存写入及诊毕／打印继续动作都检查当前患者、API 会话、权限和组件生命周期；切换后再返回原上下文也不会复活旧回执，旧渲染的回调不能捕获新会话。
- `useClinicalDraftSession.ts`：普通保存额外订阅表单和诊断／医嘱／结构化内容变化。保存期间编辑、编辑后改回、切换 API 或失去编辑权限均拒绝使用旧回执清空当前草稿或继续提交下一步；表单异步校验后也需再次核对实际提交内容。明确提示远端可能已保存，不宣称失败已回滚。
- `completeEncounter.ts`：独立诊毕和签署后诊毕均核对返回的就诊身份、完成状态与时间，并通过既有就诊 GET 接口回读确认；空回执、归属错误、状态不符或查询失败保留确认界面，同一提交重试沿用命令。只有核对通过且上下文仍有效时才退出接诊或打开批量打印。签署与诊毕仍为独立事务，回执不包含的转归明细不在此校验保证内。
- `completionFacts.ts`：诊毕模式必须来自未被依赖抑制的有效配置；加载失败、未知配置或旧 API 会话的数据不能补成合并签署模式。弹窗单独读取并核对本次就诊的医嘱、费用和支付订单；未确认资料不显示零医嘱、暂无费用或已结清。金额与归属异常、未开票费用、未完成结算、处理中支付／退款均不能通过诊毕准入，查询失败有显式重新加载入口。点击最终确认时再次读取这些事实并检查上下文，发生变化时在签署之前停止。该读取不是服务端锁或跨接口事务保证，最终业务准入仍由后端负责。
- 转归说明初始为空，切换转归不自动覆盖医生原文，也不补出“已开具入院证”等未经确认的事实；常用语仅在医生主动选择后写入。费用汇总使用实际返回币种。收款表单仅在真实支付方式及其精度、舍入规则、支付订单已确认时显示，空方式列表不生成备用支付渠道。
- 费用和账户余额保留真实正负数；后端贷项凭证可保留 `PRICED` 状态且净额为负，不按普通待收单重复收款。已结清需要确认账户余额归零、未开票金额为零、无仍需处理的普通结算单和在途支付；不同凭证的负余额不能抵消另一笔正的待收金额。
- `completionBillingWrites.ts`：诊间收款和生成结算单使用当前患者工作区内的请求协调器。核对回执中的原请求标识、账户、金额、方式／收费明细后，直接回读费用账户、支付列表及订单详情或正式结算单；失败不会被查询库的 `refetch` 返回值吞掉。页面接受已核实状态后才释放请求。支付处于待处理或失败状态时保持真实状态，不将“已创建支付指令”等同于已收款。开票传递明确的原收费明细 ID 集合，重试沿用原凭证编号。
- 结算结果不确定时，提供“核实上次结算操作”继续原请求；当前患者的弹窗关闭再打开也保留该请求。金额或支付方式变化不能绕过未核实请求；切换患者／API 会话或迟到回执不能写入当前页面。明确的服务端创建前置拒绝允许重新加载后修正输入；网络中断、异常回执和读取失败保留原请求。该保证仅覆盖当前患者工作区的内存生命周期，不涵盖整个页面重载或离开患者后的恢复，也不是跨接口事务。
- `../orders/persistOrderDrafts.ts`：药品和服务申请通过同一事务接口保存，核实回执后才允许清空草稿。
- `../DoctorWorkstation.tsx` 的 `ClinicalRecordPanel`：保留共享草稿、保存／签署／修订协调、历史带入、AI 流式字段显示、保存后的 query 失效。跨区流程变更仍需读此入口并跑集成测试。

病历模板与诊疗方案共用工作台的模板化操作体验，但不合并存储模型：病历模板提供主诉、现病史等文书段落，诊疗方案提供诊断、药品、检查检验和治疗任务。二者分别调入当前草稿并由医生确认，避免文书内容直接生成可执行医嘱。

工作站“存为病历模板”先投影真实书写段落及来源标记，裁掉两端空白后同步调整标记位置；无正文或无法定位的标记阻止提交，不静默丢弃。只有服务端返回有效身份、状态、范围及一致的保存正文后才提示成功并清空表单。目录加载失败与真实空列表分别呈现，失效选择不会自动切换为另一个模板。调入时重新核对使用回执，提示采用实际改变的段落数；零改动在弹窗内解释。接口会话、就诊、禁用状态、选择或待提交草稿变化后的迟到回执不用于当前页面。远端模板保存可能已经完成，前端不把拦截迟到响应当作远端回滚，提示先查询核实以免重复创建。

人工维护和 AI 方案调整通过 `../templates/maintainedTemplateSave.ts` 核对提交与保存回执。异常数量不能补成 1，更新必须返回同一身份、更高版本和一致的明细／维护属性。关联病历与方案是两个独立事务：先检查整份方案和病历输入，再保存病历；病历回执未确认时不提交方案。第二步失败在弹窗内提示部分完成，重试复用已确认的病历身份和版本，正文修改则更新这份病历。目录失败或关联对象消失不自动创建替代模板，清空关联正文也不静默保留旧正文。新增药品不凭空补口服、TID、三天或包装身份。尚未覆盖 AI 生成／目录匹配阶段的所有事实校验，保存成功也不代表方案已通过针对具体患者的执行预检。

AI 方案弹窗的手动目录检索通过 `../templates/templateCatalogSearch.ts` 校验真实分页、候选身份和启用状态；产品与通用药品两路检索有任一路失败时均不展示为完整成功。诊断保留真实概念 ID、编码体系与诊断域，诊疗项目采用正式字段 `sdServiceType`；不补西医诊断、检验类别、包装身份或单位。`useTemplateCatalogSearch.tsx` 区分查询中、失败和真实空列表，查询／会话／任务／启用状态变化与卸载使旧候选失效，选择只能来自当前成功查询。结果为当前关键词的首页候选，页面提示细化查询；目录匹配不称为“在库”，不代表库存预检通过。生成结果、自动转换及任务状态判定仍需继续核查。

病历与医嘱仍是先后两个 HTTP 请求，整个序列不是数据库原子事务。医嘱内部已合并成一个事务；当前编辑器按就诊保留独立医嘱命令，异常回执、网络错误和修改后重试沿用该命令，核实成功才更新。没有病历改动但有医嘱草稿时同样走保存协调器；真正没有待保存内容才跳过保存。病历或医嘱保存失败不继续开立；未确认的病历回执也不能触发医嘱提交。平台幂等记录仍有保留期限，不宣称跨页面重载或跨清理周期 exactly-once。

原 DoctorWorkstation 的辅助函数导出暂保留兼容；新测试／调用优先使用上述小模块。
验证：根目录 `./scripts/verify-scope.sh outpatient-draft`；先查看命令可加 `--list`。
验收重点：主要诊断、结构化必填、切换患者、失败重试、AI 采纳与撤销、签署及完成就诊。

AI 共写入口先按问诊要点检索当前医生可见的整体诊疗方案。命中时先展示方案选择，医生进入原有临床模板面板核对配套病历、诊断、药品与诊疗项目；不采用或无匹配时才进入原有病历生成与逐项采纳流程。医嘱列表不再承载整体方案推荐。匹配阶段不持久化建议或临床草稿；输入变化会使待选方案失效。

方案检索的诊断身份沿目录选择、工作站保存／重载、AI 上下文和请求完整传递概念 ID、编码体系与诊断域；身份变化会使旧建议失效。服务端按真实目录概念解析身份并拒绝相互冲突的字段，不把缺失体系补成 ICD-10／西医。只有体系、诊断域和编码均明确且一致时才记录编码精确命中；不完整身份仍可按实际名称匹配，推荐理由区分两者。本地辅诊的诊断候选仅校验已确认的 ICD-10 西医身份，未知或其他体系保留原草稿并提示人工核对，不转换成西医候选。`ClinicalAiPlanIdentityTest`、`ClinicalPlanRetrievalServiceTest` 和 AI 草稿边界测试覆盖这些约束；模型输出的诊断候选归一化仍需后续独立走查。

独立 AI 方案核对弹窗同样使用当前目录检查。使用回执必须与查看的完整方案及勾选内容一致，不能仅比较条目键和数量；预检须返回当前模板版本、全部选中药品、产品／包装、完整检查与一致的计数和状态。缺失检查不能显示通过，未评估的相互作用和禁忌证保留明确边界。核对中禁用勾选，失败在弹窗内持续显示。

采纳前先准备全部本地变更，再等待既有采纳留痕请求成功，最后执行受当前上下文保护的带入函数；留痕失败不带入，重试复用原命令。远端留痕与本地草稿不是数据库事务：留痕已成功后上下文变化仍会拒绝本地写入，既有远端动作记录不自动回滚。留痕也不代表病历／医嘱已正式保存或开立。该边界不能被当作跨端事务保证。

## 通用病历与结构化方案引用

病历书写字段为主诉、现病史、既往史、查体、过敏史补充、用药史、健康宣教和随访复诊。辅助检查结果不再作为当前编辑区的独立输入项，历史数据继续保留。生命体征沿用现有结构化录入。诊断与诊疗计划只引用诊断/医嘱工作区，病历、模板、历史带入及 AI 采纳均不提供自由文本诊疗计划编辑；旧版 treatmentPlan 留作历史数据兼容，新保存不采纳客户端文字计划。

AI 建方的 noteTemplateContent 只提供上述书写框架和建议；不预填未知患者事实。保存时创建配套病历模板并通过 noteTemplateId 关联既有方案，使用时仍分别带入病历与结构化诊断/医嘱草稿。宣教和随访的编辑内容以配套病历模板为准。新增字段使用既有 JSON 内容存储，无需改变物理表。

`ClinicalRecordReferences` 使用当前诊断与医嘱草稿及同一就诊的已保存医嘱，明确区分待保存草稿、已保存草稿和已开立内容，并排除取消医嘱。引用区域无文本输入控件。

病历采用连续文书显示：段落标题加粗、正文自然换行，编辑使用共享 FormField 的 document 外观。AI 建方使用内容区抽屉；对话作为辅助栏，病历书写与结构化诊疗方案左右并列，以 WorkspacePane 分别管理正文滚动，头部与保存操作固定。

AI 建方的病历内容按 noteTemplateContent 字段顺序流式预览。预览仅投影白名单书写字段，支持未闭合字符串和 JSON 转义；生成期间只读，完整响应后才替换可保存草稿，连接失败保留上一份草稿。后端提示词优先输出病历采集框架，再输出结构化诊疗条目，不编造未提供的患者事实。

流式阶段也遵守书写归属：EDUCATION/FOLLOW_UP 只投影到左侧宣教与随访，不进入右侧清单。右侧结构化条目在九个病历字符串字段闭合后显示；提前到达的诊疗条目只缓存，避免由模型 JSON 字段顺序决定界面显示顺序。

病历正文标签与生命体征标签共用 `--doctor-record-label-width`，标签右对齐、内容区起点一致，随字号档位缩放。

AI 辅诊默认输出连贯的病历正文，缺失要素集中到 `missingInformation`，不在正文堆放“待补充／待询问／待查体”或症状采集清单。已有模板预设保留正文和来源；完全没有事实或预设的段落返回空值，不能用默认正常、否认过敏等表述替代未采集事实。宣教与随访提供针对已知症状的建议及复诊触发条件。主诉默认一行、随内容增长，文书标签与标记预览／输入态均按首行对齐。

## 行内来源与变量标记

病历正文是唯一可编辑、可保存、可打印的文本；`annotations` 独立保存字段、精确片段/UTF-16 锚点、来源、语义绑定和提示。模板默认查体与阴性描述完整保留。`PRESET` 仅记录段落来源，不高亮整段；医生手工修改只保留保护元数据，界面突出模板变量、重要预设、口述事实及冲突。

`AnnotatedRecordField` 将领域标记交给共享 `AnnotatedTextarea`；阅读态可悬浮查看、点击调整/移除，输入期间保持 textarea 和焦点，避免标记更新打断输入。保存沿用原有按钮，成功后确认当前版本的标记，不逐项确认，不把自动暂存当成主动确认。复制和打印只使用正文。

`recordAnnotations.ts` 负责锚点验证、编辑重定位和语义变量更新。相同数字不能全局替换；后续口述可更新同一绑定的既有口述片段，遇到手工修改保留原文并生成冲突提示。未确认模板/AI 预设单独投影，不用作本次推理事实。服务端 `Draft.evidence()` 同步执行这一投影，模型分别收到 `draft`、`writingDraft` 和 `writingAnnotations`。模型声明的口述/上下文来源必须包含输入中存在的原文引用，失效标记丢弃，不按具体临床句式过滤正文。

相关验证：`recordAnnotations.test.ts`、`AnnotatedTextarea.test.tsx`、`DoctorWorkstation.test.tsx` 中模板带入—行内调整—保存确认用例；后端 `RecordAnnotationTest`、`ClinicalRecordAnnotationContractTest`、`OutpatientNoteTemplateTest`、`ClinicalAiPlanCompilationTest`、`OpenAiCompatibleClinicalAiModelGatewayTest`。推荐索引与连续口述调度的剩余范围见 `docs/ai/template-copilot/README.md`。

连续口述由 `ai/useStableVoiceCopilot.ts` 仅对已稳定识别片段触发；900 ms 合并停顿，普通键盘输入不自动分析。模板优先推荐，无匹配走现有流式生成。自动采纳使用 `overwriteRecord=false`，只填空白字段或按语义绑定更新；非空且无法可靠定位的新信息保留在对照建议，手工修改冲突继续显示行内标记。模板内容、患者/输入版本及取消信号共同防止迟到结果覆盖当前工作。相关工作流测试在 `ClinicalAiQuietWorkflow.test.tsx` 与 `useClinicalAiDraft.test.tsx`。


历史诊疗事实按选定就诊保留全部有效诊断、药品和服务申请，不能在领域投影阶段按模型上下文预算静默截断。`EncounterHistorySnapshot`、模型请求和历史重复方案解析均拒绝将未返回的历史集合补为空列表。模型网关单独限制每次就诊的上下文条数，并传入各类事实的 `coverage.total/included/omitted`；省略记录不能用来推断不存在其他诊断或医嘱。当前就诊范围仍受时间窗和次数限制，尚不代表患者全部病史。验证见 `JpaOutpatientClinicalHistoryDirectoryTest` 的第 51 条用法冲突用例与 `OpenAiCompatibleClinicalAiModelGatewayTest` 的真实发送报文覆盖检查。

历史就诊窗口通过 `EncounterDirectory.recentCompletedForResident` 在数据库中先限定当前租户、患者主索引、机构／科室、门诊类别、已完成状态、登记时间下界和排除当前就诊，再按登记时间与 ID 倒序取最多 10 次。不能先查询全部状态的最近 20 次再过滤，也不能把缺少工作上下文解释为无历史。`HistoricalEncounterWindowTest` 使用真实持久化记录覆盖超过旧上限的未完成就诊、时间边界、稳定排序、租户／患者／机构／科室隔离、主索引合并和缺少上下文；维护在 `outpatient-draft`／`round1` 验证范围中。

诊断管理提示通过 `diagnosisManagementEvidence.ts` 区分 `CONFIRMED` 与 `UNCONFIRMED`：只有有效的已确认规则列表才能显示管理标签或“无管理要求”的空标记。缺失、损坏或未确认快照显示“待核对”，不补为空列表；目录选择、保存回执和重载都保留确认状态。自由编码诊断及旧幂等回执缺少确认依据时也保持待核对。后端保留历史目录快照，不用今天的规则倒填历史；保存目录诊断时要求完整规则证据，诊断事件携带同样的确认状态，未确认时不发布伪造的空规则数组。

共享诊断写入必须先按真实租户和就诊身份读取并锁定就诊，再复制患者、机构、科室归属。就诊不存在或归属缺失时明确失败，不能补为 ID 1；直接创建诊断实体也必须提供完整有效的归属。原有诊断与修订保留历史事实，不自动重写历史归属。`DiagnosisOwnershipPersistenceTest` 覆盖真实数据库中的不存在就诊、跨租户写入／排除、真实归属及排除后恢复；`DiagnosisOwnershipValidationTest` 覆盖缺失或无效上下文在任何诊断／修订写入之前被拒绝。

诊断体系允许未知：自由编码诊断未声明体系时，保存、重载及修订保持空值，诊断事件不发布虚构的西医体系；门诊和住院均显示“体系待确认”。目录诊断由共享 `DiagnosisTerminology` 读取正式概念及其体系、编码版本和管理快照；住院入院／出院请求、响应和目录选择均传递概念 ID 与体系，并拒绝概念与体系／编码不匹配的输入。旧住院客户端省略目录字段时保留既有快照，新字段为空时不改变原有幂等请求结构。`V1_101_0__diagnosis_unknown_domain.sql` 同时移除诊断与修订表的默认值及非空限制，保持已存历史值不变，不推测旧西医值的来源。`DiagnosisDomainTruthTest` 与 `DiagnosisDomainMigrationTest` 验证接口、落库、事件、迁移与跨体系保存，前端诊断面板及出院用例核对传递和未知展示。

普通门诊录入与保存同样以概念 ID（有目录身份时）或编码体系＋诊断域＋编码区分诊断；不同体系／目录版本的同码条目可以独立选取、排序、移除和恢复。同一身份的重复提交会被拒绝，历史同一身份存在多条记录时也不会静默选取第一条。`DiagnosisInput.codeSystem` 为可选保存字段：目录诊断必须与实际概念体系一致；自由编码仅保留明确声明的体系，管理规则仍为未确认，缺失体系不补默认值。修改检测覆盖体系及诊断分组，保存投影保留这些字段。诊断检索筛选回调仅随筛选条件变化，普通重绘不使已显示候选失效。
